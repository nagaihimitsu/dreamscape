- ユーザーの判断（2026-11-13）：「ゲームが増えるにあたって、どんなふうにシステム構成するかは前もってしっかりと考えた方がいい。ストーリーとバトルを分けていたのを合わせたような作業は必要にならないようにしたい」。

## 0. 決めたことの一覧

| 項目 | 決めたこと | 主な理由 |
| --- | --- | --- |
| 遊べる所 | Ink の選択肢の組が出る所なら、どの場面でも（デート、道中交流と差し込み、観光案内、到着・エピローグ・ツアーの区間、バトルとフィナーレの会話） | 選択肢の場は全ての場面で同じ。場面の種類ごとの例外を作らない |
| 遊べない所 | クイズの問い・推理の止まる所・呼び口、告白のデート、全分岐の歩みで調べない会話 | 正誤を問う所、関係状態で決まる所、検査できない所 |
| 画面の道 | 5つの会話の画面が同じ `ChoicePoint` を使う。結果は1つの関数 `chooseMiniGameOutcome` で選ぶ | 道が1つなら、後で合わせ直す作業が起きない |
| 部品 | 1ゲーム1フォルダ `src/minigames/<gameId>/`。登録は1行 | 何人かが並べて作れる |
| エンジンと皮 | 遊び方の仕組み（エンジン）と、場面ごとの絵・言葉・結果の名前（皮）を分ける。札が名指すのは皮（＝ゲーム） | 1つのエンジンで何場面も作れる。結果の名前は場面ごとに要る |
| 規則 | 純粋関数 `outcomeOf(記録, 引数)` と `autoRecord(結果, 引数)`。乱数・時刻・DOM を読まない | テストできる。時刻・回数・形・どの操作で終えたか、どんな決め方も書ける |
| 札 | `# minigame: <gameId> [auto <結果>] [prefix <語>] [bg <背景>] [art.<枠> <絵>] [<キー> <値>]…` の1つの形。引数はゲームの zod で調べる | 選択肢のそばに書ける。検査は1か所 |
| 結果 | 結果は選択肢だけ。数（点数・値段）は Ink にも効果にも渡さない | 効果を表にして、払えるか・選べるかをビルドで調べる決まりを守る |

| セーブ | 新しく保存するものは無い。読み込み直すとゲームの最初から | 選択肢の所で保存する今の決まりのまま |
| 時計 | 時間は枠が持つ。ページが裏に回ると止まり、戻ると「続ける」 | どのゲームも同じに止まる |
| 読み込み | ゲームの画面は、そのゲームの場面で初めて読む別のファイル。タイトル画面では読まない | ゲームが増えても最初の読み込みが重くならない |
| 絵 | ゲームの絵は CSS・SVG と直下の `public/`。使い所ごとに、背景（`bg`）と、皮が用意した絵の枠（`art.<枠>`）へ旅行編の絵を入れられる。背景の枠には出典つきの観光写真も入れられる。無ければ CSS の見た目 | 「背景はあった方が盛り上がる」「写真の方が良くないですか」（2026-11-13）。旅行編の絵は1つの一般の仕組みで調べる |
| テスト | ゲームを足しても、テストの仕組みは足さない | 並べて作る人が配線を触らない |

## 1. どこで遊べるか

### 1.1 実装前、場所のファイルのデートだけだったのはなぜか

次の4つが、デートの所にだけ書かれているから。どれも場面の種類の都合ではない。

1. 画面：ミニゲームを出すのはデートの画面（`RomanceScene`）だけ。ほかの4つの画面（`EncounterScreen`・`EpilogueScreen`・`TourismScreen`・`BattleScreen`）は、選択肢をそれぞれの部品（`EncounterChoices`・`SceneChoices`）で出す。
2. ビルド：`content:build` は、場所のファイルのデートを歩くときだけ `TagContext.miniGames` を `true` にする（`scripts/content-validation.ts`）。ほかの歩みは `false` で、札を止める。
3. ゲームの関数：結果を選ぶのはデートの `chooseDate` だけ。E2E の補助（`tests/e2e/helpers.ts`）も `activeDate` だけを見る。
4. 相手の絵：投げる人はヒロインに決め打ち（`partner`）。

外すには、この4つを場面の種類によらない1つの形にする（1.5）。

### 1.2 遊べる所

会話の画面が Ink の選択肢の組を出す所なら、どこでも遊べる。場面の knot から呼ぶ手伝いの knot の中でも同じ。

| 場面 | 画面 | 今の選ぶ関数 | 候補の例 |
| --- | --- | --- | --- |
| デート（場所のファイル。通常・特別・再交流。告白を除く） | `RomanceScene` | `chooseDate` | クリケット、かくれんぼ、ローティー、ゴルガッパ、布で鳩 |
| 道中交流と差し込みの場面（`talk`・`encounter`。観光地の訪問のほか、宿・移動・窓口・出発・到着の時点や、デート・フィナーレの前後） | `EncounterScreen` | `chooseEncounter` | メヘンディ（宿の夜）、バラート（フィナーレの後） |
| 観光案内 | `TourismScreen` | `chooseTourismGuide` | 猿の小瓶（案内の中なら） |
| 到着・エピローグ・ツアーの区間の語り | `EpilogueScreen` | `chooseCityEpilogue` | — |
| バトルの会話（通常戦・特殊戦・都市フィナーレ） | `BattleScreen` | `chooseBattle` | バラート（フィナーレの会話） |

- バトルの会話の選択肢の札は、そのバトルを初めて遊ぶときだけ当てる（決定10）。ミニゲームの結果の選択肢も同じ。
- 観光案内の読み直しでは札を当てない。ミニゲームの結果の選択肢も同じ。
- どれも今の決まりのままで、ミニゲームのための例外は無い。

### 1.3 遊べない所

| 所 | 理由 |
| --- | --- |
| クイズの問い（バトルと道中交流のクイズ）、推理の止まる所（資料を選ぶ画面）、呼び口（`-> quiz(n) ->`・`-> reasoning ->`） | Ink の選択肢の組ではない。正誤を問う所に腕前を混ぜると、正誤・戦績・英語ノートの意味が変わる。クイズのような遊びがほしいときは、前後の会話にミニゲームを置く |
| 告白のデート（その knot と手伝いの knot） | 1.4 |
| 全分岐の歩み（`scripts/scene-walk.ts`）で調べない会話：英語ノートの解説の会話、カタログの道中交流と1場面1ファイルのデート（どちらも今の旅行編には無く、テストの元データだけ）、選択肢の無い1場面1ファイルの到着・エピローグ | 選択肢の組が結果と合うかを確かめられない。場所のファイルに書けば遊べる |
| 特殊戦の主張・追及の手伝いの knot（`<バトル>_claim`・`_press`） | 手がかり帳が単独で読む。選択肢があると止まる（今の決まり） |

止め方は今の `TagContext.miniGames` をそのまま使う。全分岐の歩み（`walkScene`）を通す全ての呼び出しで `true`、それ以外と告白のデートで `false`。止まるときの文は、なぜ止まるか、どこに書けばよいかを言う。

### 1.4 告白のデートと腕前

- AGENTS：告白の最終の成否は関係状態から決め、乱数で変えない。告白のデートの中では噛み合いを使わない。
- 腕前は乱数ではない。同じ操作なら同じ結果になる。でも、関係状態でもない。
- 告白の成否は、始めたときにゲームが関係状態から決めた `confession_result` で、選択肢では変わらない。だから告白の中のミニゲームは、成否を変えられない。
- それでも、遊ぶ人には「うまく打てなかったから断られた」と見える。気持ちの答えを、腕前や運に見せないという決まりの目的に反する。
- 決定（推奨）：告白のデートでは `# minigame:` を止める（ビルドのエラー）。告白の前後の差し込みの場面（`# at: date <告白>`）には書ける。9章の問い1。
- 再交流のデート（静かな場面）は止めない。置くかどうかは書く人が決める。

### 1.5 1つの道

画面：

- 共通の部品 `ChoicePoint` を作る。5つの画面は、選択肢を出す所でこれを使う。フレームに `minigame` があれば枠（`MiniGameHost`）を出し、無ければ画面の今の選択肢（子として渡す）を出す。
- 遊ぶ間、ゲームはその場面の画面全体に重なる。各画面は根に1つ `<MiniGameSlot />` を置く（重ねる場所。今の `minigame-host` を一般にしたもの）。
- 画面が渡すのは、そのとき舞台にいる人の絵だけ（`cast: { heroine, person? }`。ヒロインの立ち絵と、話している人物の絵）。どちらを使うかは、ゲームと引数が決める。枠は場面の種類を見ない。
- 名前・おまかせの設定・Debug モード・動きを減らす設定・`revision`・結果を選ぶ関数は、GameApp が `MiniGameProvider` で一度だけ渡す。画面ごとの配線は `ChoicePoint`・`MiniGameSlot`・`cast` だけ。

ゲームの関数：

- `src/domain/minigame.ts` に2つ。`openMiniGame(state)` は、いま開いている場面のフレームの `minigame` を返す（無ければ null）。`chooseMiniGameOutcome(state, outcome, revision, nextRoll)` は、結果の `# option:` の選択肢を探し、その画面の選択肢のボタンと同じ操作（`src/domain/player-action.ts` の `playerActionChange` の `*_choose`）を当てる。場面の種類から選ぶ関数への表は、この1つ（遊ぶ人の操作の表）だけ。
- GameApp は、5つの画面に同じ `onMiniGameOutcome` を渡す。
- 遊ぶ人の操作の一覧（`listPlayerActions`）は、ミニゲームの所では選択肢の代わりに `{ kind: "minigame", outcome }` を結果ごとに出す。画面が出すのも開始のボタンで、選択肢ではないから。

## 2. ゲームの部品の決まり

### 2.1 置き場所と登録

```
src/minigames/
  contract.ts          型（MiniGameDefinition・MiniGamePlayProps・MiniGameRules）と defineMiniGame
  tag.ts               札を読む（一般の形。今の src/content/mini-games.ts の parseMiniGameTag を移す）
  registry-list.ts     1ゲーム1行（アルファベット順）
  registry.ts          一覧から MINI_GAMES・MINI_GAME_IDS を作る
  host/                枠：MiniGameProvider・ChoicePoint・MiniGameSlot・MiniGameHost・clock・seed・host.css
  testing/             規則のテストの雛形
  engines/<engineId>/  遊び方の仕組み（エンジン）
  <gameId>/            ゲーム（皮）
```

- 登録の1行：`export { cricketBatting } from "./cricket_batting/definition";`。
- `src/content/mini-games.ts` はなくす。`src/content/tags.ts`・`src/story/*`・`scripts/scene-walk.ts` は `src/minigames/` の軽いモジュール（定義・札・型）を読む。
- ゲームの ID は `[a-z][a-z0-9_]*` で、フォルダ名と同じ。フレームと一緒に保存されるので、公開後は変えない。

### 2.2 エンジンと皮

- エンジン：入力と時計の扱い、記録の形、記録からエンジンの結果を出す関数、おまかせの記録の作り方、下の操作の所。例 `cue_tap`（近づいてくる物に合わせて1回押す）。
- 皮（＝ゲーム）：エンジンの上に、場面ごとの絵・言葉・結果の名前・調整の値・エンジンの結果から自分の結果への写し方を決めたもの。札が名指すのは皮。例：`cricket_batting`・`monkey_catch`・`cloth_flap` は、どれも `cue_tap` の皮。
- 調整の値（`tuning`：近づく時間、ちょうどの幅、近い幅など）は、皮の定義にコードで書く。札には書かない。公平さ（スマートフォンのタップの遅れより広い幅など）をテストで守るため。場面で難しさを変えたいときは、皮が `level easy` のような引数を用意する。
- 結果の名前は皮ごとに決める。既存の場面を置き換える皮は、結果の ID を今の選択肢の `# option:` に合わせられる（例：かくれんぼの `call_her_name`・`door_by_door`・`just_wait`）。
- 仕組みのコードは、皮が1つでも `engines/` に置く。2つ目の皮が来たときにコードを動かさないため。
- 作る予定のエンジン（調べた候補から）：

| エンジン | 入力 | 調整の値の例 | 皮の候補 |
| --- | --- | --- | --- |
| `cue_tap` | 1回押す | 前置き、近づく時間、ちょうどの幅、近い幅、押さないときの終わり | クリケット（今）、猿の小瓶、布で鳩 |
| `search` | 場所を押す、ボタン、何もしない時間 | 段（場所の並びと当たり。日傘は3段）、違う所の上限、時間、ボタン（呼ぶ・明日にする・どこ？。遊びか段を終える）、何もしないとき（終わる・最初の操作の前だけ終わる・その段を教えてもらう。段を任せた後は待つ時間を短くできる）、段ごとの持ち時間（`limitMs`：段が出てからその時間で探す物が手の届かない所へ行き、その段を教えてもらう。日傘の3段目の子ども。2026-11-14） | かくれんぼ、メヘンディ、日傘 |

### 2.4 規則（`rules.ts`。純粋関数）

```ts
export interface MiniGameRules<Params, Outcome extends string, PlayRecord> {
  /** 遊んだ記録から結果を決める。どの記録にも、宣言した結果のどれかを返す。 */
  outcomeOf(record: PlayRecord, params: Params): Outcome;
  /** おまかせ：その結果になる記録。outcomeOf(autoRecord(o, p), p) === o。 */
  autoRecord(outcome: Outcome, params: Params): PlayRecord;
}
```

- 任意の `rate(record, params)`：結果カードの★（1〜3）と数の行（`scoreJa`。最初の数が0から数え上がる：「13個食べた」「丸さ 82%」「0.04秒差」）、または `null`（評価しない記録）。純粋関数で、`outcomeOf` と食い違わない（良い結果ほど★が少なくならない。クリケット：ちょうど★3、近い★2、外れ★1、振らない無し）。★は画面に出すだけで、保存も Ink への受け渡しもしない（4.1）。態度を選ぶゲームは書かない（AGENTS：正解を1つにしない）。`rate` が無ければ★は出ない。
- 記録（`PlayRecord`）は、遊ぶ人がしたことの決まった形の記録。時刻だけでなく、回数・押した場所・どの操作で終えたか・なぞった線の要約など、何でもよい。
  - クリケット：振った時刻（遊びを始めてからのミリ秒）か、振らなかった（`null`）。
  - かくれんぼ：開けた扉の順と、終わりの出来事（見つけた扉、名前を呼んだ回数、待った）。開けた数で `door_quick` と `door_by_door` を分ける。
  - ローティー：なぞりごとの向きと長さ。丸さと縦横の比で形（`round`・`truck_bed` など）を分ける。
  - メヘンディ：決めた場所（当たり・外れ）か、「明日にする」か。時間の制限は無い（2026-11-13のユーザーの判断。遊ぶ人がやめると決めたときだけ `later`）。
  - ゴルガッパ：拍ごとの押した・押さない、「バス」を押した拍。
- 決まり：同じ記録と引数なら、いつも同じ結果。乱数、時刻（`Date.now`・`performance.now`）、DOM、React、ゲームの状態、生成物を読まない（6.1 の登録の検査が、`rules.ts` の文と import を調べる）。
- エンジンは、記録の形と、記録からエンジンの結果（例 `cue_tap`：`clean`・`early`・`late`・`miss`・`none`）を出す関数を持つ。皮は、エンジンの結果を自分の結果へ写す。表で足りる皮は表だけを書く（例：`cueTapRules(tuning, { clean: "six", early: "over_wall", late: "edge", miss: "bowled", none: "no_swing" })`）。`cue_tap` の遠く外れた押し（`miss`）は、1つの結果のほかに、ちょうどの時より前と後で分けて `miss: { early: …, late: … }` とも書ける（布で鳩：彼女がまだ階段の上にいるうちに広げたか、通り過ぎた後か。おまかせは、表の順 clean・early・late・miss の前・miss の後・none で、その結果に写る最初の押し方で遊ぶ）。足りない皮は関数を書く（かくれんぼ）。

### 2.5 遊ぶ画面（`Play`。別のファイル）

`Play` は次をもらう。

```ts
interface MiniGamePlayProps<Params, Outcome extends string> {
  params: Params;                 // 札の引数（定義の zod で読んだもの）
  auto: Outcome | null;           // おまかせ：rules.autoRecord の記録で、この結果まで自分で遊ぶ
  still: boolean;                 // 動きを減らす（「演出を短縮する」か、端末の設定）
  seed: number;                   // 見た目の揺らぎだけに使う（2.8）
  clock: PlayClock;               // 2.7
  cast: { heroine: ReactNode; person?: ReactNode };
  names: { player: string; heroine: string };   // 2.10
  sound(id: string): void;        // 定義の sounds の音だけ。設定の音量・オフに従う
  vibrate(kind: VibrationKind): void;           // 設定の振動に従う
  status(textJa: string): void;   // 上の帯の短い文（「2/3」「のこり8秒」）
  end(outcome: Outcome, detailJa?: string, options?: { record?: unknown; holdMs?: number }): void;
  // 終わり。決まった瞬間に呼ぶ。record は rate に渡す記録、holdMs は場がまだ見せる時間（球が飛ぶ、煉瓦が落ちる）。
  // 最初の1回だけが効く。detailJa は結果カードの数の行（rate の scoreJa が無いとき）
  decided(): void;                // end の前に結果が決まった（決めた押しの後、場がまだ見せている）：本番の「中断する」を消す
  practice: boolean;              // 練習（物語は結果を選ばない）
  juice: MiniGameJuice;           // 手応えの道具（2.6）
  react(kind: MiniGameReaction, lineJa?: string): void; // ヒロインの短い反応（2.6）
}
```

- 皮の場（`Field`）にエンジンが渡さない物は、`useMiniGameKit()`（`host/kit.ts`）で読む：`{ juice, react, practice, still, end, decided }`。エンジンを直さずに、皮が道具を使える。皮は、エンジンより良く分かる瞬間（クリケット：板が球に当たった、煉瓦が落ちた）で `end(結果, undefined, { record, holdMs })` を呼んでよい（最初の1回が効く）。
- 振動（`vibrate`）の種類：`item`・`clue`・`shake` に、`tap`（10ms）・`hit`（25ms）・`success`（15・40・15）・`fail`（40ms）を足した。枠は、皮の振動の100ms以内には終わりの振動を出さず、終わりの振動の100ms以内の皮の振動も出さない（1つの瞬間に1回。group2 N11）。

- `Play` が描くのは、場（フィールド）と下の操作の所だけ。上の帯・結果・中断・一時停止は描かない（枠が描く）。
- 結果は `Play` が規則で決めて `end` に渡す。枠は、結果が定義の `outcomes` にあることを確かめる。
- 根の要素の class は `mg-<game-id>`（ID の `_` を `-` に）、エンジンの部品の根は `mg-engine-<engine-id>`。CSS はその中だけに効かせる。本番ビルドの検査の目印にもなる（5章）。

### 2.6 共通の枠（host）

`src/minigames/host/MiniGameHost.tsx` が、全てのゲームで次を受け持つ。ゲームは書かない。

- 流れ（2026-11-13、試遊の後）：**説明カード →（練習）→ 3・2・1・スタート → 遊び → そこまで！ → 結果カード → 物語**。全て枠が持ち、皮は 2.3 の項目を宣言し、2.5 の道具を呼ぶだけ。値は `host/timing.ts` と `host/flow.ts`（純粋関数、`flow.test.ts`）。

- 練習：同じ遊びを、帯に「練習」の札を付けて遊ぶ。結果は物語に選ばれない。結果カードは「もう一回」（数えなしで「スタート！」からすぐ）と「本番へ」（数えから）。「中断する」でカードへ戻る。

- そこまで！（`end` を受けた瞬間）：調子ごとの止め（`great` 120ms・`good` 90ms・`plain` 60ms・`oops` 80ms。調子は結果の `finishTone`、無ければ★から：★3 `great`、★2 `good`、★1か評価なし `plain`。時計を止め、場の CSS の動きも止める）、明→暗のフラッシュ（★3は2往復。白一色にしない）、言葉（outcome の `finishJa`、無ければ「そこまで！」）を40pxで0.5秒（`finishAnchor: "top"` なら帯の下）、音（`great`・`good` は `quiz_correct`、`plain` は終わりの笛 `whistle`、`oops` はしくじりの `impact_thud`）と振動（`great`・`good` は `success`、ほか `fail`。皮が直前100ms以内に振動させていれば出さない）。`finishJa: null` は止めだけ。`end` の `holdMs` の間は場が動き続け（時計は動く、押しは捨てる）、結果カードは0.5秒と `holdMs` の遅い方の後（足さない）。動きを減らすと、フラッシュをやめ、止めと言葉と音は残す。

- 読み込み：フレームが出たら `load()` を始める。読めるまで開始のボタンは「準備中…」で押せない。読めなければ「読み込めませんでした」と、「もう一度」「おまかせで進める」（札の `auto` の結果を同じ道で選ぶ）を出す。遊べなくても先へ進めるように。

- 手応えの道具（`juice`。値は試遊の報告 group3 6.4）：`hitStop(ms?, target?)`（40〜150ms、既定90。時計を止め、当たった物を±3→±1pxで震わせる）、`shake("s" | "m" | "l")`（縦2px・120ms、縦横4px・200ms、8px・320ms。0.85倍ずつ収まる）、`flash("hit" | "big")`、`burst(要素か場の0〜1の点, "star" | "ring" | "dust" | "splash", size?)`（6つまで、濃い2pxの縁で明るい写真の上でも見える、400ms以内）、`squash(target, "press" | "land" | "pop")`、`denied(target)`（押しても何も起きない物：小さく揺れて `ui_denied`。押して無反応を作らない）。Web Animations の `translate`・`scale` で描くので、皮の `transform` と重なる。動きを減らすと、`shake`・`flash`・`burst`・`squash` は何もせず、`hitStop` は止めるだけ、`denied` は音だけ。
- 選ぶ：`onMiniGameOutcome(outcome)`。1回の遊びで選ぶのは1回だけ。ゲームが断ったら（起きないはず。6.3 が確かめる）、「今はこの結果を選べません」と出して開始のボタンへ戻る。
- 二度押し：枠の数えが無い遊び（と「もう一回」）を始めた直後（今の0.45秒）の押しは、開始のボタンの2回目として捨てる。ただし、なぞるゲーム（`controls: "drag"`。最初のなぞりをすぐ始めてよい）では、押したボタンのあった所（周り12px）に落ちた押しだけを捨てる（キーの押しは時間だけで捨てる）。ローティーで0.45秒以内に始めたなぞりが消えた不具合の直し（group2 N10）。
- 動きを減らす：`still` を渡し、層に `data-still` を付けて、CSS のアニメーションと transition を止める。遊びに要る動き（飛んでくる球、針）は、`Play` が時計から JS で描くので止まらない。
- フォーカス：始めると、層の主な操作（`data-minigame-primary` の要素。無ければ層）へ。中断すると開始のボタンへ。結果の後は、次のフレームの画面の決まりのまま。
- 音楽：`quietScene` のゲームの間だけ、場面の音楽と環境音を下げる（音楽の下げ方 `MusicDuck` に1つ足す）。`music` のゲームは、スタートから結果カードまで、その曲に切り替える（2.11）。
- 写真と描いた絵（D1、2.12）：`bg` の背景と、遊ぶ間の場面の絵に `mg-photo` の扱い（彩度・明るさを下げ、少しぼかす）を当てる。

### 2.7 時計と一時停止

- 時間は枠の時計 `PlayClock` が持つ。`now()`（始めてからのミリ秒。止まっていた間を除く）、`at(event.timeStamp)`（入力の時刻を同じ物差しへ）、`onFrame(callback)`（requestAnimationFrame。止まっている間は呼ばない）、`after(ms, callback)`（時計と一緒に止まるタイマー）。
- ゲームは `performance.now()`・`setTimeout` を自分で使わない。
- 枠の時計には、ほかに2つの止まり方がある（2.6）。数え（`leadMs`：時刻は0のまま、毎フレームは0で呼び、タイマーは待つ。数える間の入力の時刻は0より前）と、止め（`hold(ms)`：時刻だけが止まり、毎フレームは同じ時刻で呼ぶ）。Debug の部屋の押す遅れ（+60・+120ms）は、`at()` の時刻に足す（6.6）。
- ページが裏に回ると（`visibilitychange`）時計が止まる。戻ったら、`timed` のゲームは「一時停止中」と「続ける」「中断する」を出し、「続ける」で動き出す。時間で進まないゲームは、そのまま続く。
- 今のクリケットは、裏に回ると開始のボタンへ戻す。時計を枠に移せば、止めて続けられる。9章の問い2。

### 2.8 乱数を使わない・見た目の揺らぎ

- 結果は記録と引数だけで決まる（2.4）。乱数は結果に入れない。
- 見た目の揺らぎ（観客の位置、葉の揺れ）が欲しいときは、枠が渡す `seed` から作る（`host/seed.ts` の小さな生成器 `seededRandom(seed)`）。`seed` は、保存にある値から決める：`fnvHash(`${revision}:${gameId}:${prefix ?? ""}`)`。同じセーブで読み込み直すと同じ見た目になる。新しく保存するものは無い。
- 揺らぎは規則に渡さない。当たりの場所や難しさを揺らさない。場面で変えたいときは、札の引数にして作者が決める（かくれんぼの扉は7番目、など）。

### 2.9 入力と片手操作

- 使える入力：タップ、長押しして離す、1本指でなぞる。キーボード（Space・Enter・矢印など）。
- 使わない：2本指以上、マイク、カメラ、傾き・揺らし（端末の向きや動き）、振動が無いと分からない合図。声の大きさのような遊びは、長押しして離す（`hold_release`）で作る。
- 片手：操作のボタンは画面の下の方（親指の届く所）に置く。大きさは44px以上（主な操作は今の「振る」と同じ64px程度）。場は上と真ん中。
- なぞる場は `touch-action: none` と `overscroll-behavior: contain`（引っぱって再読み込みを起こさない）。ポインタを捕まえ（pointer capture）、座標は場の大きさで0〜1にする（`host/` の小さな関数 `fieldPoint`）。

### 2.10 名前を絵に描く

- 遊ぶ人とヒロインの名前は、枠が `names` で渡す（Ink の `player_name`・`heroine_name` と同じ値）。ゲームはゲームの状態を読まない。
- 描くのは React の文字（要素の中の文字か、SVG の `<text>`）だけ。HTML として入れない（AGENTS）。
- 名前は自由に入れた文字なので、かな・漢字・ラテン文字のどれも来る。入れた文字のまま描く。ほかの文字（デーヴァナーガリーなど）へ書き換えない。どんな名前でも正しく書き換える方法は無いので、作らない。
- 物語が「ヒンディー語で書いた」などと言う所は、作者が決めた絵（飾りの印、わざと読めない線）にし、偽の文字を作らない。どれを描くかは札の引数で選ぶ（例：メヘンディの `text player`・`text illegible`）。
- 長い名前でも欠けないように、場に合わせて文字を小さくする（切らない）。

### 2.11 音

- 効果音は、共通の `content/presentation/sounds.json` に登録した音だけを使う。ゲームはどの旅行編でも使えるコードなので、旅行編の音は使わない。定義の `sounds` に書き、`Play` は `sound(id)` で鳴らす。
- 場面の音楽と環境音は、遊ぶ間もそのまま流す。リズムのゲームは `quietScene: true` で下げる。
- ミニゲームの曲（任意、2026-11-13）：定義の `music` が `calm`（探す）・`bright`（タイミング）なら、スタートで曲 `mg_calm`・`mg_bright` へ切り替え（今の曲の切り替えと同じ1.5秒のクロスフェード。⚙設定の「BGMを流す」「BGMの大きさ」に従う）、結果カードで場面の曲へ戻す（`host/music.ts`、GameApp の `onMusic`、`scene-music.ts` の `miniGameTrack`）。曲は共通の一覧（`content/presentation/music.json`、ファイルは `public/assets/bgm/<ID>.mp3`）にあり、出典・権利の一覧に出る：`mg_calm` は Kevin MacLeod「Derp Nugget」（約110 BPM）、`mg_bright` は同「Desert of Lost Souls」（約134 BPM）。どちらも CC BY 4.0。曲を差し替えるときは ID を変えずに、ファイルとその出典だけを替える。登録の無い曲を名指すと、場面の曲がそのまま続く（エラーにもビルドの失敗にもならない）。
- 恋愛の静かな場面の中の短い遊びは、探すゲームでも場面の曲のままにする（`music: "scene"`。手のひらの模様は宿の夜のワルツを続ける。2026-11-14）。
- リズムのゲーム（ゴルガッパ・花婿の行列）には曲を付けない（2026-11-13）。ゲームの太鼓の拍（96 BPM、50→100 BPM）が音楽で、150 BPM 前後の曲を重ねると拍がずれて聞こえるため。`music` は `"scene"` のまま、`quietScene` で場面の曲を下げる。 一緒に言う（彼女の「せー」「の」と4つの言葉が約92 BPMの拍）も同じ（2026-11-14、group2 N4：134 BPM の曲が4秒の間に出入りし、拍とぶつかった）。

- リズムの判定は画面の拍（時計）に合わせ、音の遅れに合わせない。幅を広めにして、端末ごとのずれの調整は今は作らない。調整が要ると分かったら、⚙設定の項目として足す（そのときに決める）。拍の並びは皮の定義に書く。場面の音楽の曲には合わせない（ゲームの音で拍を鳴らす）。

### 2.12 絵と置き場所

- まず CSS と、コードに書く SVG（TSX）で描く。ファイルが要らず、出典の問題が無く、軽い。皮の絵は皮のフォルダ（`Skin.tsx`・`skin.css`）に置く。

- 色は共通の変数（`--ds-*`）を使う。カードや説明の左の太い線は使わない（AGENTS）。

### 2.13 読みやすさ・アクセシビリティ

- どのゲームも、⚙設定の「ミニゲームをおまかせにする」で遊ばずに先へ進める。手や目の都合で遊べない人の道。
- 層は `role="region"` とゲームの名前。状態と結果は `role="status"` で読み上げる。
- キーボードで遊べるゲームは、`keysJa` を操作のそばに出す。遊べないゲーム（`keysJa: null`）は、開始の所に「⚙設定でおまかせにできます」と出す。
- 探すゲームの場所は、フォーカスできるボタンにする。名前は中身を明かさない（「扉1」〜「扉9」）。
- 色だけで区別しない（メーターの幅は、形と明るさでも分かるように）。
- 各ゲームの読みやすさの注意（キー、動きを減らしたときの見え方、読み上げ）は、`definition.ts` のコメントに書く。

## 3. 書き方

### 3.1 札の形

選択肢の組のすぐ前の行に、1つの形で書く。

```ink
# minigame: <gameId> [auto <結果>] [prefix <語>] [bg <背景>] [art.<枠> <絵>] [retry yes] [<キー> <値>] …
```

- `retry yes`（任意、2026-11-13）：結果カードに「もう一回」を出す。物語の本番は既定で1回きり（ユーザーの判断）。書いたときだけ、結果を選ぶ前に本番をやり直せる。選ぶのは「次へ」を押したときの結果だけ。
- `auto <結果>`：おまかせの結果。書かなければゲームの `defaultAuto`。今の文の流れに合う結果を書く（例：かくれんぼ `door_by_door`、ローティー `truck_bed`、メヘンディ `found`、布で鳩 `perfect`、ゴルガッパ `together`）。
- `prefix <語>`：同じ場面で同じゲームをもう一度遊ばせるとき、そちらの `# option:` を `<語>_<結果>` にする（選択肢の ID は場面の中で1つずつのため）。
- `bg <背景>`：遊ぶ間の背景（2.12）。`# background:` に書ける背景の ID。
- `art.<枠> <絵>`：皮の絵の枠に入れる旅行編の絵（2.12）。背景の枠には、旅行編の `tourism/catalog.json` に登録した観光写真のIDも書ける。
- そのほかの語：ゲームの引数。キーは英小文字・数字・`_`、値は空白を含まない1語。順は自由。同じキーは1回。`auto`・`prefix`・`bg`・`art.<枠>`・`retry` は枠のキーで、ゲームの引数にはできない。
- すぐ後に、結果ごとに1つずつ選択肢を書く。`# option:` は結果（か `<語>_<結果>`）。選択肢の文は画面に出ないが、ログとセーブで分かるように、何が起きたかを書く（例「最後の一球：まっすぐ打ち返した」）。英語の返事を選ぶ場（道中交流）でも、結果の選択肢の文は日本語の説明でよい。
- 結果の数はゲームごとに決まっていて、使い所で減らせない。分けたくない結果は、選択肢を同じ knot へ合流させる。

### 3.2 JSON のファイルにしない理由

- 札は、置き換える選択肢の組のすぐそばにある。読む人が1か所で分かる。
- ほかの演出の札（`# se:`・`# weather:` など）と同じ書き方で、同じ読み方（`parseStoryTags`）を通る。
- JSON にすると、使い所ごとに ID と、それを指す札が要る。書く所が2つになる。
- 引数は少ない（多くて2〜3）。多くのデータが要るゲーム（拍の並びなど）は、皮の定義に持つ。場面で変えるのは、ID の引数1つで選ぶ。
- 二つの書き方は作らない。

### 3.3 状態で変える

ゲームは、フラグ・品物・関係値を読まない。状態で変えたいときは、Ink の `cond()` の分かれ道に札を書き分ける。札は、選択肢の組の前の最後の行に付いていればよい。

```ink
{ cond("flag gt_jaipur_mehndi_his_name"):
    # minigame: mehndi_search target thumb text player auto found
    花びらと蔓の間を、目でたどる。
- cond("flag gt_jaipur_mehndi_her_secret"):
    # minigame: mehndi_search target peacock text illegible auto found
    花びらと蔓の間を、目でたどる。
- else:
    # minigame: mehndi_search target vine text farhana auto found
    花びらと蔓の間を、目でたどる。
}
* [見つけた # option: found]
* [違う所を指した # option: wrong_spot]
* [「色が濃くなる明日にする」 # option: later]
    # later
```

全分岐の歩みは、どの分かれ道でも、札と選択肢の組が合うかを調べる。

### 3.4 content:build の検査（一般の形）

検査は `src/minigames/tag.ts`（札を読む）と `scripts/scene-walk.ts`（全分岐の歩み）の2か所に、一度だけ書く。ゲームを足しても、検査のコードは足さない。ゲームが足すのは引数の zod だけ。

止める（エラー）：

1. 札が読めない：無いゲーム（ゲームの一覧を出す）、結果に無い `auto`、`prefix` の形の誤り、知らないキー（そのゲームのキーと説明を出す）、同じキーが2回、値の無いキー、ゲームの zod に合わない引数（zod の文と、そのキーの説明を出す）、無い背景、無い枠（ゲームの枠を出す）、無い絵、人物の枠に webp・png でない絵、ほかの旅行編の絵。
2. 札が選択肢に付いている。
3. 札の行と選択肢の組の間に別の行がある、場面が終わる、選択肢が来ない。
4. 選択肢の組が結果と1つずつ合わない（足りない、余分、`# option:` の無い選択肢）。札のすぐ後がクイズや推理の呼び口なら、その旨の文で止まる。
5. 結果の選択肢が、選べないことがあり、ゲームの代わりの結果（4.7）をたどっても、いつも選べる結果に届かない（4.2 の保証の検査）。だから、いつも選べる結果が少なくとも1つある。
6. ミニゲームが動かない所に書いた（1.3。告白のデートは理由を言う）。
7. おまかせで抜けられない輪：おまかせの結果をたどると、ほかの選択肢の場を通らずに同じ札へ戻る。おまかせで遊ぶ人が進めなくなるため。

注意（警告。止めない）：

- おまかせの結果が `# later` の選択肢（おまかせでは、その場面をいつまでも終えられない）。

選択肢の ID が場面の中で1つずつであることは、今の検査が見る。

歩みで見つけた使い所は、`src/content/generated/minigame-uses.json` に書く（場面の ID と種類、ストーリーと knot、ゲーム、`auto`、`prefix`、`bg`、`art`、引数、札の行の文）。ゲームは読まない。テスト（6.3）と Debug の部屋（6.6）が読む。

### 3.5 クリケットの札の移し方

- 今の札 `# minigame: cricket_batting auto over_wall` と `# minigame: cricket_batting prefix again auto over_wall` は、そのまま新しい形に合う（`auto`・`prefix` は枠のキーのまま。引数は無い）。
- Ink は直さない。フレームの保存の形も変わらない（`params` は引数があるときだけ入る）。

## 4. 結果と効果

### 4.1 結果は選択肢、数は渡さない

- 結果はゲームごとに決めた有限の ID。結果は、同じ `# option:` の選択肢を選ぶことだけで物語に効く。その後は普通の選択肢の道（Ink、効果の札、デートの `# profile:`、ログ、保存）。
- 点数・値段などの数は、Ink の変数にも効果にも渡さない。
  - 効果は、ビルドが選択肢ごとの表にして、払えるか・選べるかを確かめる決まり（[02 技術設計](02_TECH_ARCHITECTURE.md#編集元と生成物の分離)）。数で変わるお金は、この確かめをできなくする。
  - 値段の交渉は、値段の段（例：`deal_high`・`deal_fair`・`deal_low`・`walk_away`）を結果にして、選択肢ごとに `# money: -1200` などを書けば作れる（額は作者が決める）。払えることは、場面の頭の `# when: money …` か、道の上の条件で保証する（4.2）か、払えないときの代わりの結果をゲームが宣言する（4.7。ラージューの地図）。
  - 画面に出すだけの数（「3球中2球」）は、`end` の `detailJa` で結果の下に出せる（保存も Ink もしない）。
- 数を Ink に渡す必要が出たら（例：台詞に点数を言わせる）、そのときに読むだけの変数を1つ足す。選択肢の道は変えない。今は作らない。9章の問い3。

### 4.2 結果の選択肢に書ける札（保証の検査）

- ゲームは、遊ぶ人が持っているものと関係なく結果を選ぶ。だから結果の選択肢は、その場でいつも選べる必要がある。選べないと、遊び終えても先へ進めない。
- 今の検査（`scripts/scene-walk.ts` の `choosable`。A10 と同じ関数）：
  - `# requires:` と、渡す・使う品物：場面の頭の `# when:` と、道の上で真と読んだ `cond("…")` が保証すれば選べる（その道で先に渡した・使った品物は除く）。猿の小瓶（`cond("item gt_delhi_rain_attar held")` の分かれ道の中の `# use: gt_delhi_rain_attar`）は、今の検査で通る。
  - お金と AP：場面の頭の `# when:` の `money`・`ap` だけを数える。道の上の条件と、道の上で先に払った分は数えない。
  - `# then: move`：いつも「選べないことがある」と数える。
- 変えること：お金と AP も品物と同じく、道の上で真と読んだ条件を数え、道の上で先に払った分（前の選択肢の `# money:`・`# ap:`）を引く。これで、品物・お金・AP・`# requires:` の全てが同じ「保証」の決まりになる。A10 も同じ関数を使うので、ミニゲームだけの特別な検査は残らない。
- 選べるかに関係しない札（`# set:`・`# rel:`・`# profile:`・`# memory:` など）は、いつでも書ける。
- 制作ガイドの今の文（「品物を渡す・使う」選択肢は全部止まるように読める）を、「その場で持っていると保証されない品物を渡す・使う」に直す。
- 道で先に払った分を引くと、今の内容で新しく止まる場面が出るかもしれない。そのときは、その場面の頭の条件を直す（8章 R9）。

### 4.3 「また今度」の結果

- `# later`（「また今度」）は、それを書ける場面（差し込みの場面）なら、結果の選択肢にも書ける。場面は終わらず、次に同じ時点が来たときにまた出る。
- 例：メヘンディの「明日にする」のボタンを、結果 `later` にする（時間切れは作らない：遊ぶ人が選んでいない「また今度」に、物語が「逃げたね」と返さないように。2026-11-13）。
- おまかせの結果を `later` にすると、おまかせではいつまでも終わらない（3.4 の注意）。

### 4.4 関係値

- ゲームは関係値を動かさない。動かすのは、作者が結果の選択肢に書いた札（`# profile:`・`# rel:`）だけ。関係の値は今どおり遊ぶ人に見せない。
- デートの噛み合いの選択肢の代わりにする（デートの knot の選択肢の組）なら、各結果に `# profile:` を書く（今の決まり：デートの knot の選択は、どれも噛み合い）。結果は腕前でなく「どう遊んだか」という態度にすると公平（かくれんぼ：名前を呼ぶ・一つずつ開ける・待つ）。
- 場面の中のゲーム（手伝いの knot、差し込み、案内、バトル）は、既定で `# rel:` を書かない。腕前で隠れた値が動かないように。書くときは、結果ごとに別の軸にし、どれか1つが得にならないようにする。
- これは書き方の決まりで、台本の点検で見る。ビルドでは止めない（AGENTS：関係値の札は作者が決める）。
- 失敗の結果は、面白いか意味のある場面にする。行き止まりにしない（例：猿の小瓶を落とすと、芝生に雨の匂いの場面）。
- 置き換える場面の、今の選択肢の関係値の札も見直す（例：メヘンディの「見つけたふり」の `trust -1` は、押し間違いの結果には付けない）。

### 4.5 もう一回と噛み合い

- 「もう一球」は、結果の選択肢から手伝いの knot へ行き、そこで `prefix` を付けて同じゲームをもう一度書く（今のメヘターブ・バーグ）。
- デートの knot の噛み合いは、1回の遊びで1回だけ。もう一回の knot は手伝いの knot なので、その選択肢は場面の中の選択（`# profile:` を書けない）。デートの噛み合いの数の検査（A14）が、そのまま守る。
- 遊びの途中のやり直しは、枠の「中断する」で開始の前に戻るか、読み込み直す。どちらも何も選んでいない。結果を選んだ後のやり直しは無い。

### 4.6 セーブ

- 新しく保存するものは無い。保存されるのは、今と同じく選択肢の所のフレーム（`frame.minigame`）と、結果の選択肢を選んだ後。
- 遊びの途中で読み込み直すと、ゲームは開始のボタンから。
- フレームの `minigame` は `{ id, auto, prefix?, bg?, art?, params? }`。`bg`・`art`・`params` は札に書いた語のまま（文字列）で、書いたときだけ入る。読み込みの検査（`storyFrameSchema` の形と、`validateStorySnapshot` の中身）は、登録にあるゲームで、札を読む関数（`parseMiniGameTag`）に通るかを確かめる。通らないセーブは、今と同じく読み込まない（元のデータは残す）。
- 今のセーブ（v23）の形は変わらない（クリケットには引数が無い）。セーブの版は上げない。

### 4.7 選べない結果と代わりの結果（2026-11-13）

ユーザーが承認した値段の交渉（ジャイガル砦のラージューの地図、`raju_haggle`）のために足した。決めた値段がそのまま払う額なので、結果の選択肢に、保証されない `# money:` が要る。

- 皮は、結果ごとに代わりの結果（定義の `outcomes` の `fallback`）を宣言できる。その結果の選択肢を今選べないとき（お金が足りない、ほか選択肢が灰色になる理由なら何でも）、遊びはその代わりの結果を取り、それも選べなければ、その代わりへと順にたどる（`src/minigames/fallback.ts` の `availableOutcome`）。ラージューは `buy_map`（₹50）→ `fair_map`（₹40）→ `haggle_map`（₹30）→ `decline_map`（買わない）。
- ゲームの関数 `miniGameAvailableOutcomes(state)`（player-action.ts）が、今選べる結果を、その場面の選択肢のボタンと同じ決まりで出す。遊ぶ人の操作の一覧も、それだけを出す。
- 枠は、今選べる結果を `available` で遊びに渡し、遊びの終わり・おまかせ・Debug の結果のボタンで代わりの結果を取る。皮はそれを絵に出してよい（ラージューの値段の紙は、払えない値段を下げた値段で見せ、どれも払えなければ「この値段で」を押せなくする）。
- ビルド（3.4 の 5）：保証されない結果は、代わりの結果をたどって、いつも選べる結果に届けばよい。届かなければ止める。おまかせの輪の検査は、おまかせが取りうる代わりの結果もたどる。登録の検査は、代わりの結果がそのゲームの結果で、輪にならないことを見る。
- 新しく保存するものは無い。今選べる結果は、読み込んだ状態から毎回計算する。払うのは選んだ結果の選択肢の `# money:` だけで、1回だけ（ふつうの選択肢と同じ）。お金も AP も0より少なくならない。
- テスト：規則（`fallback.test.ts`）、ビルドの検査（`scene-walk-minigame.test.ts`）、全ての使い所のテスト（6.3）は、結果が払う場面を、各支払いの1ルピー手前の手持ちでもう一度歩き、灰色の結果と代わりの結果を確かめる。

## 5. 読み込みとビルドの決まり

- タイトル画面で読むファイルに入るのは、登録（定義：ID・結果・文・引数の zod）と枠だけ。
- 各ゲームの `Play`・規則・CSS・SVG の絵は、`load()` の `import()` で別のファイルになる。使う場面のフレームが出たときに初めて読む。2つの皮が同じエンジンを使うと、Vite がエンジンを共通の別のファイルにする。
- Debug の部屋（6.6）は、Debug のファイルの中に置く。
- 本番ビルドの検査（`scripts/check-dist.ts`・`scripts/dist-guard.ts`）に、一般の決まりを1つ足す：登録にある全てのゲームの目印 `mg-<game-id>` と、全てのエンジンの目印 `mg-engine-<engine-id>` が、タイトル画面で読むファイルに無いこと。目印は登録から作るので、ゲームを足しても検査は直さない。
- `scripts/dist-guard.test.ts` に、全てのゲームとエンジンのフォルダのソースに目印があることを確かめるテストを足す。名前を変えて検査が効かなくなるのを防ぐ（今の Debug の目印と同じ考え）。

## 6. テスト

ゲームを足しても、テストの配線は足さない。

### 6.1 登録の検査（単体テスト、quick の組）

`src/minigames/registry.test.ts` が、全てのゲームについて確かめる。

- ID とフォルダ名が同じ。`src/minigames/` のゲームのフォルダが全て登録にあり（登録の1行の書き忘れ）、登録が全てフォルダを持つ。
- 結果が2つ以上で、ID が重ならない。`labelJa` が日本語。`defaultAuto` が結果にある。
- 引数の zod：`auto`・`prefix` をキーにしない、各キーに説明がある、`examples` が全て通る。
- `sounds` が共通の `sounds.json` にある。`art` のファイルが直下の `public/` にあり、自作の絵の一覧にある。
- ゲームとエンジンの `rules.ts`・`engine.ts` が、`Math.random`・`crypto`・`Date.now`・`performance.now`・`react`・`src/content/generated` を使わない（文を調べる）。
- 枠の表示（`renderToStaticMarkup`）：開始のボタン、遊び方、おまかせの文、Debug の結果のボタン（Debug のときだけ、結果ごとに1つ）。今の `MiniGame.test.ts` を全てのゲームに広げる。

### 6.2 規則のテストの雛形

`src/minigames/testing/rules-contract.ts` の `describeMiniGameRules(definition, rules, { records })`。各ゲームの `rules.test.ts` はこれを1行呼び、自分の細かいテストを足す。雛形が確かめること：

- 全ての `examples` の引数と全ての結果で、`outcomeOf(autoRecord(o, p), p) === o`（おまかせでどの結果にもなれる＝どの結果にも届く）。
- ゲームが渡す端の記録（何もしない、すぐ終える、時間切れ）で、`outcomeOf` が投げずに宣言した結果を返す。
- 同じ記録で2回呼んでも同じ結果。

エンジンのテスト（`engines/<engineId>/engine.test.ts`）は、調整の値の決まり（タップの遅れより広い幅など）を、エンジンの言葉で確かめる。皮のテストは、自分の調整の値をエンジンの決まりに通す。

### 6.3 全ての使い所を全ての結果で（ゲームの関数の層。content の組）

`src/minigames/minigame-uses.test.ts`：
