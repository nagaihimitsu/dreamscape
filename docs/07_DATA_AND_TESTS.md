# 07 データ契約・検証・テスト

## 必要な安定ID
`chapterId`、`dateId`、`storyId`、`rewardSourceId`、`memoryId`、`quizId`、`factId`、`choiceEffectId` は文字列で永続的に一意。画面に出す日本語名は後から変えられるがIDは変えない。

## 旅行編フォルダのデータ契約
- 旅行編は `content/journeys/<journeyId>/manifest.json` で登録し、都市・移動・Ink・クイズ・カタログを `content/` 直下の共通データと同じ相対パスで置く。統合規則・生成物・予約された名前・追加手順は [技術設計](02_TECH_ARCHITECTURE.md#統合の規則) を参照する。
- 上のIDを含むすべてのIDは全旅行編で一意（統合時に重複をエラーにする）。`storyId` はその層の `stories/` からの相対パス（`.ink` を除く）で、旅行編フォルダ名を含まない。
- 旅行編フォルダの項目は自分の `manifest.json` の都市だけを扱い、参照先は同じ旅行編か共通データに限る。共通データは都市・旅行編の項目を参照しない（`content:build` が検査）。
- `manifest.json` の都市名（`cities[].nameJa`）は都市ファイルの `nameJa` と同じ。`productionStatus: "complete"` の都市は都市フィナーレを持つ。画像は同じ旅行編の `public/` か直下の `public/` のもの（共通データは直下だけ）。`authoring` のパスは `authoring/journeys/<journeyId>/` の中の相対パス（いずれも `content:build` がエラーにする。読み込まれないファイル・参照されない配信ファイル・接頭辞のないIDは警告。[生成時の検査と報告](02_TECH_ARCHITECTURE.md#生成時の検査と報告)）。
- ゲームは `src/content/generated/` の生成物だけを読む。旅行編だけが持つ種類（道中交流、会話注釈、英語ノートの詳細など）は、どの旅行編にもなければ空として生成する。`memoryCallbacks` は空でもよい（該当がなければ `fallbackMemoryCallbackJa`）。`learning/details.json` は問題ごとに統合し、詳細を持つ問題はそれぞれ学習会話の `storyId` を持つ（同じ旅行編の会話だけを指せる）。
- 開発・テスト専用の見本の編（`authoring/templates/sample_trip/`、[技術設計](02_TECH_ARCHITECTURE.md#見本の編)）は `content/journeys/` に含めない。生成物に加えるのは `npm run content:build -- --with-sample`（単体テストと `npm run verify` の最初の生成、`npm run dev:sample`、E2Eの見本の編の段）だけで、本番ビルドには入れない。テストの一時コピー（`prepareContentFixture`）にも含めず、見本を使うテストが自分で複製する。

## 観察だけの手がかり
- 観光の手がかり（`tourism/catalog.json` の `clues`）の `relatedQuestionIds` には、同じ観光地のクイズの問題のうち、問題文・正解・解説がその手がかりの示す事実を必要とするものだけを書く。同じ場所や同じ時代の話題というだけでは書かない。
- `relatedQuestionIds: []` の手がかりを「観察だけの手がかり」と呼び、正式に認める。どの問題の根拠にもならないが、その場所の見え方を変える観察・資料として手がかり帳に残す。ゲームはこの項目を読まず、手がかり帳は問題と結び付いた手がかりと同じに表示する（問題は手がかりを見なくても解ける。[観光・対決](04_BATTLE_TOURISM.md#バトル)）。観察資料（`observation-cards.json`）の観察ポイントは問題より先に書くので `[]` のままとし、そこから `journey:scaffold`・`journey:release` で登録した手がかり（インド編の観光の手がかりなど）は観察だけの手がかりとして始まる。問題IDは、都市の公開後に旅行編の `tourism/catalog.json` の側に書く。
- `content:build` は、書いた問題IDが手がかりと同じ観光地のクイズの問題であることを確かめる（例のクイズ `*.example.json` と、観光地を持たない都市フィナーレのクイズの問題は書けない）。旅行編ごとの行には観察だけの手がかりの数を出す（例：`clues 32, observation-only clues 25`。[生成時の検査と報告](02_TECH_ARCHITECTURE.md#生成時の検査と報告)）。
- 結び付けは機械的に足さず、手がかりと問題の文を照らして1件ずつ人が決める。公開中の旅行編（ミラノ編・インド編）の観察だけの手がかりを問題へ付け直すのは、シナリオ改修のときの作業とし、その改修の脚本・問題と合わせて決める（それまでは観察だけの手がかりのままでよい）。特殊戦B・Cの証拠（`reasoning.caseClueIds`）に使う手がかりは、項目全体がその特殊戦の保存指紋に入るため、結び付けを変えると、その特殊戦の途中のセーブは再開できず（「バトルが更新されています」と案内し、データは残す）、その特殊戦の英語ノートの解答記録も表示されなくなる。証拠でない手がかりの結び付けは保存データに影響しない。

## シナリオ編集
- Inkは文章と選択肢を担当。`# speaker: heroine`、`# speaker: narrator`、`# background: milano_cafe`、`# effect: memory_milano_promise` のようなタグを採用する。
- `effect:` タグは許可済みイベントの識別子。任意の式やJavaScriptを埋め込まない。
- `#` タグの取り扱いはInk公式の`currentTags`/choice tags仕様に従い、本文の行に一度だけ適用する。
- 選択が決まった直後に状態を保存。再開時にinkjsのstate JSONを復元し、選択前か選択後かの境界を失わない。
- 同一effectの再適用を避けるため、適用済みイベントIDとシナリオ実行位置を正しく扱う。全memoryイベントを世界で一度しか起こせない仕様とは混同しない。
- プレイヤー名等はInk変数で表示し、HTMLとして解釈しない。
- 開発中はシナリオ改稿後の旧版途中セーブの再開を必須としない。異なる脚本を無理に復元せず、読み込めないデータを保護して利用者が明示的に消去できるようにする。

## APの操作契約
- 報酬は `earnRewards`（`src/domain/rewards.ts`）で報酬IDごとに一度だけ付与する。付与済みのIDは同じIDの連打/再表示でも重複加算しない。
- `startDate(state, dateId)`: 定義存在・章解放・関係段階・AP残高・未完了状態を検証し、成功時のみ費用を1回減算、アクティブデートを登録。
- 選択前に保存済みチケットと直前の関係から確率・変化量を確定し、その結果をInkへ渡す。結果と効果・`finishDate` の履歴・告白結果はそれぞれ一度だけ適用する。同一バージョン内の途中デートは保存時の方式で継続する。親しさ・信頼・恋愛の意識には正・ゼロ・負の効果があり、途中で失敗しても重複適用しない。
- 未完了状態のまま再開するなら`startDate`を再度呼ばない。開始をリトライしても重複減算しない。
- APは0以上、設定の上限以下で常に整合。

## 受け入れテストの最低限
1. 空のセーブで開始し、デフォルト名/変更名の両方が表示できる。
2. 初回章クリアでAP4（仮）。同じ章の再クリア・画面再表示・再起動でもAPが増えない。
3. デート開始でAPを1回だけ消費。AP不足/未解放なら消費しない。
4. デート1本で3択×2回が完走し、各反応・思い出の記録が異なる。
5. ページリロード後も選択途中から再開でき、APと好感度の二重加算・二重減算なし。
6. 完了済み通常デートは再開始できずAPも減らない。同一バージョン内で進行中のイベントは保存・再開でき、効果を二重に適用しない。
7. `content/journeys/<journeyId>/stories/**/*.ink` を改稿して再ビルドすると、コードを変更せず台詞が変わる。
8. 存在しないstoryId、重複dateId、未定義effect、壊れたInk、形式違反JSONで検証に失敗する。

9. 狭い画面で文字が切れない。長文の名前を入力してもレイアウトが大きく壊れない。
10. セーブデータ破損時は明確に案内し、利用者の他データを勝手に消さない。読めないセーブから新しく始めても元のバイト列は残り、別タブで同じ旅行編は開けず、手動セーブで保存していない進行は離れる前に確かめる。これらの判定は画面ではなく関数が持ち、単体テストで確かめる（[画面の保護を担う関数](10_DEVELOPMENT_CHECKS.md#画面の保護を担う関数)）。
11. ビルド/型チェック/テストの実行手順をREADMEに記載し、変更内容と影響範囲に応じて必要な確認を選ぶ。公開前や大きな変更では[開発時の確認](10_DEVELOPMENT_CHECKS.md)の全体確認を行う。
12. 旅行編フォルダを1つ追加して `npm run content:build` を実行すると、コードを変更せずに旅行編一覧・会話・クイズ・画像に加わる。どの旅行編フォルダを外しても生成と検証が通る（`scripts/journey-folders.test.ts`。追加の確認には見本の編を使う）。見本の編は共通データだけと組み合わせても生成でき、README に挙げた必須の20ファイルのどれを外しても決まったエラーで止まり、任意の部分（特殊戦B・C、道中交流）を外した最小構成でも生成できる（`tests/journeys/sample_trip/sample-journey.test.ts`）。見本の編はタイトルからエピローグまで実際のゲームの関数で遊べ（`tests/journeys/sample_trip/route.test.ts`）、画面でも新しい旅から旅の終わりまで近道なしで遊べる（`tests/e2e/sample-journey.spec.ts`、E2Eの見本の編の段）。`npm run journey:new` で見本から作った旅行編は、最小構成でも任意の部分を含めても準備中として生成・検証を通り（CIでは、作った旅行編がタイトル画面で準備中として開くこともE2Eの見本の編の段が確かめる）、日本語名がない・既にあるID・使用中の接頭辞は何も書かずに拒否する。見本の出典・画像・文章が残っているうちは `journey:readiness` が示し `journey:release` が止まり、置き換えれば公開の確認を通る（`scripts/journey-new.test.ts`、`scripts/sample-leftovers.test.ts`）。公開中にした旅行編に見本の出典（example.com）が残っていれば `content:build` が止まる（`scripts/content-validation.test.ts`）。
13. 共通のテストは特定の旅行編・都市を対象にするときはその範囲に絞って数え、旅行編を追加しても失敗しない。単体テストの生成物には公開中の見本の編が常に加わるため、この条件は毎回の単体テストで確かめられる。
14. Debug・素材のプレビュー・場面の組み立て部品（`src/dev/`）とテスト用の仮データは本番ビルドに含まれない（`npm run build` の `dist/` の検査）。Debugは起動URLから開いても通常のセーブ・英語ノート・表示設定を変えず（`debug-scenes.spec.ts`。各テストの前後で保存領域全体を比べる）、本番ビルドでは `?debug` を付けても通常のタイトルが出る（`boot.spec.ts` の本番ビルドの段）、Debugでの場面確認は保存・再開の確認に数えない（[テストの3つの道](10_DEVELOPMENT_CHECKS.md#テストの3つの道)）。
15. 1つの旅行編の内容・経路・制作ツールだけを確かめる単体テストは `tests/journeys/<旅行編ID>/` に置き、共通のテストの変更なしに単体テストへ加わる（新しい旅行編は同じ名前のフォルダを作ってテストを置くだけでよい）。共通のコード・制作ツール・テストはこのフォルダと `scripts/journeys/` を読み込まず、1つの旅行編のフォルダもほかの旅行編のフォルダを読み込まない。旅行編を外したときに残ったフォルダはテストが知らせる（`scripts/content-boundary.test.ts`。[旅行編ごとのテスト](10_DEVELOPMENT_CHECKS.md#旅行編ごとのテスト)）。旅行編を外してそのフォルダを消しても、この検査と本番ビルドの検査（`scripts/dist-guard.test.ts`）は変更なしで通る（その旅行編を例に使う共通のテストは書き直す。[技術設計](02_TECH_ARCHITECTURE.md#新しい編を追加する手順)の「旅行編をやめる場合」）。

恋愛に影響する変更では、保存済みチケットとプロフィールの再現性、各軸の確率補正・上下限・変化幅、正負両経路の会話、二重操作・別タブ競合、無作為化しない告白、APが尽きたときの再交流を必要に応じて検証する。

通常デートを順不同で選べること、特定デートIDなしのStage進行、3軸の負値と保存、告白の成立・保留・拒否、拒否後の再挑戦制限、交際後の未体験デート、現在のバージョン内での保存・途中再開を必要な範囲で検証する。旅行・都市の進行に告白を要求しない。開発中は旧開発版セーブの更新後の再開や自動移行を保証せず、新機能ごとに旧互換テストを追加することは必須としない。

旅行の変更では、地点・イベント・片道経路の参照と出典、徒歩時間順の候補、帰路・宿泊・待機、時間と予算の境界、APと交通費の二重消費防止、ロード・別タブ競合を検証する。4観光と2特殊戦の順序を入れ替えた都市フィナーレまでの進行も確認する（`tests/journeys/milano/sightseeing-order.test.ts`）。公開中の全旅行編のランダムウォーク（`tests/explore/journey-walk.test.ts`。[探索テスト](10_DEVELOPMENT_CHECKS.md#探索テスト)）は、種ごとに順序の変わる多くの進行で、毎手の安全性（保存・AP・報酬）と、旅の終わりの前に押せる操作が0にならないことを確かめ、固定の歩みでは、どの開始地点（公開中の各旅行編のタイトルと2都市目以降の始め）についても、そこから歩いた回が1回以上その都市を出る（次の都市への出発か旅の終わり）ことと、公開中の全旅行編の全都市をクリアしてそのエピローグを読むことを確かめる。都市のクリアには都市フィナーレを終える必要があるので、全都市のフィナーレに届くことも合否に入る。観光地・デート・道中交流にどこまで届いたかは要約に出るだけで、合否の条件ではない。ミラノの通しの進行（`tests/journeys/milano/full-route.test.ts`）は、タイトルから始め、観光・特殊戦B・C・都市フィナーレをすべて地図から画面と同じ関数で始める（特殊戦も初回は観光案内から入り、読めば案内の報酬を受け取る）。実際の営業時間とゲーム内時間枠、実運賃と推計・調整値の区別は [ミラノの旅行データ](../authoring/journeys/milano/research/travel/README.md) を参照する。

## 英語学習データと保存の方針
- 翻訳・学習補足は問題本文から分離し、安定したquestionIdと原文・選択肢・正解の版を照合する。問題を改稿した際は対応する翻訳・補足の再確認を検出する。
- 翻訳と復習は任意で、回答・戦績・報酬・恋愛進行を変更しない。未回答の解説を先に見せず、記録されていない個別回答を推測しない。
- バトルの途中保存は内容指紋を検証し、異なる問題を再開しない。学習設定・記録を別保存にする場合も破損・未知バージョン・古いタブを安全に扱う。
