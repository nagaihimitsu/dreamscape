# 07 データ契約・検証・テスト

## 必要な安定ID
`chapterId`、`dateId`、`storyId`、`rewardSourceId`、`memoryId`、`quizId`、`factId`、`choiceEffectId` は文字列で永続的に一意。乗り物のID（`transportModes[].id`）は旅行編の中で一意で、同じく変えない。道中交流のIDと、品物を渡す・使う選択肢のID（Inkの `# option:`）、ツアー・その行程・販売のIDも保存データに入るので変えない（[共通条件管理システムの記録](#共通条件管理システムの記録)）。画面に出す日本語名は後から変えられるがIDは変えない。品物の `carry` も、公開後は変えない（変えると、その品物を持つ途中のセーブが読めなくなることがある）。例外として、セーブ版 v14 で一度だけIDを名前の決まりにそろえて改名した（[セーブの版](#セーブの版)）。以後は変えない。

## 旅行編フォルダのデータ契約
- 旅行編は `content/journeys/<journeyId>/manifest.json` で登録し、都市・移動・Ink・クイズ・カタログを `content/` 直下の共通データと同じ相対パスで置く。統合規則・生成物・予約された名前・追加手順は [技術設計](02_TECH_ARCHITECTURE.md#統合の規則) を参照する。
- 上のIDを含むすべてのIDは全旅行編で一意（統合時に重複をエラーにする）。`storyId` はその層の `stories/` からの相対パス（`.ink` を除く）で、旅行編フォルダ名を含まない。
- 旅行編フォルダの項目は自分の `manifest.json` の都市だけを扱い、参照先は同じ旅行編か共通データに限る。共通データは都市・旅行編の項目を参照しない（`content:build` が検査）。
- `manifest.json` の都市名（`cities[].nameJa`）は都市ファイルの `nameJa` と同じ。`productionStatus: "complete"` の都市は都市フィナーレを持つ。画像は同じ旅行編の `public/` か直下の `public/` のもの（共通データは直下だけ）。`authoring` のパスは `authoring/journeys/<journeyId>/` の中の相対パス（いずれも `content:build` がエラーにする。読み込まれないファイル・参照されない配信ファイル・接頭辞のないIDは警告。[生成時の検査と報告](02_TECH_ARCHITECTURE.md#生成時の検査と報告)）。
- 都市ファイル（`cities/<cityId>.json`）の任意の `backdropAssetId` は、同じ旅行編の観光画像のID（自由時間の背景。ないとき・仮の画像のときは無地。別の旅行編の画像や知らないIDは `content:build` のエラー。[技術設計](02_TECH_ARCHITECTURE.md#画像の出典と自作の絵)）。自作の絵を背景にするときは代わりに任意の `backdropImagePath`（同じ旅行編の `public/` が配信し、その旅行編の `presentation/own-artwork.json` にある絵のパス。ないファイル・一覧にない絵・`backdropAssetId` との両方の指定は `content:build` のエラー）。移動ファイル（`travel/<cityId>.json`）の地点の任意の `photoAssetId` も、同じ旅行編の観光画像のID（自由時間の札の写真。宿の札はこの欄の写真だけ。同じくエラーの検査がある）。行の写真と背景の縮小版は生成物で、元の写真の出典を引き継ぐ（[生成物](02_TECH_ARCHITECTURE.md#生成物手動で編集しない)）。
- ゲームは `src/content/generated/` の生成物だけを読む。旅行編だけが持つ種類（道中交流、会話注釈、英語ノートの詳細など）は、どの旅行編にもなければ空として生成する。`memoryCallbacks` は空でもよい（該当がなければ `fallbackMemoryCallbackJa`）。`learning/details.json` は問題ごとに統合し、詳細を持つ問題はそれぞれ学習会話の `storyId` を持つ（同じ旅行編の会話だけを指せる）。
- 移動手段は徒歩と、`manifest.json` の `transportModes` に宣言した乗り物（2つまで）。経路の `mode` は `walk` か宣言した乗り物のID。乗り物を宣言した旅行編は都市ごとに交通判断台帳 `travel/<cityId>-transit.json` を持ち、地点の組×乗り物の判断（使う・使わない・走っていない・特定できず）が経路と一致し、使わない・走っていない判断には事実の出典を付ける。乗り物の経路にはゲーム用の推定の印と事実の出典を付け、ないものと、台帳のある都市で徒歩の経路がない向きは `content:build` の注意に出る。借りる乗り物（`"rental": true`）は、`travel/<cityId>-settings.json` の `rentals` の場所で借りるまで乗れず、借りなくてもどの地点にも行けて宿に帰れる（[乗り物と交通判断台帳](02_TECH_ARCHITECTURE.md#乗り物と交通判断台帳)）。
- ツアー（`tours/<ツアーID>.json`、ツアーの段階2a）は旅行編フォルダだけに置き、自分の旅行編の都市の地点・地図の出来事だけを指す。代金はパーティ全員分で入場料を含む。ツアーでだけ行く地点（`"access": "tour"`）は同じ地点の徒歩のほかに経路を持たず、交通判断台帳にも書かない（[技術設計](02_TECH_ARCHITECTURE.md#ツアー)）。
- 開発・テスト専用の見本の編（`authoring/templates/sample_trip/`、[技術設計](02_TECH_ARCHITECTURE.md#見本の編)）は `content/journeys/` に含めない。生成物に加えるのは `npm run content:build -- --with-sample`（単体テストと `npm run verify` の最初の生成、`npm run dev:sample`、E2Eの見本の編の段）だけで、本番ビルドには入れない。テストの一時コピー（`prepareContentFixture`）にも含めず、見本を使うテストが自分で複製する。

## 観察だけの手がかり
- 観光の手がかり（`tourism/catalog.json` の `clues`）の `relatedQuestionIds` には、同じ観光地のクイズの問題のうち、問題文・正解・解説がその手がかりの示す事実を必要とするものだけを書く。同じ場所や同じ時代の話題というだけでは書かない。
- `relatedQuestionIds: []` の手がかりを「観察だけの手がかり」と呼び、正式に認める。どの問題の根拠にもならないが、その場所の見え方を変える観察・資料として手がかり帳に残す。ゲームの表示と判定はこの項目を使わず（特殊戦B・Cの保存指紋への影響は下記）、手がかり帳は問題と結び付いた手がかりと同じように表示する（手がかりを見つけていなくても、覚えていなくても問題に答えられる。手がかり帳はバトル中も開け、特殊戦B・Cの証拠は事件の手がかりとしていつでも選べる。[観光・対決](04_BATTLE_TOURISM.md#バトル)）。観察資料（`observation-cards.json`）の観察ポイントは問題より先に書くので `[]` のままとし、そこから `journey:release --apply` で登録した手がかり（定義は `journey:scaffold` が表示する断片と同じ）は観察だけの手がかりとして始まる。問題IDは、都市の公開後に旅行編の `tourism/catalog.json` の側に書く。
- `content:build` は、書いた問題IDが手がかりと同じ観光地のクイズの問題であることを確かめる（例のクイズ `*.example.json` と、観光地を持たない都市フィナーレのクイズの問題は書けない）。旅行編ごとの行には観察だけの手がかりの数を出す（0件なら省略。例：`clues 38, observation-only clues 19`。[生成時の検査と報告](02_TECH_ARCHITECTURE.md#生成時の検査と報告)）。
- 結び付けは機械的に足さず、手がかりと問題の文を照らして1件ずつ人が決める。公開中の旅行編（ミラノ編。インド編の観光地は2026-11-11のユーザー判断で観察をなくした）の観察だけの手がかりを問題へ付け直すのは、シナリオ改修のときの作業とし、その改修の脚本・問題と合わせて決める（それまでは観察だけの手がかりのままでよい）。特殊戦B・Cの証拠（`reasoning.caseClueIds`）に使う手がかりは、項目全体がその特殊戦の保存指紋に入るため、結び付けを変えると、その特殊戦の途中のセーブは再開できず（「バトルが更新されています」と案内し、データは残す）、その特殊戦の英語ノートの解答記録も表示されなくなる。証拠でない手がかりの結び付けは保存データに影響しない。

## シナリオ編集
- Inkは文章と選択肢を担当。`# speaker: heroine`、`# speaker: narrator`、`# background: milano_cafe`、`# effect: memory_milano_promise` のようなタグを採用する。
- `effect:` タグは許可済みイベントの識別子。任意の式やJavaScriptを埋め込まない。
- `#` タグの取り扱いはInk公式の`currentTags`/choice tags仕様に従い、本文の行に一度だけ適用する。
- 選択が決まった直後に状態を保存。再開時にinkjsのstate JSONを復元し、選択前か選択後かの境界を失わない。
- 同一effectの再適用を避けるため、適用済みイベントIDとシナリオ実行位置を正しく扱う。全memoryイベントを世界で一度しか起こせない仕様とは混同しない。
- プレイヤー名等はInk変数で表示し、HTMLとして解釈しない。
- 開発中はシナリオ改稿後の旧版途中セーブの再開を必須としない。異なる脚本を無理に復元せず、読み込めないデータを保護して利用者が明示的に消去できるようにする。

## APの操作契約
- APの条件と数は、各旅行編の `progression/journey.json` の試験の値（遊ぶ人から見た表は[遊び方の「AP」](11_HOW_TO_PLAY.md#ap)）。APを足すのはTypeScriptのゲームルールの層だけ。所持の上限（`content/romance/balance.json` の `apCap`、今は12）を超える分は保留として、報酬IDと残りを別々に保存する（リロード・連打・再戦で重複も取りこぼしもしない）。都市クリアの報酬は、都市ごとに別のIDで持つ。
- 報酬（作者の `rewards`・特殊戦の `completionReward`）は `earnRewards`（`src/domain/rewards.ts`）で報酬IDごとに一度だけ付与する。付与済みのIDは同じIDの連打/再表示でも重複加算しない。
- 差し込みの場面の `# on_done: reward <報酬ID>` は、作者の一度きりの報酬を `earnRewards` で受け取る（`claimedRewardIds` に書く。本来の条件と合わせて一度だけ、上限を超える分は保留）。保存の検査は、その場面を終えたこと（`completedEncounterIds`）を受け取った理由と認める（交流の定義の `alternativeApRewardId`。`src/domain/scene-reward.test.ts`、`tests/journeys/milano/galleria-fortune.test.ts`）。
- 場面の札で得るAP（`# ap: +N`・`# on_done: ap +N`）は、ビルドが作る報酬の決まり（`scene_tag`）の数を、`earnRewards` とは別の関数で、上限までは付与・超える分は保留に分けて、選択・完了と同じ保存で一度だけ付与する（`claimedRewardIds` には書かない。読み直し・再読込・セーブ再開・連打では付与しない。繰り返す場面や「また今度」の選択肢を新しく遊んだときは、もう一度付与する。保留の記録のIDは「決まりのID@revision」）。札で使うAP（`-N`）は、使えるAP（デートなどのために先に取り分けたAPを引いた数）に収まるときだけ、選択肢は選べ、差し込みの場面は出て、本筋の場面は出発できる。選択・完了と同じ保存で一度だけ減算し、同じ保存で保留APを受け取る。
- `startDate(state, dateId)`: 定義存在・章解放・関係段階・AP残高・未完了状態を検証し、成功時のみ費用を1回減算、アクティブデートを登録。
- 選択前に保存済みチケットと直前の関係から確率・変化量を確定し、その結果をInkへ渡す。結果と効果・`finishDate` の履歴・告白結果はそれぞれ一度だけ適用する。同一バージョン内の途中デートは保存時の方式で継続する。親しさ・信頼・恋愛の意識には正・ゼロ・負の効果があり、途中で失敗しても重複適用しない。
- 未完了状態のまま再開するなら`startDate`を再度呼ばない。開始をリトライしても重複減算しない。
- APは0以上、設定の上限以下で常に整合。

## 保存の仕組み
遊ぶ人から見た保存は[遊び方の「保存」](11_HOW_TO_PLAY.md#保存)にある。
- 保存先：ゲームのセーブは旅行編ごとに `dreamscape.journey.<journeyId>.save.v1`（ミラノ編は `dreamscape.journey.milano.save.v1`、インド編は `dreamscape.journey.golden_triangle.save.v1`）。旅行編ごとに、ゲームの進行と英語ノートを分ける。セーブの形の番号は下の「セーブの版」。保存は端末・ブラウザ・URLのオリジンごと。
- 端末ごとの好み：タイトル画面が開く旅行編は、この端末で最後に開いた公開中の旅行編で、その旅行編IDだけを表示設定と同じ端末ごとの好みとして `dreamscape.last-journey.v1` に置く（セーブ・バックアップ・英語ノートに含めず、「古い保存データの整理」にも出さない）。Debugモードのオン・オフも、端末ごとの好みとして `dreamscape.debug-mode.v1` に置く（「保存データの消去」でも消えず、「古い保存データの整理」にも出さない）。
- 表示設定（`dreamscape.presentation.v1`）はゲーム本体とは別に保存する。破損・未知の版・別タブでの更新を見つけたら、勝手に上書きしない。設定や演出は、得点・報酬・セーブのシナリオの指紋に影響しない。
- 英語ノート（`dreamscape.journey.<journeyId>.learning.v1`）は、対訳の設定・開閉・復習の印・各バトルの直近の回答を持つ。壊れたデータや未知の版は自動で上書きせず、別タブで更新されたときは再読込を案内する。問題やバトルの内容の指紋が変わった古い回答は、今の問題に重ねない。戦績はあるのに英語ノートに回答の記録がないバトルは「以前の回答内容は未記録」と出し、回答を推し量らない。
- セーブが持つもの：名前・AP・関係状態・思い出・デートの履歴・告白と交際の状態（解放済みのイベントID、告白の保留／成立、交際エンディングの到達）、進行中のInk、バトルの回答と戦績、観光と発見、今の都市、旅行の現在地・日数・時刻と進行中の活動、`completedEpisodeIds`・`completedCityIds`・`completedGuideIds`・`pendingApRewards`・`battleRewardReceipt` など。
- 章と都市：デートの `chapterId` は都市ID（エピソードの `cityId`）と同じ。デートが開く条件はデートごとの `when`（閉じる条件は `until`）に書き、標準は `{ "episodesCompleted": { "city": "<都市ID>", "atLeast": 1 } }`（その都市のエピソードを1つでも終えた）。セーブには書かず `completedEpisodeIds` から求める（下の「v14 で変えたこと」）。章の完了は都市全体のクリアを意味しない。各観光地・フィナーレは `completedEpisodeIds`、都市全体は `completedCityIds` に分ける。ミラノの都市クリアには、4観光地・2特殊戦・都市フィナーレを終えることが要る。
- 恋愛：新しい恋愛イベントは、始めたときに保存した乱数から、関係状態に応じた反応を決める。進行中の確率デートは、始めた時点の設定（プロフィール）を保存し、再開しても同じ設定を使う。告白の成否は乱数で変えない。同じ版の中のデートの途中は、保存時の脚本と指紋を照らし合わせて再開する。通常デートを選べず関係を築き直す必要があるときは、APの要らない短い再交流を使える。成立の思い出とエンディングは、告白を読み終えた時点で一緒に確定するので、成功の反応の途中で更新しても欠けたり二重に付いたりしない。
- 自動保存は設定で切り替える。オフの間は進行をメモリに持ち、上の「設定」→「セーブ」を押した時点で保存する。保存していない進行があるときのロードやページを離れる操作には確認を出す。保存先は旅行編ごとに1枠で、別のタブで更新されていたら上書きを断り、ロードを案内する。各旅行編は Web Locks で、同じ旅行編を複数のタブで同時に編集しないようにする。
- 操作はリビジョンを照らし合わせ、保存に成功してから画面を進める。交流の中の選択・支払い・持ち物・抽選の結果と抽選時の設定は保存し、再読込や古いタブからの操作で二重に当てない。
- 特殊戦B・Cの推理：`activeBattle.reasoning` に、主張の knot の名前・選択中と提出済みの証拠・追及したか・推理の状態を保存する（通常戦は `null`）。推理の間も同じInkの実行位置を保存し、違う証拠への反応・追及の途中・英語の回答の前後から再開できる。選択と提出はリビジョンを確かめ、連打で二重に採点しない。特殊戦の指紋には証拠のデータも入れ、資料の意味が変わったセーブを勝手に判定し直さない。
- バトルから観光へ戻ったときは、同じ観光地の `activeBattle` と `activeTourism` を同時に持つ。観光を開いている間は回答の操作を止め、バトルへ戻ると同じ回答・得点・ヒント・Inkの位置から続ける。特殊戦はケース資料の中で画像を確かめられ、観光の画面へ移らない。恋愛の会話とは同時に進めない。
- 読めないデータ：破損・未知の版・保存領域の読み込みの失敗と、判別できる対応外の旧版を区別し、どれも自動で消さず上書きしない。案内の画面から明示的に新しく始めるときだけ、元のデータを `dreamscape.journey.<journeyId>.save.v1.backup.<時刻>` に退避する。ほかのアプリの保存データは消さない。シナリオの更新で進行中のInkと合わなくなったときも、元のデータを守る。バトルは問題・正解・シナリオの定義を含む指紋を照らし合わせ、更新前の回答を新しい問題で勝手に採点し直さない。観光画像を替えるだけでは案内の指紋は変わらない。書き直したInkの実行位置を移す機能はない。書き直しを確かめるときは、Debugモードか別のブラウザのプロファイルを使うと、今の旅を残せる。

## セーブの版
- ゲームセーブの形式は1つの番号（`schemaVersion`、`src/domain/game-state-schema.ts` の `GAME_STATE_VERSION`）で、全旅行編に共通。現在は **v23**。保存の形が変わるときだけ番号を上げ、移行処理は作らない。
- v22 以前のセーブは「旧版」として読み込まず、元のデータを変えずに残して「保存データの形式はバージョン22です。…元のデータは残っています。」のように、その版の番号で案内する（破損との区別はつかないため、その旨も伝える）。v23 より新しい番号は「新しいバージョン」と案内し、どちらも勝手に上書き・削除しない。新しく始めるときは元のデータを退避してから始める。ほかの旅行編の旧版のセーブと退避したバックアップは、利用者が設定の「古い保存データの整理」で選んで消せる（[古い保存データの整理](#古い保存データの整理)）。開いている旅行編の旧版のセーブは、そのタイトルの案内と「保存データの消去」で扱う。

共通条件管理システム（場面が「起きてよいか」を記録から決める仕組み。設計は段階に分けて入れる）が読む事実を、セーブ版 v14 から保存する。今は書くだけで、まだ遊びの結果を変えない。読み込み時にほかの記録と食い違えば、そのセーブは読み込まない（元のデータは残す）。
- `seenEncounterIds`（見た道中交流）：最後まで終えた道中交流のID。「また今度」で終えたものも含め、1回だけ記録する。終えた交流（`completedEncounterIds`、「また今度」以外で終えたもの）は必ずこの中にある。今の都市か、クリアした都市の交流だけ。書くのは交流が終わるとき（`finishEncounter`）。
- `itemUses`（品物を渡した・使った記録）：渡した・使った品物ごとに、その交流と選んだ選択肢のID。選択肢を選んで品物の状態が「渡した」「使った」になるのと同じときに書く（`chooseEncounter`）。読み込み時に、渡した・使った品物と1対1であること、その選択肢が本当にその品物を渡す（`giftItemId`）・使う（`consumeItemId`）こと、その交流が終わっているか、その選択肢を選んで進行中であることを確かめる。都市を出ても残る。
- `travel.rideCounts`（乗った回数）：その都市で、徒歩以外の乗り物ごとに地図の出来事へ乗って出かけた回数。乗り物で場所が変わったときだけ数え（`beginTravelEvent`）、徒歩、宿へ帰る道、今いる場所の出来事を始めるときは数えない。次の都市へ出発すると空になる。読み込み時に、旅行編が宣言した徒歩以外の乗り物であること、借りる乗り物なら借りていることを確かめる。
- `storyProgress`（物語の状態：筋の段 `lines` とずっと続く印 `flags`）と `travel.temporaryFlags`（その日・その都市にいる間の印）：作者が決める物語の進み具合。使う筋と印を宣言する仕組みはまだないので、空でなければ読み込まない。
- `activeEncounter.afterBattle`（戦いの結果を出たときに始まった交流）・`activeEncounter.trip`（地図の出来事へ出かけるときに始まった交流）：頭の札で本筋の後・本筋の前に置いた交流（今は見本の編だけ）が書く。進行中の交流が持てる続き先は、観察への戻り先（`returnTourism`）を含めて1つまで。読み込み時に、続き先の出来事・バトル・交流の位置が今の内容と合うことを確かめ、合わなければ読み込まない。続き先のない進行中の交流（なくした自由時間から始める道の形）も読み込まない。

## 古い保存データの整理
設定の「古い保存データの整理」は、このブラウザに残る、今のゲームが使わない保存データを一覧し、利用者が選んだものだけを消す。押さない限り何も消えず、ゲームが自動で消すことはない。何を一覧に出すかと消し方の判定は画面ではなく `src/persistence/old-data.ts`（`listOldData`・`removeOldData`、選んだ項目の旅行編の排他だけを取って消す `removeChosenOldData`。単体テスト `old-data.test.ts`）が持ち、排他の取り方は `runWithSlotLocks`（`src/persistence/journey-lock.ts`。`journey-lock.test.ts`）が持つ。Debugの画面には出さない。
- 一覧に出るもの。項目ごとに、キー名、中身（旧版のバージョン・新しい版・読み込めないデータ・英語ノート。この版にない旅行編のセーブで版の分からないものは「この版では読み込めないセーブ」）、バックアップを退避した日時（キーの時刻から）、大きさの目安（キーと値の文字数×2バイト。0.1 KB単位で切り上げ）、消したときの影響を示す。
  1. ほかの旅行編のゲームセーブで、旧版と判定できたもの（`schemaVersion` が1〜13。v13を含む）。
  2. 読めないセーブを新しく始める前に退避したバックアップ（`dreamscape.journey.<旅行編ID>.save.v1.backup.<時刻>`。同じ時刻に2つ目があれば `.<番号>` が付く。ゲームが作るこの形のキーだけ）。開いている旅行編のものも含め、旅行編ごとに1項目。
  3. 旅行編ごとに保存先を分ける前のミラノ編のキー：セーブ `dreamscape.save.v1` とそのバックアップ（1項目）、英語ノート `dreamscape.learning.v1`（別の項目）。
  4. この版にない旅行編のキー（`dreamscape.journey.<旅行編ID>.…`）：セーブとバックアップ（1項目）、英語ノート（別の項目）、既読の記録（別の項目）、覚えたその国の言葉（別の項目）。見本の編を含めずに生成した開発用の画面では、見本の編（`sample_trip`）のキーもここに出る。
- 一覧に出さず、消さないもの：開いている旅行編のセーブ（タイトルの案内と「保存データの消去」で扱う）、今の版で読み込めるゲームセーブ（バックアップや、この版にない旅行編のキーにあっても）、ほかの旅行編の旧版でないセーブ（壊れたデータ・新しい版・別の旅行編のセーブ・準備中の保存。その旅行編のタイトルで扱う）、この版にある旅行編の英語ノートと既読の記録と覚えたその国の言葉、表示設定（`dreamscape.presentation.v1`）、最後に開いた旅行編の記録（`dreamscape.last-journey.v1`。表示設定と同じ端末ごとの好み）、Debugモードのオン・オフ（`dreamscape.debug-mode.v1`。同じく端末ごとの好み。「保存データの消去」も消さない）、`dreamscape.` で始まらないキー（同じオリジンのほかのサイトなど。読み取りもしない）、上の形に当てはまらない `dreamscape.` のキー。Debugの一時データはメモリの中にだけあり、保存領域にはない。
- 消すときは2段階で確かめる：項目を選んで「選んだデータを消去する」を押し、確認の画面（消す項目・キー名・影響、「元には戻せません」、残るもの）で「消去する」を押す。確認の画面の「消去する」は、画面が出てから0.5秒は押せない（前の画面のボタンを素早く2回押したとき、2回目が入れ替わった「消去する」に当たって消えないように。「保存データの消去」の確認の「保存データを消去する」も同じ）。一覧と確認の画面は大きさとボタンの位置が同じで、「選んだデータを消去する」があった位置には「消去せず戻る」、「閉じる」があった位置には「消去する」が出る。「選んだデータを消去する」を2回押すと、速くてもゆっくりでも、2回目は「消去せず戻る」に当たって一覧に戻る（何も消えない）。結果が出た後の一覧の「閉じる」と「選んだデータを消去する」も0.5秒は押せない（「消去する」を素早く2回押したとき、2回目の「閉じる」で結果を見ないまま画面が閉じないように）。一覧を開いた後に値が変わった・無くなったキーが1つでもあれば何も消さず、一覧を読み直して選び直してもらう。消している途中で消せないキーがあれば、そこで止めて、消したキーの数と止まったキーを示し、一覧を読み直す。
- 別タブ：選んだ項目の旅行編の排他（旅行編を開くときと同じWeb Locksの名前）を待たずに取り、別のタブがその旅行編を開いていれば何も消さずに案内する（「〇〇を別のタブで開いているため、何も消去しませんでした。…」）。開いている旅行編のバックアップは、このタブが排他を持っているので取らない。以前のミラノ編のキーを使っていた版は排他を取らなかったので、その項目にはない。Web Locksのないブラウザでは消さない（旅行編もそもそも開けない）。

## 受け入れテストの最低限
1. 空のセーブで開始し、デフォルト名/変更名の両方が表示できる。
2. 初回章クリアでAP4（仮）。同じ章の再クリア・画面再表示・再起動でもAPが増えない。
3. デート開始でAPを1回だけ消費。AP不足/未解放なら消費しない。
4. デート1本で3択×2回が完走し、各反応・思い出の記録が異なる。
5. ページリロード後も選択途中から再開でき、APと好感度の二重加算・二重減算なし。
6. 完了済み通常デートは再開始できずAPも減らない。同一バージョン内で進行中のイベントは保存・再開でき、効果を二重に適用しない。
7. `content/journeys/<journeyId>/stories/**/*.ink` を改稿して再ビルドすると、コードを変更せず台詞が変わる。
8. 存在しないstoryId、重複dateId、未定義effect、壊れたInk、形式違反JSONで検証に失敗する。

9. 狭い画面で文字が切れない。長文の名前を入力してもレイアウトが大きく壊れない。
10. セーブデータ破損時は明確に案内し、利用者の他データを勝手に消さない。古い保存データの整理は、旧版・バックアップ・以前のミラノ編・この版にない旅行編のキーだけを、キー名と影響を示して2段階の確認のあとに消し、別タブでその旅行編を開いている間は消さない。読めないセーブから新しく始めても元のバイト列は残り、別タブで同じ旅行編は開けず、手動セーブで保存していない進行は離れる前に確かめる。これらの判定は画面ではなく関数が持ち、単体テストで確かめる（[画面の保護を担う関数](10_DEVELOPMENT_CHECKS.md#画面の保護を担う関数)）。

## 英語学習データと保存の方針
- 翻訳・学習補足は問題本文から分離し、安定したquestionIdと原文・選択肢・正解の版を照合する。問題を改稿した際は対応する翻訳・補足の再確認を検出する。
- 翻訳と復習は任意で、回答・戦績・報酬・恋愛進行を変更しない。未回答の解説を先に見せず、記録されていない個別回答を推測しない。
- バトルの途中保存は内容指紋を検証し、異なる問題を再開しない。学習設定・記録を別保存にする場合も破損・未知バージョン・古いタブを安全に扱う。
