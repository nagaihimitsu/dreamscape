`npm run content:check` は差分検証ではなく全コンテンツを検証・生成する。対象テストを絞る場合、例えば `npm test -- src/domain/encounter.test.ts` は通常どおり `pretest` でコンテンツを生成してから、そのテストだけを実行する。Playwrightの `webServer` は、開発サーバーの段では `npm run dev` を実行してその `predev` がコンテンツを生成し、本番ビルドの段では `npm run build` の後に `vite preview` を起動し、見本の編の段では `npm run dev:sample`（見本を含めた生成と開発サーバー）を別のポートで起動する。既に起動したサーバーを再利用する場合は、対象の変更が反映され、生成物が最新であることを確認する。自動テストの通過だけを写真の切れ方や操作性の目視確認の代わりにはしない。

小変更のたびに全単体テストや全E2Eを手元で実行する必要はない。日常の単体テストは `npm run test:quick`（速い組。[単体テストの組](#単体テストの組と所要時間)）とし、全件（`npm test`）はCIと、公開前・大きな変更の `npm run verify` で実行する。PRと `main` へのpushでは、GitHub Actionsが全単体テスト・本番ビルド・E2E一式を自動実行する（[CI](#cigithub-actions)）。上の表でE2E一式を挙げた変更は、PRを出す前に手元でも実行する。開発中は、現在の版より前の旧開発版セーブを更新後に再開できることは保証せず、旧互換テストを新機能ごとに増やす必要はない。現在のゲームの保存・再開や読めないデータの保護は維持する。

`npm test`・`npm run test:quick` と `npm run build` はそれぞれ実行前にコンテンツを生成する。単体テストの前の生成は見本の編を含め（`npm run content:build -- --with-sample`。[見本の編](02_TECH_ARCHITECTURE.md#見本の編)）、`npm run build` と `npm run dev` の前の生成は含めない。`npm run verify` は、見本を含めた生成、全ユニットテスト、`npm run build`（見本なしの生成、型検査、製品ビルド、`dist/` の検査）を順に行う一括用コマンドで、生成は2回行う。最初の生成は会話の全分岐検査のキャッシュを使わずにすべて検査する（`content:build -- --no-cache --with-sample`。[キャッシュ](#会話の全分岐検査のキャッシュ)）。この中の `npm run test --ignore-scripts` は直前の生成を利用して `pretest` のみ省略している。個別に `--ignore-scripts` を付ける、または `npx vitest run` を直接呼ぶ場合は自動生成されないため、Ink・JSON等を変更した後は事前に `npm run content:build -- --with-sample` を実行する。見本の編を前提とするテスト（`tests/journeys/sample_trip/route.test.ts` など）は、見本なしで生成した後に実行すると、このコマンドを案内して失敗する。生成物は1つなので、`npm run dev` を起動したまま単体テスト（`npm run test:quick`・`npm test`）を実行すると、テストの前の生成で見本の編が加わり、その開発サーバーにも「見本の旅」が出る。次に見本なしで生成する（`npm run content:build`、`npm run dev` の起動し直し、`npm run build`。`npm run verify` は最後に行う）まで残る。逆に `npm run dev:sample` の起動中に見本なしで生成すると、見本は消える。E2Eの見本の編の段も見本を含めて生成し、終わると見本なしで生成し直す（[E2Eの段](#e2eの段)）。生成物の鮮度が分からない場合も再生成する。

ゲームと、データを参照するだけの単体テストは `content/` のJSONを直接読まず、`npm run content:build` が検証・統合して書き出す `src/content/generated/content/`（生成物。手動編集しない）を読む。JSONを編集した後も `npm run content:build` を実行する。一方、原本を一時フィクスチャへ写して書き換え、生成を検証するテスト（`src/content/*-content.test.ts` など）と制作ツールは `content/`（旅行編フォルダを含む）の原本を読む。画像も同様に、`npm run content:build` が直下の `public/` と各旅行編の `public/` を `src/content/generated/public/` にまとめ、開発サーバー・`vite build`・Playwrightはこのフォルダを配信する（`npm run dev` / `build` / `test` は先に `content:build` を実行する）。`vite`（`npx vite`・`vite build`・`vite preview`）を直接起動する場合は、先に `npm run content:build` を実行する。このフォルダがないと、画像なしで起動・ビルドされる（警告は出ない）。

`scripts/journey-folders.test.ts` は、原本の一時コピーで旅行編フォルダの改名・追加（見本の編 `authoring/templates/sample_trip/` を写す）・各旅行編フォルダの除外を行い、そのたびに `content:build` 相当の生成と検証を実行する（約1分、旅行編が増えるほど長くなる）。特定の旅行編・都市の内容を確かめる単体テストは、全旅行編の合計件数や一覧ではなく、その旅行編・都市の範囲に絞って数える。単体テストの生成物には見本の編（公開中、都市 `mihon`）が加わるため、リポジトリの生成物と一時コピーの生成結果を比べるテストは、一時コピー自身の生成結果（`buildContent` の戻り値や一時コピーの生成物）どうしを比べる。

`src/content/index.ts` は都市・移動のファイルを `import.meta.glob` で集める。Vitestは変換したモジュールをディスクに保存して次回も使う（`node_modules/.vitest-cache`）が、本文に `import.meta.glob(` を含むモジュールだけは保存しない。型引数を付けた `import.meta.glob<T>(` はこの判定をすり抜け、生成で都市が増減しても古い一覧が使われる（見本の編を含めた生成の後に `Unknown city: mihon` になる）ため、型引数は付けない（`src/content/city-registry.test.ts` が検査する）。古い変換結果が疑わしいときは `npx vitest --clearCache` で消せる。

テストは簡潔な dot レポーターを使い、成功したテスト内のログを省略する。失敗したテストのログ、失敗箇所、終了コードは保持する。内容を詳しく追う場合は、生成後に `npx vitest run --reporter=verbose <対象>` とする。通常のコンテンツ生成は、旧会話注釈の警告と内容の警告（旅行編フォルダの読み込まれないファイル、参照されない配信ファイル、`npm run images:optimize` で軽くできる観光写真、接頭辞のないID、経路に使われない乗り物。[技術設計](02_TECH_ARCHITECTURE.md#生成時の検査と報告)）を件数で示し、個々の警告は `npm run content:build -- --verbose` で確認できる。警告は生成・単体テスト・CI・`verify`・公開のいずれも止めない（旅行編フォルダに置いたままのメモやエディタの控えファイルがあっても `test:quick` は通る）。成功時の最後には旅行編ごとに1行、そのフォルダが持つ都市・ストーリー・クイズ・配信ファイルと各カタログの項目の数が出る。どの英文にも使われない語の意味があれば、その数も出る（一覧は `--verbose`）。生成に失敗した場合は旧会話注釈の警告の詳細と原因を表示し、失敗のまま終了する。

検証の絞り込みと成功ログの抑制は、テストを削除したことや実行時間・トークンの削減量を意味しない。今回確認したコマンドと、実施できなかった確認は作業報告に記載する。

## 単体テストの組と所要時間

単体テストは2つの組に分かれる（`vite.config.ts` の `test.projects`）。

| 組 | 内容 | 実行 |
| --- | --- | --- |
| `quick` | ゲームルール、保存、画面部品、生成物を読むだけのテスト、制作ツールの純粋関数など | `npm run test:quick`（生成してから、この組だけ）。日常の確認用 |
| `content` | コンテンツ全体の生成と検証（`buildContent`）や一時コピーの準備（`prepareContentFixture`）を使うテストと、それらを使う制作ツール（`city-bundle`・`promote-journey`・`inspect-content` など）を読み込むテスト。長い探索（`tests/explore/`。[探索テスト](#探索テスト)） | `npx vitest run --project content`（先に `content:build`） |

`npm test` と `npm run verify`、CIは両方の組を実行する。どちらの組に入るかは一覧で管理せず、`scripts/test-sets.ts` がテストファイルの `import` から自動で決める。テストファイル自身の相対 `import` を何段でもたどり、`scripts/content-pipeline.ts`（`buildContent`）か `src/content/test-fixtures.ts`（`prepareContentFixture`）に届くファイルが `content`、それ以外が `quick` になる（型だけの `import type` は数えない）。`tests/explore/` のファイルは、読み込むものに関係なく `content` に入る（全旅行編を種付きで長く歩く探索で、数十秒かかる。`scripts/test-sets.ts` の `longTestFolders`）。新しいテストもこの規則で自動的にどちらかに入り、どちらにも入らないテストはない（`scripts/test-sets.test.ts` が確認する）。ファイルを指定した `npx vitest run <ファイル>` は組に関係なく実行できる。

判定はモジュール単位で、関数の呼び出しまでは追わない。そのため `scripts/content-pipeline.ts` は `buildContent` だけを公開し、テストが単独で使う検査関数は軽いモジュールに置く（Inkのコンパイルと会話の検査は `scripts/ink-validation.ts`、クイズ1件の検査は `scripts/quiz-validation.ts`、都市のつながりは `scripts/city-links.ts`、読み込んだ内容全体の検証は `scripts/content-validation.ts` の `validateContent`）。テストはこれらを直接 `import` すれば `quick` に入る。`validateContent` は、メモリ上に作った小さな内容（`contentTreeFromFiles`）で拒否を確かめるテストに使う。リポジトリ全体の内容を検証すると生成と同じだけ時間がかかるため、そうしたテストは `buildContent` を使う（`content` に入る）。一方、`buildContent` を読み込む制作ツールのモジュールから純粋な関数だけを使うテストも `content` に入る（2026年11月時点で `src/content/inspect-content.test.ts`、`scripts/journey-authoring.test.ts`、`scripts/journey-release.test.ts`。3ファイル合わせて約1秒）。これらは日常の `test:quick` では実行されないが、`npm test`・`npm run verify`・CIでは実行される。モジュール単位の判定は、読み込むだけで使わない場合も `content` に数える。

`import` の読み取りは正規表現による簡易なもので、たどれるのは行頭の `import`・`export … from`（複数行も可）、`import "…"`、文字列を直接書いた `import("…")` で、行き先は `.` で始まる相対パスの `.ts`・`.tsx`・`.mts`（`index` を含む）だけである。次の書き方はたどらない：行の途中から始まる `import`、`require()`、変数やテンプレート文字列で指定した `import()`、子プロセスで実行する生成、パスの別名、拡張子を `.js` と書いたTypeScriptファイルの指定（`./x.js` → `x.ts`）。逆に、テンプレート文字列の中で行頭にある `import` 文は読み込みとして数える。2026年11月時点のテストと読み込み先には、これらの書き方はない。たどれなかった先が生成に届くテストは `quick` に入り、日常の `test:quick` が遅くなる（`npm test`・`verify`・CIは両方の組を実行するので、実行されないテストは出ない）。そうした書き方は使わない。また、組は設定を読み込んだときに一度だけ決まる。監視モード（`npx vitest`）の実行中に追加したテストファイルはどちらの組にも入らず実行されず、`import` を変えたテストの組も変わらないため、Vitestを起動し直す。

`prepareContentFixture` は `content/` と `public/` を一時フォルダへ写すが、各旅行編の画像（`content/journeys/<journeyId>/public/` のファイル。リポジトリの大半の容量）は写さず、フォルダだけを作って各ファイルへのシンボリックリンクを置く（リンクを作れない環境、たとえばリンク作成の権限がないWindowsでは、ファイルをコピーする。遅くなるが結果は同じ）。テストはそこへファイルを追加・削除してよいが、リンクされたファイルへ上書きするとリポジトリの画像が変わるため、差し替えは `replaceFixtureFile` を使う。単体テストの実行の前後で各旅行編の画像の大きさと更新時刻を比べ、変わっていれば実行全体を失敗にする（`scripts/test-image-guard.ts`）。失敗の表示には、変わったファイルと、最後にコミットした版へ戻すコマンド（`git checkout -- <ファイル>`）が出る。テストが追加したファイルは削除する。まだコミットしていない画像や、コミット後に編集した画像はgitから戻せないため、画像を追加・編集したら単体テストの前にコミットしておく。

### 旅行編ごとのテスト

単体テストは、確かめる対象で置き場所を分ける。

| 置き場所 | 置くテスト | その旅行編を外すとき |
| --- | --- | --- |
| 共通のコードの隣（`src/**/*.test.ts`・`scripts/**/*.test.ts`） | 共通の規則・関数・制作ツールのテスト。旅行編の内容（多くはミラノ編）を例として使ってよい | 例に使っていれば、残る旅行編向けに書き直す |
| `tests/journeys/<旅行編ID>/` | 1つの旅行編の内容・経路・その旅行編だけの制作ツール（`scripts/journeys/<旅行編ID>/`）を確かめるテストと、その補助（例：インド編の三都市を仮の都市で作る `tests/journeys/golden_triangle/test-journey.ts`） | フォルダごと消す |

- 新しい旅行編のテストは、`tests/journeys/<旅行編ID>/` を作って `*.test.ts` を置くだけで `npm test` に加わる。`quick`・`content` のどちらの組かも `import` から自動で決まり（`scripts/test-sets.ts` の `testFilePatterns`）、共通のテストや設定は変えない。フォルダ名は旅行編ID（見本の編は `sample_trip`）にし、ファイル名には旅行編IDを繰り返さない（例：`tests/journeys/milano/full-route.test.ts`）。
- 共通のコード・制作ツール・テスト（`src/`・`scripts/`・`tests/e2e/` など）は `tests/journeys/` と `scripts/journeys/` を読み込まない。1つの旅行編のフォルダ（`scripts/journeys/<旅行編ID>/`・`tests/journeys/<旅行編ID>/`）は、同じ旅行編のフォルダは読み込んでよいが、ほかの旅行編のフォルダは読み込まない（その旅行編を外すと、読み込んだ側のテストまで壊れるため）。旅行編を外した後に残ったフォルダ（同じIDの旅行編フォルダがないもの）とあわせて `scripts/content-boundary.test.ts` が検査する。読み込みとして数えるのは `from "…"`（型だけの `import type`、`export … from` を含む）、`import "…"`、`import("…")` の相対パスで、`vi.mock("…")`・`vi.importActual("…")` のパスは数えない（2026年11月時点で、共通のテストにそうした指定はない）。この検査自身は旅行編を名指ししない（例は架空の旅行編）ので、どの旅行編を外しても直す必要はない。旅行編のテストの補助には本番ビルドの検査の目印も付けない（[本番ビルドの検査](#本番ビルドの検査)）。
- 判断の目安：その旅行編を外したら消すテスト（確かめる対象がなくなる）は旅行編のフォルダ、別の旅行編で書き直すテスト（共通の規則が残る）は共通の場所に置く。1つのファイルが両方を含む場合は共通の場所に残す（例：`src/content/date-tourism-experience.test.ts` は全旅行編の通常デートの検査とミラノ編の台詞の検査を持つ）。
- 旅行編のフォルダのテストだけが確かめていた共通の規則があれば、フォルダを消す前に共通のテストへ移す（例：`tests/journeys/golden_triangle/auto-travel.test.ts` は、都市のエピローグの最後の一歩と次の都市への出発が1回の保存になることも確かめている）。
- E2E（`tests/e2e/`）は段ごとの設定で動くので、ここには置かない（旅行編を名指しするE2Eは[技術設計](02_TECH_ARCHITECTURE.md#新しい編を追加する手順)の「旅行編をやめる場合」）。

所要時間（4コアの開発環境で計測、2026年11月。[会話の全分岐検査のキャッシュ](#会話の全分岐検査のキャッシュ)の導入前、キャッシュが空のとき、保存済みのとき）：

| 確認 | 導入前 | キャッシュが空 | 保存済み |
| --- | --- | --- | --- |
| `npm run content:build` | 約15.7秒 | 約15.4〜16.0秒（`--no-cache` も同じ） | 約3.4秒 |
| `npm run test:quick`（生成を含む） | 約44秒（110ファイル） | 約46秒（111ファイル） | 約30秒 |
| 全単体テスト（`npx vitest run`、生成を除く） | 約400秒（全ワーカーの作業時間 約1,530秒分） | 約190秒（約690秒分） | 約150秒（約530秒分） |
| `npm run verify`（生成はキャッシュなし。単体テストはキャッシュを使う） | 約416秒 | 約200秒 | 約165秒 |

- キャッシュが空でも全単体テストが速いのは、同じ内容の生成を繰り返すテストが、同じ実行の中で先に計算された結果を使うため（1回の実行で約2,700項目・約14MBが保存される）。2回目以降は、テストが一時コピーで作る内容の変化も保存済みになる。単体テストの組を分ける前（ワーカー数の調整も前）は約610秒だった。
- 時間の長いファイル（保存済みのキャッシュで）は `content` の組にある：`scripts/city-bundle*.test.ts` のうち3ファイル（各約45〜60秒。全9都市の書き出し・反映を繰り返す）、`src/content/content.test.ts`（約50秒）、`scripts/story-validation-cache-content.test.ts`（約42秒。比較のためキャッシュなしの生成を含む）。`quick` の組で最も長いのは `tests/journeys/milano/sightseeing-order.test.ts`（約10秒。`scripts/journey-scenario-validation.test.ts` は約14秒から約2秒になった）。
- 1回の生成（約15秒）のうち約12秒はデートの会話の全分岐の検査（`validateStory`。1回の生成で212回）で、キャッシュはこの部分を省く。残りの約3.4秒は、Inkのコンパイル（約1秒）、画像の中身の検査（約1.3秒）、ほかの検証、起動など。キャッシュ導入前の単体テスト一式では `validateStory` が約18,000回呼ばれ、全ワーカーの作業時間の約7割を占めていた。
- ワーカーはCPUのコア数だけ使う（`vite.config.ts` の `maxWorkers`）。1つのファイルの中のテストは順に実行されるため、極端に長いファイルは分けて、別々のワーカーで並列に動くようにする（`scripts/city-bundle*.test.ts` は1つのファイルだったときに約610秒かかり、全体の待ち時間を決めていたため4つに分けた）。
- 計測は `npx vitest run --reporter=dot --reporter=json --outputFile.json=<出力先>.json`（先に `content:build`）で、JSONの各ファイルの `startTime`・`endTime` を比べる。
- 制作ツール（`city:bundle`・`journey:release`）は、検証中に入力が変わっていないことを確かめるため、`content/` と `public/` の全ファイルの指紋（`journeyInputFingerprint`）を取る。1回約80〜110ミリ秒（約73MBを読む）で、ツールの実行時間に比べて小さい。生成と検証は全旅行編を統合した結果に対して行うため、指紋を対象の旅行編だけに絞ると、別の旅行編での同時編集（IDの重複など）を見逃す。このため絞り込みは行わない（2026年11月に判断）。画像を内容ではなくパス・大きさ・更新時刻で比べて読む量を減らす案は、制作ツールの手直しの際に検討する。

### 会話の全分岐検査のキャッシュ

デートの会話の全分岐検査（`validateStory`）は生成時間の大半を占めるため、成功した結果をディスクに保存し、同じ入力と同じ検査コードの組み合わせでは検査をやり直さずに結果を使う（`scripts/story-validation-cache.ts`）。`npm run content:build`・`npm run journey:scenario`、単体テストと制作ツールの中の生成（一時コピーを含む）のすべてが同じ場所を使う。

- 保存場所はGit管理外の `node_modules/.cache/dreamscape/ink-validation/`（1回の生成分で約200項目・約1MB）。フォルダはいつ消してもよく、消すと次の生成ですべて検査し直す。`npm ci` でも空になる。検査コードの指紋ごとにフォルダを分け、新しい方から3つだけを残す（ブランチの行き来で残す分）。
- 項目は内容を変えるたびに増える。鍵には全体のID（効果・背景・表情）・効果の定義・思い出の一覧が入るため、どこか1か所のデータを変えると、ほぼすべてのデートが新しい項目になる（生成1回で約1MB、全単体テストで約14MB。古い項目は残る）。このため1つの指紋のフォルダには最近使った10,000項目（約50MB）までを残し、それを超えた分は、キャッシュを開くとき（生成のたび）に最後に使った日時の古いものから消す。使った項目は使うたびに更新日時を新しくする。
- 鍵（項目の名前）は、検査が読む入力のすべて（コンパイル済みのInk、タグとして許すID〔効果・背景・表情〕、デートの選択の数・効果の数・種類、Inkへ渡す変数、効果の定義、思い出、偶然の反応と関係トーンの指定）と、検査コードの指紋から作る。指紋は `scripts/ink-validation.ts` と `scripts/story-validation-cache.ts`、そこから読み込むすべてのモジュール（何段でもたどる。2026年11月時点で `src/content/tags.ts`・`src/story/memory.ts`・`src/domain/romance-tone.ts` など8ファイル）の中身、使うパッケージ（`inkjs`・`zod`）の版、Node.jsの版から作る。どれか1つでも変われば別の項目になり、検査を実行する。読み込み先が見つからないなど指紋を作れない場合は、キャッシュを使わない。
- 保存するのは成功した結果（経路の数と、検査が通った台詞・効果の一覧）だけ。失敗は保存しないため、エラーの文言は常にその場で検査した結果になる。保存した結果を使うときは、台詞と効果を一度ずつ（最初に通った順に）検査の受け手へ渡し直す。受け手（会話注釈の「古い注釈」警告、効果を使うデートの集計）は集合として数えるので、結果は検査し直した場合と同じになる。読めない・壊れた・鍵の合わない項目は、無いものとして検査する。
- `npm run content:build` は「`Ink validation cache: 212 reused, 0 run`」のように再利用と実行の件数を表示する。キャッシュを使わずにすべて検査するには `npm run content:build -- --no-cache`（`journey:scenario` も同じ）、または環境変数 `DREAMSCAPE_INK_CACHE=off` を使う（`off`・`0`・`false`・`no`）。結果に疑いがあるとき、検査コードの外（例えば `node_modules` の中身を手で書き換えた場合）を変えたときは、これで確かめる。
- `npm run verify`（手元の公開前の確認と、`pages.yml` の公開前の確認）：最初の生成は `--no-cache` で、キャッシュを読まず書かずにすべて検査する。続く単体テストはキャッシュを使う（手元では、同じ検査コードで以前に保存した結果も使う）。
- CI：キャッシュは持ち越さない。各ジョブは `npm ci` で `node_modules` を作り直し、ワークフローの `actions/cache` はPlaywrightのブラウザ（`~/.cache/ms-playwright`）だけを持ち越す（`setup-node` が保存するのは `~/.npm` だけ）。このため、使われる結果はすべて同じジョブの中で同じコードが計算したもの。そのうえで公式の内容検査（`ci.yml` の「Content, types and production build」）は `DREAMSCAPE_INK_CACHE=off` で、キャッシュなしにすべて検査する。単体テストの各ジョブ（3つに分けたもの）は、空のキャッシュで始まる最初の生成ですべて検査し、そのジョブの以降のテストがその結果を再利用する。`pages.yml` は上の `npm run verify`。`scripts/story-validation-cache.test.ts` がワークフローと `verify` のこの条件も確かめる。
- 正しさの確認：`scripts/story-validation-cache.test.ts`（`quick`）は、指紋が読み込み先をすべて含むこと（読み込みの解析とは別の広い検索でも確かめる）、指紋に入るモジュールが実行中にファイル・環境変数・時刻・乱数などを読まないこと、検査コード・Inkの本文・タグのID・変数などの入力のどれを変えても検査し直すこと、保存した結果で経路数・台詞（同じ文を別の話者が話す場合を含む）・効果・会話注釈の警告が同じになること、失敗を保存しないこと、壊れた項目を無視すること、項目数の上限で最近使ったものを残すことを確かめる。テストは環境変数 `DREAMSCAPE_INK_CACHE` に関係なく自分の一時フォルダのキャッシュを開くため、`off` を付けて `npm test` などを実行しても失敗しない。`scripts/story-validation-cache-content.test.ts`（`content`）は、実際のコンテンツでキャッシュなし・空のキャッシュ・保存済みのキャッシュの生成結果と警告が一致し、壊したデートのエラーが同じ文言になることを確かめる。
- `validateStory` に引数を足す場合は、`StoryValidationInput` にも加える（キャッシュ付きの呼び出しは、この入力だけを `validateStory` に渡す）。検査が使うデータは必ずこの入力から渡し、検査コード（指紋に入るモジュール）の中でファイル・`import.meta.glob`・環境変数・時刻・乱数などから読まない。そうしたデータは指紋にも鍵にも入らず、変わっても古い結果が使われる（上のテストが検出する）。

## E2Eテスト

`tests/e2e/` のE2Eは、利用者と同じ操作で主要な流れが最後まで通ることと、重大な不具合（起動できない、進行が止まる、保存が失われる、致命的なJSエラー、Debugモードがオフの本番でDebugが開く・タイトル画面でDebugのファイルを読み込む）がないことを確かめる。個々の観光地・シナリオ・選択肢・デート・品物の網羅や、細かな見た目・位置は対象にしない。ルールは単体・統合テストで、見た目は[人が画面を確かめる](#人が画面を確かめる)と [UIレビュー](../UI_REVIEW_CHECKLIST.md) で確認する。少数の重要な流れに、過去に起きた・起きやすい失敗を狙う確認（エラー推測）を数手ずつ足す形をとり、状態の移り変わりの網羅は画面ではなく単体テストの層で行う。

### E2Eの段

テストは段（tier）に分け、CIでは段ごとに別のジョブとして並列に実行する（[CI](#cigithub-actions)）。どの段で動くかは各テストのタグで決める（`tests/e2e/helpers.ts` の `tier`。`test("…", { tag: [tier.gate, tier.prod] }, …)`）。タグのないテストはどの段でも実行されないため、`scripts/e2e-specs.test.ts`（単体テストの `quick`）が失敗にする。

| 段 | タグ | 起動するもの | 内容 | 件数と所要時間（4コアの開発環境、2026年11月） |

### テストの3つの道

状態の作り方と数え方は、次の3つの道に分ける。

| 道 | 内容 | 確認として数えるもの |
| --- | --- | --- |
| 1. 通常の操作 | タイトルから利用者と同じ操作で進める。`play.spec.ts`・`save-load.spec.ts`・`sample-journey.spec.ts` はDebugも近道も使わない（`scripts/e2e-specs.test.ts` が確かめる） | 遊び方・保存・再読み込みからの再開・別タブ・読めないデータの保護 |
| 2. 本物の関数で作った状態を通常セーブとして置く | 実際の操作では数分かかる前段だけを、`src/dev/scenario-builders.ts`（本物のゲーム関数だけで状態を作り、最後に `validateGameState` を通す部品）で作り、ゲーム自身の `saveGame` で通常のセーブとして置く（`helpers.ts` の `placeSave`。最初の都市の観光案内を開いたセーブは `placeGuideSave`）。その後は画面で操作する（例：`inter-city.spec.ts`、`save-load.spec.ts` の切り替えと「再試行」の二重タップ、`short-screen.spec.ts`、`relationship-change.spec.ts`（デートを開いたセーブは `placeDateSave`））。ページ内で開発サーバーの `/src/...` を読み込むので、本番ビルドの段では使えない（`place…Save` の名前の補助はすべて、`scripts/e2e-specs.test.ts` が本番の段のあるspecで拒む） | 置いた後の画面操作と、その後の保存・再開 |
| 3. Debugを場面の起動台にする | [Debug起動URL](#debug起動url)で場面へ直接入り、その場面を最後まで操作して離れられることだけを確かめる（`debug-scenes.spec.ts`）。各テストは通常のセーブを置いた状態から始まり、終わりに `localStorage` と `sessionStorage` の全体が始めと同じであることを自動で確かめる。Debugの状態は開発用の読み取り口 `window.__dreamscapeDebug` から読む | 場面の確認だけ。保存・再開・別タブ・英語ノートの保存の確認には数えない（AGENTS.mdの「Debugを通常の保存・再開確認の代わりにしない」） |

- Debugの一時データはメモリの中だけにあり、再読み込みで消える。Debugから通常セーブを作る機能はなく、作らない。道2のセーブはテストのコードが作る。手書きの正常なセーブJSONは使わず、意図的に壊したデータ（読めないセーブ、未知の新しい版）は保護の確認にだけ使う。
- Debugは別タブの排他と英語ノートの保存を通らないため、それらの確認は道1で行う。Debugの「場面の確認」の細部はE2Eにしない。
- `debug-mode.spec.ts` は道1ではない（Debugに入る）。ゲームの設定（上の帯の⚙設定から開く）のDebugモードの欄は利用者と同じ操作で切り替え、Debugにはその欄のリンクと、Node側で組み立てた起動URLから入る。読み取り口・開発サーバーのモジュールを使わないので本番ビルドで動き、本番ビルドの段だけで実行する（合否判定の段の時間の予算のため。[不安定さと時間の決まり](#不安定さと時間の決まり)）。開発サーバーでの確認は `debug-mode-dev.spec.ts`（Debug起動台の段。同じくゲームの設定の欄とそのリンクだけを使う）。
- 単体テストも同じ部品を使う。「バトルを結果まで解く」「都市をクリアする」処理を各テストに書かず、`playBattleToResult`・`readGuide`・`finishEpisode`・`playCityToFinaleResult`・`clearCity`・`cityStart`・`cityFinaleResult`・`completedCity` などを使う。回答の選び方（既定は全問正解。`wrongAnswer`・`firstCorrect(n)`・独自の関数）と、操作ごとの確認や保存・復元（`after`）を渡せる。各操作は状態を必ず変え（変わらなければその場で止まって理由を示す）、地図から始めた予定はゲーム画面と同じく結果の時点で精算する。1手ごとに独自の確認をするテスト（全選択肢の採点、回答の二重送信、手がかりの選び直し）は自前の繰り返しのままでよい。
- 部品は、場面を開く処理（地点への配置、AP・関係値の設定、保存した抽選値でのデートと交流）も持ち、Debugもこれを使う。交流は、遊びと同じように、その交流の時点で始める（観察の後の交流は、その観光地の観察を開いて始め、終わると観察に戻る。本筋の前・後の交流は、その観光地への出発・バトルの結果から始める）。`src/dev/scenario-builders.test.ts` が、公開中の全旅行編の全都市（見本の編を含む）で開始・フィナーレ結果・クリア・エピローグを作れることを確かめる。

### 期待値の決め方と直し方

- 合否の基準は仕様（[docs/07](07_DATA_AND_TESTS.md) の受け入れテスト、AGENTS.md）から決め、各テストにその根拠を注記する。観察した数値を書き写さず、関係で確かめる（例：「APは受領記録の合計だけ増えた」「デートを始めた時点から減らない」）。
- テストが落ちたら、まず仕様と照らす。直してよいのは「どこを操作するか」（`ops` の文言、`data-testid`、待つ対象）で、合否の基準を実装に合わせて書き換えない。仕様が変わる場合は、先に仕様の文書を直し、同じ変更でテストを直す。AIに直させるときも同じ。
- 仕様どおりに動かないことが分かったら、ゲームを直し、規則の単体テストを足す（E2Eの期待値を緩めない）。

### 不安定さと時間の決まり

- 再試行しない（`retries: 0`）。たまたま通ったテストを合格にしない。不安定なテストは原因を直すか削除する。
- 新規・変更したテストは `--repeat-each=3` で3回通してから入れる。
- 1件30秒以内を目安にする（長い流れは理由を注記して `test.setTimeout(120_000)` まで）。Debugの段のうち3つのファイル（`debug-scenes.spec.ts`・`short-screen.spec.ts`・`relationship-change.spec.ts`）は、全件が開発サーバーでアプリを2回以上読み込んで場面を遊ぶ長い流れなので、どれもファイル全体を120秒にしている（`debug-scenes.spec.ts` はCIでは1件6〜22秒。2026-11-08にいつもの約4倍遅いランナーで、このファイルの当時の15件中9件が30秒を超えて失敗した。うち1件では、そのとき途中だった `page.clock.pauseAt` も「Cannot fast-forward to the past」で失敗した。その後、起動URLのテストを2つに分け、誤答の後の長い解説のテストを足して今は17件。`short-screen.spec.ts` は1件で、2回の読み込みの後にバトルを遊んで「ロード」もする。手元で約7秒、CPUを6倍遅くして4ワーカーで動かすと約15〜21秒）。合否判定の段は約20件・2ワーカーで2分以内、各段のCIのジョブはブラウザの導入を含めて8分以内を目安にし、超えたら件数や前段の作り方を見直す。合否判定の段は、二重タップや準備中の旅行編などの確認を足して19件になったため、2026年11月に件数の目安を約15件から約20件に上げた（時間は2分以内のまま）。2026-11-08に古い保存データの整理の確認（ゆっくりの2回目のタップと「消去する」の素早い2回目を、それぞれ390×844と320×568で）を足して23件になった。目安の約20件は超えるが、時間は2ワーカーで2分以内（負荷の高い4コアで約1分50秒〜2分）に収まるため、件数の目安は上げずに受け入れる。次に合否判定の段へ確認を足すときは、先に件数や前段の作り方を見直す。2026-11-08のDebugモード（ユーザーの判断）では、これに従って見直し、関係の変化の表示の確認（`relationship-change.spec.ts`。開発サーバーの部品でデートを置く道2）はDebug起動台の段に置き、合否判定の段には本番ビルドの段と同じ1件の `debug-mode.spec.ts`（設定のパスワードでの切り替え）だけを足して24件にしたが、負荷の高い4コア（負荷 約6）でサーバーの起動込み約2分10秒と、2分を超えた。そこで同じ日に見直し、`debug-mode.spec.ts` を本番ビルドの段だけで動かして、合否判定の段を23件に戻した。この確認の要（`?debug` を開く式 `import.meta.env.DEV || …` と、タイトル画面がすぐ読み込むファイル）は本番ビルドでだけ意味を持ち（開発サーバーでは `?debug` は常に開く）、本番ビルドの段もPRごとに合否判定の段と並列に動くので、合否判定から外れることはない。開発サーバーでだけの確認（Debugモードがオンでも、「場面の確認を開く」を押すまで `/src/dev/` を読み込まない）は、Debug起動台の段の `debug-mode-dev.spec.ts` に移した。合否判定の段へ確認を足すときは、今後も先に件数や前段の作り方を見直す。`debug-mode.spec.ts` は5回のページの読み込みとDebugの遅延読み込みを含む長い流れなので120秒にしている（本番ビルドで約8〜9秒）。`debug-mode-dev.spec.ts` も3回のページの読み込みと開発サーバーでのDebugの読み込みを含むので120秒にしている（手元で約6〜9秒、CPUを6倍遅くして4ワーカーで約24秒）。
- 小さな変更のたびに全段を手元で実行しない。関係するspecだけを実行し、全体はCIに任せる（上の表でE2E一式を挙げた変更は、PRの前に手元でも `npm run test:e2e` を実行する）。

### E2Eテストを追加する際の判断基準

1. まず単体・統合テストで確認できないか考える。ゲームルール、AP・報酬、分岐・解放条件、保存形式・別タブ競合・破損データの保護、コンテンツ参照は `src/**/*.test.ts`・`scripts/**/*.test.ts` に書く。画面の中にしかない判定は、先に純粋関数へ移せないか検討する。
2. E2Eに残すのは、ブラウザで組み合わせて初めて起きる重大な失敗（画面の遷移、ReactとInkの実行、ブラウザの保存領域・再読み込み・別タブ、画像やスクリプトの読み込み、本番ビルド）を、利用者と同じ操作で確かめる場合に限る。
3. 新しいファイルやテストを増やす前に、既存の流れへ1〜2個の確認を足せないか検討する。足したテストには段のタグを付ける。
4. 全観光地・全シナリオ・全選択肢・全デート・全品物の網羅、台詞や文言の一致、要素の位置・幅・余白、画面幅ごとの繰り返し、Debug画面の細部はE2Eにしない（見た目は[人が画面を確かめる](#人が画面を確かめる)）。
5. 状態の近道は、実際の操作では数分かかる場合だけ道2を使う。通常の流れで確かめていない場面の表示・操作だけを確かめる場合は道3を使ってよい。どちらも理由をコメントに残す。テストのためにゲーム側の設計・分岐・設定を変えない。
6. 追加・変更したら上の「不安定さと時間の決まり」に従う。

## 探索テスト

決まった流れのテストとは別に、種（シード）で決まる乱数で遊び方を変えながら、起きてはならないこと（安全性）と、進めなくなること（活性）を探す。関数の層のランダムウォーク（固定の種）は単体テストの一部なので、PRの確認と公開前の `npm run verify` で合否に入る（`main` で失敗すると公開も止まる）。モンキーとWebKitは週1回と手動で動かし、合否にも公開にも関わらない。

ここでいう活性は、毎手では「旅の終わりの前に、押せる操作が1つ以上ある」ことを指す（モンキーも同じ）。押せる操作は残るのに先へ進めない詰み（例：対決の結果に「自由時間へ」がなく、手がかり帳から観光に戻っても同じ結果に戻るだけ）は毎手の確認では見つからないため、ランダムウォークは固定の歩み全体で、どの開始地点についても、そこから歩いた回が1回以上その都市を出る（次の都市へ出発する。最後の都市なら旅の終わりに届く）ことと、公開中の全旅行編の全都市をクリアしてそのエピローグを読むことを確かめる（どこかの都市から先へ進めなければ失敗）。対決の結果の出口は、全旅行編の全対決（観光地の対決・特殊戦・都市フィナーレ）について `src/domain/player-action.test.ts` が確かめる（フィナーレ以外は都市の移り方によらず「自由時間へ」がある）。それでも、ほかの道でその都市を出られる詰み（例：特殊戦の証拠をどうしても提出できず、待機・休むだけが続く場面が一部の進み方にだけある）や、`listPlayerActions` が画面の操作を書き漏らしたこと（その操作は試されないだけで、失敗にならない）は、どちらの探索でも見つからない。決まった進行はシナリオのテスト（E2Eの `debug-scenes`・`sample-journey`・`inter-city`、単体の都市の通しテスト `tests/journeys/milano/full-route.test.ts`・`sightseeing-order.test.ts`）で確かめる。細かい進み具合の判定（例：何泊しても新しい内容がない）と、画面と一覧の自動の突き合わせは今後の課題。

### 関数の層のランダムウォーク

- `listPlayerActions(state)`（`src/domain/player-action.ts`）が、今の状態で画面が出す操作（押せるボタン・選択肢）を返す。画面が使うのと同じ判定の関数だけで作る。画面に残っていた判定（対決の結果の出口、エピローグ・出発・保管中のAPの受け取り・待機の可否、証拠の数と選び直し、観察画像の手がかりと手がかり帳で読める資料、道中交流の終わり方）は関数に移し、画面もそれを呼ぶ。画面に操作を足す・押せる条件を変えるときは、判定を関数に置いて `listPlayerActions` にも足す（ずれると、探索が画面にない操作を試すか、画面にある操作を試さない。最初の実行で、手がかり帳の「3枚目の証拠は選べない」の判定が画面にしかないことが分かり、関数へ移した）。
- `playerActionChange(action, roll)` が、その操作を GameApp と同じ関数で状態の変化にし、`applyPlayerAction` で反映する。次の操作は種で決まる乱数で選ぶ（物語を進める操作を多めに、正答を約6割、ヒント・観察へ戻る・待機などは少なめ）。
- 開始地点：公開中の各旅行編（単体テストの生成物にある見本の編を含む）のタイトル（`createGame` と到着の会話）と、2都市目以降の都市の始め（`cityStart`）。開始地点は種と回数で順に回る（種 s の r 回目は、開始地点の一覧で (s + r) を開始地点の数で割った余りの位置。0から数える）。固定の種は開始地点の数だけある（1から開始地点の数まで。`FIXED_SEEDS`）ので、どの開始地点も固定の種のどれか1つの最初の回になる。旅行編を公開する・都市を足すと開始地点とともに固定の種（歩み）が増え、ほかの開始地点の歩みが減ることはない。旅の終わり（`isJourneyComplete`：最後の都市をクリアし、そのエピローグを読み、次の都市がない）では多くの場合（8割）次の開始地点へ移り、残りはまだ始められるデートのために留まる。1,200手でも次へ移る。
- 毎手の確認：
  - 安全性：提示した操作は必ず状態を変える。ゲームの `saveGame`（`validateGameState` を含み、リビジョンが増えない保存を拒む）で保存でき、`loadGame` で読み戻すと同じ状態になる。APが0〜上限にある。一度記録した報酬IDは消えず、AP（所持と保管の合計）は新しく記録した報酬IDの分だけ増え、その手で始めたデートの分だけ減る（二重受給・二重消費・記録のない加算はここで見つかる）。
  - 活性：旅の終わりの前に、できる操作が0にならない（0なら詰み）。
  - 進行：まだクリアしていない都市のフィナーレにもう届かない状態（都市をクリアできなくなった状態）に入らないことを確かめる。`content:build` の進行の検査（`scripts/progression-check.ts`）と同じ関数を、今の状態からかける（失敗の理由は「the city can no longer be cleared」）。今のお金やAPでは、その都市のフィナーレにまだ要る本筋やデートを回れなくなった種は、到達の要約に都市ごとに出すだけで、合否にはしない（予算とAPはシナリオを書き終えた後のバランス調整で決めるため）。
- 歩み全体の確認（固定の種で、`DREAMSCAPE_WALK_SEEDS` を指定しないときだけ）：すべての種が最後の手まで歩く。どの開始地点も、そこから始めた回のどれかが開始地点の都市を出る（次の都市への出発。最後の都市なら旅の終わり）。歩みがその手で行ったことだけを数えて、公開中の全旅行編の全都市をクリアし、そのエピローグを読む（どれかの都市で先へ進む操作が欠けると、その都市から始めた回が都市を出られず失敗する。旅の終わりには、各旅行編の最後の都市から始めた回が届く）。乱数は種で決まるので、同じコードと生成物なら結果も同じになる（2026-11-09、インド編の交通を徒歩・オートリキシャ・地下鉄に切り替えた後の計測：どの最初の回も510手以内で開始地点の都市を出る（最も長いのはゴールデン・トライアングルのタイトルからの504手。見本の編は約150手）。旅の終わりにはミラノ3回、ゴールデン・トライアングル2回、見本の編2回届く。見本の編のない生成物（種4つ）ではミラノ2回、ゴールデン・トライアングル2回）。失敗すると、都市を出なかった開始地点か、クリア・エピローグに届かなかった都市を挙げる。`npm run test:walk` の要約でどこまで進んだかを見て、先へ進む操作が欠けていないかを調べる。旅行編が大きくなって1回（1,200手）では都市を出られなくなったときは、手数（`FIXED_STEPS`・`RESTART_STEPS`）を増やす。この確認はファイル内の先の歩みの結果を使う。`-t` で一部の歩み（テスト名は「seed <種> (from 「<開始地点>」)」）だけを選ぶと、名前の合わないこの確認は実行されず、名前が合えば「最後まで歩いていない種」として失敗する。
- 失敗の表示（確認の失敗も、開始地点の組み立て・操作の一覧・操作の適用・APの計算・保存領域の用意・保存と読み込みなどの関数が例外を出した場合も同じ）：理由、種、手数、開始地点、直前の25手、歩いた旅行編と、同じ歩みを繰り返すコマンド（`DREAMSCAPE_WALK_SEEDS=<種> DREAMSCAPE_WALK_STEPS=<手数> npm run test:walk`）。同じ種・同じコード・同じ生成物なら同じ歩みになる。開始地点の一覧は生成物にある旅行編で決まるので、`npm run test:walk`（先に見本の編を含めて生成する）で繰り返す。`npm run dev` の後（見本の編のない生成物）に `npx vitest` で直接動かすと、同じ種でも別の歩みになる。
- 到達の要約：歩みが自分で到達した内容を旅行編ごとに数え（到達した都市、クリアした都市、読んだエピローグ、終えた観光地、始めた対決・デート、出会った道中交流、借りた乗り物、乗った乗り物（都市と乗り物ごと。保存された乗った回数 `travel.rideCounts` が増えた手））、一度も届かなかったIDを「never」として並べる（`artifacts/explore/journey-walk-coverage.txt` にも書く）。合否にはしない。乱数と手数で変わる目安で、ある回に届かなかったことは不具合を意味しない。種を変えても「never」に残り続けるものは、通常の遊び方では届かない内容の候補になる。2026年11月時点では、ミラノの道中交流のうち `galleria_fortune` と（ガッレリアより先に最後の晩餐を終えたときの）`galleria_print` 以外が届かない。ユーザーの判断（2026-11-08）で、これらは今のまま残し、シナリオの改稿でまとめて見直す。各交流が今いつ起こるか（起こらないならその理由）は、`content/journeys/milano/stories/encounters/` の各Inkファイルの先頭のコメントに書いてある（JSONにはコメントを書けないため、カタログと入場ルールには書かない）。道中交流は、今は観光地の観察から「進む」でバトルへ向かうときだけ始まる（カタログの `availability`（`dormant`）は、使っていなかったミラノの3件の交流と一緒にセーブ版 v14 でなくした）。都市のクリア（都市フィナーレを終えること）・エピローグ・旅の終わりは、上の歩み全体の確認で合否に入る。それ以外の行（観光地・対決・デート・道中交流）は合否の条件ではない。`npm test` は成功したテストの出力を省くので、要約は `npm run test:walk`（`--silent=false` で出力を表示する）か週1回の成果物で見る。
- 週1回：`DREAMSCAPE_WALK_SEEDS`（コンマ区切りの種）と `DREAMSCAPE_WALK_STEPS`（種ごとの手数）で広げる（CIは実行番号から12個の種、4,000手）。

### モンキー

- 画面の押せる部品（`#main` の中。下の帯の待機・休むを含む。ダイアログが開いていればその中）から、種付きの乱数で1つを選んで押し続ける。誤検出と取り返しのつかない操作を避けるため、次は押さない（`monkey.spec.ts` の除外）：「消去」を含む部品、Debugを離れる「通常プレイに戻る」「場面の選択へ戻る」、旅行編の選択欄、リンク（外部の出典）、文字の入力欄。ほかの部品に覆われて押しても届かない部品（中心の位置で別の要素に当たるもの。例：会話ウィンドウを隠している間の、全画面の「タップして会話を表示」の下）も選ばない。画面上部の英語ノートと⚙設定（セーブ・ロード・ゲームの設定）は範囲の外にある。
- 開始地点（テスト3件）：新しい旅（タイトルから。旅行編は種で選ぶ）、都市の途中の通常セーブ（`cityMidway` で作り `placeSave` で置く。道2）、Debugの場面（[URLの例](#urlの例)のうち、ゲームの状態を持つ場面を開くもの（`debugSessionExampleUrls`）から種で選ぶ。道3。終わりに通常の保存領域が始めと同じことも確かめる）。制作中の都市の地図・交通の確認（`scene=map`）は、Debugの場面（`debug-session`）も読み取り口の状態も持たず、押す前に失敗するので除く。モンキーの開始地点がちょうど「場面を開く例」であることは `src/dev/debug-state.test.ts` が毎回確かめる。
- 確認：共通のエラー検出（コンソールエラー・未処理の例外・画像の欠落。未処理の例外はその場で止める）。押すたびに、通常のセーブ（`localStorage`）かDebugの読み取り口の状態が `validateGameState` を通り、APが0〜上限で、リビジョンが戻らないこと。5秒待っても押せる部品がなければ詰み（旅の終わりは除く）。40回ごとに再読み込みし、通常のセーブが変わらないこと（読み込み直した後は、遊び手と同じくタイトルで旅行編を選んで再開する）。200回ごとに開始地点からやり直す。
- 恋愛の抽選（`crypto.getRandomValues`）は、テスト側の `addInitScript` で種付きの値に差し替える（ゲームのコードは変えない）。押す部品と抽選が種で決まるので同じ流れをたどりやすいが、描画の速さで押せる部品の一覧が変わることがあり、再現は完全ではない。
- 失敗したら（開始地点が開けない・再読み込みの後に戻らない・押した後に落ち着かない・終わりの保存領域の確認の場合も同じ形で失敗する。共通のエラー検出の失敗にも同じコマンドが付く）：表示された `MONKEY_SEED`・`MONKEY_SECONDS` と開始地点の名前で `MONKEY_SEED=<種> MONKEY_SECONDS=<秒数> npm run test:e2e:explore -- -g "<開始地点の名前>"` を実行する（CIは開始地点ごとに55秒、手元の既定は40秒なので、秒数を合わせないとCIで後半に見つかった失敗まで届かない）。Playwright のテストの時間切れ（秒数＋120秒）はこの形の失敗にならないので、テストの初めに出力される行（`monkey from <開始地点の名前>: MONKEY_SEED=… (start point …), MONKEY_SECONDS=…`）か注釈 `reproduce` の種と秒数で、同じコマンドを実行する。直前30回の押下が `monkey-trace.txt` として添付され、トレースとスクリーンショットも残る（CIでは成果物 `e2e-explore-monkey-<番号>`）。
- 誤検出の扱い：ゲームとして正しい動き（意図した確認ダイアログ、長い演出など）を失敗と判定した場合は、ゲームを変えずに除外の一覧か待ち方（`ops.settled` の印（`data-answer-settling`・`data-tap-settling`・`data-tap-hold`・`travel-transition`）が消えるのを待つ）を直し、理由を注記する。合否の基準は緩めない。本当の不具合はゲームを直す（最初の実行で、地図の拡大・縮小ボタンの直後に行き先を選ぶと Leaflet が未処理の例外を出すことが分かり、`PlaceMap` を直した）。

### WebKit

- `playwright.webkit.config.ts` の `mobile-webkit`（`devices["iPhone 13"]` の WebKit）が `@smoke` のテスト（`boot`・`play`）だけを開発サーバーで実行する。Web Locks・CSS の `:has()`・Leaflet など、ブラウザによって差が出やすい機能の確認にあたる。Linux の WebKit は実機の Safari と同じではないため、公開前の実機確認は残す。
- WebKit を使うのはこの設定だけで、`npm run test:e2e`・ほかの段・PRの確認は WebKit を必要としない。CI では `e2e-explore.yml` だけが WebKit を入れる。手元に WebKit がない場合は、同じ2件を Chromium で確かめる（`npx playwright test --grep @smoke`）。

## Debug起動URL

`npm run dev` で開いたページのURLに `?debug` だけを付けると、Debugの「場面の確認」（場面を選ぶ画面）が開く。項目を足すと、場面の確認を通らずにその場面を直接開く。公開版（本番ビルド）でも、旅を始めた後の上の帯の⚙設定→「ゲームの設定」→「Debugモード」でパスワード `adminmode` を入れてDebugモードをオンにした端末では、同じURLとゲームの設定の「場面の確認を開く」で開ける（オフの間は通常のタイトルが開く。開発サーバーでは常に開く）。**このパスワードは秘密ではない**（ユーザーの判断。見られても構わず、誤ってオンにしないための確認にすぎない。[docs/02](02_TECH_ARCHITECTURE.md) の「Debugモード」）。見本の編の場面は `npm run dev:sample` で開く。URLの形式は開発用で、変えるときに互換は保証しない。読み取りとURLの組み立ては `src/dev/debug-query.ts`（ゲームのデータを読まない純粋な関数。PlaywrightなどNodeからも使える）、データとの照合は `src/dev/debug-state.ts` の `resolveDebugLaunch` が行う。

| 項目 | 値 | 省略したとき |
| --- | --- | --- |
| `city` | 都市ID | 既定の旅行編の最初の都市（ミラノ） |
| `scene` | `tourism`（観光・場所）、`battle`（バトル。通常戦・特殊戦B/C・都市フィナーレ）、`encounter`（人物との交流）、`date`（デート）、`epilogue`（都市のエピローグ）、`map`（制作中の都市の地図・交通） | 省略できない（`?debug` だけなら場面の確認） |
| `target` | 対象のID。場面の確認の「対象」の括弧内のID（エピローグは都市フィナーレのエピソードID） | その場面の一覧の最初 |
| `progress` | `completed`（都市クリア後）、`initial`（旅の開始時） | `completed` |
| `ap` | 0〜12の整数 | 12 |
| `affection`・`trust`・`spark` | -20〜20の整数（親しさ・信頼・恋愛の意識） | 0 |
| `roll` | `positive`（成功寄り、抽選値0）、`negative`（失敗寄り、抽選値9999）。デートと交流の反応に使う | `positive` |
| `data` | `fixture`（仮の場面） | 都市データ |

- 場面は本物のゲーム関数で作る（[テストの3つの道](#テストの3つの道)の部品）。「都市クリア後」は、その都市までの都市を実際の規則でクリアし、旅行編の進み方どおりに出発した状態（エピローグの後に次の都市へ進む旅行編は、エピローグも読んだ状態）。そのうえで場面の地点に移り、AP・関係値をURLの値にする。都市のエピローグはそのまま読み進められ、次の都市がある旅行編では到着まで続く。
- `data=fixture`（仮の場面）は、準備中の旅行編の都市に、実在する1都市を役割ごとに複製した試験データを入れる。元にする都市は `npm run dev` ではミラノ、`npm run dev:sample` では見本の街（データから自動で選ぶ。[docs/02](02_TECH_ARCHITECTURE.md) の「Debugの「仮の場面」」）。元の都市にない場面（例：ミラノ編がない構成での特殊戦B・C、道中交流）は作られず、場面の確認に注記され、場面の一覧では「（この都市にはありません）」と表示される。そのURLは「…には「人物との交流」の場面がありません。」のように表示する。
- 人物との交流（`scene=encounter`）は、遊びと同じ時点で始める。観察の後の交流は、その観光地の観察を開いて（初めての訪問なら観光案内を飛ばす）始め、終わるとその観察の画面に戻る（同じ観察で出会える交流が続くこともある）。本筋の前・後の交流は、その観光地への出発・バトルの結果から始め、終わると次の画面（案内・観察・自由時間など）へ進む。
- Debugの場面は品物を持たない状態から始まる（前の都市から持ち歩く品物も持たない。品物は道中交流で受け取るが、Debugは場面の前に交流を進めない）。そのため、どの選択肢にも品物が必要な道中交流（例：見本の街の「しおりを渡す」、ミラノの「弦を一本、余らせて」）は、対象の一覧で選べず「（品物「三時のしおり」が必要なため開けません）」のように理由を表示し、そのURLも同じ理由で開かない（`src/dev/debug-state.ts` の `debugTargets`。`debug-state.test.ts` が、一覧で選べる対象はすべて開き、選べない対象はゲームの規則でも始まらないことを確かめる）。「観光地の時点」（`scene=occasion`、場面から始める）の `prep=` は同じ都市の場面だけを流す。`from=` の場面が前の都市の品物を要るときは、始まらなかった理由に「デリーの品物 gt_delhi_kamla_memo が要ります」のように出して止まり、`prep=` にほかの都市の場面を書いたときも、その都市の名前を出して止まる（`tests/journeys/sample_trip/occasion.test.ts`）。
- 誤った項目名・値、データにない都市・対象、その進行では開けない場面（例：旅の開始時のデート、品物が必要な交流）は、理由（`role="alert"`）と場面の確認へのリンク（「場面の確認へ」）を表示する。選んだ進行で交流の入場の条件（`when`）やデートの条件（`when`・`until`）が満たされないときは、その理由に満たしていない部品も並ぶ（例：「入場の条件を満たしていません：エピソード「無人の広場、一名追加」を終えた」。`src/dev/condition-explain.ts`。Debugだけの説明で、ゲームの画面は条件の理由を出さない）。
- 場面の確認の下の「この場面のURL」欄に、選んでいる設定のURLが出る。「この場面のURLをコピー」で写せる。自動でコピーできない環境（スマートフォンからPCの開発サーバーを `http://<IPアドレス>` で開いた場合など）では、欄のURLが選択されるので長押しなどで写す。場面を開いている間はアドレス欄も同じURLになり、再読み込みするとその場面を最初から開き直す（Debugの進行は残らない）。「場面の選択へ戻る」でアドレス欄は `?debug` に戻る。
- 開発用の読み取り口：開発サーバーでDebugの画面を開いている間だけ `window.__dreamscapeDebug` があり、`getState()`（Debugのゲームの最後に保存された状態）と `getScene()`（開いた場面の設定・URL・開始地点）を返す。どちらも複製を返し、Debugやゲームを変えられない。場面の確認では `null`。E2EがDebugの状態を確かめるために使う。本番ビルドには入らない（`DebugMode.tsx` が `import.meta.env.DEV` のときだけ付ける）。
- 本番では：Debug（場面の確認・起動URL・場面の組み立て部品・仮の場面）と素材のプレビューは、`src/main.tsx` の `React.lazy` から開いたときにだけ読み込む別のファイルとして入る。`?debug` は開発サーバーでは常に、本番ではDebugモードがオンの端末だけで開く（その式を `scripts/dist-guard.test.ts` が固定し、`boot.spec.ts` の本番の段が新しいブラウザで確かめる）。テスト用の読み取り口・テスト用の仮データ・見本の編は入らない。`npm run build` の `dist/` の検査は、本番に入れないものの目印をどのファイルにも、Debugの目印をタイトル画面ですぐ読み込むファイルに許さない（[本番ビルドの検査](#本番ビルドの検査)）。`scripts/dist-guard.test.ts` は、本番のコードが `src/dev/` を `src/main.tsx` の2つの動的な `import` からしか読み込まないこと、`src/dev/` の本番に入るファイルが `tests/`・テスト用の仮データを読み込まないことも確かめる。Debugでの遊びは本番でも、通常のセーブ・英語ノート・表示設定を変えない（メモリの中だけ）。
- Debugモードがオンの間（Debugのページでは常に）、デートや道中交流で関係の値が変わる返答をすると、場面の上に「Debug」の印付きで各軸の増減と前後の値、反応と噛み合う確率（道中交流では反応だけ。今の道中交流には値の変わる返答がないので、交流では出ない）が出る（[docs/02](02_TECH_ARCHITECTURE.md) の「Debugモード」）。

### 人が画面を確かめるときの使い方

- UIを変えたら、変えた画面に当たる場面を上の一覧から選ぶか、場面の確認で選んで「この場面のURLをコピー」で写し、ブラウザの端末表示やスマートフォンで開く。`npm run dev` は同じネットワークの端末からも開ける（`http://<PCのIPアドレス>:<表示されたポート>/?debug&…`）。320・360・390px程度の幅で、[UIレビュー](../UI_REVIEW_CHECKLIST.md) に沿って確かめる。
- 成功寄りと失敗寄りの反応、AP不足など、値だけを変えたURLを並べて比べられる。
- 確かめたURLを作業報告やPRに書くと、レビューする人が同じ場面をすぐ開ける。
- Debug起動での確認は、場面の見た目と操作の確認に限る。保存・再読み込みからの再開や別タブの確認は、通常の操作（道1）で行う。
- 主要な画面をまとめて見るときは `npm run screens` の画面一覧を使う（[人が画面を確かめる](#人が画面を確かめる)）。

## 人が画面を確かめる

見た目・操作感・実機での確認は、CIの合否とは別に人が並行して行う。CIの合否を待つ必要はなく、CIの通過は目視確認の代わりにならない（逆に、目視の結果でE2Eの期待値を決めない）。

- `npm run screens`：主要な画面を320pxと390pxの幅で撮り、画面一覧 `artifacts/screens/index.html`（Git管理外）にまとめる。撮るのは、タイトルから通常の操作で開く画面（タイトル、旅の始まりの行き先、移動手段の選択（路面電車の路線つき）、⚙設定を開いた状態、ゲームの設定、ゲームの設定のDebugモード（違うパスワードを入れた後）、古い保存データの整理（旧版のセーブ・バックアップ・以前のミラノ編の英語ノートを置いて開く）とその確認（ミラノ編のバックアップを選ぶ）、観光案内、バトルの会話、会話の窓を隠した状態、クイズの問題・回答後の解説・結果と報酬、デート（行き先と訪問先の写真）、英語ノート。`tests/screens/screens.spec.ts`）と、[URLの例](#urlの例)のDebug起動URL（見本の編の行を除く）で開く画面、Debugのデートで返答した後の関係の変化の表示。E2Eと同じく外部通信を遮断し、演出を短くして撮る（地図のタイルとWebフォントは写らない）。約2分50秒（4コア・2ワーカー、64枚。2026-11-09）。開発サーバー（4173番）が起動していれば使い、なければ起動する。借りる乗り物の画面（「乗り物を借りる」の確認と「…を借りています」の行）は撮らない。公開中の旅行編に借りる乗り物がなく、借りる乗り物のある見本の編は開発サーバーの生成物に入らない（見本を含めて生成すると、同じ生成物を使う開発サーバーの内容が変わる）ため。操作と表示は見本の編の段のE2E（`sample-journey.spec.ts`）が確かめ、制作中のルアンパパーン編の貸し自転車は上のDebug起動URL（地図・交通の試作）で見られる。
- 前の一覧と比べる：前回の `artifacts/screens/` を別の場所へ写しておき、`npm run screens -- --previous <そのフォルダ>` とする。場面と幅ごとに「新規」「変更あり（変わった点の割合）」「ごく小さな差（0.1%未満。点線の位置などの描画の揺れ）」「変更なし」（画像のバイト列が同じ）を付け、変わった場面を一覧の最初に挙げる。合否の判定ではなく、見る場面を絞るための目印。
- CI：PRと `main` へのpushで `e2e.yml` の「Screens for review (320 and 390 px)」が同じ一覧を作り、成果物 `screens` として14日間残す（失敗してもチェックを失敗にしない）。ダウンロードして展開し、`index.html` を開く。前の実行と比べるときは、その成果物を展開したフォルダを `--previous` に渡して手元で作り直す。
- 撮る画面を足すときは、通常の操作なら `tests/screens/screens.spec.ts`、Debugで開く場面なら[URLの例](#urlの例)の表に足す（`src/dev/debug-state.test.ts` が表のURLがどれも開けることを確かめる）。Playwrightの設定は `playwright.screens.config.ts`（`npm run screens -- --config <ファイル>` で差し替えられる）。
- 撮った一覧で見るのは配置・切れ・重なりまで。フォーカスの移動、ダイアログの復帰、文字送り、長押し、実機のSafariでの表示は実画面で試す（[Debug起動URL](#人が画面を確かめるときの使い方)で場面へ直接入れる）。

### タップ領域

指で押す部品は、主な操作も常用の操作も、押せる領域を44×44px以上にする（WCAG 2.2 の達成基準2.5.5と同じ大きさ。最低限の2.5.8は24px）。見た目の文字や枠が小さくても、ボタン自体の領域が44pxあればよい。隣り合う操作は、領域を重ねず、間違えて押しても取り返せる並びにする。

- 確かめ方：ブラウザの端末表示（320・360・390px）で開発者ツールの要素の選択を使い、ボタンの幅×高さを見る。スクロールや開閉で重なる部品は、重なった状態で押して、上に来たものが働くか試す（例：自由時間の行き先の一覧を、上に残る地図の下と下の帯の下までスクロールする。下に入った行は押せない）。中身で大きさが変わる部品は、小さくなる場合も確かめる（例：1行だけの台詞、短い名前の選択肢）。
- 44px未満でよいもの：文の中で押す部品（英文の単語、本文中のリンク、地図の出典の表示）、Debugの「場面の確認」の中の開発用の操作（ゲームの設定のDebugモードの欄は遊び手の画面なので、ほかの設定と同じく44px以上）。
- いま44px未満で残しているもの（理由つき）：バトル結果の「AP報酬の内訳」などの開閉の見出しは高さ約28px（画面いっぱいの幅で、結果の主な操作を画面内に収めるため）。地図の印は32px、選んだ印は40px（地図の印は選ぶだけで出発しない。行き先は一覧の名前から選べる）。変えるときはこの一覧も直す。UI 段階1で44px以上にしたもの：自由時間の「待機」「休む」（以前は44×32px。今は下の帯）、場面の「出典」（以前の「画像の出典」は高さ32px）、上の帯の所持アイテム（以前は40px）。

## CI（GitHub Actions）

GitHub Actionsは次のワークフローを実行する。同じイベントで動くジョブはすべて並列に動き、互いの完了を待たない（単体テストの結果をまとめる「Unit tests」だけは、分けた3つのジョブの終わりを待つ）。

| きっかけ | ワークフローとジョブ | 内容 |
| --- | --- | --- |
| PR（作成・push） | `ci.yml`「Content, types and production build」 | `npm run build`（コンテンツの検証・生成、型検査、本番ビルド、`dist/` の検査）。会話の全分岐検査はキャッシュを使わずにすべて行う（`DREAMSCAPE_INK_CACHE=off`。[キャッシュ](#会話の全分岐検査のキャッシュ)） |
| | `ci.yml`「Unit tests (1/3)」「Unit tests (2/3)」「Unit tests (3/3)」と「Unit tests」 | 全単体テストを3つのジョブに分けて並列に実行する（`npm test -- --shard=<番号>/3`）。3つを合わせると `npm test` と同じファイルをすべて実行する。「Unit tests」は3つがすべて通ったときだけ成功になり、どれかが失敗したときや実行が取り消されたときは失敗になる（スキップにしない。スキップされたチェックは必須チェックとして通過扱いになりうるため。分け方を変えてもチェックの名前は変わらない） |
| | `e2e.yml`「E2E (gate)」「E2E (debug)」「E2E (prod)」「E2E (sample)」 | E2Eの4つの段（[E2Eの段](#e2eの段)）。段ごとに別のジョブ |
| | `e2e.yml`「Screens for review (320 and 390 px)」 | 画面一覧（`npm run screens`）を作って成果物に残す。合否にしない（[人が画面を確かめる](#人が画面を確かめる)） |
| `main` へのpush | `pages.yml` | `npm run verify` の後にGitHub Pagesへ公開する |
| | `e2e.yml` の5つのジョブ | PRと同じ。公開と並列に動く |
| 毎週月曜（UTC 4:23）、手動、このワークフローか探索テストとその部品のファイルを変えたPR | `e2e-explore.yml`「Monkey (seed 1〜3)」「WebKit smoke (iPhone 13)」「Random walk (more seeds)」 | [探索テスト](#探索テスト)：モンキー（種3つを並列。手動では種と秒数を指定できる）、WebKit の `@smoke`、ランダムウォークの長い実行（到達の要約を成果物 `journey-walk-coverage` に30日残す）。合否判定にせず、ほかのワークフローも公開も待たない |
| 手動（Actions画面の「Run workflow」） | 4つのワークフロー | それぞれ上と同じ内容 |

- 公開はE2Eの合格を待たない。`main` のE2Eは公開と並列に動き、失敗するとそのコミットのチェックが失敗（赤い×）になり、GitHubの通知設定に従って知らされる。公開済みの版に問題があれば、修正をPRで取り込んで再公開する。
- 単体テストを3つに分けたのは待ち時間のため。2026年11月の計測（2コアのランナー）で、1つのジョブでは `npm test` が約408秒（ジョブ全体で約7分20秒）かかり、PRの確認で最も遅かった。手元の2ワーカー・空のキャッシュでの計測（全体で約402秒とCIに近い）では、3つに分けると各ジョブはコンテンツの生成を含めて約114〜184秒になる（インド編の全面改稿を取り込んだ後の再計測。取り込み前は約117〜186秒）。どのファイルをどのジョブが実行するかは Vitest がファイルのパスのハッシュで決め、ファイルの数をそろえるだけで時間はそろえない（長いファイルが同じジョブに集まるとそのジョブが遅くなる）。各ジョブは自分で `npm ci` とコンテンツの生成を行い、会話の全分岐検査のキャッシュもそのジョブの中だけで使う。手元の `npm test`・`npm run verify` と、`pages.yml` の公開前の `npm run verify` は分けずに1回で全件を実行する。失敗したテストは、そのファイルを指定して手元で確かめる（`npx vitest run <ファイル>`。同じジョブの組み合わせで動かすなら `npm test -- --shard=<番号>/3`）。分ける数を変えるときは `ci.yml` の `matrix.shard` の一覧（1から順に）だけを変える。ジョブ名と `--shard` の分母はその数（`strategy.job-total`）に従う。
- PRでは、新しいpushが来ると同じPRの実行中のCIとE2Eを取り消して最新のコミットだけを確かめる。`main` へのpushと手動実行は取り消さず、最後まで実行する。
- 画面の見た目・操作感・実機の確認は人が並行して行う（[人が画面を確かめる](#人が画面を確かめる)）。CIの合否を待つ必要はなく、CIの通過は目視確認の代わりにならない。
- E2Eはマトリクスの段（tier）ごとに別のジョブになり、並列に動く：`gate`（`npx playwright test --project=gate`）、`debug`（`--project=debug`）、`prod`（`-c playwright.prod.config.ts`。ジョブの中で `npm run build` から行う）、`sample`（`-c playwright.sample.config.ts`）。`sample` のジョブは、段の前の手順（`matrix.prepare`）で `npm run journey:new -- ci_new_trip --name 新しい旅 --city ci_new_town --city-name 新しい街` を実行して旅行編を1つ作る。ジョブのチェックアウトは終わると捨てられる使い捨てのコピーなので、リポジトリには残らない。段の `boot` が、作った旅行編も生成でき、タイトル画面で準備中（公開待ちの案内だけ）として開くことを確かめ、これを `journey:new` の受け入れの確認とする（作成と生成は単体テストの `scripts/journey-new.test.ts` でも確かめる）。`scripts/e2e-specs.test.ts` が、合否判定に使う段ごとにジョブがあることと、この手順を確かめる。段を足すときや、長い段を `--shard=1/2`・`--shard=2/2` で分けるときは、`e2e.yml` の `matrix.include` に項目を足す。各ジョブは自分でコンテンツを生成する（並列なので待ち時間は増えない。別のジョブの生成物を受け渡すと、受け渡しを待つ分だけ遅くなる）。
- Playwrightのブラウザ（`~/.cache/ms-playwright`）は、固定した `@playwright/test` の版をキーに `actions/cache` で実行の間に持ち越し、見つかったときはダウンロードを省いてシステムのライブラリだけを入れる。`node_modules` とその中の会話の検査キャッシュは持ち越さない（`scripts/story-validation-cache.test.ts` が、ワークフローの `actions/cache` がこのフォルダだけを対象にすることを確かめる）。
- 本番ビルドの段は、タイトル画面までに読み込む量を実行結果ページ（Summary）に表として出し、HTMLレポートにも添付する（報告のみ。上限は設けない）。
- `e2e-explore.yml` はPRでは自分のファイル（このワークフロー、`playwright.explore.config.ts`・`playwright.webkit.config.ts`、`tests/e2e/explore/`・`tests/explore/`）と、モンキーがゲームを操作するのに使うテスト用のコード（E2Eの共通部品 `tests/e2e/helpers.ts`、Debug起動URLを読む `scripts/dev/screen-gallery.ts`・`src/dev/debug-query.ts`）を変えたときだけ動き、その変更で探索がまだ動くことを確かめる。ゲームのコード、[URLの例](#urlの例)の一覧、組み立て部品（`cityMidway` など）を変えたPRでは動かない（URLの一覧がモンキーの開始地点に使えることは単体テストが毎回確かめる。モンキーで確かめたいときは手動で実行する）。モンキーの種は実行番号から毎回変わり、ログの「Print the seed」に出る。失敗したら成果物（`e2e-explore-monkey-<番号>`・`e2e-webkit`）を14日残す。`scripts/e2e-specs.test.ts` が、このワークフローの起動条件と、ほかのワークフローが WebKit も探索も使わないことを確かめる。
- Playwrightの設定（`playwright.config.ts`。本番ビルドの段の `playwright.prod.config.ts`、見本の編の段の `playwright.sample.config.ts`、画面一覧の `playwright.screens.config.ts`、週1回の `playwright.explore.config.ts`・`playwright.webkit.config.ts` は共通の部分をここから読む）：失敗したテストは再試行しない（不安定なテストは再試行で隠さず原因を直す）。失敗したテストだけ、スクリーンショットとトレースを `test-results/` に保存する。CI（環境変数 `CI` がある場合）では、さらに `test.only` が残っていれば失敗にし、2ワーカーで実行し、失敗の注釈・HTMLレポート（`playwright-report/`）・一覧を出力する。CIの実行は12分で打ち切り（`globalTimeout`）、打ち切った場合もレポートと、そこまでに失敗したテストのトレースを残す。`e2e.yml` はテストの手順に16分、ジョブに25分の上限を置き、手順が時間切れになった場合も成果物（下記）を保存する（ジョブ全体の時間切れでは保存の手順が実行されないため）。手元では一覧だけを出力し、ワーカー数はPlaywrightの既定（CPUの半数）。

### 失敗したときの見方

1. PRの「Checks」タブ、またはコミットの赤い×から失敗したジョブを開く。単体テスト（3つに分けたジョブのうち失敗したもの）・ビルドはジョブのログの末尾に、失敗したテストと理由が出る。
2. E2Eは、失敗したテストの行が注釈として実行結果ページ（Summary）の「Annotations」に出る。そのファイルがPRの差分に含まれる場合は、差分（Files changed）の該当行にも出る。ジョブのログには各テストの成否と失敗箇所が出る。
3. E2Eが失敗した実行（時間切れを含む）では、実行結果ページ（Summary）の「Artifacts」に `e2e-<段の名前>` が14日間残る。失敗したテストには、各タブのURLと `localStorage`（`dreamscape.` で始まるキー）を記録した `storage.json` も添付される。ダウンロードして展開し、`npx playwright show-report playwright-report` でHTMLレポートを開く。レポートから各テストのスクリーンショットとトレース（操作ごとの画面・DOM・コンソール・通信）を見られる。トレースだけを見る場合は `npx playwright show-trace test-results/<テスト名>/trace.zip`。`test-results/<テスト名>/error-context.md` には失敗時のページの構造が残る。
4. 手元で同じテストを実行して再現する（`npx playwright test tests/e2e/<ファイル> --repeat-each=3` など）。CIでだけ失敗する場合は、待ち時間ではなく画面の状態・保存のリビジョンで待っているかを確かめる。

### 本番ビルドの検査

`npm run build` と `npm run verify` は、`vite build` の後に `npm run dist:check`（`scripts/check-dist.ts`）で `dist/` を検査する。Debug（場面の確認・起動URL・場面の組み立て部品・仮の場面）と人物素材のプレビュー（`src/dev/`）は、Debugモード（[Debug起動URL](#debug起動url)）のために本番にも入るが、タイトル画面で読み込まない別のファイルに限る。検査は目印の文字列の2つの一覧で行う。本番に入れないもの（`devOnlyMarkers`：テスト用の読み取り口 `__dreamscapeDebug`、開発・テスト専用の見本の編 `sample_trip`（画像のフォルダ名にも使う）、テスト用の仮データ `src/content/test-fixtures.ts`、開発・テスト用のファイルのパス `src/dev/`・`tests/fixtures/`・`tests/journeys/`。ソースマップや開発用のJSX変換が書き込む）が、公開されるファイルの名前か内容に1つでもあれば失敗にする。Debug・プレビュー・場面の組み立て部品・仮の場面に固有の文字列（`lazyDebugMarkers`）は、`index.html` と、それがすぐ読み込むファイル（`<script type="module" src>`・`<link rel="modulepreload">`・`<link rel="stylesheet">`。`eagerFiles`）にあれば失敗にする（遅れて読み込む別のファイルにあるのはよい）。どちらもファイル名・文字列・その由来を表示する。どの一覧でどのファイルを調べるかは `scripts/dist-guard.ts` の `checkDist` が決め、`scripts/check-dist.ts` はフォルダの全ファイルを渡して結果を表示するだけにする（`scripts/dist-guard.test.ts` が `checkDist` を小さなビルドで確かめ、`scripts/check-dist.ts` 自身も一時フォルダの小さなビルドで実行して、問題のないビルドで成功し、遅れて読み込むファイルの読み取り口・見本の編と、タイトル画面のファイルのDebugのコードと、`index.html` が読み込むのにビルドにないファイルで、それぞれの理由を表示して失敗することを確かめる。この小さなビルドには `package.json` の `dependencies` を載せたライセンス一覧があり、失敗がライセンスの検査によるものでないことを区別する。一覧を除くとライセンスの検査で失敗することも確かめる）。あわせて、`vite.config.ts` の `build.license` が書き出すライブラリのライセンス一覧 `dist/third-party-licenses.json` が、読めるJSONの配列で、各項目に名前・版・識別子・本文があり、`package.json` の `dependencies` のすべてを載せていることを確かめ、足りなければ日本語の理由を表示して失敗にする（`checkThirdPartyLicenses`。単体テストは `scripts/dist-guard.test.ts`）。

- 失敗した場合は、ゲームのコードから `src/dev/` のモジュールを静的な `import` で読み込んでいないか（Debugは `src/main.tsx` の `React.lazy` からだけ）、読み取り口を `import.meta.env.DEV` の分岐の外で付けていないか、生成物（`src/content/generated/`）に見本の編が入っていないか（`src/content/generated/build-info.json` の `extraJourneyFolders`。単体テストや `npm run dev:sample` の後に `vite build` を直接実行した場合など）を確かめる。生成物が原因なら `npm run content:build` で生成し直してからビルドする。
- 検出に使う文字列と由来のファイルは `scripts/dist-guard.ts` にある。由来のファイルを改名・改稿して文字列が消えると `scripts/dist-guard.test.ts` が失敗するので、そのファイルに固有の別の文字列へ差し替える。本番のコードやコンテンツが同じ文字列を使うとビルドが失敗するため、目印には開発用のファイルにしかない文字列を選ぶ。
- 目印による確認なので、目印を持たない開発用のコード（目印を登録していない新しいファイルなど）が入っても失敗しないことがある。`src/dev/`・テスト用の仮データに新しいファイルを足したら、そのファイルに固有の文字列を、本番に入れないものか遅れて読み込むものかに分けて目印に加える。ただし旅行編ごとのテストのフォルダ（`tests/journeys/<旅行編ID>/`）の補助には加えない。旅行編を外すときにフォルダを消すだけで済むようにするためで、パスには `tests/journeys/` の目印が出て、本番のコードとDebugのファイルからの読み込みは次の確認が見つける。
- 目印を補うため、`scripts/dist-guard.test.ts` は本番のコード（`src/` のうち `src/dev/`・テスト・仮データ以外）を読み、`src/dev/`・`tests/`・`src/content/test-fixtures.ts` を読み込んでいるのが `src/main.tsx` の2つの動的な `import`（`React.lazy`。Debugとプレビュー）だけであること、`?debug` を開く式（開発サーバーか、Debugモードがオンの端末）、読み取り口を `import.meta.env.DEV` のときだけ付けることを確かめる。`src/dev/` のうち本番に入るファイル（単体テスト以外。下のフォルダのファイルも含む）が `tests/`・テスト用の仮データを読み込まないことも確かめる（`tests/` のパスの目印はソースマップにしか出ないため）。Debug起動URLの読み取り（`src/dev/debug-query.ts`）、場面の組み立て部品（`src/dev/scenario-builders.ts`）などには遅れて読み込むものの目印がある。
