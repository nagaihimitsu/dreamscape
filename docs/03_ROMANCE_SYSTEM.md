# 03 恋愛システム仕様

## 目的

恋愛は観光の報酬ではなく、相手の言葉や反応を読んで二人の時間を選ぶゲーム。旅行を進めると複数の行き先が自由時間に現れ、プレイヤーはAPを使って好きなデートを選ぶ。デートが行き先に出る条件は制作者がデートごとに書け、ほかのデートを遊んだこと・品物・お金なども条件にできる。条件を書かない通常デートは順不同で、最初に選んでも成立する。

デート中の選択と積み重ねで関係が変わり、誘いや任意の告白につながる。交際成立は恋愛上の大きな到達点。告白や交際を旅の進行に必須にするかは、制作者が都市ごとに決める（決めない都市では必須でない）。告白せず友達に近い関係のまま旅を続けることもできる。交際後の長編や結婚・家族編は扱わない。

## 自由時間とAP

- 旅行エピソードの進行や最低限の関係条件など、制作者がデートごとに書いた条件に応じ、観光地・街角などの行き先を増やす。同じ場所を将来メイン観光の後にデートで再訪することもできる。
- 通常デートは行き先に合う背景を表示し、その土地ならではの観察や、確認済みの小話を二人の会話に自然に組み込む。見て楽しいことと話したくなる発見を、恋愛会話から切り離さない。画像の出典・利用条件を記録し、実物と異なる仮画像を正確な観察資料として扱わない。
- APは限られた時間をどこに使うかを選ぶ資源であり、全デートを体験することは必須ではない。制作者は、場面の選択や完了でもAPを増やしたり使ったりでき（Inkの `ap` の札）、APを使う選択で関係値が変わってもよい。
- 上限は12。未使用・保留中のAPと報酬IDを維持し、再訪・再読込・連打で二重に増減しない。場面の札で増減するAPも、読み直し・再読込・セーブ再開・連打では二重に増減しない（繰り返す場面や「また今度」の選択肢を新しく遊んだときは、書いたとおりにもう一度付与・消費される。上限を超えて得た分は保留になる）。AP不足では開始・消費せず、APを使う選択は選べない。
- 通常デートは原則3択を2回、一度完了した通常デートは再開始しない。未体験のデートは交際後も選べる。
- ヒロイン自身からの誘いと期間限定の小さな出来事は、既存の特別イベントとして通常の行き先と区別する。参加は任意で、Stageの必須イベントにはしない（告白のデートが出る条件に使うかは、制作者がデートごとに決める）。

## 関係状態

内部には親しさ `affection`、本音を話せる安心や尊重を表す `trust`、恋愛を意識する気持ちを表す `spark` を持つ。これらの値や告白の確率はプレイヤーには表示しない。Debugモードがオンの間だけ、制作者の確認用に、選択や場面の終わりごとの各軸の増減・前後の値・反応の結果と噛み合う確率を、場面・地図・自由時間の上に出す（場面を閉じるときの変化は、次の画面の上に出す）。会話ログ・セーブには入れない。制作者は、場面の条件や分岐にこれらの値を使える（プレイヤーには、条件が満たされたかどうかも見せない。Debugモードがオンの間だけ、制作者の確認用に出す）。選択肢の効果は正・ゼロ・負を取れ、複数の軸に異なる影響を与えられる。結果は会話や態度の変化として示す。

現在の三軸から、会話向けの `relationship_tone` を導出する。`reserved`（遠慮）、`strained`（慎重）、`comfortable`（安心）、`guarded_attraction`（意識しつつ警戒）、`warm`（温かい親しさ）、`romantic_tension`（親しさと信頼を伴う恋愛的な緊張）の六種類で、値そのものや分類名は表示しない。親しさは一緒に過ごす喜び、信頼は安心して本音を言えること、恋愛の意識は視線や距離への反応として表現する。交際後も現在の三軸によって変わる。

分類はTypeScriptの純粋関数で一元的に決定し、セーブに別途記録しない。デート開始時と選択の直前・直後に現在値から算出し、Inkに `relationship_tone`、`relationship_tone_before`、`relationship_tone_after` として渡す。選択のリアクションは確率結果と選択後の空気感の両方を反映し、すべての台詞を別々にする必要はない。同一バージョン内の途中イベントは保存時の内容と指紋を照合して安全に再開する。更新後の旧セーブの再開は保証しない。Stageが進んだ後に信頼が下がり、慎重な空気に戻ることもある。

`romanceStage` は親しさの雰囲気や呼称を示す4段階であり、特定のデートIDでは決めない。一度親しくなった事実は原則戻さず、信頼などの現在の値は下がることがある。Stage、告白条件、選択の効果はデータで管理し、物語全体で特定の言い方が常に最良にならないよう脚本と一緒に検討する（その場の増減で片方が得に見える選択はあってよい）。

名前は自由に変更できる。Inkには名前・呼称と、必要に応じ関係段階や交際状態を渡す。同じバージョン内でセーブした `affection`、`playedDateIds`、`memories`、Stageや進行中の会話を保護する。

## 選択とリアクション

恋愛では、同じ言葉がいつも同じ反応につながるとは限らない。選択の性格と、その直前の `affection`・`trust`・`spark` によって反応が噛み合う確率が変わる。関係段階は呼称や会話に使い、確率に重複加算しない。噛み合った場合にも緊張が薄れることがあり、噛み合わなくても相手を意識することがある。プレイヤーには内部の確率や数値でなく、言葉・表情・仕草を見せる。恋愛や道中の選択は、その場の増減で片方が得に見えてもよい。後の場面で別の展開が起きるなど、物語全体で正解を1つに決めない作り方をする。

プロフィールは `content/romance/response_profiles.json`、選択とプロフィールの参照はInkの選択肢の札（`# profile:` など。ビルドが選択肢ごとの表にする。共通の効果 `common_*` は `effect_catalog.json`。改稿前のミラノ編とインド編は今の `effect_catalog.json` の参照のまま）、会話の違いはInkに記録する。選択時の現在値で確率を計算し、最小・最大へ収める。デート開始時に各選択の反応と3軸の乱数チケット、およびプロフィールとeffect参照のスナップショットを保存し、選択時はそのチケットを使って一度だけ結果を確定する。1回目の変化は2回目の確率に影響する。リロード・連打・保存競合で抽選や効果を再実行しない。

制作者は、噛み合いのほかに、選択ごとに各軸の決まった増減（`# rel:`）を書ける。デートの3択、デートや観光の場面の中の選択、道中交流の英語の選択、繰り返す場面や「また今度」の選択肢、告白のデートや再交流の中でも書ける。決まった増減は乱数を使わず、選んだのと同じ保存で一度だけ当てる。告白の成否は、告白のデートを始めたときの関係の状態で決まる（デートの中の決まった増減は、その後の出来事に効く）。告白のデートの中では噛み合い（`# profile:`）を使わない（告白の成否も告白中の選択も乱数で変えないため）。何度でも得られる形や大きな増減は止めず、シナリオを書き終えた後のバランス調整で確かめる。

悪い結果が重なっても関係を築き直せるよう、通常デートを選べず関係がまだ整っていない場合には、AP不要の短い再交流を利用できる（ふつうは始めるのにAPは要らない。APを付けるかは制作者が決める）。再交流には、ふつうは思い出や報酬を付けない（場面の札でAPや関係値を動かすかは制作者が決め、何度でも得られる形は、シナリオを書き終えた後のバランス調整で確かめる）。実際に完了した経験のみ最大3回までStage・告白の経験条件へ加算する。拒否後の再告白には、新たな通常デートまたは再交流の完了が必要。

告白以外の恋愛イベントには確率方式を適用する。同じバージョン内で再開するイベントは保存時の効果方式と抽選結果を保つ。更新後の旧開発版セーブの自動移行・途中再開は保証しない。告白の成立・保留・拒否は関係状態から決め、最終成否も告白中の選択も乱数で変えない。

## 選択肢と思い出

- 3択はその場の会話と相手の考えに根ざしたものにし、冗談・共感・率直な好意を毎回同じ序列で並べない。選択の結果は会話から推測でき、失敗時の返答にも人物らしさを持たせる。
- 同程度に距離の近い言葉でも、関係段階や交際状態によって異なる反応にできる。甘い言葉を常に最高評価としない。
- 思い出は二人が経験したことの記録で、後の会話や告白で参照する。通常デートやStageの進行鍵として特定の思い出を要求しない。未経験の会話を既成事実として語らない。

## 告白

告白はある程度一緒に過ごした後の任意の選択。結果は親しさ・信頼・恋愛の意識や一緒に過ごした経験に応じ、成立 `accepted`、答えを待つ `deferred`、現在は恋人になれない `rejected` を区別する。親しさだけで必ず成立することはない。

保留・拒否はゲームオーバーにせず、観光やデートを続けられる。再告白には新しい時間や経験を挟み、結果直後に同じ告白を繰り返せない。交際後も未体験の通常デートを遊べる。同一バージョン内の途中セーブは、保存時の脚本・効果と整合性を検証したうえで再開する。
