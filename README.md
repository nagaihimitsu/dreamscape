# Dreamscape

恋愛 × 世界観光 × 英語学習の、モバイル優先ブラウザゲーム。ミラノ編と、デリー→アーグラ→ジャイプールを巡るインド・ゴールデントライアングル編を実装しています。各都市の4観光地、各3問の通常戦、5問の都市ボスを経て、都市エピローグまで遊べます。自由時間にはデートを選び、ヒロインとの関係を築けます。ミラノには矛盾追及・証拠連結の特別対決も各1本あります。旅行編ごとに新規ゲームと保存領域が独立しています。仕様の優先順位は [AGENTS.md](AGENTS.md)、全体設計は [docs/](docs/) を参照してください。

## 起動

Node.js 22.12以上を推奨（開発・検証環境: Node.js 24.19.0 / npm 11.9.0）。

```sh
npm ci
npm run dev
```

表示されたURL（通常 `http://localhost:5173`）で遊べます。Viteは `0.0.0.0` にバインドします。同じネットワークのスマートフォンからは開発機のIPと表示ポートにアクセスしてください。外部のクラウド開発環境では環境側のポート公開URLを使用します。

```sh
npm run build
npm run preview
```

本番出力は `dist/`。静的ホスティングで配信でき、サブディレクトリ配信にも対応する相対パス設定です。HTMLファイルを直接開かず、HTTP経由でアクセスしてください。バックエンド・アカウント・クラウド保存はありません。

### 開発用の場面確認

`npm run dev` で起動し、表示されたURLに `?debug` を付けると、観光・バトル（特殊戦B/C・都市フィナーレを含む）・交流・デート・都市のエピローグを直接開けます。AP、関係状態、旅の進行、デートの抽選値を設定でき、成功寄りと失敗寄りの反応を再現できます。背景・衣装・表情は画面内の「背景・人物・表情を確認」から既存プレビューで切り替えます。確認データを「仮の場面」にすると、準備中の旅行編の都市を、実在する1都市を複製した試験データで遊べます。元にする都市はデータから自動で選ばれ、`npm run dev` ではミラノ、`npm run dev:sample` では見本の街になります。どの都市を元にしたかと、元の都市にないため作られない場面（例：特殊戦や道中交流）は設定画面に表示されます。

`?debug&city=milano&scene=date&target=milano_brera_date_01&roll=negative` のように項目を足したURL（Debug起動URL）は、設定画面を通らずにその場面を開きます。設定画面の「この場面のURLをコピー」で、選んだ場面のURLを写せます。項目の一覧・URLの例・画面確認での使い方は[開発時の確認](docs/10_DEVELOPMENT_CHECKS.md#debug起動url)にあります。場面は単体テスト・E2Eと同じ部品（`src/dev/scenario-builders.ts`。本物のゲーム関数だけで状態を作る）で作ります。

Debugの進行・学習記録・設定はメモリ内だけで、通常の保存領域には触れません。設定へ戻る・再読込・終了で一時状態は破棄されます。通常のゲームに戻るには「通常プレイに戻る」を選びます。本番ビルドではDebugとプレビューは公開されません（`npm run build` が `dist/` を検査し、入っていればビルドを失敗にします）。通常セーブの確認は別途行ってください。

## GitHub Pages

公開先: https://nagaihimitsu.github.io/dreamscape/

`.github/workflows/pages.yml` が `main` へのpushで、コンテンツ検証・単体テスト・型チェック・本番ビルド（`dist/` の検査を含む）を実行し、成功した `dist/` をGitHub Pagesへ公開します。E2Eは `e2e.yml` が公開と並列に実行し、公開はE2Eの合格を待ちません（失敗はコミットのチェックの失敗として表示されます）。PRでは `ci.yml`（本番ビルド・全単体テスト）と `e2e.yml`（E2E一式）が並列に動きます。詳しくは [CI](docs/10_DEVELOPMENT_CHECKS.md#cigithub-actions) を参照してください。初回のみリポジトリの **Settings → Pages → Build and deployment → Source: GitHub Actions** を選択してください。設定後はActionsの「Deploy to GitHub Pages」から手動実行もできます。公開設定とデプロイの権限はGitHub側で必要です。

## ミラノ編の遊び方

1. 主人公名・ヒロイン名を設定して「旅をはじめる」。既定は「たいち」「あゆみ」、最大24文字（UTF-16単位）。新規プレイは架空の滞在先から9:00に始まり、行き先を選びます。
2. ヒロインの案内を読み、写真を自由に観察します。案内・観察は任意で、発見せずにバトルへ進めます。
3. 日本語の掛け合いと英語3択3問を最後まで読むと、エピソードと戦績・APが確定します。結果画面から行き先一覧へ戻ります。
   結果画面の「AP報酬の内訳」「今回の正誤と戦績」を開くと、詳しい記録を確認できます。保管中のAPがある場合は、その項目から受け取れます。
4. **ドゥオモ、ガッレリア、最後の晩餐、スフォルツェスコ城**と、スカラ座のB型矛盾追及・ブレラ絵画館のC型証拠連結を好きな順に訪れます。メイン観光とデートは同じ一覧で選べ、目的地ごとに移動手段を選びます。
5. 4箇所とその途中の対決を終えるとダルセナの水辺を舞台にした都市フィナーレが解放されます。4観光地の知識を組み合わせる英語3択5問です。5問正解でPERFECT、3〜4問でVICTORY、0〜2問でDEFEATですが、**どの成績でもミラノ都市クリア**となり、旅は詰まりません。
6. ボス結果から「エピローグへ進む」。台詞は現在の関係段階・交際状態に応じて変わります。都市クリアと恋愛の交際開始は別の達成です。
7. 都市クリア後も未体験のデートを楽しめます。交際済みでも遊べる出来事があり、既存の恋愛エンディングを取り消しません。

ミラノ編「十秒のミラノ」では、ヒロインが旅先の音を十秒ずつ記録しようとします。自由時間では次の目的地やデートを選び、各観光地のクリア状態、発見数、戦績を確認できます。完了した観光・対決と通常デートは行き先に表示されず、再プレイできません。都市エピローグは未読のときに一度見ることができます。

行き先は同じ場所のイベントをまとめ、徒歩時間順に最大5地点を表示します。5地点に選択可能な未クリアのメイン観光がなければ、5地点目を最寄りの未クリアのメイン観光に差し替えます。複数のイベントがある地点では、場所を選んでから内容を選べます。「ほかの行き先を見る」から残りの地点を選べます。地図は補助で、大きく表示して操作することも、地図を使わずに行き先を選ぶこともできます。昼は9:00〜18:00、夜は18:00〜21:00です。移動と活動で時刻が進み、待機や帰宿・翌朝までの休息も選べます。宿泊にはゲーム内予算を使い、APは消費しません。予算不足時は宿泊費の不足分を補助します。

移動は徒歩・路面電車・タクシーです（路線は経路の名前の後に「（16番）」のように出ます）。徒歩所要時間は歩行網からの推計であり、路面電車・タクシーの時間・料金、架空の滞在先や宿泊費はゲーム内の調整値です。実際の出入口や運行、営業時間を保証しません。出典、確認日、推計方法とゲーム用の簡略化は [ミラノの旅行データ](authoring/journeys/milano/research/travel/README.md) に記載しています。

寄り道は条件を満たした観光地で、観察の後に自動的に発生します。ガッレリアでは床の雄牛の近くにいる親子と出会い、英語の返答・行動をA/B/Cから選べます。個別の訳も開け、会話の選択に正解・不正解はありません。完了した観光は再プレイできないため、後から条件を満たした寄り道を体験できない場合があります。

以前のカフェ・贈り物・展示への寄り道は、新しくは発生しません。同じ旅行編の都市移動では、旅行予算とAP・保留AP、思い出や交流履歴を引き継ぎます。ミラノ編には次都市を登録していないため、出発は表示されません。

開発中の更新では、以前のセーブや途中会話が使えなくなる場合があります。読み込めないデータは勝手に消さず、案内から消去を選べます。

## インド・ゴールデントライアングル編の遊び方

新規ゲームでインド編を選び、名前を設定するとデリーの滞在先から始まります。ミラノのクリアは不要で、進行・関係値・予算を引き継ぎません。初期予算はゲーム用設定の ₹30,000、宿泊は無料です。

物語は「言わなかった言葉」。デリーの路地で出会った老婦人カムラの、妙な注釈つきの手書きの見どころ一覧から始まり、遠足の中学生、願掛けの父親、隠れて会う恋人、新婚と勘違いするホテル、座り込む退役大佐、疑いをかけてしまった画家、漬物の重さで揉める母子など、それぞれ欲しいものを持った人たちとぶつかりながら、遠慮がちなヒロインが自分の言葉を持つまでを描きます。クイズの答えは、誤解を解く、嘘を見抜く、行き先を突き止めるといった形で場面を動かします。各都市に案内4本・通常戦4本・任意のデート6本・都市ボスとエピローグを収録し、3都市で51本のInk（到着会話3本を含む）と51問のクイズがあります。主人公の直接台詞はデートの選択肢に限り、ヒロイン・街の人・ナレーションが物語を進めます。各都市の開始時は短い都市ロゴの演出とヒロインとの会話を挟み、AP・関係値・予算・時刻は変えません。ロゴの完了と会話の途中も保存されます。

都市内の4観光地は好きな順に訪問できます。すべてを完了すると都市ボスが解放され、成績にかかわらず都市クリアとなります。ボス後のエピローグを読み終えると、デリーからアーグラ、アーグラからジャイプールへ自動で進みます。デートは任意なので、体験したいものはエピローグ読了前に選んでください。最終都市ではクリア後も滞在できます。都市間の地図・交通費・移動時間は設けません。

都市間では予算・AP・関係値・思い出・履歴を維持し、新都市の滞在先で1日目9:00から再開します。都市固有の品物は持ち越さず、入手・使用履歴は残ります。現行の脚本の設計は [インド編改稿の設計](authoring/journeys/golden_triangle/drafts/SCENARIO_REWRITE.md)、旧稿の脚本・出典・検証方法は [インド編の制作記録](authoring/journeys/golden_triangle/drafts/scenario/README.md)、追加・編集手順は [旅行編共通の制作手順](authoring/JOURNEY_AUTHORING.md) を参照してください。

ここでいう実装済み・`available` は、このソースでのビルド登録状態です。サイトへの反映は別途GitHub Pagesへのデプロイが必要です。

## AP報酬のルール

条件と数値は各旅行編の `content/journeys/<旅行編ID>/progression/journey.json` の試験設定です。APの加算はTypeScriptのゲームルール層だけで行います。

| 対象                           | 案内初読了 | バトル初完了 |   初好成績 | エピソード／都市クリア |
| ------------------------------ | ---------: | -----------: | ---------: | ---------------------: |
| ドゥオモ・ガッレリア・城（各） |          1 |            1 | 2問以上で1 |                      1 |
| 最後の晩餐                     |          1 |            1 | 2問以上で1 |    4（旧報酬IDを維持） |
| ミラノの都市ボス               |          ― |            1 | 3問以上で1 |            都市クリア3 |
| B/C特殊戦（各）                |          1 |            1 | 2問以上で1 |             対決クリア1 |
| インドの通常観光（各）         |          1 |            1 | 2問以上で1 |                      1 |
| インドの都市ボス（各）         |          ― |            1 | 3問以上で1 |            都市クリア4 |

APの獲得量は案内の読了やクイズの成績により変わります。完了した観光や対決は再プレイできないため、初回に獲得できなかった案内・好成績ボーナスは後から獲得できません。クイズは好感度を直接変えません。

特殊戦B/Cも初訪問時に観光案内を読め、最大4APを獲得できます。案内をスキップした場合は読了報酬を得られません。初完了と対決クリアの報酬は通常観光と同じく正解数にかかわらず得られます。既に特殊戦を完了しているセーブは引き続き読み込めますが、今回追加した報酬を過去の完了分へ自動加算はしません。

ガッレリアでは、通常戦での2問以上の正解と、親子との会話の完了が同じ1APの代替条件です。どちらを先に達成しても、同じ報酬は一度だけ受け取れます。すでに受け取った報酬は重複しません。

所持上限は**12AP**。上限を超える統合報酬は「保留中のAP」として保存し、空きができてから受け取れます。デートでAPを使った際も、保留分を自動で受け取ります。報酬IDと残額を別々に保存し、リロード・連打・再戦による重複や取りこぼしを防ぎます。

報酬IDは一度だけ適用し、都市クリア報酬は個別のIDで管理します。

新規ゲームは観光・バトル・都市報酬で進行します。

## 観察・バトルの操作

画像の番号または一覧を選ぶと、対象を拡大・中央へ寄せ、説明を手がかり帳へ記録します。大聖堂の大理石や尖塔、ガッレリアの屋根、城の壁や中庭など、写真で見える特徴を観察できます。『最後の晩餐』では遠近法、使徒のまとまり、光輪に代わる光の表現、後世に広げられた扉を扱います。写真で確認できない制作技法・歴史は独立した資料カードです。

発見した箇所の説明は画像のそばに表示され、見比べながら拡大・移動や別の発見ができます。発見ポイントや資料は手がかり帳からも確認できます。

拡大・縮小ボタン、ドラッグ、2本指のピンチに対応します。「全体を見る」で戻り、「印を隠す」で画像だけを眺められます。倍率は1〜5倍で、移動は画像の端で止まります。キーボードでは観察領域にフォーカスして矢印キーで移動、`+` / `-` で拡大縮小、`0` で全体表示できます。拡大位置は画面を開き直すと全体表示に戻ります。

バトル中の **「手がかり帳」** は1回押すと開き、閉じても同じ会話・問題・回答後の画面に戻ります。「観光に戻って調べる」で追加の観察をしてから「バトルに戻る」で続けられます。発見の有無によって正解や採点は変わりません。スキップした案内や旧版で読了を確認できない案内は「観光案内をもう一度読む」で読み直せます。

手がかり帳は「前へ」「次へ」または一覧で1件ずつ切り替えます。通常戦・特殊戦とも、画像を説明文の上に表示し、枠のある画像はタップすると該当部分を拡大できます。特殊戦では敵の主張と選択ボタンを表示したまま比較でき、選んだ証拠は閉じても残ります。長い説明や拡大画像・出典は、必要に応じて説明欄の中をスクロールして確認できます。

通常戦のクイズはB1を基本とした英語3択3問。語彙の日本語補足と任意ヒントがあり、回答後は選択肢をロックして正誤・日本語解説を表示します。3問正解で **PERFECT VICTORY**、2問で **VICTORY**、0〜1問で **DEFEAT**。敵の結末とヒロインの余韻が変わり、初回・最高・直近の正解数と完了回数を記録します。ヒントを使っても完走・報酬獲得が可能です。

## 保存データの消去

「設定」→「保存データの消去」で確認画面を開き、消去を確定できます。このブラウザにある旅の進行・名前・AP・恋愛やバトルの記録、英語ノートと対訳設定を消去し、開始画面へ戻ります。操作は取り消せません。以前に退避したバックアップ、他のサイト、別のブラウザや端末のデータは消去しません。読めないセーブがある場合も、開始画面の案内から明示的に消去できます。別のタブで更新されていた場合は消去せず、再読み込みを案内します。

「設定」→「古い保存データの整理」では、このブラウザに残る、今のゲームが使わない保存データ（ほかの旅行編の旧版のセーブ、読めないセーブを新しく始める前に退避したバックアップ、旅行編ごとに保存先を分ける前のミラノ編のキー、この版にない旅行編のキー）を一覧します。項目ごとにキー名・中身・大きさの目安と、消したときの影響を示し、選んだものだけを、もう一度確かめてから消去します。開いている旅行編のセーブ、今の版で読み込めるセーブ、この版にある旅行編の英語ノート、表示設定は一覧に出ず、消しません。選んだ旅行編を別のタブで開いている間は何も消しません。詳しくは[データ契約の「古い保存データの整理」](docs/07_DATA_AND_TESTS.md#古い保存データの整理)にあります。

## 英語の対訳と振り返り

問題文や選択肢の英単語を押すと意味を表示し、同じ単語をもう一度押すと、その文の日本語訳を表示します。押す間隔に制限はなく、訳が表示中ならそのまま維持します。単語を触っても解答は確定せず、各選択肢の左端にある A・B・C のボタンで回答します。既存の語彙補足にある文脈上の意味を優先し、それ以外は一般的な意味を表示します。キーボードでも単語を選べます。問題文と各選択肢の「訳を見る」でも原文の下に日本語を表示します。「すべての訳を見る」で一括表示でき、設定の「常に日本語訳を表示する」も選べます。訳を見る操作で回答は確定せず、点数や報酬も変わりません。語彙補足とヒントは従来どおり利用できます。

回答後の「英文を確認する」では、問題・全選択肢・自分の回答・正解・訳を見比べられます。『最後の晩餐』の通常戦3問には、文の組み立て、文法・表現、例文、ヒロインとの短い確認も用意しています。その他の問題は対訳・語彙・観光の正誤解説を利用できます。バトル中は回答済み問題、結果画面は全問を振り返れます。自由時間の「英語ノート」では過去の回答と「あとで復習する」の登録・解除を確認できます。再戦やAPは不要です。

対訳設定・開閉・復習マーク・各バトルの直近の回答は、ゲーム本体とは別に旅行編ごとの `dreamscape.journey.<旅行編ID>.learning.v1`（ミラノ編は `dreamscape.journey.milano.learning.v1`）に保存します。壊れたデータや未知の版は自動上書きせず、別タブで更新されたときは再読込を案内します。問題やバトル内容の指紋が変わった古い回答は現在の問題に重ねません。改名・削除で無くなったバトルの記録はそのまま残し、表示しません。戦績はあるのに英語ノートに回答が記録されていないバトルは「以前の回答内容は未記録」と表示し、回答を推測しません。

対訳は各旅行編の `content/journeys/<旅行編ID>/learning/translations.json` に、安定した問題IDと原文・選択肢・正解の照合用スナップショット、日本語訳を置きます。問題を変更すると `npm run content:check` が不一致を報告するので、訳を確認して照合用の原文も更新します。詳しい文法・語法は各旅行編の `content/journeys/<旅行編ID>/learning/details.json` に問題ごとに置き、問題ごとに学習会話の `storyId` を指定します（ミラノ編の会話は `content/journeys/milano/stories/learning/milano_english.ink`）。語句・質問の対象が英文中にあること、資料URL、会話の話者・行数・効果なしの契約をビルドで確認します。英語の自然さや訳の妥当性は人が確認してください。

## 特別対決：矛盾追及・証拠連結

通常の旅ではA型を中心に、スカラ座のB型とブレラ絵画館のC型も登場します。いずれも成績にかかわらず最後まで進め、対決の間に自由時間を取ることもできます。完了した対決は再戦できません。最後の晩餐を舞台にした旧B/Cは新規の旅には登場しません。

英語ノートでは、回答した問題を一覧または「前へ」「次へ」で切り替えられます。

| 形式        | 対決の内容                                               | 推理するラウンド |
| ----------- | -------------------------------------------------------- | ---------------- |
| A：通常戦   | 各観光地で出会う人物との英語3択                          | 追加操作なし     |
| B：矛盾追及 | スカラ座の観客席についての主張を劇場の資料と照らし合わせる | 第2問            |
| C：証拠連結 | ブレラの《接吻》について、色と発表当時の事情をつなぐ     | 第3問            |

どれも英語3択3問です。敵の主張にヒロインが応じると、B/Cそれぞれの短い演出が入り、スキップもできます。Bでは必要なら **「追及する」** で詳しく聞き、推理画面の **「手がかり帳を開く」** で証拠を1枚選んで **「証拠を突きつける」**。Cでは2枚を選び **「2つの証拠を組み合わせる」**。どちらも資料を示しただけでは得点にならず、続く英語3択で理由・結論を答えます。誤った資料には不足している観点を短く説明し、その場で選び直せます。推理操作に時間制限・AP消費・減点はありません。

手がかり帳は1タップで開けます。敵の主張と英文問題を上部に残したまま、証拠の詳しい説明・出典・観光画像を比較できます。画像の枠は観光画面と同じ相対座標で、拡大して確認できます。必須の証拠は **「ケース資料」** として未発見でも読め、事前に観察したものには「観察済み」と表示します。読んだだけで観光の発見履歴を変更しません。選択は即時保存され、帳面を閉じても再読み込みしても残ります。

Bでは劇場の客席の歴史に関する断言を資料で確かめます。Cでは《接吻》の色の組み合わせと、発表当時の事情を結び付けます。

B/C戦の戦績と途中状態は保存します。反論とカットインは表示だけの演出で、再読み込みした途中セーブでは繰り返しません。反論は `content/journeys/<旅行編ID>/presentation/reasoning-intros.json` と別Inkで管理し、既存バトルの指紋や敵の主張を変更しません。本編のB/C戦は通常観光と同じく、案内初読了・バトル初完了・初好成績・対決クリアで各1 APを獲得し、所持上限を超える分は保管されます。好感度・告白条件は変更しません。A/B/Cの80/15/5という比率は将来の目安で、出現抽選や数合わせは実装していません。

## 自由時間とデート

行き先一覧で、解放条件を満たしたデートにAPを使って出かけられます。カフェ・散歩・夜景に決まった順番はありません。旅を進めると、スカラ座、ブレラ絵画館、ナヴィリオ地区、サン・サティロ教会、スターバックス・ロースタリー、プラダ財団、ノヴェチェント美術館、サン・マウリツィオ教会などが候補に加わります。

通常デートは3択を2回。選んだ言葉によって親しさ、信頼、恋愛の意識がそれぞれ変化します。数値や告白の成功率は表示せず、会話や態度から伝えます。ヒロインからの無料の誘いや、特定の旅の途中だけ現れる短い出来事も任意です。

ミラノの告白も任意で、成立・保留・拒否があります。拒否後も旅を続けられ、再告白には新たなデートを挟みます。交際後も未体験の通常デートを楽しめます。いずれの旅行編も、告白や交際を都市クリアの条件にしません。

通常デートでは行き先にちなんだ実景と小話を会話で楽しめます。背景上の「画像の出典」から作者・利用条件を確認できます。周辺の街並みを用いた画像は出典欄にその旨を記載し、画像を用意できない場合は中立色で表示します。行き先や出典の追加方法は[制作マニュアル](authoring/CONTENT_GUIDE.md)を参照してください。

同じバージョンで進行中のデートは、保存時の脚本と指紋を照合して再開します。

文字送り速度は「設定」で選べます。台詞をタップすると、表示途中なら全文を表示し、次のタップで会話が進みます。会話枠の「閉じる」「ログ」「高速送り」で、ウィンドウの非表示、表示済み台詞の確認、速い自動送りを操作できます。会話ログは現在のイベントで表示済みの台詞を最大100件読み返せます。ログは画面を開いている間だけ保持し、再読み込み後は表示した台詞から記録します。名前は会話の外で「設定」から変更できます。

通常の自動送りは設定で選べます。高速送りは選択肢や問題、ログ・設定、ウィンドウ非表示、中断時に停止します。隠したウィンドウは画面を一度タップすると戻り、そのタップで台詞は進みません。

通常戦では英語や訳を読んでも回答は確定せず、各選択肢の左端にある A・B・C のボタンで答えます。回答の保存後、正解と不正解を異なる短いエフェクトと文字で表示します。「設定」の「演出を短縮する」または端末の動きを減らす設定で動きを抑えられます。表示設定はゲーム本体とは別の `dreamscape.presentation.v1` に保存され、破損・未知バージョンや別タブでの更新を検出した場合は勝手に上書きしません。設定や演出は得点・報酬・セーブのシナリオ指紋に影響しません。

人物素材は [`content/presentation/characters.json`](content/presentation/characters.json) で登録します。人物ID `heroine` はプレイヤーが設定する名前とは独立しています。地域に属さない基本衣装 `default_01` に、提供された12表情の透過画像を登録しています。

### 基本衣装・表情の画像を追加する

1. 背景を透過した全身PNGまたはWebPを用意します。白背景の参照画像は正式な立ち絵とは別に管理し、拡張子だけを変えて登録しないでください。基本衣装 `default_01` の `standing_01` は **1024×1536px** を共通キャンバスとして設定しています。同じ衣装・ポーズの差分は、人物の位置とキャンバスを揃え、画像ごとにトリミングしません。
2. 例えば `public/assets/characters/heroine/default_01/standing_01/neutral.png` に置き、`characters.json` の `heroine` → `costumes` → `default_01` → `poses` → `standing_01` の `expressions` に `"neutral": "assets/characters/heroine/default_01/standing_01/neutral.png"` と登録します。パスは `public/` からの相対パスです。
3. 表情IDは `neutral`、`smile`、`happy`、`shy`、`shy_deep`、`surprised`、`surprised_big`、`worried`、`serious`、`teasing`、`teasing_big`、`exasperated` です。差分が届いたら `expressions` に一枚ずつ追加し、未納品のファイルは登録しません。`neutral` だけでもその衣装が使われ、未登録の表情は同じ衣装・ポーズの `neutral` が表示されます。表情の指定にはInkの既存の `emotion` タグを使います。
4. `npm run content:check` を実行します。登録済みファイルの存在、実際の形式・寸法・透過画素、表情や衣装の参照を検証します。これは背景が適切に切り抜かれたことや透過の縁の品質まで保証するものではないため、下記プレビューで目視確認してください。衣装が未納品の場合は基本素材を使い、画像の読み込みに失敗しても会話は続きます。

人物の配置は各人物の `placement`、衣装・ポーズごとの補正は同じポーズの `placement` で設定します。`x`・`bottom`・`width`・`height`・`scale`・`originX`・`originY` を差分間で共有し、画像を歪めずに表示します。既存の `imagePath`、`variants`、敵の `battleCharacters` の設定も使えます。観察用画像と座標は別管理です。

既存の台詞に表情を付ける場合は各旅行編の `presentation/dialogue-expressions.json`（例: [ミラノ編](content/journeys/milano/presentation/dialogue-expressions.json)）に `storyId`・`speaker`・`text`・`emotion` を指定できます。名前などの変数を含まないInk原文の一行を完全一致で登録してください。台詞に既存の `emotion` タグがある場合はその指定を使い、同じ行への重複指定はしません。`npm run content:check` は登録された検証条件の分岐で、話者・台詞の存在や表情ID・タグとの競合を検証します。脚本を変更した際は、未検証の分岐も含めて編集者が表情とタグの対応を確認してください。表情指定は表示だけに使い、保存した会話位置や好感度を変更しません。Ink自体を編集する場合は、途中セーブの指紋に影響する点に注意してください。

`heroine` の `defaultCostume` と `defaultPose` が地域に属さない基本衣装とポーズです。`wardrobe` の `cities`・`countries`・`regions` では、将来の都市から国・地域・標準衣装を指定できます。既存の `milano` → `IT` → `south_europe` → `south_europe_01` 設定は維持していますが、南欧衣装は未納品のため、現在は基本衣装を表示します。個別指定の優先順位は `scenes`、都市、国、地域の標準衣装、基本衣装、仮素材の順です。`scenes` のキーには既存のデートID、バトルID、観光地ID、都市エピローグのエピソードIDを使い、例えば `"milano_cafe_01": { "costume": "south_europe_01", "pose": "standing_01" }` と登録します。未納品の衣装から別の表情だけ別衣装に切り替わることはありません。

都市データは登録カタログから読み込み、観光・バトル・デート・背景は現在都市に絞って参照します。都市の追加と所属の検証は [都市の追加手順](authoring/FUTURE_CITIES.md) を参照してください。

素材の確認は `npm run dev` を起動し、表示されたURLに `?character-preview` を付けて開きます。衣装・ポーズ・表情、明暗背景、台詞枠を切り替え、基準線と見比べながら差分の顔や足元、透過の縁を確認できます。「全体を確認」と「ゲーム中の配置」を切り替えて表示範囲を確認できます。未制作の差分と画像の読み込みエラーは区別して表示します。プレビューは開発サーバー専用で、ゲームのセーブやAPには触れません。

会話用の背景画像は各旅行編の `romance/presentation.json`（例: [ミラノ編](content/journeys/milano/romance/presentation.json)。共通の既定背景 `default_scene`「旅の余白」は [`content/romance/presentation.json`](content/romance/presentation.json)）の各背景に任意の `imagePath`（配信時の `assets/` 以下のパス。画像の置き場所は下記）を追加して差し替えます。未登録・読込失敗時は既存の仮背景を表示し、観察用画像には影響しません。タイトル画面の絵は旅行編ごとに `manifest.json` の任意の `titleArt`（画像・説明・切り抜き位置）で指定し、ない旅行編は既定背景の色だけの場面を表示します。推奨サイズ（1760×560px）と安全域は [技術構成](docs/02_TECH_ARCHITECTURE.md#既定背景とタイトルの絵) にあります。会話窓の色・透明度・角丸・余白・文字サイズなどは [`romance-scene.css`](src/features/romance/romance-scene.css) 冒頭の `--vn-*` でまとめて調整できます。背景・人物・テーマ・ウィンドウ表示は進行中のInkやクイズの指紋を変更しません。

会話・選択肢・戦闘画面はPlaywrightのChromiumで360×780、430×932、1280×800、横向き780×360を確認しました（現在の自動E2Eは主要機能の動作確認に絞り、画面幅ごとの表示は実画面で確認します）。長い英文や対訳は縦にスクロールして読めます。実機Safariでは未確認です。

スマートフォンの縦画面では会話・戦闘を画面内に収め、長い台詞や対訳だけをその欄の中でスクロールできます。観察では画像の操作とバトルへの入口を近くに配置しています。横向きや高さの小さい画面では、内容を切らないよう必要に応じてページをスクロールします。

通常デートは一度完了すると再選択できず、終了後は自由時間に戻ります。思い出の一覧は表示しませんが、後の会話に使う記録は保存されます。交際状態は保存され、到達後も観光・バトル・未読の都市エピローグ・未体験の通常デートを楽しめます。

現在の観光クイズの編集上の棚卸しは [編集メモ](authoring/journeys/milano/quiz-editorial-review.md)、未採用の小話候補は [下書き](authoring/journeys/milano/drafts/) にあります。候補はゲームに読み込まれず、史実の最終確認や公開承認を示すものではありません。

## フォルダ構成

ゲームの仕組み（共通コード・共通データ）と、各旅行編（ミラノ編、インド・ゴールデントライアングル編など）のデータを分けています。旅行編は `content/journeys/<旅行編ID>/` のフォルダ1つで、フォルダを追加して `npm run content:build` を実行すると、コードを変えずに旅行編一覧に加わります。追加手順・統合の規則・IDの付け方は [技術設計](docs/02_TECH_ARCHITECTURE.md#新しい編を追加する手順) を参照してください。最小の例は、遊べる架空の旅行編 [見本の編](authoring/templates/sample_trip/README.md)（開発・テスト専用）です。

```

  journeys/<旅行編ID>/            # 旅行編フォルダ（フォルダ名＝旅行編ID）
    manifest.json                 # 登録（名前・並び順 order・公開状態・都市の順序・通貨・初期値・任意のタイトルの絵）
    cities/ travel/               # 都市・都市内の地点と移動
    stories/**/*.ink quizzes/     # 会話とクイズ
    battles/ progression/ romance/ tourism/ encounters/ learning/ presentation/  # 各カタログ（必要なものだけ）
    public/assets/                # その旅行編だけが使う画像
public/                           # ファビコン・アプリアイコン（npm run icons:build で生成）
  assets/                         # 全旅行編で共有する画像（ヒロイン、演出、共通アイコン）
authoring/                        # 共通の制作手順とテンプレート
  brand/                          # ファビコン・アプリアイコンの元画像
  journeys/<旅行編ID>/            # 旅行編ごとの下書き・調査記録（ゲームは読み込まない）
  templates/sample_trip/          # 見本の編（開発・テスト専用の架空の「見本の街」。npm run dev:sample で遊べ、本番には入らない。npm run journey:new の元）
  templates/journey-new-checklist.md  # journey:new が新しい旅行編に書く CHECKLIST.md の元
scripts/                          # 生成・検証・共通の制作ツール
  journeys/<旅行編ID>/            # その旅行編だけの制作ツール

tests/screens/                    # 人が見る画面一覧の撮影（npm run screens）
.github/workflows/                # CI（ci.yml・e2e.yml）、週1回の探索（e2e-explore.yml）と GitHub Pages への公開（pages.yml）

```

単体検証はJSON構文・型やInkコンパイルを確認します。ファイル間の参照、実行時タグ、画像、報酬条件は `--all` または `npm run content:check` で検証してください。`test:saves` はコンテンツを生成してから保存関連の単体テスト（`src/persistence/`）を実行するコマンドで、過去のセーブの更新後の再開を保証するものではありません。公開済みIDの変更や、進行中Ink・問題の改稿は保存データに影響し得ます。文章の面白さ、英文の自然さ、史実と画像使用権は人が確認します。

## 文章・データの編集

会話の編集元は各旅行編フォルダ `content/journeys/<旅行編ID>/stories/` の `.ink` ファイルです。ストーリーIDは `stories/` からの相対パスです。ミラノのデートは、例えば [`dates/milano_date_cafe.ink`](content/journeys/milano/stories/dates/milano_date_cafe.ink) にあります。インドの配置は [制作記録の編集元一覧](authoring/journeys/golden_triangle/drafts/scenario/README.md#編集元) を参照してください。台詞と選択肢をReactに埋め込まず、Inkに置いています。

```ink
# speaker: heroine
「……{player_name}さん。明日の予定、一つだけ書いてもいい？」
```

名前は `player_name` / `heroine_name` をゲーム状態から渡します。新しい恋愛シナリオでは `player_address`（段階に応じた敬称つき呼称）、`romance_stage`、`memory_callback`（過去の思い出）、`confession_ready` も利用できます。AP・段階・告白条件の計算はTypeScript側で行い、Inkには結果だけを渡します。`* [選択肢]`、`->` の合流で短い分岐を編集します。タグは `speaker`（narrator/heroine/player/enemy）、`background`、`emotion`、`effect` に限定。背景・表情はpresentationに登録、effectはeffect_catalogのIDに限定し、文字列をコードとして実行しません。本文タグとInk公式choice tagsの両方を検証・処理します。

`<旅行編>` は `content/journeys/<旅行編ID>/`（例: `content/journeys/milano/`）、`<共通>` は `content/` 直下の共通データです。

| 編集ファイル                                     | 内容                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------- |
| `<旅行編>/stories/**/*.ink`                      | 会話、選択肢、リアクション、タグ                                     |
| `<旅行編>/romance/date_catalog.json`             | 種別、表示文、AP費用、必要章・履歴、シナリオ参照、選択回数・検証条件 |
| `<旅行編>/romance/effect_catalog.json`           | 好感度差分、思い出ID、告白結果（accepted/deferred）。共通デート効果は `<共通>` |
| `<共通>/romance/progression.json`                | 4段階の閾値・必要履歴・敬称、告白成立条件（思い出の引用は `<旅行編>`） |
| `<旅行編>/romance/presentation.json`             | 背景・思い出。表情・保留案内・エンディングの文章と既定背景は `<共通>` |
| `<共通>/romance/balance.json`                    | AP上限・既定名・名前長                                               |

各旅行編の都市・移動・クイズ・Ink と各カタログの該当項目は、同じ相対パスで `content/journeys/<旅行編ID>/` 以下に置き、`npm run content:build` が `content/` 直下の共通データと統合します。旅行編フォルダの項目は自分の都市だけを扱い、参照先は同じ旅行編か共通データに限ります。共通データには都市・移動・Ink・クイズや旅行編専用のカタログを置けません。

画像は、旅行編だけが使うもの（観光写真・デート背景・その旅行編の品物アイコン）を `content/journeys/<旅行編ID>/public/assets/` に、全旅行編で共有するもの（ヒロイン・演出・共通アイコン）をリポジトリ直下の `public/assets/` に置きます。データには `public/` を除いた配信時のパス（例: `assets/tourism/india/agra_taj_mahal.jpg`）を書き、置き場所によって変わりません。`npm run content:build` がこれらを `src/content/generated/public/`（生成物。Git管理せず、手動編集しない）へまとめ、開発サーバーとビルドはこのフォルダを配信します。同じパスの画像を二か所に置くとビルドが失敗します。画像を追加・差し替えた後も `npm run content:build` を実行してください。

新しい通常デートは、InkとJSON定義・効果を追加するだけで既存のメニューと会話画面に表示されます。`kind` は `normal` / `special` / `confession` / `reassurance`。通常は `choiceCount: 2`、無料イベントは必要に応じて0〜2回の3択を設定できます。`effectCount` は各経路で期待する効果数です。`actionLabelJa` もJSONにあり、Reactにイベント固有の文言を追加する必要はありません。

`validationContexts` に関係段階、告白結果、引用するmemoryId、交際状態を指定し、その文脈から全分岐を検証します。告白は成立・保留・拒否の文脈をすべて指定します。通常デートは各文脈9経路、選択機会1回のイベントは各文脈3経路です。

```sh
npm run content:check
```

`inkjs/compiler/Compiler`（公式inkjsのコンパイラ）でコンパイルし、`src/content/generated/stories.json` を生成します。独自Inkパーサー・外部コマンド・.NETの準備は不要です。生成JSONはGit管理せず、手動編集しません。ブラウザには `inkjs` のランタイムを使用します。

`dev` 起動前、`test` 前、`build` 内で必ずコンパイル・検証します。開発サーバー起動中にInkを改稿したら別ターミナルで `npm run content:build` を実行してください。生成JSON変更をViteが反映します。**Ink原稿そのものの自動監視はありません。**

ゲームが読むJSONは、`content/` を検証・統合して `npm run content:build` が書き出す `src/content/generated/content/`（生成物。手動編集しない）です。`content/` のJSONを編集した後も、Inkと同様に `npm run content:build` を実行してください。

検証はJSONスキーマ、重複ID、章・背景・シナリオ・思い出参照、許可タグ、前提イベントの循環、段階設定、報酬ID重複、シナリオごとの選択数・効果数・告白結果を確認します。壊れたInk・参照切れ・未定義effect・不正JSONはビルド失敗になります。例のクイズ（`quizzes/*.example.json`。ミラノ編の `milano_last_supper_example_quiz.example.json`）は検証だけに使い、出題しません。クイズのファイル名はクイズIDと同じにします（`quizzes/<クイズID>.json`。違うとビルド失敗。会話・クイズ・問題の名前の決まりは [IDの付け方](docs/02_TECH_ARCHITECTURE.md#idの付け方)）。

### クイズ・敵シナリオの編集

新しい通常バトルは、3問入りクイズJSON・Inkを用意し、`content/journeys/<旅行編ID>/battles/catalog.json` に登録します。既存の画面を直接編集する必要はありません。クイズの `englishLevel` は A2/B1/B2 を表現できます。ミラノは7セット（通常4本、B/C各1本、都市ボス1本）、インドは各都市5セット（通常4本、都市ボス1本）です。各問の `difficulty` は easy/medium/hard。選択肢IDと正解IDを一致させ、正解位置に偏りがないか確認してください。

出典は `sources` に公式資料のURL・発行元・タイトル・確認日・根拠文を保存します。`claimType` は documented_fact / interpretation / legend で区別し、学説は断定せず根拠文に明記します。今回は美術館の公式解説 [A powerful theatrical machine](https://cenacolovinciano.org/en/story/a-powerful-theatrical-machine/) と [Backstage](https://cenacolovinciano.org/en/museum/backstage/) を参照しています。プレイヤーには解答後に根拠リンクを表示し、出題前に解説を見せません。

Inkには `battle_scene`（catalogのシーン名）、`answer_correct`（直前の正誤）、`battle_score`（正解数）、設定した名前と `player_address` を渡します。導入・各中間ラウンド後・決着をそれぞれ独立した短いシーンとして `-> END` で閉じます。最終問の反応と勝敗別の結末は決着シーン内で分岐します。クイズの選択・採点はTypeScriptが担当するため、バトルInkには選択肢や恋愛effectを置けません。既存の文字送り・speaker/background/emotionタグを使い、演出を後から加えられる形にしています。

バトル用検証は、通常3問／都市ボス5問・各3択・正解参照・重複ID・語彙・出典・シーン参照に加え、通常戦の13通り、都市ボスの31通りのシーン入力と、特殊戦の追加シーンをInkで最後まで実行します。日本語の導入や証拠提示成功時の台詞が、続く英語の答えを直接教えていないか、史実が正しいかは脚本レビューでも確認してください。クイズも `src/content/generated/quizzes.json` に生成されます。生成物は手動編集しません。

### 特殊戦の追加・編集

バトル定義の `format` は省略時Aです。既存Aのデータとシナリオはそのまま保持しています。Bは `format: "B"` と `reasoning.kind: "contradiction"`、Cは `format: "C"` と `reasoning.kind: "connection"` を設定します。`reasoning` は次の情報だけを持ちます。

- `roundIndex`: 推理を入れる1問の位置（0から数える）。残りは通常3択。
- `caseClueIds`: 手がかり帳へ常時提供する既存の証拠ID（3〜5枚）。観光の `clues` を再利用。
- `correctClueIds`: Bは1枚、Cは異なる2枚。Cは順不同で判定。
- `claimScene` / `successScene` / `failureScene`: 主張・証拠受付・不足点の説明を記したInkシーン。Bだけ `pressScene` も指定。

推理の結論は、同じ `roundIndex` のクイズの `correctOptionId` で指定します。証拠の選択と英語の採点は独立しており、証拠だけで3択に自動回答しません。追加シーンも既存の `battle_scene` で分岐し、`-> END` で閉じます。主張は帳面にも表示されるため、短い日本語にしてください。台詞はInk、証拠・条件はJSON、判定・保存はTypeScript、入力と描画はReactです。

ビルド時に形式と推理種別、証拠枚数・重複・正解の包含、証拠IDと観光地の一致、ラウンド範囲、シーンIDの重複と実行可能性を検証します。正解証拠と結論が論理的に一意かは出典と脚本も照合してください。本編への配置は `content/journeys/<旅行編ID>/progression/journey.json` の `storyBattles` に、対決ID、前後のエピソードID、案内文とボタン名を指定します。B/C戦績を完了記録に使い、観光エピソードや報酬を重複登録しません。

### 観光地・発見ポイント・画像の編集

`content/journeys/<旅行編ID>/tourism/catalog.json` の `landmarks` に観光地を、`assets` に画像を、`clues` に発見内容を登録します。観光地は都市ID、日本語・英語名、画像アセットID、案内InkのID、既存バトルID、手がかりID一覧を持ちます。追加には都市の `landmarkIdsPlanned` と対応するバトル定義も登録します。React画面の修正は不要です。

`clues[].region` は**画像全体に対する0〜1の相対座標**で、左上の `x` / `y` と `width` / `height` を指定します。画面のpx値は書きません。`kind: "hotspot"` は領域必須、`kind: "document"` は `region: null` とし、技法など画像から直接観察できない知識を資料カードにします。`factId` は安定ID、`relatedQuestionIds` は同じ観光地のクイズで、その手がかりの内容を必要とする問題のIDです（どの問題にも結び付かなければ `[]` の「観察だけの手がかり」。[データ契約](docs/07_DATA_AND_TESTS.md#観察だけの手がかり)）。説明はJSON、人物の台詞はInkに分けます。出典の `claimType` は事実・解釈・学説・伝承を区別し、画面にも区分と根拠を表示します。

観光案内Inkには `player_name` / `heroine_name` / `player_address` を渡します。短い日本語の線形会話として書き、恋愛effectや選択肢を入れません。コンテンツ検証ではID・参照・座標範囲・資料カードとの区別・出典・画像ファイルの形式・案内の実行を確認します。

### エピソード・報酬の編集

`content/journeys/<旅行編ID>/progression/journey.json` の `episodes` が観光地・バトル・解放条件を結びます。各都市の最初のエピソードは前提なしで始まり、旅行開始時の選択を限定しません。`requiredEpisodeIds` の循環や参照切れを検証します。通常観光は `kind: "episode"`。都市ボスは `kind: "city_finale"`、`landmarkId: null` の独立したフィナーレです。ミラノでは同都市の4観光地と2つの特殊戦、インドでは各都市の4観光地が前提です。架空の5番目の観光地を作りません。

都市ボスのバトル・クイズも `scope: "city_finale"` と都市IDを指定し、`landmarkId: null` にします。クイズは5問、中間シーンは4つ。通常戦の3問・中間2つは維持します。得点上限・ラウンド・結果・保存の整合性は、登録された問題数に照らして判定します。

報酬の条件は `guide_read` / `battle_complete` / `battle_score` / `episode_clear` / `city_clear`。対象は通常の `episodeId` または特殊戦の `battleId` のどちらか一方を指定します。特殊戦の `episode_clear` はその対決の初完了を条件とし、観光エピソード数や都市のクリア条件は増やしません。`minScore` は好成績報酬だけに指定します。特殊戦の既存 `completionReward` は `battle_complete` として共通の報酬処理で扱います。IDは保存に使うため、公開後に変更しないでください。ミラノの `firstClearReward`（`chapter_milano_first_clear`、4AP）は『最後の晩餐』の `episode_clear` 報酬で、都市クリアのIDとは別です。章末の短い地の文はこのJSON、人物の台詞はInkに置きます。

フィナーレの `epilogueStoryId` は都市ごとに設定します（ミラノは `epilogues/milano`）。Inkに名前・呼称・`romance_stage`・`ending_reached` を渡し、恋愛効果や選択肢は許可しません。デート間の固定順序はなく、実体験だけを思い出として参照します。都市クリアと交際状態は別々に記録します。

## 実装とセーブ

- `src/app/` / `src/components/`: 表示・操作・保存後の状態反映。APや好感度の計算はありません。
- `src/domain/game.ts`: デート可否・AP消費・恋愛の選択効果・思い出と告白の進行。
- `src/domain/battle.ts`: 採点・ラウンド・勝敗・戦績、証拠選択・追及・組み合わせ。通常戦の決着時に共通の章進行処理を呼ぶ。
- `src/domain/tourism.ts`: 案内・訪問・発見・バトルとの往復。案内読了時に共通の報酬処理へ通知する。
- `src/domain/chapter.ts`: エピソードと特殊戦の解放、都市完了、自由時間、デート解放に使う章の記録。
- `src/domain/travel.ts` / `src/domain/travel-game.ts`: 旅行の事前計算と、現在地・時刻・支払いの状態更新。
- `src/domain/epilogue.ts`: 効果のない都市の到着会話とエピローグの開始・途中保存・読了。
- `src/domain/rewards.ts`: 一度限りのAP獲得、上限を超えた残額、結果画面の報酬記録。
- `src/features/tourism/viewport.ts`: 画像座標・拡大・移動範囲の計算。
- `src/story/`: 公式 `Continue` / `currentChoices` / `ChooseChoiceIndex` とstate JSONを包むアダプタ。
- `src/persistence/`: localStorageアダプタ・保存データ検証・バックアップ・古い保存データの整理（`old-data.ts`）。
- `src/dev/`: 開発用のDebug（`?debug`・Debug起動URL）と素材のプレビュー。`scenario-builders.ts` は単体テスト・Debug・E2Eが共有する場面の組み立て部品、`test-cities.ts` は仮の場面と単体テストの試験用の都市、`fixture-template.ts` はその元にする都市を役割で選ぶ関数です。本番ビルドには含まれません。
- `src/content/` / `scripts/`: データ契約・許可タグ・ビルド時検証。`scripts/journeys/<旅行編ID>/` はその旅行編だけの制作ツール（例：インド編の `india:check`）で、共通のコードとツールからは読み込みません。

保存キーは旅行編ごとに `dreamscape.journey.<旅行編ID>.save.v1` です（ミラノは `dreamscape.journey.milano.save.v1`、インドは `dreamscape.journey.golden_triangle.save.v1`）。旅行編ごとにゲーム進行と英語ノートを分離し、データ内の `schemaVersion` は **14** を使います。名前・AP・関係状態・思い出・デート履歴・告白と交際状態、進行中のInk、バトル回答と戦績、観光と発見、現在都市、旅行の現在地・日数・時刻と進行中の活動を保持します。同一バージョン内のデート途中データは、脚本と指紋を照合して再開します。新しい恋愛イベントは開始時に保存した乱数から関係状態に応じた反応を決めます。通常デートを選べず関係を築き直す必要がある場合は、AP不要の短い再交流を利用できます。告白の成否は乱数で変わりません。進行中の確率デートは開始時点のプロフィールを保存し、再開後も同じ設定を使います。`completedEpisodeIds`、`completedCityIds`、`completedGuideIds`、`pendingApRewards`、`battleRewardReceipt` も維持します。

ゲーム進行の自動保存は設定で切り替えられます。オフの間は進行をメモリに保持し、「セーブ」を押した時点で保存します。未保存の進行がある状態でのロードやブラウザ離脱には確認が出ます。保存先は旅行編ごとに1枠で、他のタブで更新されていた場合は上書きを拒否します。各旅行編はWeb Locksで同じ旅行編の複数タブ同時編集を防ぎます。英語ノートと表示設定はゲーム進行とは別に保存されます。

Phase 6では `activeBattle.reasoning` に主張のシーンID、選択中・提出済みの証拠、追及済みか、推理の状態を保存します。通常戦では `null`。推理中も同じInkの実行位置を保存し、誤った証拠への反応・追及の途中・英語回答の前後から再開できます。選択と提出はリビジョンを検証し、連打で二重採点しません。特殊戦の指紋には証拠データも含め、資料の意味が変わったセーブを勝手に再判定しません。

デートの `chapterId` と開始条件 `requiredCompletedChapters` の章IDは都市ID（エピソードの `cityId`）と同じです。章はその都市のエピソードを1つでも終えると完了とみなし、セーブには書かず `completedEpisodeIds` から求めます（v14で保存項目 `completedChapters` をなくしました）。章の完了は都市全体のクリアを意味しません。各観光地・フィナーレは `completedEpisodeIds`、都市全体は `completedCityIds` に分けます。ミラノ都市クリアには4観光地、2特殊戦、ボスの完了が必要です。

開発中は、過去のセーブが更新後も利用できることや自動移行を保証しません。**v1〜v13のゲームセーブは現在の形式へ自動移行されず、読み込めません。**データは消さず、旧版として案内します。v14で変えたことは[データ契約の「セーブの版」](docs/07_DATA_AND_TESTS.md#セーブの版)にまとめています。以前のミラノ編の保存キー `dreamscape.save.v1` / `dreamscape.learning.v1` は読み込まず、ゲームが自動で消すこともありません。ほかの旅行編の旧版のセーブ・バックアップ・以前のミラノ編のキーは、設定の「古い保存データの整理」で利用者が選んで消せます（開いている旅行編の旧版のセーブは、そのタイトルの「保存データを消去する」で消せます）。同一バージョン内では有効なセーブの保存・再開を維持します。安全に読めないデータは自動消去・上書きせず、内容を案内して利用者が消去を選べます。一般公開時には互換性方針を改めて検討します。

交流中の選択、支払い、所持状態、抽選結果と抽選時の設定は保存され、再読込や古いタブからの操作で二重に適用しません。破損、未知の新しい版、保存領域の読込失敗と、判別できる対応外の旧版は区別し、いずれも自動消去しません。

操作はリビジョンを照合し、保存が成功した後で画面を進めます。

通常バトルから観光へ戻った場合は、同じ観光地の `activeBattle` と `activeTourism` を同時に保持します。観光を開いている間は回答操作を止め、バトルへ戻ると同一の回答・スコア・ヒント・Ink位置を再開します。特殊戦ではケース資料内で画像を確認でき、観光画面への移動は不要です。恋愛会話との同時実行はできません。

Phase 2では解放済みイベントID、告白の保留/成功、交際エンディングの到達を保持します。成立の思い出とエンディングは告白を読み終えた時点で一緒に確定するため、成功反応の途中で更新しても欠落・二重付与しません。古いタブからの上書きも検出してロードを案内します。

破損・未知バージョン・不整合な保存は自動上書きしません。案内画面から明示的に新しく始める場合に限り、元データを `dreamscape.journey.<旅行編ID>.save.v1.backup.<時刻>` に退避します。他アプリの保存データは削除しません。シナリオ更新で進行中のInkとの互換性が失われた場合も元データを保護します。バトルでは問題・正解・シナリオの定義を含む指紋を照合し、更新前の回答を新しい問題で勝手に採点し直しません。観光画像の交換だけでは案内の指紋は変わりません。任意に改稿したInkの実行位置を移す機能はありません。改稿確認には上記のDebugモードまたは別ブラウザプロファイルを使うと既存の旅を残せます。保存は端末・ブラウザ・URLのオリジンごとです。

日常の確認には、コンテンツ全体の生成を何度も繰り返す重いテストを除いた `npm run test:quick` を使います。`npm test`・`npm run test:quick`・`npm run build` を個別に使う場合はそれぞれコンテンツを再生成します（単体テストの前は見本の編を含め、`build` の前は含めません）。`npm run verify` は単体テスト用と本番ビルド用の生成を一度ずつ行います。空のcheckoutで `npm run typecheck` を単独実行する場合は、先に `npm run content:check` で生成してください。
