# Dreamscape

恋愛 × 世界観光 × 英語学習の、モバイル優先ブラウザゲーム。現在は **Phase 6まで**を実装しています。名前設定から、ミラノ『最後の晩餐』の観光・任意の観察・英語3択バトル・試遊章クリア・AP獲得・章末の恋愛モードまで、一続きで遊べます。通常戦に加え、矛盾追及・証拠連結の特別対決を各1本試せます。恋愛ルートは通常デート3本、ヒロインの誘い、告白と交際エンディングまで。仕様の優先順位は [AGENTS.md](AGENTS.md)、全体設計は [docs/](docs/) を参照してください。

## 起動

Node.js 22.12以上を推奨（開発・検証環境: Node.js 24.19.0 / npm 11.9.0）。

```sh
npm ci
npm run dev
```

表示されたURL（通常 `http://localhost:5173`）で遊べます。Viteは `0.0.0.0` にバインドします。同じネットワークのスマートフォンからは開発機のIPと表示ポートにアクセスしてください。外部のクラウド開発環境では環境側のポート公開URLを使用します。

```sh
npm run build
npm run preview
```

本番出力は `dist/`。静的ホスティングで配信でき、サブディレクトリ配信にも対応する相対パス設定です。HTMLファイルを直接開かず、HTTP経由でアクセスしてください。バックエンド・アカウント・クラウド保存はありません。

## GitHub Pages

公開先: https://nagaihimitsu.github.io/dreamscape/

`.github/workflows/pages.yml` が `main` へのpushで、コンテンツ検証・単体テスト・型チェック・本番ビルドを実行し、成功した `dist/` をGitHub Pagesへ公開します。初回のみリポジトリの **Settings → Pages → Build and deployment → Source: GitHub Actions** を選択してください。設定後はActionsの「Deploy to GitHub Pages」から手動実行もできます。公開設定とデプロイの権限はGitHub側で必要です。

## 通常の試遊手順

1. 主人公名・ヒロイン名を設定して **「旅をはじめる」**。既定は「なお」「りえ」、最大24文字（UTF-16単位）。既存セーブがあれば、その場面から続けられます。
2. **「ミラノ第1話／最後の晩餐編」** の「このエピソードを始める」から修道院の旧食堂へ。ヒロインの短い案内を最後まで読み、「観察を始める」を押すと初回読了の1APを受け取ります。案内を閉じて観察へ進むこともできます。
3. 絵の気になる場所を自由に観察します。発見は手がかり帳へ保存されます。**観察は任意**で、何も発見せずに「バトルを始める」を押しても構いません。
4. アルド・ヴェルニーチェとの日本語の掛け合いを読み、英語3択を3問解きます。0問正解でも最後まで遊べ、試遊章をクリアできます。
5. 決着まで読むと、戦績・章クリア・初回報酬が一緒に確定します。結果画面に今回のAP、現在の所持AP、短い章末の余韻を表示します。**「自由時間へ進む」** でそのまま恋愛モードへ。
6. 「運河沿いのカフェ」に2APで誘い、日本語3択を2回選びます。デート後は「自由時間に戻る」。この一連の進行に仮クリア操作は必要ありません。

今回の章は**ミラノ第1話の試遊章**です。将来予定しているミラノ4観光地や都市全体のクリアは意味しません。再訪・復習用の観光とバトル入口は「旅先を再訪する」にまとめています。通常戦をそこから遊んだ場合も同じ完了条件・一度限りの報酬管理を通り、直接アクセスで章を未プレイのままクリアすることはできません。特別対決は別枠で、章やAP報酬に影響しません。

## AP報酬のルール

数値と条件は `content/progression/journey.json` の試験設定です。

| 条件                             |  AP | 一度限りの報酬ID                    |
| -------------------------------- | --: | ----------------------------------- |
| 観光案内を初めて最後まで読む     |   1 | `guide_last_supper_first_read`      |
| クイズバトルを初めて最後まで完了 |   1 | `battle_last_supper_first_complete` |
| 初めて2問以上正解する            |   1 | `battle_last_supper_first_victory`  |
| 試遊章を初めてクリアする         |   4 | `chapter_milano_first_clear`        |

新規ゲームで案内をスキップし、0問正解でも**5AP**を受け取って自由時間へ進めます。案内を読了して2問以上正解した場合は合計**7AP**です。初回に好成績を取れなくても、再戦で初めて条件を満たすと1APを受け取れます。再戦やリロードで初回完了・章クリア報酬を再取得することはできません。クイズ成績は好感度を直接変えず、恋愛の進展はデートで選んだ言葉によって決まります。

所持上限は**12AP**。統合報酬が上限を超えた分は、失わずに「保留中のAP」として保存します。空きがあれば画面の「保留中のAPを受け取る」で受け取れ、デート開始時にAPを使った場合も残額を自動で受け取ります。すでに得た報酬IDと残額を別々に記録するため、連打・途中再開・設定値の変更で同じ報酬を増やすことはありません。

告白まで遊ぶための有限の補助APは `content/romance/trial_progression.json` に分離しています。カフェ後と散歩後に**各4APを一度だけ**受け取れ、画面にも「試遊専用の補助AP」と表示します。この補助枠は新しい観光エピソードの報酬ではなく、将来それらに置き換える予定です。上限を超える補助APは空きができるまで受け取れません。現在の新規ゲームの総供給量は通常報酬5〜7APと補助8APの**13〜15AP**、所持上限は常に12APです。

## 観察・バトルの操作

絵の番号または一覧を選ぶと、対象を拡大・中央へ寄せ、説明を手がかり帳へ記録します。4箇所は遠近法、使徒のまとまり、光輪に代わる光の表現、後世に広げられた扉。画像だけでは確認できない制作技法は独立した資料カードです。

拡大・縮小ボタン、ドラッグ、2本指のピンチに対応します。「全体を見る」で戻り、「印を隠す」で絵だけを眺められます。倍率は1〜5倍で、移動は画像の端で止まります。キーボードでは観察領域にフォーカスして矢印キーで移動、`+` / `-` で拡大縮小、`0` で全体表示できます。拡大位置は画面を開き直すと全体表示に戻ります。

バトル中の **「手がかり帳」** は1回押すと開き、閉じても同じ会話・問題・回答後の画面に戻ります。「観光に戻って調べる」で追加の観察をしてから「バトルに戻る」で続けられます。発見の有無によって正解や採点は変わりません。スキップした案内や旧版で読了を確認できない案内は「観光案内をもう一度読む」で読み直せます。

クイズはB1を基本とした英語3択3問。語彙の日本語補足と任意ヒントがあり、回答後は選択肢をロックして正誤・日本語解説を表示します。3問正解で **PERFECT VICTORY**、2問で **VICTORY**、0〜1問で **DEFEAT**。敵の結末とヒロインの余韻が変わり、初回・最高・直近の正解数と完了回数を記録します。ヒントを使っても完走・報酬獲得が可能です。

## 特別対決：矛盾追及・証拠連結

通常の旅は従来のA型バトルです。一度自由時間へ進むと、**「旅先を再訪する」→「特別対決」** からB型・C型を選べます。旧版の自由時間・交際エンディングのセーブからも遊べます。途中の恋愛会話がある場合は、会話を終えてから選びます。

| 形式        | 試遊内容                                                 | 推理するラウンド |
| ----------- | -------------------------------------------------------- | ---------------- |
| A：通常戦   | アルド・ヴェルニーチェとのテンポのよい英語3択            | 追加操作なし     |
| B：矛盾追及 | 原因を一つにまとめたがるニーノに、異なる損傷の証拠を示す | 第2問            |
| C：証拠連結 | 何でも切り離すエットレに、人物配置と遠近法の関係を示す   | 第3問            |

どれも英語3択3問です。Bでは敵の主張を読み、必要なら **「追及する」** で詳しく聞きます。「手がかり帳」で証拠を1枚選んで **「証拠を突きつける」**。Cでは2枚を選び **「組み合わせる」**。どちらも資料を示しただけでは得点にならず、続く英語3択で理由・結論を答えます。誤った資料には不足している観点を短く説明し、その場で選び直せます。推理操作に時間制限・AP消費・減点はありません。

手がかり帳は1タップで開けます。敵の主張と英文問題を上部に残したまま、証拠の詳しい説明・出典・観光画像を比較できます。画像の枠は観光画面と同じ相対座標で、拡大して確認できます。必須の証拠は **「ケース資料」** として未発見でも読め、事前に観察したものには「観察済み」と表示します。読んだだけで観光の発見履歴を変更しません。選択は即時保存され、帳面を閉じても再読み込みしても残ります。

Bの争点は、乾式技法による劣化と、後世の出入口拡張による損傷の区別です。Cの結論は、観察できる人物配置と遠近法を踏まえた構図の**解釈**であり、作者の意図が証明されたとは扱いません。

特殊戦は試遊用です。戦績と途中状態は保存しますが、AP・章クリア・好感度・告白条件は変更しません。終了後は「自由時間へ戻る」、または再戦できます。A/B/Cの80/15/5という比率は将来の目安で、出現抽選や数合わせは実装していません。

## 恋愛ルートを告白まで試す

1. カフェ（2AP）を完了し、補助AP「翌日の自由時間」（4AP）を一度だけ受け取ります。
2. 「夕暮れの散歩」（3AP）を完了。ヒロインからの無料・一度限りの誘い「彼女の寄り道」に応えます。
3. 補助AP「夜の自由時間」（4AP）を一度だけ受け取り、「灯りを数える夜」（3AP）を楽しみます。
4. 無料の「旅の続きに、きみと」で気持ちを伝えます。過去のカフェの言葉を振り返り、交際開始か保留に分かれます。
5. 保留になったら、無料の「書きかけのポストカード」で話してから再告白できます。通常デートで低めの好感度の選択を重ねても、誠実に気持ちを伝えれば交際エンディングへ到達できます。

通常デートは3択2回、特別イベント・保留後の会話・告白は3択1回です。好感度の数値、段階名、解放閾値は表示せず、呼び方や会話で変化を伝えます。これらはシステム検証用の短編で、本番脚本の推敲は別途行う前提です。

一文ずつの文字送りは3速度・全文表示に対応し、恋愛の選択は確認画面で言い直せます。「中断する」やリロード後も、表示中の一文・選択肢・選択後の反応から再開できます。「セーブ」「ロード」は自動保存と同じ枠なので、過去へ巻き戻す機能ではありません。名前は会話の外で「設定」から変更できます。

再鑑賞は元のAP費用を使い、好感度・思い出を再獲得しません。これから必要なデートのAPまで使い切る再鑑賞は無効になります。特別イベントと保留後の会話は一度だけ、保留中の告白は無料で再挑戦できます。交際エンディングは保存され、到達後も観光・バトルを再訪できます。

開発者向けの最低経路確認: 案内スキップ・クイズ全問不正解から、カフェ選択1→1、散歩1→2、誘い1、夜景1→2、告白1で保留、ポストカードは任意、再告白1で成功。補助APを含め、この経路で詰まらず完了できます。

## 文章・データの編集

会話の編集元は `content/stories/milano/` の各 `.ink` ファイルです。既存 [`cafe_01.ink`](content/stories/milano/cafe_01.ink) はPhase 1から変更していません。台詞と選択肢をReactに埋め込まず、Inkに置いています。

```ink
# speaker: heroine
「……{player_name}さん。明日の予定、一つだけ書いてもいい？」
```

名前は `player_name` / `heroine_name` をゲーム状態から渡します。新しい恋愛シナリオでは `player_address`（段階に応じた敬称つき呼称）、`romance_stage`、`memory_callback`（過去の思い出）、`confession_ready` も利用できます。AP・段階・告白条件の計算はTypeScript側で行い、Inkには結果だけを渡します。`* [選択肢]`、`->` の合流で短い分岐を編集します。タグは `speaker`（narrator/heroine/player/enemy）、`background`、`emotion`、`effect` に限定。背景・表情はpresentationに登録、effectはeffect_catalogのIDに限定し、文字列をコードとして実行しません。本文タグとInk公式choice tagsの両方を検証・処理します。

| 編集ファイル                             | 内容                                                                 |
| ---------------------------------------- | -------------------------------------------------------------------- |
| `content/stories/**/*.ink`               | 会話、選択肢、リアクション、タグ                                     |
| `content/romance/date_catalog.json`      | 種別、表示文、AP費用、必要章・履歴、シナリオ参照、選択回数・検証条件 |
| `content/romance/effect_catalog.json`    | 好感度差分、思い出ID、告白結果（accepted/deferred）                  |
| `content/romance/progression.json`       | 4段階の閾値・必要履歴・敬称、告白成立条件、思い出の引用              |
| `content/romance/trial_progression.json` | 試遊専用の有限AP報酬と前提イベント。将来の章報酬とは分離             |
| `content/romance/presentation.json`      | 背景・表情・思い出・保留案内・エンディングの文章                     |
| `content/romance/balance.json`           | AP上限・既定名・名前長                                               |
| `content/progression/journey.json`       | 試遊章の接続・開始/章末の表示文・AP報酬条件と一度限りのID            |
| `content/cities/milano.json`             | 都市名・予定観光地・旧章報酬の互換設定                               |
| `content/battles/catalog.json`           | A/B/Cの形式、敵、クイズ・Ink参照、推理ラウンド、ケース資料・正解証拠 |
| `content/quizzes/*.json`                 | 各対決の英語3問、正解ID、語彙、ヒント、正誤解説、難易度、出典        |
| `content/stories/battles/*.ink`          | 日本語の敵の台詞・正誤反応・勝敗別の結末・ヒロインの余韻             |
| `content/tourism/catalog.json`           | 観光地・画像の出典と権利情報・発見範囲・説明・史実とクイズの参照     |
| `content/stories/tourism/*.ink`          | ヒロインの短い観光案内                                               |
| `public/assets/tourism/`                 | 同梱する資料画像。外部サイトへの画像直リンクは使用しない             |

新しい通常デートは、InkとJSON定義・効果を追加するだけで既存のメニューと会話画面に表示されます。`kind` は `normal` / `special` / `confession` / `reassurance`。通常は `choiceCount: 2`、無料イベントは必要に応じて0〜2回の3択を設定できます。`effectCount` は各経路で期待する効果数です。`actionLabelJa` もJSONにあり、Reactにイベント固有の文言を追加する必要はありません。

`validationContexts` に関係段階、告白可能/保留、引用するmemoryIdを指定し、その文脈から全分岐を検証します。告白は成立条件の真偽を両方指定する必要があります。通常デートは各文脈9経路、選択機会1回のイベントは各文脈3経路です。現在は6シナリオを合計105経路・文脈で検証しています。

```sh
npm run content:check
```

`inkjs/compiler/Compiler`（公式inkjsのコンパイラ）でコンパイルし、`src/content/generated/stories.json` を生成します。独自Inkパーサー・外部コマンド・.NETの準備は不要です。生成JSONはGit管理せず、手動編集しません。ブラウザには `inkjs` のランタイムを使用します。

`dev` 起動前、`test` 前、`build` 内で必ずコンパイル・検証します。開発サーバー起動中にInkを改稿したら別ターミナルで `npm run content:build` を実行してください。生成JSON変更をViteが反映します。**Ink原稿そのものの自動監視はありません。**

検証はJSONスキーマ、重複ID、章・背景・シナリオ・思い出参照、許可タグ、前提イベントの循環、段階設定、報酬ID重複、シナリオごとの選択数・効果数・告白結果を確認します。壊れたInk・参照切れ・未定義effect・不正JSONはビルド失敗になります。旧 `last_supper_B1.sample.json` は参考サンプルの検証だけに使用し、出題しません。

### クイズ・敵シナリオの編集

新しい通常バトルは、3問入りクイズJSON・Inkを用意し、`content/battles/catalog.json` に登録します。既存の画面を直接編集する必要はありません。クイズの `englishLevel` は A2/B1/B2 を表現でき、現在はB1の3セット（A/B/C各1本）です。各問の `difficulty` は easy/medium/hard。選択肢IDと正解IDを一致させ、正解位置に偏りがないか確認してください。

出典は `sources` に公式資料のURL・発行元・タイトル・確認日・根拠文を保存します。`claimType` は documented_fact / interpretation / legend で区別し、学説は断定せず根拠文に明記します。今回は美術館の公式解説 [A powerful theatrical machine](https://cenacolovinciano.org/en/story/a-powerful-theatrical-machine/) と [Backstage](https://cenacolovinciano.org/en/museum/backstage/) を参照しています。プレイヤーには解答後に根拠リンクを表示し、出題前に解説を見せません。

Inkには `battle_scene`（catalogのシーン名）、`answer_correct`（直前の正誤）、`battle_score`（正解数）、設定した名前と `player_address` を渡します。導入・第1問後・第2問後・決着をそれぞれ独立した短いシーンとして `-> END` で閉じます。最終問の反応と勝敗別の結末は決着シーン内で分岐します。クイズの選択・採点はTypeScriptが担当するため、バトルInkには選択肢や恋愛effectを置けません。既存の文字送り・speaker/background/emotionタグを使い、演出を後から加えられる形にしています。

バトル用検証は、全3問・各3択・正解参照・重複ID・語彙・出典・シーン参照に加え、通常戦の13通りのシーン入力と、特殊戦の追加シーンをInkで最後まで実行します。日本語の導入や証拠提示成功時の台詞が、続く英語の答えを直接教えていないか、史実が正しいかは脚本レビューでも確認してください。クイズも `src/content/generated/quizzes.json` に生成されます。生成物は手動編集しません。

### 特殊戦の追加・編集

バトル定義の `format` は省略時Aです。既存Aのデータとシナリオはそのまま保持しています。Bは `format: "B"` と `reasoning.kind: "contradiction"`、Cは `format: "C"` と `reasoning.kind: "connection"` を設定します。`reasoning` は次の情報だけを持ちます。

- `roundIndex`: 推理を入れる1問の位置（0から数える）。残りは通常3択。
- `caseClueIds`: 手がかり帳へ常時提供する既存の証拠ID（3〜5枚）。観光の `clues` を再利用。
- `correctClueIds`: Bは1枚、Cは異なる2枚。Cは順不同で判定。
- `claimScene` / `successScene` / `failureScene`: 主張・証拠受付・不足点の説明を記したInkシーン。Bだけ `pressScene` も指定。

推理の結論は、同じ `roundIndex` のクイズの `correctOptionId` で指定します。証拠の選択と英語の採点は独立しており、証拠だけで3択に自動回答しません。追加シーンも既存の `battle_scene` で分岐し、`-> END` で閉じます。主張は帳面にも表示されるため、短い日本語にしてください。台詞はInk、証拠・条件はJSON、判定・保存はTypeScript、入力と描画はReactです。

ビルド時に形式と推理種別、証拠枚数・重複・正解の包含、証拠IDと観光地の一致、ラウンド範囲、シーンIDの重複と実行可能性を検証します。正解証拠と結論が論理的に一意かは出典と脚本も照合してください。今回のB/Cは `journey.json` のエピソード・報酬には登録しません。既存の2種類の仕組みで新しい対決を作る場合、カタログ・クイズ・Inkの追加で表示できます。

### 観光地・発見ポイント・画像の編集

`content/tourism/catalog.json` の `landmarks` に観光地を、`assets` に画像を、`clues` に発見内容を登録します。観光地は都市ID、日本語・英語名、画像アセットID、案内InkのID、既存バトルID、手がかりID一覧を持ちます。追加には都市の `landmarkIdsPlanned` と対応するバトル定義も登録します。React画面の修正は不要です。

`clues[].region` は**画像全体に対する0〜1の相対座標**で、左上の `x` / `y` と `width` / `height` を指定します。画面のpx値は書きません。`kind: "hotspot"` は領域必須、`kind: "document"` は `region: null` とし、技法など画像から直接観察できない知識を資料カードにします。`factId` は安定ID、`relatedQuestionIds` は既存クイズの問題IDです。説明はJSON、人物の台詞はInkに分けます。出典の `claimType` は事実・解釈・学説・伝承を区別し、画面にも区分と根拠を表示します。

観光案内Inkには `player_name` / `heroine_name` / `player_address` を渡します。短い日本語の線形会話として書き、恋愛effectや選択肢を入れません。コンテンツ検証ではID・参照・座標範囲・資料カードとの区別・出典・画像ファイルの形式・案内の実行を確認します。

現在の画像は [Wikimedia Commons掲載のParis Orlando撮影写真（2019年）](https://commons.wikimedia.org/wiki/File:Last_Supper_by_Leonardo_da_Vinci.jpg)。CommonsのPD-Art / PD-old-100-expiredおよび [Public Domain Mark 1.0](https://creativecommons.org/publicdomain/mark/1.0/) 表示を確認した忠実な複製画像です。3840px版を全体の構図を保ったまま2560×1422pxのWebP（約1.53MB）へ縮小・圧縮しました。描き足し・左右反転・生成AIによる補完はしていません。クレジット・出典・権利表示・確認日・加工内容はアセットJSONと画面内に残しています。

画像は `public/assets/tourism/last-supper.webp` の差し替えで反映できます。同じ構図・縦横比を維持してください。構図やトリミングを変える場合はアセット寸法と発見領域を再確認・更新します。別の画像に替えた場合は出典・利用条件・加工情報も更新してください。資料として正確でない仮画像は `isPlaceholder: true` で明示します。

### エピソード・報酬の編集

`content/progression/journey.json` の `episodes` が都市・観光地・バトル・既存デート解放用の章IDを結び、`entryEpisodeId` が入口を指定します。今回は `kind: "trial_episode"` の1話のみです。新しい観光地・バトルを用意したら、既存のカタログとエピソード定義を追加して接続できます。画面遷移に観光地名を追加する必要はありません。章末の文章は人物の台詞を含まない短い地の文として、このJSONに置いています。

`rewards` は `guide_read` / `battle_complete` / `battle_score` / `episode_clear` の完了条件とAPを指定します。好成績の閾値は `minScore`。章クリアや観察を勝利必須にする条件は置きません。IDは保存に使用するため、公開後に変更しないでください。旧章報酬の互換性を保つため、`chapter_milano_first_clear` の額を調整するときは都市設定の `firstClearReward.ap` と揃えます。参照切れ・ID重複・補助報酬との衝突・到達不能な閾値・AP上限超過・旧報酬との不一致はビルドで検出します。

## 実装とセーブ

- `src/app/` / `src/components/`: 表示・操作・保存後の状態反映。APや好感度の計算はありません。
- `src/domain/game.ts`: デート可否・AP消費・恋愛の選択効果・思い出と告白の進行。
- `src/domain/battle.ts`: 採点・ラウンド・勝敗・戦績、証拠選択・追及・組み合わせ。通常戦の決着時に共通の章進行処理を呼ぶ。
- `src/domain/tourism.ts`: 案内・訪問・発見・バトルとの往復。案内読了時に共通の報酬処理へ通知する。
- `src/domain/chapter.ts`: エピソード完了、自由時間の解放、既存章IDとの互換性。
- `src/domain/rewards.ts`: 一度限りのAP獲得、上限を超えた残額、結果画面の報酬記録。
- `src/features/tourism/viewport.ts`: 画像座標・拡大・移動範囲の計算。
- `src/story/`: 公式 `Continue` / `currentChoices` / `ChooseChoiceIndex` とstate JSONを包むアダプタ。
- `src/persistence/`: localStorageアダプタ・保存データ検証・バックアップ。
- `src/content/` / `scripts/`: データ契約・許可タグ・ビルド時検証。

保存キーは旧版と同じ `dreamscape.save.v1`、データ内の `schemaVersion` は **6**。名前・AP・非表示好感度・思い出・デート履歴・告白とエンディング、進行中のInk、バトル回答と戦績、観光と発見を保持します。Phase 5の `completedEpisodeIds`、`completedCityIds`、`completedGuideIds`、`pendingApRewards`、`battleRewardReceipt` も維持します。通常バトル完了・戦績確定・試遊章クリア・報酬付与は1回の状態更新として保存するため、結果表示前の中断や再戦でも報酬を取りこぼしたり重複させたりしません。

Phase 6では `activeBattle.reasoning` に主張のシーンID、選択中・提出済みの証拠、追及済みか、推理の状態を保存します。通常戦では `null`。推理中も同じInkの実行位置を保存し、誤った証拠への反応・追及の途中・英語回答の前後から再開できます。選択と提出はリビジョンを検証し、連打で二重採点しません。特殊戦の指紋には証拠データも含め、資料の意味が変わったセーブを勝手に再判定しません。

`completedChapters: ["milano"]` は、既存デートの解放に使う互換用の記録として維持します。これを都市全体のクリアと読み替えません。実際にバトルを完了した試遊章は `completedEpisodeIds`、都市全体は `completedCityIds` に分け、今回のプレイで後者は空のままです。旧版の仮章クリア済みプレイヤーも、既存の恋愛をそのまま続けられます。

Phase 1〜5（schemaVersion 1〜5）は検証後にメモリ上で6へ移行し、次の保存を伴う操作で書き込みます。**読み込み時のAP残高と既存の進行中データは保持**します。Phase 5の通常戦には `reasoning: null` を追加するだけで、既存のコンテンツ指紋・Ink・回答は変えません。Phase 1〜4では従来どおり完了済みバトルから試遊章の完了を判定し、未獲得の初回・好成績・章報酬を保留中のAPとして用意します。旧報酬 `chapter_milano_first_clear` がすでに記録されていれば、同じ4APを追加しません。旧版の訪問履歴だけでは案内を読了したか判断できないため、読了報酬は推測せず、案内を読み直して受け取れます。

既存の恋愛・通常バトル・観光Inkと問題データは変更していません。Phase 1の恋愛段階は既存の好感度と完了履歴から再評価します。実際の旧実装で作成した `tests/fixtures/phase1-saves.json` 〜 `phase5-saves.json` を互換性検証に使っています。リビジョン付き操作で古い入力や別タブからの上書きを防ぎ、保存が成功してから画面を進めます。

通常バトルから観光へ戻った場合は、同じ観光地の `activeBattle` と `activeTourism` を同時に保持します。観光を開いている間は回答操作を止め、バトルへ戻ると同一の回答・スコア・ヒント・Ink位置を再開します。特殊戦ではケース資料内で画像を確認でき、観光画面への移動は不要です。恋愛会話との同時実行はできません。

Phase 2では解放済みイベントID、告白の保留/成功、交際エンディングの到達を保持します。成立の思い出とエンディングは告白を読み終えた時点で一緒に確定するため、成功反応の途中で更新しても欠落・二重付与しません。古いタブからの上書きも検出してロードを案内します。

破損・未知バージョン・不整合な保存は自動上書きしません。案内画面から明示的に新しく始める場合に限り、元データを `dreamscape.save.v1.backup.<時刻>` に退避します。他アプリの保存データは削除しません。シナリオ更新で進行中のInkとの互換性が失われた場合も元データを保護します。バトルでは問題・正解・シナリオの定義を含む指紋を照合し、更新前の回答を新しい問題で勝手に採点し直しません。観光画像の交換だけでは案内の指紋は変わりません。Phase 1〜5の既存シナリオには対応していますが、任意に改稿したInkの実行位置を移す機能はありません。改稿確認には別ブラウザプロファイルを使うと既存の旅を残せます。保存は端末・ブラウザ・URLのオリジンごとです。

## 検証

```sh

```

空のcheckoutでは `npm ci` のあと、生成物を必要とする単独 `typecheck` より先に `content:check` を実行してください。`npm run build` はこの順序を含みます。

単体テストは通常デート各9通りの保存・復元、段階と履歴の判定、告白の成功/保留/再挑戦、特別イベントの一度限り実行、AP上限/不足/未解放/連打、再鑑賞による資金不足の防止、旧セーブ移行、破損/未知schema/保存失敗、コンテンツ検証エラーを対象とします。バトルは全27回答経路で各状態の保存・復元、正誤反応、3種の勝敗、ヒント、二重送信、再戦、恋愛状態の不変性を検証します。

PlaywrightはモバイルChromiumで既存カフェ、低好感度からの保留・回復・交際開始、高好感度での成功、過去の思い出・名前変更、旧セーブの途中再開を操作します。バトルは360px幅で0〜3問正解の通しプレイ、ヒント・語彙、回答ロック、反応中の再読込、再戦、Phase 2の交際エンディングからの出入りを操作します。実機Safariでの検証は別途必要です。

観光は拡大・移動・相対座標の単体検証に加え、360px幅のPlaywrightで画像読み込み、タッチ入力によるピンチ・ドラッグ、移動制限、発見と再読み込み、手がかり帳の開閉、観察をスキップしたバトル、途中回答を保持した観光への往復、旧Phase 3セーブを検証します。

統合テストでは、新規ゲームから案内・観察・バトル・章末・APを使うデートまでを仮クリア操作なしで進めます。0問正解から告白までの経路、再戦で初めて得る好成績報酬、初回報酬の再取得不可、上限で保留したAPの受取、観光・バトル・デート途中の再読み込み、旧Phase 1〜5セーブと交際済みセーブの再訪も確認します。

特殊戦のテストは、正しい証拠・無関係な証拠・順不同の組み合わせ、追及と再挑戦、未発見のケース資料、帳面の開閉・画像確認、選択中やInk途中の再読み込み、二重採点防止、AP・恋愛状態の不変性、Phase 5の実セーブ移行を確認します。証拠を揃えても英語3択は別に解答することを検証します。

恋愛の背景と敵の立ち絵は簡易SVGイラストです。観光画面と証拠帳は上記の実物資料画像を使用しています。フォントはNoto Sans JP / Noto Serif JP（Google Fonts、SIL OFL）を任意取得し、取得できなくてもシステムフォントで動作します。
