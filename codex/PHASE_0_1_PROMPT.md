# Codexへ送信する初回実装指示（Phase 0 + Phase 1）

対象: GitHubリポジトリ `nagaihimitsu/dreamscape`（名前は `dreamscape`）。

あなたはこのリポジトリの実装担当です。まず既存ファイルを調査し、追加済みの場合は `AGENTS.md` と `docs/` を熟読し、その方針に従ってください。資料がまだ置かれていない場合でも、以下の概要と実装条件を使ってPhase 0+1から着手してください。

## 作品概要（確定）
恋愛×世界観光×英語学習×奇妙な敵との3択クイズバトルのスマホ優先ブラウザゲーム。プレイヤーとヒロインの名前は編集可能（既定値：なお、りえ）。**最大の強みは圧倒的に面白い日本語の文章と会話**。敵とヒロインの台詞・通常会話は日本語、**3択クイズの問題文と選択肢だけ英語**。クイズはレイトン式のシンプルな3択中心。証言の矛盾追及B、証拠連結Cは後から稀に登場する特殊戦。観光地は任意で観察・発見できる。史実は出典を確認する。

恋愛は「クイズのおまけ」ではなく単独の攻略ゲーム。通常パートや章クリアでAP（行動ポイント）を獲得、章末の恋愛モードでAPを消費してデートに誘い、短い日本語の3択会話を約2回選んで女の子を口説く。APは好感度を直接買う通貨ではなく、デートの機会の費用。最終ゴールは**告白成功・交際開始**。恋人後の長編は作らない。好感度の数値はプレイヤーに非表示。

## 今回実装すること（Phase 0+1に限定）
1. リポジトリの現状を調査し、既存コードを尊重する。土台が無ければ Vite + React + TypeScript のモバイル優先SPAを構築。
2. 会話・分岐は編集しやすい `content/stories/**/*.ink`、実行はビルド時コンパイルJSON + `inkjs` を第一候補として導入。ゲームUIに台詞・選択肢を直書きしない。独自のInkパーサーは作らない。選択肢／話者／背景／表情／イベントタグを安全に扱う。コンパイルエラーはビルド失敗にする。
3. デートの定義はJSON（ID、タイトル、AP費用、必要章、シナリオ参照）。AP・好感度・報酬付与・イベント履歴はUIから分離されたTypeScriptのロジックで管理。
4. 最初の遊べる縦切り：**開発用の「ミラノ章初回クリア」操作→AP4獲得→恋愛モード→2APのカフェデート選択→3択会話2回→リアクション→デート終了**。
5. 主人公・ヒロインの可変名を台詞にも反映する。初期画像がなくても、背景色・シンプルなプレースホルダーで確実に遊べるUIを優先。スマホで問題なく操作できる。
6. 初回章クリア報酬の二重付与防止、AP不足の防止、デート開始の二重消費防止、イベントの再読込による二重好感度付与防止を実装。未使用APは持ち越し。試験上限12AP（変更可能な設定値）。
7. localStorageにschemaVersion付きで保存。選択中・デート中にブラウザを再読み込みしても、APや分岐が破綻しない。保存データの破損は安全に扱う。
8. TypeScript型チェック・ビルド・コンテンツ検証・AP/保存の単体テストを用意し、実行して確認する。
9. READMEを更新して、起動コマンド、試遊手順、`.ink`台詞の編集方法、今後のPhase 2への拡張点を示す。

## 技術とデータの参照例
資料がrepoに置かれていれば `docs/02_TECH_ARCHITECTURE.md` `docs/03_ROMANCE_SYSTEM.md` `docs/07_DATA_AND_TESTS.md` を参照。`content/stories/milano/cafe_01.ink`、`content/romance/date_catalog.json`、`content/romance/effect_catalog.json` は初期の例として採用し、必要に応じて規則と一致する形へ修正してよい。資料がない場合は、この指示のデータ形式を実装時に自分で用意する。

## 厳守すること
- 今回は**恋愛モードの最初の一本のみ**。クイズバトル、観察、B/C特殊戦、4段階恋愛進行、告白、他都市、大量AI生成は作らない（Phase 2以降）。
- シナリオ文は短くても面白いことを優先。薄いテンプレ台詞、過剰な自動生成、選択肢だけの大量追加をしない。
- YAGNI/KISS/単一責任/可読性・命名を守る。既存ファイルを必要なく消さない。
- 暫定バランス値・仮の文章は変更しやすいデータに置く。
- 途中停止・ページ更新・多重クリックでAPとイベントが重複しない。

## 完了条件
1. 初回章クリアでAPが一度だけ増える。
2. カフェデートがAP消費で開始され、3択2回を選んで終われる。
3. 同じ選択イベントを再表示・再開しても数値/メモリが二重付与されない。
4. ブラウザ更新後も状態が保存・復元される。
5. データファイルを変更すればUIコードを触らず会話が変わる。
6. モバイル幅で動作し、ビルド・型チェック・テストが通る。

実装前の長い説明だけで終えず、リポジトリにコードを作成し、起動して手順を検証してください。実装後はPhase 2には着手せず、Phase 1のプレイ可能な状態を保ってください。
