# 旅の数字（運賃・時間・予算）の決め方

旅の運賃、移動にかかる時間、旅の予算を決める人のための手引きです。ふつうは AI が数えて案を作り、制作者（ユーザー）が選びます。

- 元にしたのは、2026-11-07〜11-13 の交通の設計（ミラノ・ウズベキスタン・ルアンパパーン・インド）と、インド編の予算を決めたバランス調整（#123・#124）です。数字は、その日の記録とリポジトリのデータのままです。
- 手順は [新しい都市を1つ足す手引き](NEW_CITY_GUIDE.md) の [手順3](NEW_CITY_GUIDE.md#手順3-移動手段を選ぶ徒歩著名な乗り物2つ宿地点と経路)（地点と経路）と [手順21](NEW_CITY_GUIDE.md#手順21-バランスを調整する)（バランス）にあります。道と運賃の出典の落とし穴は [調べものの落とし穴集の3章](RESEARCH_PITFALLS.md#3-道と運賃) にあります。この手引きは手順を繰り返さず、「数字をどう出し、どう決め、どう守るか」を書きます。
- 決まりの元は [AGENTS.md](../AGENTS.md#目的と第一原則) の第一原則と「データ・セーブ・品質」です。食い違うときは、そちらに従います。
- 書き終えた後のバランス調整では、[8章のチェックリスト](#8-バランス調整のチェックリスト) をそのまま使えます。

## 1. 三つの約束

1. 数字は、資料（時刻表・料金表・公定の運賃）と、書き残した式から出す。式と道具と丸め方を残す。
2. 資料のない数字は「仮の値」と書く。本物に替えるまで、見える所に残す。
3. 予算は、物語を書き終えてから数えて決める。決めた理由をテストにする。

なぜか。

- 遊ぶ人にとって、移動の時間は一日の時計から、運賃は旅全体の予算から引かれます。どの乗り物を選ぶかの迷いは、この数字から生まれます。
- 画面の時間と料金は「ゲーム内の推定」と出ます。推定でも、都市ごとに出し方がばらばらだと、旅の手ざわりがずれます。
- 後で「なぜこの数か」と聞かれます。式と道具が残っていれば、流し直して答えられます（3.2 の「17分か18分か」）。
- 予算は、ほかの全部の数字の合計で決まります。途中で決めると、場面を足すたびに決め直しになります。

## 2. 数字のありか

パスは旅行編のフォルダ `content/journeys/<旅行編ID>/` からです。

| 数字 | 書く所 | メモ |
| --- | --- | --- |
| 旅の予算 | `manifest.json` の `initialBudget` と、最初の都市の `travel/<都市ID>-settings.json` の `initialBudget` | 旅全体で1つの残高。インド編は2か所とも `38000`、ほかの都市の設定は `0`（ミラノは都市の設定 `milano-settings.json` だけ） |
| 宿泊費 | `manifest.json` の `cityPlan.lodgingCost` と、都市の設定の `lodgingCost` | 2つは同じ値にする |
| 運賃の人数 | `manifest.json` の `farePartySize` | インド編・ウズベキスタン編は2 |
| 乗り物 | `manifest.json` の `transportModes` | 徒歩のほかに2つまで |
| 移動の分と運賃 | `travel/<都市ID>.json` の `routes` の `minutes`・`cost` | 片道。運賃は `farePartySize` 人分 |
| 入場料 | 同じファイルの `events` の `admissionCost` | 2人分 |
| 判断と出典 | `travel/<都市ID>-transit.json`（交通判断台帳） | 地点の組×乗り物ごとに、状態・確認日・理由 |
| 借りる乗り物の料金 | 都市の設定の `rentals` | 滞在中の分の目安 |
| ツアーの値段 | `tours/<ツアーID>.json` の `offers[].price` | 全員分。入場料を含む |
| 場面のお金 | Ink の `# money:`・`# on_done: money` | |
| AP | デートの `apCost`、報酬の `ap`、`cityPlan.cityClearAp` | |
| 計算のもと | `authoring/journeys/<旅行編ID>/research/` | 式・道具・元の表 |

形と検査は [技術設計の乗り物と交通判断台帳](../docs/02_TECH_ARCHITECTURE.md#乗り物と交通判断台帳)、書き方は [コンテンツ制作ガイドの都市内の移動](CONTENT_GUIDE.md#都市内の移動乗り物) と [ツアー](CONTENT_GUIDE.md#ツアー決まった行程の日帰り) にあります。

## 3. 時間を出す

### 3.1 時刻表データから、道具で数える

ミラノの路面電車8本の時間は、ミラノ市の公開時刻表データ（GTFS、ds929。2026年10月26日〜11月30日の分。ライセンスは CC BY）から数えました（2026-11-07）。式は台帳の出典 `tram_model` にあります。

- 停留所まで歩く分（直線距離×1.3を分速75mで）
- 平均の待ち（10〜18時の運行の間隔の半分）
- 時刻表の乗車時間（中央値）
- 停留所から歩く分
- 平日（2026-11-10）と日曜（2026-11-08）を数え、長いほうを切り上げる

例：ドゥオモ → プラダ財団（24番）は平日31.3分・日曜34.3分なので、35分です（[`MILANO_TRANSPORT.csv`](journeys/milano/research/travel/MILANO_TRANSPORT.csv)）。

なぜ時刻表データか。旅行サイトの「約◯分」は、どこから測ったか分かりません。時刻表データなら、同じ式で全部の組を数えられ、後で同じ答えをもう一度出せます。

残すもの：

- 使ったデータの名前・URL・期間・読んだ日（台帳の `sourceRefs`）。
- 式（出典の `claimJa`）と、元の表（`research/`）。
- 数えた道具そのもの。ミラノの道具はリポジトリに残っていません。残っているのは、式と表とテストの数だけです。12月の時刻表で数え直すときに困るので、次からは道具も `research/` に置きます。

### 3.2 丸め方を一つに決め、丸める前の値に当てる

ミラノの路面電車の丸め方は、ユーザーが決めた M3 です。小数の分は切り上げます。

**起きたこと**：最後の晩餐 → 宿の日曜の推定は、2 + 480 / 33 / 2 + 6.75 + 1 = 17.02分です。調査の表は小数1桁なので「17.0」と見え、17分と読めます。丸める前の値に M3 を当てると、18分です。後で「17分か18分か」と問われたとき、道具を流し直して答えられました。`tests/journeys/milano/transport.test.ts` が、この理由をコメントに書いて18分を守っています。

**防ぐ習慣**

- 丸めは一度だけ、丸める前の値に当てる。表示のために丸めた表から、丸め直さない。
- 丸め方は、乗り物ごとに書く。今の例：インド編のオートと地下鉄の時間は5分単位、徒歩は1分単位、オートの運賃は₹10単位で切り上げ。ウズベキスタンのタクシーは1,000スム単位で切り上げ。ミラノの路面電車の運賃は2人分の €4.40 を €5 に切り上げ。
- 決まりに名前（M3 など）と日付を付け、台帳の出典とテストのコメントに書く。

### 3.3 歩く時間：歩行者の経路計算に、余白を足す

経路計算を二つの道具で比べること、点がどの道に吸い付いたかを見ること、道具・設定・日付・測った2点を書くことは、[落とし穴集の3.1](RESEARCH_PITFALLS.md#31-地図の経路計算が遠回りしていた) と [3.2](RESEARCH_PITFALLS.md#32-何から何まで測ったかを書いていない) にあります。二つ目の道具を見る理由も、そこにあります（OSRM の徒歩の設定は幹線道路を歩く道に入れないので、ヤムナー川を渡る約2.61km・約35分の遠回りを出した。Valhalla は幹線道路を歩いて約1.22km）。ここでは、値の出し方を足します。

インド編の式（2026-11-13 と 11-16 に使った）：

- （経路の距離 ＋ 地点の代表点から道までの距離）÷ 分速75m を、1分単位で切り上げる。
- 例：チーニー・カ・ラウザー → ラーム・バーグは 1,236.8m → 16.5分 → 17分。逆向きは 1,301.8m → 17.4分 → 18分。Valhalla 自身の時間は15.9分・16.6分でした。
- アンベール城 ↔ パンナ・ミーナー・クンドも同じ式で12分（398c04b）。

なぜ余白を足すか。経路計算は、道の上の点から測ります。地点の代表点（建物の真ん中など）は道から離れています。その差を足さないと短く出ます。道具ごとの歩く速さは違うので、全部の組を同じ分速75mに直します。

ミラノは別の道具です。OpenSidewalkMap の歩行グラフで最短距離を出し、両端の吸い付けの距離を足し、分速75mで割って切り上げます（違う地点は最低1分。[ミラノの徒歩経路の計算](journeys/milano/research/travel/MILANO_ROUTE_METHOD.md)）。

**残っている仮の徒歩**：インド編の徒歩の経路（違う地点どうし）104本のうち、経路計算で出したのは上の4本だけです。ほかの100本は、直線距離に迂回の係数を掛けた仮の値です（出典の題は "Prototype pedestrian movement, not measured OSM walking road"。2026-11-16 にデータで数えた）。インド編では徒歩15分以内の組を「徒歩だけ」にするので、直すと選べる乗り物まで変わることがあります。2026-11-16 にユーザーに伝え、答えは「問題ありません」でした。今のまま使います。

## 4. 運賃を出す

### 4.1 配車アプリの料金の式（ウズベキスタンのタクシー）

Yandex Go の「スタート」料金（タシュケント。2026-11-07 に読んだ）は、最低4,600スム（1km・3分を含む）、1kmごと1,050スム以下、1分ごと500スム以下です。

ゲームの式（台帳の出典 `taxi_fare_model`）：

- 料金 ＝ 4,600 ＋ 1,050 ×（道のり − 1km）＋ 500 ×（乗車時間 − 3分）を、1,000スム単位で切り上げる。1台（2人）分。
- 道のりと乗車時間は、OSRM の車の経路計算の、渋滞なしの値（2026-11-07）。
- 割増と、車を呼ぶ料金は入れない。料金には乗っている分だけを使う（画面の分数は、待ちと乗り降りの歩きを含む今までの値）。
- 都市ごとに料金表が違う（ブハラは最低3,700スム、1km 900スム、1分 270スム）。

結果は、タシュケント5,000〜19,000、サマルカンド5,000〜15,000、ブハラ4,000〜9,000スムでした。

なぜ式か。配車アプリには、区間ごとの料金表がありません。公開の料金表は式の形なので、経路計算の値を入れれば、全部の組を同じ決まりで出せます。料金表の値は「以下」と書く上限なので、ゲームの値は上限で数えた値です。

### 4.2 公定の運賃と、旅行情報の目安（インドのオートリキシャと地下鉄）

- デリーのオート：デリー政府の告示（2023-01-09）の運賃。最初の1.5km ₹30、その後1kmごとに₹11。道路の距離は OSRM の車の表。
- アーグラとジャイプールのオート：公定の距離制の運賃が見つかりませんでした。旅行情報の目安（例：アーグラ・カント駅 → タージ・マハル 約₹150〜250）に合う式、₹60＋道路1kmあたり₹20 にしました（2026-11-07 のユーザー判断。都市ごとに基準が違う）。
- ナハルガル城の10方向：式では₹340〜360になりますが、旅行情報の目安（₹150〜250）の上限₹250にしました（2026-11-07 のユーザー判断）。式と資料が食い違ったら資料に寄せ、理由を台帳に書きます。
- オートの時間：探して料金を決める5分（仮定）＋道路距離÷時速20.8km（2025年のニューデリーの朝夕の平均。車全体の統計）。アーグラとジャイプールは、10kmを超える部分を時速40km（仮定）。
- 地下鉄：デリーは経路案内のページの普通運賃（平日）×2人、アーグラは駅の数ごとの運賃（1駅₹10、2駅₹15、3〜6駅₹20）×2人。時間は、駅まで歩く分＋入場・検査・待ちの10分（仮定）＋乗車＋駅から歩く分。

表と出典の全部は [インド編の都市内の交通の調査記録](journeys/golden_triangle/research/golden-triangle-transport-20261107/README.md) にあります。

### 4.3 タクシーの式1（ミラノ）

ミラノのタクシーはメーター制です。ロンバルディア州の共通の料金（平日昼）から、式にしました（式1）。初乗り €4.10 ＋ 1km €1.32 ＋ 混雑で延びた時間1分 約€0.575 を、2人で1台として切り上げます。時間は、車をつかまえる5分＋渋滞なしの時間の2倍（切り上げ）です。

どの式にするか（問い Q4）は、返事がないうちに調べもののおすすめ（式1）を仮に入れ、そう知らせました。2026-11-08 に作者が確かめて決まりました（[ミラノの調査記録](journeys/milano/research/travel/README.md)）。式の値は後から戻せるので、仮に進めてよい例です（[決め方の手引き 8章](DECISION_GUIDE.md#8-話の糸を落とさない)）。

### 4.4 人数と単位をそろえる

- 経路の `cost` は片道の `farePartySize` 人分。オートとタクシーは1台分、地下鉄と路面電車は1人分×人数。
- ツアーの `price` は全員分で、入場料を含みます。例：ファテープル・シークリーの宿のフロント₹3,200 は、車の往復₹1,800〜2,000（資料）と入場料（外国人1人₹610×2）に合わせた値です。
- 単位を混ぜると、都市どうしを比べられません。台帳の理由と出典に「2人分」「1台分」を書きます。

## 5. 資料のない値と、期限のある値

### 5.1 仮の値は、そう書いて、注意に残す

例（ファテープル・シークリーまでのオート）は [落とし穴集の3.3](RESEARCH_PITFALLS.md#33-資料のない数字) にあります。ここでは、仮の値の始めから終わりまでを書きます。

1. 2026-11-07、約38〜44km 先のオートの資料は見つかりませんでした。市内と同じ式で出した仮の値（20方向、80〜95分・₹820〜940）にしました。
2. 台帳の理由に「資料の裏付けはない」と、何で置き換えるか（「ツアーで置き換える」、2026-11-09 のユーザー判断）を書きました。
3. 事実の出典がない乗り物の経路なので、`content:build` の注意に出続けました。
4. ツアー（#41、セーブ v18）でこの地点はツアーで行く場所になり、20本はなくなり、注意も消えました。

**防ぐ習慣**

- 仮の値の出典は `hypothesis` だけにする。届かない事実を付けて、注意を消さない（市内のオートの運賃は、約40km先のオートの根拠にならない。[コンテンツ制作ガイド](CONTENT_GUIDE.md#都市内の移動乗り物)）。
- 注意は、本物に替えるまで残す。注意の数が減ったら、なぜ減ったかを言えるようにする。

### 5.2 注意に出ない仮の値もある

`content:build` の注意に出るのは、乗り物の経路で事実の出典がないものです。徒歩の経路は事実の出典を求めないので、仮の徒歩時間は注意に出ません（3.3 の100本）。地下鉄の「入場・検査・待ちの10分」、タージ・マハルの「駐車場と門の間の10分」のような仮定も、式の中にあるので注意に出ません。

こういう値は、調査の記録の「ゲームの決まりと仮定」の節に並べます。バランス調整の前に、その節を読んで数えます。

### 5.3 期限のある料金表

**起きたこと**

- ウズベキスタンの配車アプリの料金表には「2026年11月10日まで有効」と書いてありました。出典の `claimJa` にそう書きました。この日はもう過ぎています。2026-11-16 にユーザーに伝え、答えは「問題ありません」でした（料金表は読み直さず、今の値のまま）。
- ミラノの時刻表データは「2026年10月26日〜11月30日の分」です。12月の時刻表が出たら読み直します（[決め方の手引き 8.3](DECISION_GUIDE.md#83-答えの仕分け) の「材料待ち」）。
- [07 データとテスト](../docs/07_DATA_AND_TESTS.md) には、この2つを公開の前に確かめ直すと書いてあります。

**防ぐ習慣**

- 期限は、出典の `claimJa` に資料の言葉のまま書く。期限を書く専用の欄はありません。
- 公開の前に、期限のある出典を探す。例：`grep -rn 'まで有効\|11月30日の分' content/journeys/*/travel/`
- 読み直したら `checkedAt` を新しくする。値が変わったら、運賃を数え直す（[落とし穴集の6.1](RESEARCH_PITFALLS.md#61-読んだ日と読み直した日)）。

### 5.4 作者の現地確認も出典になる

書き方は [落とし穴集の6.1](RESEARCH_PITFALLS.md#61-読んだ日と読み直した日) と [コンテンツ制作ガイドの都市内の移動](CONTENT_GUIDE.md#都市内の移動乗り物) にあります。日付の記録がなければ月までを書き、日を作りません。

例はルアンパパーンの自転車です。作者は2026年7月に現地で確かめていました。サッカリン通りについての答え（2026-11-08）：

> 確認済み。日中は通れますと回答した。夜は出店のため通れないが、歩道を押して通れた。ゲームなので夜も通れることにして良い。

この答えを [確認メモ](journeys/luang_prabang/research/field-check-2026-07/README.md) に書き、`documented_fact`（発行元「Dreamscape 作者の現地確認」）として引きました。事実（夜は通れない）と、ゲームの割り切り（夜も通れる）は分けて書き、割り切りは台帳の理由に置きました。メモにない道は「未確認」と書いて作者に聞きます。

## 6. 予算を決める

### 6.1 開発中は多めにする

ユーザーの言葉（2026-11-08）：

> てか予算とか最後にバランス調整で決めるものやん。テストの時は多めに持ってていいんでない

ユーザーの言葉（2026-11-09。インド編の交通を切り替えたとき）：

> いっそ3000000くらいにして最後のバランス調整で決める

同じ考えを、ユーザーは記録の上で約6回言っています（2026-11-08 に3回、11-09、11-10、11-13）。

なぜか。書いている間は、支払いのある場面が増えます。少ない予算のまま試すと、話の不具合ではない「お金が足りず進めない」に何度も当たります。インド編は 2026-11-09 に ₹30,000 から ₹3,000,000 にしました。切り替えの計画の概算で、速い経路を選ぶとジャイプールの欠かせない入場料と運賃に足りなくなる遊び方があったからです。

ただし、多すぎる予算は何も語りません。₹3,000,000 では、全部をいちばん高く遊んでも予算の1.4%しか使いませんでした。だから、最後に決めます。

### 6.2 数える：`balance:report`

ユーザーの提案（2026-11-08）から作った道具です（#123）：

> シナリオ制作終了バランス調整時に Inkと交通ファイルから お金の増減と関係値の増減をまとめたファイルを作り バランスを確認するのはどうでしょうか シナリオ制作終了後のバランス調整時としたのは、少し変えただけで毎回作るのは手間だからです

- `npm run content:build` の後に `npm run balance:report -- --journey <旅行編ID> --out <ファイル>`。都市ごとのお金・AP・関係値の出入りの表で、何も検査しません（[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md#お金ap関係値のまとめ)）。
- 見る所：「全部遊んだとき」のいちばん安い回り方といちばん高い回り方、「本筋だけ」、都市ごとの「予算の残り」。
- 数えないもの：宿泊費、都市間の移動、同じ場所への2回目の入場。2回目の入場の分は、余りで見ます。
- 「本筋だけ」に入らないもの：場面の `cond("…")` の分かれ道の中の支払い。収支表は場面ごとに道のいちばん安い値を取るので、払えるときだけ払う道（例：出発の時点の手付金。払えない道は0円）は、いちばん安い本筋の道で必ず払われても「本筋だけ」に入りません（2026-11-18）。そうした支払いは、その旅行編の予算のテストで足して確かめます。
- インド編（2026-11-13）：全部遊んで₹37,230〜₹41,229、本筋だけで₹25,210〜₹26,198。入場料とツアーが全体の約7割で、交通費は₹6,610〜₹8,358でした。インドでは、乗り物の選び方はお金より時間の差になります。

### 6.3 案は A/B/C で出し、「何が足りればよいか」も聞く

聞き方の型は [決め方の手引き 3章](DECISION_GUIDE.md#3-聞き方番号おすすめ理由) にあります。予算では、案ごとに「いちばん高く遊ぶと」「いちばん安く遊ぶと」「進めなくなる心配」を並べます。

**ウズベキスタン（2026-11-07〜08）**：タクシーを 4.1 の式で数え直すと、運賃が下がりました。案は A 2,600,000、B 3,000,000（おすすめ）、C 今の 4,000,000 のまま。ユーザーは B を選びました。B は「40件の観光とデートに、いちばん高い乗り物（タクシーが走る所は全部タクシー）で行き帰りしても足りる」額です。これが線です。

**インド（2026-11-13）**：表から出した案は次のとおりでした。

| 案 | 予算 | いちばん高く遊ぶと | いちばん安く遊ぶと |
| --- | --- | --- | --- |
| A | ₹42,000 | ₹771 残る | ₹4,770 残る |
| B（おすすめ） | ₹45,000 | ₹3,771 残る | ₹7,770 残る |
| C | ₹50,000 | ₹8,771 残る | ₹12,770 残る |
| D（参考） | ₹35,000 | ₹6,229 足りない | ₹2,230 足りない（ジャイプールで進めなくなる） |

おすすめは、ウズベキスタンと同じ線（いちばん高くても足りる）でした。ユーザーが決めたのは ₹38,000 です。いちばん安く回れば全部遊べ（₹770 残る）、いちばん高く遊ぶと足りなくなります（₹3,229 足りない）。足りなくなるのは旅の一部、という線です（#124）。

学んだこと：線（何が足りればよいか）も、制作者が決めることです。前の旅行編の線を使うなら、そう書き、別の線の案も並べます。進めなくなる案（D）は止める対象なので勧めません。

### 6.4 決めた額をテストで守る

- どの旅行編も：`scripts/journey-budget.test.ts` が、公開中の全部の旅行編で「いちばん安く回れば本筋を最後まで遊べる」を確かめます（[AGENTS.md の第一原則](../AGENTS.md#目的と第一原則)）。
- インド編：`tests/journeys/golden_triangle/budget.test.ts` の2つ目のテストが、決めた線の両側を見ます。いちばん安い回り方は予算以内、いちばん高い回り方は予算を超える。値段が変わってどちらかが崩れたら、線を考え直す合図です。
- ウズベキスタン編：`tests/journeys/uzbekistan/foundation.test.ts` が、いちばん安い回り方と高い回り方の両方で、40件と各都市のフィナーレの入場の取り置きをまかなえるかを見ます。
- テストは `balance:report` と同じ数え方（`scripts/journey-balance-input.ts` の `balanceInputs`）を使います。#124 でこの形にしたので、表の数とテストの数が食い違いません。
- テストが本当に守っているかは、予算を少し下げて落ちるのを見て確かめます。ウズベキスタンでは、開始の額を119,000スム下げると、いちばん高い回り方のテストだけが落ちました（2026-11-08）。

### 6.5 残る額を書く

- 決めた額といっしょに、残る額を書きます。次に支払いを足す人が、余りを見て判断できるからです。
- ウズベキスタン：調査の記録の注記に「約600,000 UZS 残ります」（2026-11-08。2026-11-13 の表では soʻm 624,000）。
- インド：遊び方の説明（[11 遊び方](../docs/11_HOW_TO_PLAY.md)）と下書きの README に、何ができる額かを書きました。
- 余りが小さいと、すぐ崩れます。インド編の案A の余り₹771 は、タージ・マハル（₹2,200）への2回目の入場1回で足りなくなる額でした。

### 6.6 足りなくなるのは遊びの結果。ただし安く回れば終わりまで

[AGENTS.md の第一原則](../AGENTS.md#目的と第一原則)：

> お金を使いすぎて旅を続けられなくなるのは、壊れているのではなく遊びの結果とする。ただし、いちばん安く回れば本筋を最後まで遊べることは、テストで守る。

- お金が尽きてその街でできることがなくなると、街歩きの画面が知らせます（2026-11-13 のユーザー判断。`src/domain/budget-dead-end.ts`、[11 遊び方](../docs/11_HOW_TO_PLAY.md)）。
- `content:build` の注意「お金で詰むおそれ」だけに頼らない。この注意は、いちばん安い運賃で、場面の中の支払いを数えずに下限を見ます。₹30,000 のとき、ジャイプールで進めなくなる遊び方があったのに、注意は出ませんでした（2026-11-13 に確かめた）。表とテストで見ます。

## 7. 値を変えるとき

### 7.1 書き方の違いを全部探す

**起きたこと**：ウズベキスタンの予算を 4,000,000 から 3,000,000 にしたとき（2026-11-08）、`4000000`・`4_000_000`・`4,000,000`・`400万` を探しました（`node_modules`・`dist`・生成物を除く）。8ファイルの10か所が見つかり、全部直しました（データの2ファイル。都市の設定は `initialBudget` と注記（今は「旅行開始資金300万スム」）の2か所。テスト3ファイル、README、調査の記録2ファイル）。

インド編の ₹38,000 は、今（2026-11-16）、データ4つ（`manifest.json`、`travel/delhi-settings.json`、下書きの2つ）、文書（`docs/11_HOW_TO_PLAY.md`、`authoring/FUTURE_CITIES.md`、この手引き、新しい都市の手引き、下書きの README）、テストのコメント2つにあります。

```sh
grep -rn --exclude-dir=node_modules --exclude-dir=dist --exclude-dir=generated --exclude-dir=.git \
  -e '38000' -e '38,000' -e '38_000' -e '3万8' .
```

探す書き方：数字だけ（JSON）、桁区切り（文章と表）、`_` 区切り（テストのコード）、万（「300万スム」）、通貨の記号つき（₹38,000、soʻm 3,000,000）。生成物は `content:build` で作り直されるので、探す所から外します。同じ型を全部探す考え方は [横の点検](SWEEP_CHECK_GUIDE.md) にあります。

### 7.2 版・日付・表

- 公開中の旅行編で運賃を上げる・経路をなくすときは、セーブの版を上げます。保存済みの帰りの交通費の確保（`returnReserve`）が合わなくなるからです（[07 データとテスト](../docs/07_DATA_AND_TESTS.md)、[手順21](NEW_CITY_GUIDE.md#手順21-バランスを調整する)）。いつ上げるかは、先にユーザーと決めます。
- 予算は新しく始める旅の初めの値です。ウズベキスタン（準備中）で変えたときは、版を上げませんでした（2026-11-08）。
- 読み直した出典だけ `checkedAt` を新しくします。読み直していないのに、日付だけを新しくしません。
- 変えた後は `balance:report` を作り直し、前の表と比べます。決めたことは、番号と日付で書き残します（[決め方の手引き 7章](DECISION_GUIDE.md#7-決めたことを書き残す)）。

## 8. バランス調整のチェックリスト

時間と運賃

- □ 期限のある出典を読み直した（ウズベキスタンの配車アプリの料金表「2026年11月10日まで有効」、ミラノの時刻表データ「〜11月30日の分」）。値が変わったら数え直した
- □ 読み直した出典だけ、`checkedAt` を新しくした
- □ 数えた道具と式と丸め方が `research/` にある（ミラノの路面電車の道具は、今はない）
- □ 丸めは、丸める前の値に一度だけ当てた（M3：17.02分 → 18分）
- □ 運賃の単位（2人分・1台分・入場料込み）が、台帳の理由と出典に書いてある
- □ 仮の値の一覧を作った：注意に出る乗り物の経路、注意に出ない仮の徒歩（インド編は100本）、式の中の仮定（待ちの10分など）
- □ 仮の値を残すか替えるかを決め、台帳の理由に書いた
- □ 作者の現地確認は、確認メモ（月まで）を `documented_fact` として引いた

予算

- □ `npm run content:build` の後に、`npm run balance:report -- --journey <旅行編ID> --out <ファイル>` を作った
- □ 「全部遊んだとき」の安い回り方と高い回り方、「本筋だけ」、都市ごとの残りを読んだ
- □ 線（何が足りればよいか）を制作者に聞いた。前の旅行編の線を使うなら、そう書いた
- □ 案を A/B/C（おすすめ1つと理由）で出し、案ごとに安い・高い回り方の残りと、進めなくなる心配を並べた
- □ ツアーの値段と場面の支払いも見直した（インド編のツアー₹3,200・₹3,500 は「バランス調整で見直す」、2026-11-10）
- □ 決めた額と線を、番号と日付で書き残した
- □ いちばん安く回れば本筋を最後まで遊べる（`scripts/journey-budget.test.ts` が通る）
- □ 決めた線を `tests/journeys/<旅行編ID>/` のテストにした。予算を少し下げて、落ちるのを見た
- □ 残る額を、調査の記録・遊び方の説明・テストのコメントに書いた
- □ 予算の書き方の違いを全部探して直した（JSON 2か所、下書き、`docs/11_HOW_TO_PLAY.md`、`authoring/FUTURE_CITIES.md` など）
- □ 公開中の旅行編で運賃を上げた・経路をなくしたなら、セーブの版を上げた
- □ まだ決めていない旅行編を確かめた（2026-11-13 の表：ミラノ €60 に対し全部をいちばん高く遊ぶと €145、ルアンパパーン ₭2,000,000 は準備中）
