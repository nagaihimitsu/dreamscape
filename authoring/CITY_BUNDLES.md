# 都市データをまとめて編集する

都市の地点・観光と観察・交通・宿泊・デート先・背景・画像情報を、都市ごとに１つのJSONで編集できます。例えばデリーなら、`india-delhi.json` に必要な設定と出典をまとめられます。各カタログを個別に探して編集する必要はありません。

このJSONは**編集用の作業コピー**です。現在ゲームが読む `content/` の各カタログが正本で、書き出しただけではゲームは変わりません。編集後に `check` で検証し、`apply` で反映します。作業コピーを長期間保存するより、編集のたびに新しく書き出すことを推奨します。

## 基本的な使い方

リポジトリのルートで次を実行します。`delhi` は登録済みの都市IDに、出力先は作業しやすいファイル名に変更できます。画像を新規追加・差し替えする場合は、**先に画像本体を `public/assets/` に用意してから**書き出してください。

```sh
# 編集用ディレクトリを用意する（Gitには含まれません）
mkdir -p artifacts/city-work

# 1. 現在の内容を書き出す
npm run city:bundle -- export delhi artifacts/city-work/india-delhi.json

# 2. india-delhi.json を編集し、変更内容を検証する
npm run city:bundle -- check artifacts/city-work/india-delhi.json

# 3. 検証済みの変更を既存カタログへ反映する
npm run city:bundle -- apply artifacts/city-work/india-delhi.json
```

`check` は入力と既存データを照合し、一時領域でコンテンツ検証を行います。反映はしません。`apply` も検証を実行し、成功した場合に関連ファイルを更新します。`apply` はサイトの公開、Gitへのコミット、プッシュを行いません。

`apply` が書き込むのは、その都市の都市ファイルがある層（`content/` または旅行編フォルダ `content/journeys/<旅行編ID>/`）だけです。まだ都市ファイルがない新しい都市は、同じ旅行編の既存の都市と同じ層へ、旅行編に都市が一つもなければその旅行編フォルダへ作られます。その層にまだないカタログ（例：`romance/date_destinations.json`）は、項目が追加されるときにフォルダごと作られます。他の層に登録された背景・画像は参照できますが、この都市の編集では変更・削除できません。ID の重複は全層を合わせて確認します。

`apply` が通常のエラーで途中終了した場合は、更新済みファイルを元に戻します。別の編集ツールとの同時書き込みや、プロセス・OSの強制終了に対しては完全な原子性を保証できません。強制終了後に `.city-bundle.lock` が残って再実行できない場合は、他の `city:bundle apply` が動いていないことと変更内容を確認してからロックファイルを取り除いてください。

書き出し先には `content/` と `public/` の外を指定してください。既存のファイルは上書きされないため、再度書き出すときは別のファイル名を指定します。

現在の9都市のIDは `milano`、`delhi`、`agra`、`jaipur`、`tashkent`、`samarkand`、`bukhara`、`khiva`、`luang_prabang` です。例えばミラノは `npm run city:bundle -- export milano artifacts/city-work/italy-milano.json` のように書き出します。ミラノとインド3都市には登録済みの観光地と観察ポイントも含まれます。ウズベキスタン4都市は制作基盤の状態で、脚本やクイズの登録は別途必要です。

書き出してから `content/` や `public/` のいずれか、インド編の観察カードや公共交通の調査台帳が変更された場合、他都市の変更や画像の追加も含め、古い作業コピーの反映は拒否されます。その場合は、画像・元データを準備したうえで、別名へ再度 `export` し、編集した項目を新しいコピーへ移してください。新しいコピーの `baseFingerprint` は移し替えず、そのまま残します。`baseFingerprint` は競合検出に使うため、手で変更しないでください。都市IDや公開状態もこの操作では変更できません。

都市の到着会話を付ける場合は、都市定義の `arrivalStoryId` に登録済みInkのIDを指定します。ロゴに使う都市名も同じ都市定義から表示します。本文の作り方は [旅行編の制作手順](JOURNEY_AUTHORING.md#都市に到着したときの会話) を参照してください。

## 新しい都市を作る

先に対象旅行編の `content/journeys/<旅行編ID>/manifest.json` の `cities` に都市IDと都市名を登録し、都市の順番や通貨などの旅行編共通設定を決めます。都市IDは既存の都市と重ならないものを使います。使用する画像の本体を `public/assets/` に用意した後、その都市の編集用JSONの雛形を作ります。

旅行編に都市IDだけを先に追加すると、都市データの `apply` が終わるまで全体のコンテンツ検証は通りません。専用ブランチで作業し、必要な都市データをまとめて準備してください。

```sh
# sample_city は旅行編へ登録した都市IDに置き換える
npm run city:bundle -- new sample_city artifacts/city-work/sample-city.json

# 必要な都市・地点・交通・背景・画像・出典などを入力した後
npm run city:bundle -- check artifacts/city-work/sample-city.json
npm run city:bundle -- apply artifacts/city-work/sample-city.json
```

雛形は入力の出発点であり、実在地点・経路・料金・画像の内容は自動で埋まりません。必要な項目を入力して検証を通した後、`apply` で都市データを登録します。新しい都市は制作中として扱われ、この操作だけで公開済みにはなりません。

少なくとも都市名・国・滞在先の名前と座標・出典、開始予算・宿泊費などを入力し、各地点には同じ地点への徒歩０分・０円の移動データも用意してください。下記の共通設定を使えば、各地点に１件ずつ記入する必要はありません。各地点間で必要な交通手段や、観光・デートの候補、背景と出典は、調査に基づいて追加します。

## 都市内の経路を編集する

新たに書き出した作業コピーと新都市の雛形は `schemaVersion: 2` です。`travel.routeSources` に経路の出典をまとめ、`travel.routes` の `sourceRef` から参照します。出典IDはその作業コピー内の名前です。複数の経路が同じ出典を使う場合、一度だけ記入できます。出典を修正すると参照しているすべての経路に反映されます。１つの経路だけ出典を変えるには、`routeSources` の該当する出典配列を別のIDで複製し、複製先の内容を修正して、その経路の `sourceRef` だけを新しいIDに付け替えてください。`sourceRef` は存在する出典を指定します。出典の内容・確認日・主張の区別は省略しないでください。

`routeSources` は `"source_1": [出典, ...]` のように、IDごとに出典の配列を持ちます。各出典には書き出された `publisher`・`title`・`url`・`checkedAt`・`claimType`・`claimJa` を入力します。新しい経路に異なる出典が必要な場合は、既存の配列をひな形として別のIDで作り、実際の調査内容に書き換えます。バージョン２の経路には `sources` を直接書かず、`sourceRef` を使ってください。

次は `travel` 内の経路設定の抜粋です。地点ID、所要時間、料金、出典IDは説明用で、作業中の都市の調査結果に置き換えます。料金は**片道の２人分**です。

```json
{
  "samePlaceRoute": { "sourceRef": "source_1" },
  "routes": [
    {
      "fromPlaceId": "sample_hotel",
      "toPlaceId": "sample_station",
      "mode": "taxi",
      "minutes": 20,
      "cost": 300,
      "estimation": "game_model",
      "sourceRef": "source_2",
      "bothDirections": true
    }
  ]
}
```

`bothDirections: true` は時間・料金・乗り換えの注記・推定種別・出典のすべてが両方向で共通する場合にのみ使います。反映時に２つの片道経路へ展開されます。片方向だけの経路や、逆方向で値または出典が異なる経路はこの指定を付けず、それぞれの方向を別々に登録します。**両方向を１件にまとめた経路の片方向だけ出典を変える場合**は、その経路から `bothDirections` を外し、出発地と到着地を入れ替えたもう１件の片道経路を追加します。そのうえで、変更したい方向の `sourceRef` だけを複製・修正した出典IDに付け替えます。明示しない逆方向は作られません。ゲーム用推定値には上の例のように `estimation: "game_model"` を付け、推定である根拠を出典に記載します。

`samePlaceRoute` を設定すると、その出典を使う徒歩０分・０円の経路を、`travel.places` の全地点に生成します。同じ場所の経路を個別に作成する場合や地点ごとに出典が異なる場合は、共通設定を使わず `routes` にそれぞれ登録します。共通設定で生成される経路と個別の経路が重複すると検証エラーになります。共通設定にも、必要に応じて `estimation` と `transferNote` を指定できます。

`export` は、往復の内容が出典を含めて完全に一致する場合にだけ両方向指定へまとめます。同一地点の経路も、全地点で共通の内容にできる場合に限って共通設定へまとめます。その他の方向差や出典は個別に残ります。`check` と `apply` は展開後の重複・存在しない地点や出典の参照などを検証し、`apply` は検証後、従来の片道形式で正本へ反映します。以前の `schemaVersion: 1` の作業コピーも、競合がなければ引き続き検証・反映できます。

地図上の直線距離だけから現実の移動時間を生成しません。経路に書かれていない公共交通を、現実に存在しないものと決めつけないでください。インドの不採用・未特定の調査判断は `transitDecisions` で方向別に管理します。経路の追加や削除時は、調査判断と矛盾しないよう確認します。

## 作業コピーに含まれるもの

| 項目 | 内容 |
| --- | --- |
| `city` | 都市名、国、テーマ、予定される観光地点などの都市定義 |
| `travel` | 地点・座標・営業時間、都市内の経路と時間・料金、観光・デート候補、各項目の出典 |
| `travelSettings` | 滞在先、宿泊費、再試行時間など、その都市の旅行設定 |
| `dateDestinations` | デートの行き先、説明、背景の参照、調査した事実と出典 |
| `landmarks` | 都市内の観光地の説明、観光案内やバトル、観察画像への参照 |
| `clues` | 各観光地の観察ポイント・資料とその出典 |
| `backgrounds` | 地点で表示する背景名、表示色、画像アセットへの参照 |
| `assets` | 画像のパス、寸法、説明、作者・ライセンス・出典などの情報 |
| `transitDecisions` | インド３都市の公共交通について、登録しない候補・未特定の調査判断と出典。他の都市では `null` |

画像本体は `public/assets/` に置く必要があります。JSONへ画像の実体は含まれません。画像のファイル名・出典・ライセンス・利用条件を確認し、参照に合うファイルを `export` / `new` の前に用意してください。画像を変える場合は、観察位置や説明も新しい画像で確認が必要です。

インド編の観察画像は記録済みのハッシュと照合します。ミラノの既存観察画像には旧画像のハッシュがないため、`export` より前に同じパスの画像ファイルを差し替えた場合、その差し替えを自動では検出できません。画像を変更したときは、観察ポイントの位置・説明・出典を必ず再確認してください。

複数都市が使う画像も参照できます。例えばインド３都市のホテル背景は共通画像を使用しています。共通画像の情報を一都市だけの編集として変更・削除することはできません。他都市の定義・参照や既存IDと衝突する変更、必要な画像が存在しない変更も検証で拒否されます。

交通時間・料金・座標・営業時間にはゲーム用の推定値があります。実際の時刻や運賃と混同せず、出典や推定の根拠も各項目に残してください。徒歩経路を座標の直線距離だけから現実の経路として扱うことはできません。

インド３都市で公共交通の経路を追加したときは、`transitDecisions` に同じ方向・手段の不採用または未特定の判断が残らないよう、あわせて編集します。ゲームで採用しない判断は、現実の路線が存在しないことを意味しません。

## ほかに必要な作業

- 旅行編の都市順、通貨、開始予算などの共通設定は、都市ごとの作業コピーとは別途、旅行編ごとの `content/journeys/<旅行編ID>/manifest.json` で管理します。
- シナリオのInk、クイズ、日本語訳、登場人物、各デートの思い出、都市フィナーレなどの制作と登録は別途必要です。単に都市データを反映するだけでは、プレイできる完成都市にはなりません。
- インド編には既存の[制作補助](india-scaffold/README.md)と[完成確認・公開手順](drafts/golden-triangle/RELEASE_GATE.md)があります。シナリオ・クイズとそのメタデータ・訳を用意したうえで、生成・検証できます。特殊戦B・Cは現行の制作補助では自動設定されず、別途制作・登録が必要です。
- 都市や旅行編を公開可能にする判断と検証は、この編集操作とは別です。未完成の都市が本番でプレイ可能と表示されないよう、制作状態を維持します。

調査資料として残すファイルと、現在のゲームに反映済みの値は一致しないことがあります。特に `authoring/drafts/golden-triangle/cities/` と `travel/` は古い研究由来の生成ドラフトで、現在の交通や入場料の正本ではありません。編集用コピーの代わりにそのドラフトを本番データへ上書きしないでください。同じ旅行編の `scenario/` には今回の脚本・クイズの制作記録を置き、実行用Inkの正本は `content/stories/` にまとめています。

## ウズベキスタン4都市

同じコマンドで、例えば `npm run city:bundle -- export tashkent artifacts/city-work/uzbekistan-tashkent.json` と書き出せます。写真・料金・地点・全方向の交通判断も含まれます。`transitDecisions` の `available` と実際の経路が一致しない場合、出典が欠ける場合、未確認の判断が残る場合は反映を拒否します。`not_suitable` はこの地点間のゲーム用移動として採用しない意味で、市全域のサービス不存在を示しません。写真の差替え時は観察資料の確認も必要です。シナリオの追加は [旅行編共通の手順](JOURNEY_AUTHORING.md) を参照してください。

## ルアンパパーン

`npm run city:bundle -- export luang_prabang artifacts/city-work/laos-luang-prabang.json` で編集できます。市街地の観光候補・写真・徒歩と車の推定経路を登録し、旅行編は制作中です。根拠・交通の採否・未制作項目は[調査記録](research/luang-prabang-20261104/README.md)を参照してください。クァンシーの滝と将来のツアー機能は含まれていません。
