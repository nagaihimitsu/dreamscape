# 将来の都市追加：現状と作業手順

この文書は、将来の都市制作と実装のための調査メモです。Phase 8で複数都市を有効にしたものではありません。新都市の原稿は、必要なら `authoring/drafts/` 等に置き、ゲームには読み込ませずに準備できます。下書きフォルダは任意です。

## 現在できることと境界

会話はInk、観光・発見・クイズ・バトル・恋愛・進行・報酬はJSON、画像は `public/assets/` に分かれています。既存のミラノ内で対応するカタログや参照を揃えれば、新しい通常バトルやデートを画面コードに書き込まずに追加できます。実際の内容・位置・利用条件は制作時に検証してください。

**現行ゲームは都市を一つだけ読み込みます。** `content/cities/` に別の都市JSONを置くだけでは、その都市はゲームに登場しません。現行の検証も、都市と観光地のIDがミラノの設定に属することを要求します。他都市IDを既存カタログへ追加すると、参照エラーになります。都市切り替えや複数都市ルートは後続の実装が必要です。

表示用の `nameJa` などと保存・参照用の `id` は別です。表示名は必要に応じて変えられますが、公開済みの都市・場所・手がかり・バトル・問題・章・報酬・思い出のIDを安易に変更・削除しないでください。過去の達成記録、保留AP、途中のバトルなどが参照しています。

## 原稿として準備する順序

1. 新都市・観光地・各コンテンツに、既存と重複しない安定IDを決めます。表示名は日本語・英語それぞれ自然に付けます。
2. 都市データは `content/cities/milano.json`、ルートは `content/progression/journey.json` の構造を参考に、観光地・順番・ボス・報酬・必要条件を設計します。既存のミラノファイルを新都市の情報で上書きしないでください。
3. 各観光地の画像とアセット情報、案内Ink、発見ポイント・資料カードを準備します。`content/tourism/catalog.json` の `assets`・`landmarks`・`clues` が現行の正規形式です。画像には出典、利用条件、作者、加工内容を記録します。画像で確認できない事項は資料カードにします。
4. `content/quizzes/` のJSONに英語問題と3択、日本語の補足・解説・出典を用意します。`content/battles/catalog.json` のバトル定義、`content/stories/battles/` のInkで敵と反応を結びます。通常3問、都市フィナーレ5問が現行の契約です。B/Cの証拠には観光地の手がかりIDを使います。
5. 恋愛イベントがあれば `content/romance/date_catalog.json`、`effect_catalog.json`、`presentation.json` と `content/stories/` のInkを揃えます。表示される思い出、背景、Inkで使うeffectの各IDを一致させます。
6. 現行進行の通常エピソードには `guide_read`、`battle_complete`、`battle_score`、`episode_clear` が各1件、フィナーレには `battle_complete`、`battle_score`、`city_clear` が各1件必要です。報酬IDは一度だけの受給判定にも使います。新都市には既存の `chapter_milano_first_clear` を流用しません。最小・最大の獲得量とAP上限・保留を設計します。
7. 原稿は通常のGitレビューで採用します。現行コードの制約が解消されるまでは、新都市を `content/` に混ぜてゲームに追加したと見なさず、ミラノ本番データを守ってください。

事実・伝承・解釈を区別し、根拠URLと確認日を記録します。自動検証は文章の面白さ・英語の自然さ・史実の真偽・画像の最終的な使用権を保証しないため、編集者が原典と画像を確認します。人間が書いた原稿もAIが補助した原稿も同じチェックを受けます。

## 開発者が後続フェーズで対応する箇所

以下は現行コードの具体的な制約です。単に新しい都市ファイルを読み込むだけでは完了しません。

- **データ読込・参照検証**：`src/content/index.ts` と `scripts/content-pipeline.ts` は `content/cities/milano.json` を直接読みます。後者と `scripts/tourism-validation.ts` は単一都市のID・観光地一覧に対し、観光、クイズ、バトル、デートを検証します。都市の集合と都市ごとの所属関係を読み込み、重複ID・参照・他都市の誤接続を検証する必要があります。
- **都市進行**：`scripts/journey-validation.ts` は単一都市、直前エピソードを必須とする一本の順路、最後に1つのフィナーレ、旧初回報酬の一致を前提とします。複数都市間の解放・移動と各都市内の順路を仕様として決めてから、検証と `src/domain/chapter.ts` の次エピソード選択・達成判定を合わせて変更します。フィナーレは架空の観光地にしません。
- **旧セーブ・報酬**：`src/domain/game.ts` と `src/domain/chapter.ts` は `city.id` とミラノの `firstClearReward` を、旧 `completedChapters` と `chapter_milano_first_clear` の互換に利用します。この旧対応は新都市のクリアに使い回せません。都市別の進行と報酬を導入する場合は既存フィールドを保持し、安全なマイグレーションと重複・欠落の検証を追加します。未知・破損データは勝手に消去しません。
- **表示・演出**：`src/app/App.tsx`、`src/features/journey/CityProgress.tsx`、`src/features/tourism/ClueNotebook.tsx` は現在の単一 `city` を参照し、一部に4観光地前提の表示があります。`src/components/CanalScene.tsx` は色やキャプションをデータから取得しますが、絵そのものは共通の仮SVGです。`portrait` は現在の限られた種類の仮立ち絵です。都市選択と、必要な場合のアセット拡張を、実際の仕様に合わせて行います。
- **背景・シナリオ**：背景IDと表情IDは `content/romance/presentation.json` の許可一覧で管理します。新しい背景名の登録だけで新規の風景画像が表示される仕組みではありません。`src/story/runtime.ts` の未指定時の背景もミラノの既定値です。
- **テスト**：`src/content/`・`src/domain/`・`src/persistence/` と `tests/e2e/` のミラノの期待値・実セーブを維持し、複数都市の参照エラー、進行順、各報酬の一度限り、AP上限・保留、交際済み状態、途中再開を追加検証します。特に、旧ミラノ章の記録から新都市や都市全体をクリア扱いにしないことを確認します。

`npm run content:check` は現行の全体検証とInkコンパイルを行い、`npm run typecheck`、`npm test`、`npm run build` と必要な `npm run test:e2e` で挙動を確認します。フィールドや参照の変更はゲームの読込契約と保存検証に影響するため、後続対応時は既存セーブでの再開も確認してください。

## 公開済み原稿を編集するとき

進行中のInkやバトルは内容の指紋と保存位置を検証します。表示名がIDと分離されていても、**進行中の同じシナリオや問題を改稿すれば、その途中セーブを自動的に再開できるとは限りません**。内容が一致しないときは元の保存を保護する設計です。改稿は別のブラウザプロファイルで確認し、互換性への影響をレビューしてください。観光画像の差し替えだけは案内Inkの指紋に影響しませんが、縦横比や構図が変わるなら相対座標も見直します。
