# 外の書き手とのやりとり（説明書を渡す・原稿を受け取る）

この会話とリポジトリの外で書く人（別の会話の AI や人。以下「外の書き手」）に書き方の説明書を渡す人と、届いた原稿を点検する人のための手引きです。務めるのは、ふつうは AI です。人が務めるときにも使えます。

- 読むとき：説明書を渡す前。原稿が届いたとき。直した次の版が届いたとき。
- 元にしたのは、2026-11-08〜09 の二つの仕事です。一つは、Ink の書き方の説明書2本と、その試し書き。もう一つは、インド編の改稿版（新しい書き方の原稿）の点検で、届いた版ごとに4回（v1〜v4）行いました。原稿は #36（本筋とデート）と #38（差し込みの場面13）でゲームに入りました（2026-11-10）。
- 説明書と点検の報告は、その会話の作業用フォルダにあり、リポジトリには入っていません。いずれ消えるので、大事な所はこの手引きに写しました。今の札の書き方は [コンテンツ制作ガイド](CONTENT_GUIDE.md) にあります。
- 近い手引き：リポジトリの中で書く人と直す人を分ける話は [シナリオ改稿のポイント 1章](SCENARIO_EDITING_GUIDE.md#1-なぜ書く人と直す人を分けるのか)、自分のエージェントへの指示書は [AIに仕事を分けて頼む手引き 3章](AI_DELEGATION_GUIDE.md#3-一人ずつの指示書) です。この手引きは、外の書き手に特有のこと（リポジトリも会話も見えない。原稿はユーザーが運ぶ）を書きます。

## 1. 外の書き手と、変わらない決まり

2026-11 のインド編の書き手は、ユーザーと別のチャットで書いていました。ファイルはユーザーが運びました。原稿は zip でこちらに届き、こちらの点検とメモは、ユーザーが書き手のチャットへ渡しました。

外の書き手について、分かっていたこと：

- この会話を知らない。決まったことは、説明書とメモに書いたことしか知らない。
- リポジトリを読めるとは限らない。
- Ink をコンパイルできないことがある。4回目の点検の報告には「書き手は Ink を組み立てられませんでした」とあります。組み立てと全部の道の確かめは、こちらでしました。

変わらない決まり：

- **原稿は、書き手とユーザーのもの。** AI は点検して報告し、札の直しを自分の写しに入れます。文は書き直しません（3章）。話の事実と、遊ぶ人に見える言葉は、聞いて決めます（[シナリオ改稿のポイント 1章](SCENARIO_EDITING_GUIDE.md#編集者がしてはいけないこと)、[AIと決めごとを進める型 4.2](DECISION_GUIDE.md#42-必ず聞くこと)）。
- **AI は書き手の中身（台詞・地の文・書き手が書く欄）を書かない。書いたら、そう知らせる。** 例：
  - 書き手が書く欄の説明は仕組みだけにし、例は見本の編だけで書く（2026-11-11 の決めごと）。
  - 見本の編の人物リリの別れの台詞は AI が書いたので、ユーザーに知らせた（2026-11-09）。
  - インド編の28人の役どころ（`titleJa`）は、台本から AI が下書きし、書き手が変えてよいと添えた（2026-11-11）。

なぜ：書き手が面白さに集中できるのは、自分の文が知らないうちに変わらないと分かっているからです。誰が書いた文かが分からなくなると、ユーザーは採るかどうかを決められません。

## 2. 説明書を書いて渡す

### 2.1 説明書だけで書けるようにする

2026-11-08 に作った説明書は2本です。

- 「Ink で書ける新しい仕様（インド編のデートを考える人へ）」：新しいデートの筋と Ink の台本を頼む。渡したときは296行。
- 「通常シナリオを書き直すときの補足」：デート以外の場面（案内・観察・クイズ・道中交流・到着・エピローグ・差し込み）の書き直しを頼む。メインの説明書と一緒に使う。渡したときは317行。

どちらも「この文書だけで書けるように」書きました。そのためにしたこと：

- **頭に「使い方」の章を置く。** 頼むこと、印の意味（【今】は今のゲームで動く、【1】〜【6】は作っている途中の段階）、言葉の意味（場面・札・本筋・差し込み・時点）、ユーザーの方針（作者が自由に作れることがいちばん）。
- **読めないときの頼み方を書く。** 「リポジトリを読めるなら先に読む」として読む順を挙げ、「読めないなら、docs/09 の全文をユーザーに貼ってもらってください」と書きました。
- **書き手のものと、そうでないものを書く。** メイン：「あなたの文は下書きで、ユーザーが推敲して採ります」。補足：「本番の文は、ユーザーが採るまで変えない。書き直しは提案の下書きとして出してよい」。
- **食い違ったら、どちらに従うかを書く。** 補足の頭：「2つが食い違うときは、この補足を優先してください」。
- **出してほしいものを並べる。** デートの一覧、各デートの筋、Ink の台本、足りないデータの一覧（品物・フラグ・人物・出典メモなど）、確認の質問。
- **見本は架空の「見本の街」で、台詞は仮。** 見本の見出しには「インド編の台詞は使っていません。台詞は仮」と書きました。AI が書き手の台詞を書かないためと、見本の文がそのまま本番に入らないためです（見本の編は AGENTS.md の例外）。
- **決まるたびに直し、頭に書く。** その日のうちに決めごとが次々に入ったので、版を重ねました。頭の段落には、どの決めごとまで入れたかを書きました。問いが全部決まった後は、前の版で頼んだ「確認待ち」の印をもう書かないよう、書き添えました。

### 2.2 見本のInkはコンパイルし、全部の道を歩かせる

書き手は、説明書の見本を写して書きます。見本が組み立てられなければ、写した原稿も組み立てられません。だから、見本の Ink は、渡す前に本物の道具で確かめます。

メインの説明書の見本は、使い捨てのスクリプトで次のように確かめました（リポジトリには入れていません）。

1. リポジトリの `node_modules/inkjs` のコンパイラ（`inkjs/compiler/Compiler.js`）で組み立てる。頭の札を残した形と、外した形の両方で。
2. 場面ごとに、選択肢をすべての番号で選び、全部の道を終わりまで進める。`cond(…)` は、いつも真といつも偽の2回にする。
3. 頭の札が、頭の外（knot の行に続く札の並びの外）に出ていないか見る。

リポジトリに入った場面なら、`npm run content:build` が組み立てと全部の道の検査をします（[シナリオ改稿のポイント 5.3](SCENARIO_EDITING_GUIDE.md#53-検査)）。説明書の見本はリポジトリの外にあるので、自分で確かめます。

### 2.3 知らない書き手に試し書きしてもらう

説明書を書いた人は、書いていないことも知っています（[知識の呪い](SCENARIO_EDITING_GUIDE.md#21-知識の呪い画面に出たことだけで読む)）。だから渡す前に、この会話を知らないエージェントに説明書だけを渡し、短い下書きを書いてもらいました。

メインの説明書（試す前は253行）の試し書きで分かったこと：

- 書き手は、段階の印を札の行の後ろに書いた（`# scene: talk // 【3】`）。説明書が「新しい札の横には、動く段階をコメント `// 【4】` で添えてください」と書いていたからです。これでは頭の札の並びが切れ、後の札が頭の外になって、ビルドが止まります。小さな試しの Ink を本物のコンパイラで組み立てて確かめてから、「knot の行の**上の行**に、コメント `// 【4】` で書きます。頭の札の間や、札の行の後ろには書きません」に直しました。
- 書き手はキャラクターバイブルを読めず、下書きの頭に「キャラクターバイブル（docs/09）は読めていない。ヒロインの口調は推測。」と書いた。説明書の1章には、ヒロインの要点を抜き出してありました。要点だけで書けると思われないよう、「（1章の要点は、全文の代わりになりません）」と足しました。

補足（317行）の試し書きでは、大きな問題2つと小さな問題18が見つかりました。試しの下書きの最後には、説明書から分からなかった所が「未確認」として並んでいました（背景をどこで宣言するか、クイズの相手に人物の登録が要るか、など）。どれも、説明書に足すべきかを見る所です。

試し書きとは別に、説明書の文が今のコードと合っているかも照らしました。補足では、大きな問題3つと小さな問題14が見つかりました。両方を直してから、ユーザーに渡しました。二つは見つけるものが違います。試し書きは「分かりにくい・抜けている」を、照らし合わせは「書いてあることが違う」を見つけます。

頼み方：

- 渡すのは、本物の書き手が受け取るものだけ（説明書と、渡す予定の資料）。会話の流れは渡さない。
- 短い下書きを頼む。分からなかった所と、推測した所を、下書きに書いてもらう。
- 下書きの間違いは、試した人ではなく説明書の誤りとして読む。直す前に、本当にそうなるかを小さな Ink で確かめる（2.2）。

作っていない人に試してもらう考え方は、ミニゲームの試遊と同じです（[ミニゲームの手応えの作り方と確かめ方 5章](MINIGAME_FEEL_GUIDE.md#5-作っていない人に試遊してもらう)）。

### 2.4 書いてみると、仕組みの穴が見つかる

補足を書き手の目で書いていくと、仕組みで決まっていない所が出ました。補足の見直しで1つ足し、合わせて8つです。どれも、書き手が書こうとすると迷う所でした。

1. 推理クイズで違う資料を出したとき、もう一度選べるか、次の問いへ進むか
2. 到着とエピローグの選択、到着の `# then:`、到着で話す人
3. 案内の「とばす」は、読んだことになるか
4. 場面の長さの上限
5. デート以外の噛み合い（`# profile:`）と `romance_result`
6. 今の形のファイルで `cond` を使うとき
7. 1つの選択の場に、選択肢を4つ以上
8. 人物に「会った」は、いつからか

1問ずつ「決まったこと（おすすめ）／ほかの案／理由／見本の街の例」の形で並べました。おすすめは第一原則に合わせ、「作者が Ink で決める」側を選びました。例：1は、外れたときの文の後に `-> stop` の1行を書けばもう一度選べる。書かなければ次の問いへ進む。ユーザーの答えは「全部おすすめで (Recommended)」でした（2026-11-08）。決まったことは説明書にも入れました。

旅の中身の問い（ミラノに到着の会話を足すか、インド編の文をどこまで書き直してよいか、など）は別の節に分け、おすすめを付けませんでした。中身は、ユーザーと書き手が決めることだからです。

説明書を書くことは、仕組みの点検にもなります。書けない所が出たら、説明書の文でごまかさず、問いにしてユーザーに出します（問いの形は [AIと決めごとを進める型 3章](DECISION_GUIDE.md#3-聞き方番号おすすめ理由)）。

## 3. 原稿を受け取る

### 3.1 早めに、読み取りだけで点検する

2026-11-08、ユーザーが原稿の zip を送ってきました。

> インド編のシナリオデート改稿版です 実装してもらいたいです タイミングは任せますが、内容のチェックは早めに行ってください

届いたもの：README・DATA.md・データの下書き（`data/*.draft.json`）・書き手の検査の道具、本筋（場所のファイル15本と、クイズの場面の写し4本）、デート（18本と宿の屋上の3本）、差し込み（13本）。README の8章には、書き手のチャットでユーザーが答えた13の答えが書いてありました。

進め方：

- **受け取った版は、読み取りだけの所に広げて、触らない。** 直しは別の写しに入れる。受け取った版が届いた zip と一字も同じかを、チェックサムで確かめる。直す前の写しも残す。
- **点検は、受け取った日に始める。** 実装は後でよい（「タイミングは任せます」）。1回目の点検で出した11の問いには、同じ日にユーザーが答えました。

なぜ読み取りだけにするのか：

- こちらが変えた所を、一行ずつ示せる（3.4）。
- 報告の「ファイル:行」が、書き手の手元の行と同じになる。
- 次の版が届いたとき、届いた版どうしを比べられ、こちらの直しを入れ直せる（3.5）。

なぜ早めにするのか：早いほど、書き手は次の版に取りかかれます。ユーザーにしか答えられない問いは、答えが出るまでに時間がかかります。

### 3.2 何を確かめるか

1回目の点検で見たことです。

- **組み立てと道**：Ink 43本が誤りなく組み立てられた（README には「まだ組み立てていない」とあった）。どの選び方をしても、話は最後まで進む。
- **移した所**：本筋の形の移し替えは、597行を1行も変えずに移せていた。
- **出典**：50件、どれも実在するページだった。
- **今のゲームとの照らし合わせ**：新しいデート6本の下書きに、もう消すと決めた欄 `actionLabelJa` が残っていた。地図に出す登録もなかった。どちらも、実装のときにこちらが手当てする所として書いた。
- **場面の順番**：どの順で流れても合うか（宿の夜と朝の場面）。
- **事実**：言い過ぎが2つ（バーブルが褒めたもの、マリアムの「四百年」）。
- **人物**：キャラクターバイブルと照らす（ヒロインの同意、関係の距離が浅いときの振る舞い）。
- **決まりとのぶつかり**：満たさない `# requires:` の選択肢が灰色で出ると、隠している恋の段階が遊ぶ人に分かってしまう。

原稿をリポジトリの写しに入れた後は、`npm run content:build` の注意に加えて、`npm run text:check`（文の決まりの注意）と `npm run sources:check`（出典の題）も流します。文の読み方は [シナリオ改稿のポイント 2章](SCENARIO_EDITING_GUIDE.md#2-直す所と直し方) です。

### 3.3 報告は、書き直さずに出す

1回目の報告の頭には、こう書きました。

> パッケージのファイルは一字も変えていません。写しを作って調べました。
> 文はあなたのものなので、私たちは書き直していません。下の「案」は提案だけです。入れるのは、あなたが良いと言ったものだけです。

報告の形：

- **まとめ**：全体の印象（良い所も書く）と、数の表。ほかの見方の指摘と重なるものは、1つにまとめて数えました。

  | 種類 | 数 |
  | --- | --- |
  | 直さないと動かない所 | 0 |
  | 決めてほしいこと | 11 |
  | 直したほうがよい所 | 11（書き手の文が8つ、実装のときにこちらが足すデータが3つ） |
  | 小さな直し | 49 |

- **決めてほしいこと**：1つずつ「今のこと・おすすめ・ほかの案・理由」。頭に「すべておすすめで」でもよい、と書く。
- **直したほうがよい所・小さな直し**：所（ファイル:行）・今の文・問題・方向。
- **読むのはユーザー**：ID と「ファイル名:数字」の意味を、頭で説明しました。

ユーザーは11の問いに1つずつ答えました。問い4の答えは、1つの場面を超えて、仕組みの決まりになりました（[表現の道具を足すときの考え方 2.2](EXPRESSION_TOOLS_GUIDE.md#22-1つの場面の困りごとを全部の場面の決まりにする)）。点検の問いは、仕組みを決める入口にもなります。

### 3.4 札の直しはこちら、文の直しは書き手へのメモ

直しは二つに分けます。

| | 札・条件だけで直せるもの | 文が要るもの |
| --- | --- | --- |
| 直す人 | こちら（自分の写しに入れる） | 書き手（メモで頼む） |
| 1回目の例 | お腹を壊した夜の場面の頭に `# until: seen gt_delhi_hotel_sick_morning` を足す（翌朝の場面が先に流れたら、前の夜の場面を出さない）。駅の正面とホームで `# background:` を分ける。告白の前置きの、背中の字の条件の行3つ | 告白の前置きを、告白の結果で分ける（断る・「待って」の道でも、彼女から屋上に誘っていた） |
| 残すもの | 一覧（ファイル:行〔元 → 写し〕・前 → 後・理由・報告の番号） | メモ（下） |

札の直しの後は、文が一字も変わっていないことを確かめます。届いた版と写しの差から、札・コメント・空行のほかに変わった行だけを出します。

```sh
diff -ru -U0 -x '*.json' -x '*.md' -x '*.py' <届いた版> <こちらの写し> \
  | grep -E '^[-+]([^-+]|$)' \
  | grep -vE '^[-+] *(#|//|$)'
```

1回目の写しで出たのは、一覧に書いた条件の行3つ（前と後で6行）だけでした。

書き手へのメモ（2026-11-08 の「文の直しのお願い」）の形：

- 頭に、ユーザーの答えをそのまま引く（どれを採ったか）。
- 文を書く必要があるものだけを頼む。
- 「『方向』は案で、『例』も言い回しの一例です。言い方は自由に決めてください」と書く。
- 【採用】（ユーザーが採ると答えたもの）と【任意】（このままでもよいもの）の印を付ける。
- 「ファイル:行」は、書き手が送った元の版の行で書く。
- メモはユーザーが運ぶので、それだけで読めるように書く。

札では直せないこともあります。2回目の点検では、メヘンディの夜の色の順番について「札だけでは直せません。夜の場面を閉じると、「明日にする」の続きも消えるためです」と書き、書き手に頼みました。札で直すと別の道の文が消えるなら、それは文の直しです。

分けておくと、答えが変わっても動きやすくなります。小さな直しについて、ユーザーは「5.の小さな直しは、できれば直さないで欲しい」と答えた後、「ごめん、5はやっぱり直す」と変えました。札だけのものは写しに入れ、文の要るものはメモに足して済みました。

### 3.5 ユーザーが採った文の変更は、別に記録する

2回目の版で、書き手は変更の一覧（CHANGES.md）の8章に問いを2つ書きました。その一つは、ユーザーが書いた本筋の文（アーグラの宿の部屋）を変える提案でした。ユーザーは、その提案を採りました（2026-11-09）。

こちらは、この変更を写しに入れ、札の直しとは別に「ユーザーが採った文の変更」として記録しました。3回目と4回目の版は、本筋のフォルダが前の版のままで、この文が入っていませんでした。毎回入れ直し、前の写しと一字も同じかを確かめました。4回目の報告には「入れないと、リポジトリに入れた文が古い文で上書きされます」と書いています。

だから、文の変更をこちらの写しに入れたときは、どの文を、誰がいつ採ったか、どのファイルの何行かを一覧にします。次の版が届くたびに、入っているかを確かめます。

## 4. 次の版と、点検の終わり方

### 4.1 前のメモの項目ごとに確かめる

2〜4回目の点検では、前のメモの項目を1行ずつ並べ、直ったかを書きました。4回目の表の一部：

| 前のメモの項目 | 結果 |
| --- | --- |
| メヘンディの夜（朝の後の「分からない」） | 直った（3か所。64通りのうち36 → 0） |
| 【任意】挑み直しの一文（3都市） | 直った（断る返事の後でも通る） |
| 【任意】フラグの行 | 直った（27か所。ずれ0） |

書き手の変更の一覧も、差と照らします。4回目の一覧（CHANGES_v4.md）は正確で、ずれは README の行の範囲が1つ（「222–232」は本当は 222–231）だけでした。変わったファイルも数えます（3回目から4回目では10本）。

確かめ直しの形は、ミニゲームの試遊と同じです（[ミニゲームの手応えの作り方と確かめ方 5.4](MINIGAME_FEEL_GUIDE.md#54-前の指摘を1つずつ確かめ直す)）。直した所の近くに、新しい問題が出ていないかも見ます。

### 4.2 任意の指摘だけになったら終える

| 版 | 点検した日 | 動かない所 | 直したほうがよい所 | 小さな直し・任意 |
| --- | --- | --- | --- | --- |
| v1 | 2026-11-08 | 0 | 11（ほかに決めてほしいこと11） | 49 |
| v2 | 2026-11-09 | 0 | 3（書き手へ2、こちらの条件1） | 10 |
| v3 | 2026-11-09 | 0 | 1 | 任意4 |
| v4 | 2026-11-09 | 0 | 0 | 任意1 |

4回目に残ったのは、同じ言い方が近くで続く、という任意の1つだけでした。報告の最後には、決めてほしいことを1つだけ書きました。任意のメモを書き手に渡すかどうかです。渡さないなら、今の写しで実装に進む。渡すなら、次の版をまた確かめる。ユーザーの答えは「メモは渡さず、work4で進めましょう」でした（2026-11-09）。翌日、#36 と #38 でゲームに入りました。

なぜ、ここで終えるのか：

- 任意の指摘は、直さなくても遊びに関わらない。
- 一回ごとに、書き手が直し、ユーザーが運び、こちらが確かめる手間がかかる。
- 新しい版は、新しい食い違いを持ち込むことがある（3.5 の部屋の文）。

終えるかどうかは、ユーザーが決めます。AI は、渡すときと渡さないときに何が起きるかを書いて聞きます。

### 4.3 AIが出した言葉も確かめる

こちらのメモの言葉は、書き手の文に入ります。だから次の版では、こちらが勧めた言葉も、書き手の文と同じ目で確かめます。

- 1回目のメモで、こちらは動物の名前「インドレイヨウ」を勧めた。2回目の点検で確かめると、この名前は確かめられなかった（ja.wikipedia では「インドカモシカ」）。報告に「こちらの誤り」と書き、書き手に直しを頼んだ。
- 2回目の点検では、ジャイガル砦の注の日付の書き方の元が、前のメモのこちらの書き方だと分かり、そう書いた。
- 3回目の点検で見つけた「分からない」の一文は、1回目からあった文だった。報告に「前のメモで、こちらが見落としていました」と書いた。

自分の誤りと見落としは、隠さずに報告に書きます（[AIと決めごとを進める型 10章](DECISION_GUIDE.md#10-報告のしかた)）。事実の確かめ方は [調べものの落とし穴集 1章](RESEARCH_PITFALLS.md#1-三つの約束) にあります。
