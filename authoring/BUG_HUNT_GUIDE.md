## 1. 調べる順番

1. どこで見たか（公開版・作業版・Debug）を確かめる（2章）。
2. 画像があれば、いつの画面かを確かめる（3章）。
3. 本番と同じ形で再現する（4章）。
4. 失敗が「どこの何か」を一文で言う（5章）。
5. CI だけなら、成果物 → 字体 → CPU → 機械の順に見る（6章）。
6. 直したら、落ちた形と同じ形のテストを足す（10章）。

**なぜ順番を決めるか。** 安く確かめられることから見ると、違う所を直さずに済みます。2026-11-08 の CI の失敗では、手元で30回流しても通り、CPU を4倍・6倍遅くしても通りました。CI の字体にしたら、10回とも同じ失敗が出ました（6章）。遅さから疑っていたら、時間の枠を広げるだけで、本当の原因（押す点が画面の外）は残りました。

## 2. どこで見たかを確かめる

同じ「おかしい」でも、見ている形で答えが変わります。

| 形 | 何か | 気をつけること |
| --- | --- | --- |
| 公開版 | `main` に合流し、GitHub Pages の公開が終わった版 | 直しが作業の枝にあるだけなら、まだ変わっていない |
| 作業版 | 作業の枝、合流前の PR、手元の開発サーバー | 全部の旅行編を読む。本番とは読み方が違う（4章） |
| Debug | Debug モードがオンの端末。公開版でもオンにできる | 遊ぶ人には出ない表示が出る（[Debugで確かめる手引き 6章](DEBUG_CHECK_GUIDE.md#6-出ない理由を読む)） |

**例：「まだ行けません」は2回あった（2026-11-13）。**

- 1回目：公開版が古かった。直しは作業の枝にあり、まだ公開していませんでした。
- 2回目（20:46）：ユーザーの言葉は「まだ行けません　デリーの観光を一つ終えてから　というのが未だに出ています　これは修正したのでは？」。これは鍵のかかったデートの札（`# hint:`）で、Debug モードがオンの間だけ出る決まりです。遊ぶ人には出ません。そう答え、遊び方の資料も直しました（474be0a）。

どちらも、ゲームを直す必要はありませんでした。形を確かめずに直し始めると、同じ所を2回直すことになります。

**聞く前に、自分で調べられることを調べる**（[決め方の手引き 5章](DECISION_GUIDE.md#5-聞く前に調べる)）。

- 直しの PR が合流したか：`gh pr view <PRの番号> --json state,mergedAt`。Claude Code の作業環境では `gh pr view` が通りません（GraphQL が止められている。2026-11-16 に確かめた）。そこでは `gh api 'repos/{owner}/{repo}/pulls/<PRの番号>' --jq '{state: .state, merged_at: .merged_at}'` で見ます。squash で合流するので、作業の枝のコミットの SHA では `main` を探せません。
- 公開が終わったか：`gh run list --workflow pages.yml --limit 3`
- 見えている物が Debug だけの表示か：[Debugで確かめる手引き 6章](DEBUG_CHECK_GUIDE.md#6-出ない理由を読む) と、その表示を出すコード。

公開の後は、ページを一度読み込み直してもらいます。ページはネットワークを先に見るので、読み込み直すと新しい版になります（[技術設計「読み込みを速くする工夫」](../docs/02_TECH_ARCHITECTURE.md#読み込みを速くする工夫)のサービスワーカー）。ただし「オフラインで遊ぶ」で旅行編を端末に入れている人は別です。その端末は入れた版を開き、新しい版は、通信があるときに変わった分を入れ終えた次の起動から出ます（変わった分が約30MBより大きいときは、「オフラインで遊ぶ」の「新しい版の分を入れる」を押してもらいます）。強制の再読み込み（Shift を押しながら再読み込みなど）でも同じです：サイトの新しい版が一瞬出ても、すぐ入れた版に戻ります。直ったかをすぐ確かめてもらうときは、通信のある所でページを2回開いてもらうか、「端末から消す」を押してから読み込み直してもらいます（[技術設計「オフラインで遊ぶ」](../docs/02_TECH_ARCHITECTURE.md#オフラインで遊ぶ)）。

調べても分からないときだけ、番号で聞きます。「1. 公開版　2. 手元の開発サーバー　3. Debug モードがオン」。

## 3. 画像が「いつの画面か」を確かめる

画像は、ある一瞬しか写しません。操作の前か、途中か、後かで、読み方が逆になります。

**例：スワイプしても始まらない（2026-11-13）。**

- ユーザー（20:53）：「観光地カードを上にスワイプしても始められない、なぜ？」と、画像が1枚。
- AI の最初の答え：「上の列の真ん中が空いています。…スワイプする対象のカードが消えているので、始められないのだと思います。」
- ユーザー（20:58）：「いいえ、これはジャーママスジドのカードを上にスワイプしたあとの画像です　カードを上に飛ばした後、ストーリーへ遷移されなかったという不都合報告です」

AI は、操作の前の画面だと読み違えました。空いていた所は原因ではなく、**不具合の結果**でした。出発の処理が失敗し、飛ばしたカードが戻らなかったのです（4章）。

- 画像を読む前に、「これは◯◯した後の画面ですか」と一文で確かめる。答えが要らないほど明らかなら、自分の読み（「◯◯の後の画面として読みます」）を一文書いてから答える。
- 画像の中のおかしな所（空き・止まった絵）は、不具合の跡のことが多い。原因と決めつけず、「その直前に何をしたか」を聞く。

## 4. 本番と同じ形で再現する

開発サーバーと単体テストは、全部の旅行編のデータを読みます。本番のページは、**開いた旅行編の分だけ**を読みます（[技術設計「読み込みを速くする工夫」](../docs/02_TECH_ARCHITECTURE.md#読み込みを速くする工夫)）。この違いの所でだけ起きる不具合があります。

**例：スワイプの不具合の原因（a365529、#127）。** インド編を開いたページ（最後に開いた旅行編が開いたとき、または読み込み直したとき）で、観光地への出発のたびに、ミラノ編の場面の場所を読もうとして「Unknown city: milano」で止まっていました。開発サーバーとテストは全部を読むので、誰も気づきませんでした。直したのは2か所です。

- `src/domain/encounter.ts`：読み込んだ都市の場面だけを見る。
- `src/features/journey/useCardGestures.ts`：出発が失敗しても、飛ばしたカードを戻す。

| 形 | 読む旅行編 | 見本の編 | 準備中の旅行編の写真 | Debug |
| --- | --- | --- | --- | --- |
| 開発サーバー（`npm run dev`） | 全部 | なし（`npm run dev:sample` ではあり） | あり | `?debug` でいつも開く |
| 単体テスト | 全部 | あり | — | — |
| 本番（公開版、`npm run build` の後の `npm run preview`） | 開いた旅行編だけ | なし | なし | Debug モードがオンの端末だけ |

再現するときにそろえるもの：

- 本番の形：`npm run build` の後に `npm run preview`（[Debugで確かめる手引き 1.2](DEBUG_CHECK_GUIDE.md#12-公開版本番ビルドで)）。E2E なら本番ビルドの段（`npm run test:e2e:prod`）。
- 開いている旅行編と、そこへの入り方（新しく選んだか、読み込み直したか）。
- 画面の大きさ（例：390×844、320×568）と、Debug モードのオン・オフ。
- モンキーで見つかった失敗は、ログの種（`MONKEY_SEED`）で同じ押し方を繰り返す（[開発時の確認「探索テスト」](../docs/10_DEVELOPMENT_CHECKS.md#探索テスト)）。

ユーザーの「なぜ？」には、本番の形で再現してから答えます。再現できないうちの答えは、推測だと書きます。

## 5. 失敗が「どこの何か」を先に言う

2026-11-14 08:55、ユーザーは「最後のCA bundle ssetのテストが失敗してるのは何？確かめて」と頼みました。調べると、これは写真を探す担当（AI）の Commons の検索が1回失敗したもので、**ゲームのテストではありませんでした**。同じ日の単体テストには、本当の失敗も1つありました。新しく足した写真の権利の検査に、テストの仮の写真が合っていなかったのです（38f663b）。

失敗を見たら、直す前に、出どころを次のどれかに分けます。

| 出どころ | 見分ける手がかり | 例 |
| --- | --- | --- |
| ゲーム | 本番の形でも、遊ぶ人の操作で起きる | スワイプの出発（a365529） |
| テスト | テストの前提（字体・時間・数）が外れた。ゲームは仕様どおり | CI の字体で押す点が外れた（0416942） |
| 生成のしかた | 見本の編なしで生成して、見本を読むテストを流した | 「Unknown city: mihon」（7章） |
| 機械 | ランナーが始まらない・止まった、ディスクがない、ブラウザの版が違う | PR #36（6.4） |
| テストでない道具 | 調べものの検索・通信。ゲームのコードを通らない | 「CA bundle」（2026-11-14） |

報告の初めの一文は、「どこで（ジョブ・ファイル）、何が、ゲームの不具合か、次に何をするか」にします。型と例は [決め方の手引き 10章](DECISION_GUIDE.md#10-報告のしかた) の「失敗を隠さない」です。

## 6. CIだけで落ちたとき

2026-11-08〜09 に、CI で落ちた回が6回ありました。どれも、PR ごとに単体テストと E2E が動いていた頃です。2026-11-10 からは、PR で動くのはビルドだけで、単体テストと E2E は Actions から手で動かしたときだけ CI で流れます（[開発時の確認「CI」](../docs/10_DEVELOPMENT_CHECKS.md#cigithub-actions)）。

| 日 | どこで | 原因 | 直したもの |
| --- | --- | --- | --- |
| 11-08 | E2E の Debug 起動台の段（PR #16） | CI の字体で、解説が1行多く折り返した。押す点が画面の外へ出た | テスト（0416942） |
| 11-08 | 同じ段の15件中9件（PR #17） | ランナーがいつもの約4倍遅く、1件30秒の枠を超えた | テストの時計の止め方と時間の枠（c50d31d） |
| 11-09 | E2E の合否判定の段（PR #29） | CI の字体で、選んだ行が下に伸びた | テスト（9786480） |
| 11-09 | ランダムウォークのジョブ（PR #29） | ランナーの停止の合図。テストの失敗ではない | 一度だけ流し直した |
| 11-09 | 単体テスト `scripts/journey-new.test.ts`（PR #35） | 見本の編の例がわざと出す注意が、`journey:new` で写した旅行編にも出た | テスト（d351b7f） |
| 11-09 | 単体テストの1/3と見本の編の段（PR #36） | ランナーが始まらなかった | 一度だけ流し直した |

6回とも、CI を通した直しは、テストの側か流し直しでした。ゲームの不具合ではありませんでした。ただし合否の基準は緩めません（[開発時の確認「期待値の決め方と直し方」](../docs/10_DEVELOPMENT_CHECKS.md#期待値の決め方と直し方)）。調べて分かった見え方の問題は、別に直します。PR #16 の後には、長い解説の始めが隠れる所を、画面の側でも直しました。

### 6.1 成果物（記録と画像）を見る

手元で流し直す前に、CI が残した物を見ます。見方は [開発時の確認「失敗したときの見方」](../docs/10_DEVELOPMENT_CHECKS.md#失敗したときの見方) にあります。

- 落とし方：`gh run download <実行の番号> -n e2e-<段の名前> -D <置き場所>`。中のトレースは `npx playwright show-trace <トレース>` で開きます。
- トレースで、押した点の座標と画面の大きさを比べる。PR #16 では、押した点が y=665.3、画面の高さが 664px でした。失敗の画像でも、ボタンが下で切れていました。
- ジョブの記録で、手順ごとの時間を、通った回と比べる。11-08 の遅い回は、開発サーバーの起動が93秒（流し直しでは23秒）、ライブラリの導入が54秒（同13秒）でした。これで「機械が遅い」と分かります。
- 単体テストは、記録の終わりに落ちたテストが出ます。同じ組を手元で流すなら `npm test -- --shard=<番号>/3` です。

### 6.2 CIの字体で流す

CI の機械（GitHub の Ubuntu）では、日本語の字が WenQuanYi Zen Hei になります。この開発の機械では IPA P ゴシックです。WenQuanYi は句読点を全角の幅で描くので、PR #16 では解説の高さが 404.2px から 432.2px になりました。そのぶん、ボタンが画面の外へ押し出されました。

手元で CI の字にするには、IPA P ゴシックと Inter を隠す設定を作り、`FONTCONFIG_FILE` で渡します。設定はリポジトリの外に置き、絶対パスで渡します（相対パスでは、fc-match が設定を読めませんでした）。

```xml
<?xml version="1.0"?>
<!DOCTYPE fontconfig SYSTEM "urn:fontconfig:fonts.dtd">
<fontconfig>
  <include ignore_missing="yes">/etc/fonts/fonts.conf</include>
  <selectfont>
    <rejectfont>
      <pattern><patelt name="family"><string>IPAPGothic</string></patelt></pattern>
      <pattern><patelt name="family"><string>Inter</string></patelt></pattern>
    </rejectfont>
  </selectfont>
</fontconfig>
```

- 隠せたかを確かめる：`FONTCONFIG_FILE=<設定> fc-match IPAPGothic` が `DejaVu Sans` を、`FONTCONFIG_FILE=<設定> fc-match 'sans-serif:lang=ja'` が `WenQuanYi Zen Hei` を返せば隠れています。機械によって入っている字は違うので、毎回確かめます。
- 確かめた範囲：上の設定は、記録をもとに 2026-11-16 に書き直したものです。この機械で確かめたのは、fc-match の2つだけです。この設定で E2E は、まだ流していません。11-08 から後の E2E では、同じく IPA P ゴシックと Inter を隠す設定を使っていました（そのファイルは残っていません）。
- 流す：`FONTCONFIG_FILE=<設定> npx playwright test tests/e2e/<ファイル> --repeat-each=10`。PR #16 では、IPA P ゴシックを隠す設定で流し、10回とも CI と同じ失敗が出ました。
- 座標で押すテストを足したときも、一度この字で流します。PR #29 も、同じ字体の差でした。

### 6.3 CPUを遅くして流す

字体で再現しないときに、遅さを疑います。Chromium だけですが、CDP でページの CPU を遅くできます。一時の写し（`git archive HEAD` を展開したフォルダなど）の共通部品に足し、コミットしません。ポートはほかと重ならない番号にします（[AIへの頼み方の手引き 6章](AI_DELEGATION_GUIDE.md#6-ディスクポート重いコマンド)）。

```ts
const cdp = await page.context().newCDPSession(page);
await cdp.send("Emulation.setCPUThrottlingRate", { rate: 4 });
```

- 確かめた範囲：この2行は、11-08〜09 に一時の写しで使ったしかけ（テストのページごとに CPU を遅くする）と同じ呼び出しです。この形のまま流しては、確かめていません。

- 倍率は、CI の遅さに合わせる。11-08 の遅い回（約4倍）は、手元の4倍で、推理クイズ（B・C）を遊ぶ2件が CI と同じく30秒の枠で時間切れになりました。6倍・4ワーカーでは3件が落ち、さらに厳しくなります。
- 効いたかを確かめる。同じ空回しの時間が、6倍で約16〜26ミリ秒から約108〜111ミリ秒になりました。
- 直す向き：時間で待たず、画面の状態や保存のリビジョンで待つ（[失敗したときの見方](../docs/10_DEVELOPMENT_CHECKS.md#失敗したときの見方)の4）。長い流れは、理由を書いて枠を120秒までにする（[不安定さと時間の決まり](../docs/10_DEVELOPMENT_CHECKS.md#不安定さと時間の決まり)）。11-08 には、時刻を読んでから時計を止めるまでに1.5秒の間を入れると、時計のテスト7件が「Cannot fast-forward to the past」で落ちることを確かめてから直しました（c50d31d）。

### 6.4 機械の不調なら、一度だけ流し直す

ランナーが始まらない（「abandoned」）、停止の合図で止まった、テストまで届いていない。こうした記録なら、テストの失敗ではありません。落ちたジョブを**一度だけ**流し直します。

- PR #36 では、一度流し直し、同じ組（1/3）を手元でも流しました（73ファイル・722件が通過）。PR にそう書きました。
- 二度目も同じ所で落ちたら、機械のせいではありません。6.1 に戻ります。
- テストが落ちたのを、流し直して通ったことにはしません。E2E は再試行しない決まりです（`retries: 0`。[不安定さと時間の決まり](../docs/10_DEVELOPMENT_CHECKS.md#不安定さと時間の決まり)）。

## 7. 手元の機械で落ちるとき

手元の失敗には、ゲームともテストとも関係のないものが多くありました。報告には「ゲームの不具合ではない」と書きます。

- **重いときだけ落ちる。** 機械が重くて時間切れになり、そのテストだけなら通る、が 11-05〜11-08 に4回ほどありました。まず、そのテスト1つだけで流し直します（`npx vitest run <ファイル>`、`npx playwright test <ファイル>`）。結果と一緒に、そのときの重さ（`uptime` の数字）を書きます。1つの時間切れが、続くテストまで落とすこともあります。そのときは、最初に落ちた1つだけを見ます。1つだけなら通っても、遅い CI では落ちうる待ち方なら、6.3 で再現して直します。1つだけでも落ちるなら、重さのせいではありません（5章に戻る）。
- **ディスクがない。** `ENOSPC` や `ERR_INSUFFICIENT_RESOURCES` は、空きの不足です（[AIへの頼み方の手引き 6章](AI_DELEGATION_GUIDE.md#6-ディスクポート重いコマンド)）。
- **ブラウザの版が違う。** Playwright 1.64.1 が求める chromium_headless_shell-1248 がなく、1243 しか入っていない。これが 11-08 に4回ありました。手元にある別の版の Chromium を `DREAMSCAPE_CHROMIUM` で渡します（[開発時の確認「E2Eの段」](../docs/10_DEVELOPMENT_CHECKS.md#e2eの段) の実行の表）。
- **見本の編がない。** 「Unknown city: mihon」は、見本の編なしで生成してから単体テストを流した印です（11-14〜11-16 に5回。2026-11-15 には38件）。`npm run test:with-sample -- <ファイル>` で流します。見本入りで生成して流し、落ちても見本なしで生成し直します（2026-11-16 から。手で行うときは [AIへの頼み方の手引き「見本の編の生成」](AI_DELEGATION_GUIDE.md#見本の編の生成) の手順）。

## 8. 中身を足したら落ちやすいテスト

台本を長くした、ゲームを足した、検査を足した。そのときは、数や時間を決め打ちしたテストを先に見ます。

| 足したもの | 落ちたテスト | 直し |
| --- | --- | --- |
| ミニゲームが11本になった（11-13） | `tests/e2e/minigames.spec.ts`：全部を通す確認が、CI で固定の2分を超えた（1本約11秒） | 30秒＋1本20秒に（fef54b5） |
| デリーの到着の台詞を分けた（11-14） | `src/domain/city-arrival.test.ts`：20行の輪の見張り | 見張りを緩めた。終わらない輪を止めるだけの枠（0082bbe） |
| 写真の権利の検査を足した（11-14） | `src/content/content.test.ts`：仮の写真に同じライセンスの一文がない | 仮データに一文（38f663b） |
| 見本の編の `then: epilogue` の例（わざと注意が出る。PR #35、11-09） | `scripts/journey-new.test.ts`：写した旅行編にも同じ注意が出た | 見本のほかの例と同じに除く（d351b7f） |

- 数は、その旅行編・都市の範囲で数える。全旅行編の合計を書かない（[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md) の初め、`scripts/journey-folders.test.ts` の段落）。
- 時間の枠は、中身の数から決める（fef54b5 の形）。
- 検査を足したら、同じ変更でテストの仮データも合わせる。

## 9. 実機でしか分からないこと

手元の WebKit は Linux 版で、本物の iPhone とは同じではありません（[開発時の確認「WebKit」](../docs/10_DEVELOPMENT_CHECKS.md#webkit)）。たとえば iPhone は、最初のタップの後でないと読み上げを始めません（2026-11-14、英語の自動の読み上げ）。

- 実機での確かめは、**3点ほどに絞って**ユーザーに頼む。例は [決め方の手引き 10章](DECISION_GUIDE.md#10-報告のしかた) の読み上げの3点です。
- 1点ごとに、「どこで何をするか」「どう見えればよいか」を書く。違ったら、画像と、見た形（2章）を送ってもらう。
- 答えが来るまで、報告の「確かめていないこと」に残す。

## 10. 直したら、同じ形のテストを足す

落ちた形と同じ形で確かめるテストを足します。いつものテストの形では、その不具合は見えなかったからです。

- 本番の読み方で起きた → 本番の読み方のテスト。`src/domain/one-journey-content.test.ts` は、ほかの旅行編の分を外して、本番のページと同じにします。そのうえで、最初の街歩きのすべての行き先へ出発します。直す前は「Unknown city: milano / mihon」で落ちました（a365529）。
- CI の字体で押す点が外れた → 押す前に、その点に目当てのボタンがあるかを確かめる（0416942。押す前に見える所まで流す）。
- iPhone の Safari がクリックを送らないことがある → 周りの暗い所で閉じる確認に `@smoke` も付け、WebKit の段でも流す（`tests/e2e/dialog-backdrop.spec.ts`、#133）。

足したテストは、直す前の形で落ちることを一度見ます。守りたい所をわざと壊して確かめるやり方は [「前と同じ」を確かめる手引き 7章](SAME_AS_BEFORE_GUIDE.md#7-テストを足したら守る所を1つ壊す) にあります。新しい E2E は `--repeat-each=3` で3回通してから入れます。

直したら、同じ型の所をほかにも探します（[横の点検 3章](SWEEP_CHECK_GUIDE.md#3-直した後にも同じ型を探す)）。新しい確かめ方は、[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md) の表にも1行足します（a365529 は「読み込み」の行に足した）。
