# 没入感を上げる進め方（見本の画面と iPhone から直す）

ユーザーが「この画面のほうが入り込める」と見本の画面を見せたとき、または iPhone で遊んで「ここが気になる」と画面の写しを送ったときの進め方です。主に、開発する人と AI のエージェントに向けて書きました。ユーザー（作者）が読んでも分かるようにしてあります。

- 元にしたのは、2026-11-25 の1日の作業です。恋愛ゲームの会話画面とゲームの会話画面を iPhone で比べたことから始まり、会話・街歩き・クイズ・夜の画面まで直しました。いくつかの会話（チャット）が同時に進めました（2章）。
- 決まった見た目は [デザインの決まり](../docs/14_DESIGN_RULES.md)、画面ごとの仕組みは [技術設計の「UX/スマホ」](../docs/02_TECH_ARCHITECTURE.md#uxスマホ)（「会話の窓」など）にあります。ここには写しません。
- 画面を大きく作り直すとき（部品の一覧を作り、番号つきの問いで決める）は [画面を作り直す進め方](UI_REDESIGN_GUIDE.md) を使います。この手引きは、できている画面の見え方を、見本と実機の感想から少しずつ直す進め方です。

## 1. 流れ

1. 見本の画面と今の画面を並べ、違いを表にする。効いている順に並べる（4章）。
2. 前に決めたこと（docs・コードのコメント）と食い違う所を探し、ユーザーに聞く（5章）。
3. 作る。見た目の値は、デザインの決まりの名前で書く（7章）。
4. 同じ場面を、前と後で撮って比べる（6章）。
5. PR を出し、自動の確認が通ったら squash で取り込む。聞かずに進める（[AGENTS.md の「開発の進め方」](../AGENTS.md)）。
6. ユーザーが iPhone で見る。感想が来たら、1つずつ小さな PR で返す（9章）。
7. 決まったことを docs に書く。次の会話は、この会話を読めないからです。

## 3. 没入感の考え方

1日で決まったことを、次に直すときの考え方として並べます。くわしい形は docs/02 にあります。

- **場面が主役。UI は場面の上に浮かべる。** 濃い板の窓は、場面をそこで終わらせていました。窓・札・カードは明るいすりガラスにし、縁の線をなくして端を場面に溶かし、影は淡くします。ぼかすのは窓の後ろだけで、写真そのものには手を加えません（出典どおりの画素）。
- **人物との距離を近くする。** 全身を小さく出すのは「人物紹介」の構図です。会話では腿から上まで寄せます。最初の行だけ全身を見せ（服と立つ所）、次の行で寄ります。寄せても頭が上の帯の下で切れないよう、絵の上端を全身のときの高さに保ちます（目の高さで保ったら帽子が切れた。#221）。
- **誰が話しているかを、位置と色で見せる。** 名前札は話している人の上に出し、その人の服の色にします。右の人が話しているのに札が左にあると、分かりにくかった（#221）。
- **操作は控えめに。** 隠す・ログ・高速送りは、地のない白い印にします。場所と時刻は会話の始まりに出し、5秒で薄れさせます。
- **同じことを二度言わない。** 名乗りの札と名前札が同じ名前を出して重なったので、名乗りは画面の上へ移しました（#221）。地の文の「旅の風景」の札、選択肢の上の「あなたは、どう返す？」もなくしました（#221・#229）。
- **場面を横切る強い色は使わない。** テラコッタの選択肢は目立ちすぎて、場面を横切りました。煙ったガラスに金の細い縁へ変えました（#229）。
- **読みやすさは数で守る。** 字と地の明るさの差（コントラスト）を計算し、すりガラスの上で8:1以上、名前札では後ろが黒でも白でも4.5:1以上にします。透けるものは、後ろが黒のときと白のときの両方で数えます。

見本から取り入れなかったものも残します。左端の色の線（AGENTS.md で禁止）、関係の値を見せる顔とゲージ（関係の状態は遊ぶ人に見せない決まり）、白くて平らなカード（仕事のアプリの見た目で、場面が消える）です。

## 4. 見本の画面との違いを言葉にする

ユーザーは「没入感が全然違う」と言いました。その「違い」を、作れる言葉に分けます。

- 今の画面と見本を、同じ種類の場面（1人・複数人・選択肢）で並べます。
- 違いを表にします。項目は、人物との距離、足もと、常に出ている UI、会話の窓の素材、窓の位置、選択肢、名前札でした。
- 効いている順に3つ選んで先に書きます。2026-11-25 は「寄りの構図」「UI の量」「窓の素材」でした。
- 見本の言葉を、ユーザーの言い方でも読みます。ユーザーは会話の窓を「ログ」と呼んでいました。分かりにくいときは、どう読んだかを返事に書きます。

**なぜ**：「没入感」のままでは作れません。違いを部品の言葉にすると、どれから直すかを一緒に決められます。

## 5. 前に決めたことと食い違うときは聞く

見本の形が、前のユーザー判断と違うことがあります。2026-11-25 は3つありました。

- 窓の操作の字は消さない（docs/02 の「会話の窓」）→ 印だけにしてよいか。
- 写真にフィルターをかけない（`line-stage.css` のコメント）→ 窓の後ろだけぼかしてよいか。
- 会話の間も場所と時刻を出す → 薄れさせてよいか。

探し方：変える部品の名前で docs/02 とその CSS のコメントを検索し、「ユーザー判断」「決定」の文を読みます。食い違う所は、提案と一緒に並べて聞きます。決まったら、その文を docs で直します（[AGENTS.md](../AGENTS.md) の第一原則）。

好みで決まるもの（字体・色）は、画像を見せて決めてもらうのが早いです。2026-11-25 の字体は、明朝 → Noto Sans JP → Zen Kaku Gothic New → Noto Sans JP と往復しました。

## 6. 撮って確かめる

- 場面は [Debug 起動 URL](../docs/10_DEVELOPMENT_CHECKS.md#debug起動url) で直接開きます。URL の最後に `&shot=1` を足すと、Debug の帯と印が消えて、遊ぶ人と同じ見た目になります。
  - デート：`?debug&shot=1&city=delhi&scene=date&target=gt_delhi_date_agrasen_baoli`（1人・3人・選択肢が続けて出る）
  - クイズの会話：`?debug&shot=1&city=delhi&scene=battle&target=gt_delhi_main_jama_masjid_battle`（2人と3人、名乗りが出る）
- 撮る大きさは 390×844 を基本に、320×568（低い画面）、1280×800（広い画面）、844×390（横向き）を1回ずつ見ます。全部の組み合わせは撮りません（[画面を作り直す進め方 4.3](UI_REDESIGN_GUIDE.md#43-測るのは決める前に一度)）。
- ユーザーに見せる画像は、画素の密度を2倍にして撮ります（Playwright の `deviceScaleFactor: 2`）。自分で確かめるだけなら1倍で足ります。
- 前と後は、同じ場面・同じ行で撮って横に並べます。前の画面は `git stash` で変更を外して撮れます（撮り終えたら `git stash pop`）。
- Playwright で行を進めるときに待つもの：
  - 旅の図鑑の小窓が出たら閉じる。
  - 名乗りの札は約2.4秒で消える。見たいときは、その行に来てすぐ撮る。
  - 場所と時刻の札は5秒で薄れる。
  - 最初の行は全身。寄った姿は2行目から。
  - 動きを減らす設定（`reducedMotion: 'reduce'`）で撮ると、途中の動きが写らない。
- 色を変えたら `npm run content:build` を流してから撮ります。人物の色は生成した内容から読むので、流す前は前の色のままです。生成した後に開発サーバーが止まっていることがあるので、そのときは起動し直します。
- 決まった値は、撮った画面からも測ります。例：名前札の縁取りの影は、計算では出ていても、細くて見えませんでした（#221）。3倍に拡大して撮って確かめ、太くしました。

## 7. デザインの決まりで書く

見た目は [デザインの決まり](../docs/14_DESIGN_RULES.md) で書きます（2026-11-28 に作り直しました：すりガラス、白と灰色だけ、Noto Sans JP、数値は1つの性質につき6種類まで）。値は `src/app/styles.css` の `:root` にあります。

- 字の大きさ・行の高さ・余白・字の太さ・字間・線の太さ・不透明度・影・角・色は、決まりの名前（`--ds-*`）で書きます。数字や色の値を直接書きません。
- 段階は足しません。合う段階がないときは、役目のいちばん近い段階を選び、それでも決まらなければユーザーに確かめます。
- 物そのものの色（携帯の本体、ミニゲームの絵）は、そのファイルの頭で一度だけ名前を付けます（例：`line-stage.css` の `--phone-body`）。藍・紺・金・羊皮紙は使いません。手紙・メモ・写真・SNS は紙として描かず、ガラスで出します。
- すべてのスタイルシートが決まりどおりかを、`src/app/design-tokens.test.ts` が確かめます。

**なぜ**：決まりができる前は、字の大きさが29種類、色の値が318種類ありました。#229 は選択肢の色を `--ds-action` の1か所で変え、5つの会話の画面の選択肢が全部そろって変わりました。

## 8. 人物の名前札の色を足す

名前札は、話す人の服の色で出ます。新しい人物を足したら、その人物の `nameBand` を書きます。

- 書く所：旅行編の `presentation/characters.json` の人物（ヒロインは `content/presentation/characters.json` の衣装ごと）。
- 形：`"nameBand": { "fill": "#918788", "edge": "#484448" }`。`fill` は服でいちばん目立つ色（札の地）、`edge` は次に目立つ色（札の縁取り）です。
- 選び方：インド編の67人とヒロインの衣装は、立ち絵の胴（上から22〜56%、左右の28〜72%）の色から、肌の色を除いて多い順に2つを取りました。服と違う色が出たら手で直します（例：ピンクの服の花嫁で黒が出た）。一覧の画像を作って、人物と色を並べて見ます。
- 字の色は、白か濃い灰色のうち読みやすいほうになり、読めない地は自動で少し暗く（明るく）なります（`src/components/name-band.ts` の `bandColours`）。書かなければ窓の青です。
- 書いたら `npm run content:build` と `npm run schemas:build`（入力補助のスキーマ）を流します。

## 9. iPhone の感想を、小さな PR で返す

ユーザーが iPhone で見て、画面の写しと一言を送ります。2026-11-25 は、#220 の後に8回ほどありました。

- 1回の感想を1つか2つのコミットにし、同じ PR に足すか、新しい PR にします。次にユーザーが見るとき、変わった所が1つにしぼれます。
- 言葉は、ユーザーの言い方のまま読みます。「被ってる」は「重なっている」とも「同じものが二つある」とも読めます。両方に当たる直し方（名乗りを上へ移して、重なりも二重もなくす）を選び、どう読んだかを書きます。
- 直し方の提案が違ったら、すぐ戻します。例：名乗りを名前札の場所に出して名前札を隠したら、「そうじゃなくて上に」と返ってきました。次の直しで、名乗りを画面の上へ移し、名前札を隠すのをやめました（#221）。
- 頼まれた所だけを直します。ほかに気づいた所（例：ヒロインのいない3人の並び）は、報告で「同じようにしますか」と聞きます。
- 直した画面を撮って、PR と返事に1枚付けます。

## 10. ほかの会話と同時に進めるとき

2026-11-25 は、同じ時間に別の会話も画面を直していました（#222・#227〜#229）。同じファイルを触るので、次のことを守ります。

- **始める前と push の前に、main を見る。** `git fetch origin main` の後、`git log HEAD..origin/main` で入った PR を読みます。別の会話が、同じ決まりや部品を変えていることがあります（例：#229 は、こちらが作った `--ds-action` の値を変えた）。前提が変わったら、それに合わせます。
- **競合しやすいファイル**：`docs/02_TECH_ARCHITECTURE.md` の「会話の窓」（長い1行の段落）、`src/app/styles.css` の `:root`、`src/features/romance/romance-scene.css`、`src/features/battle/battle.css`。
- **競合したら、main を作業用の枝に merge する。** rebase も force-push もしません。docs の競合は、両方の文を残します（こちらの段落と、相手が足した段落）。解いた後に `npm run content:build`、型の確認、変えた所のテストを流し、画面を1枚撮ります。
- **PR が「競合あり」の間は、自動の確認が走りません。** 取り込む前に PR の状態を見て、競合を解いてから確認を待ちます。
- **取り込んだら、作業用の枝を main にそろえます。** `npm run branch:after-squash -- <取り込んだ PR の最後のコミットの SHA>` が、枝を main に合わせ、前の履歴もつなぎます。次の push は上書きなしで通ります（[開発の手引きのコマンド](../docs/12_DEVELOPMENT.md#コマンド)）。2026-11-25 は `git checkout -B <枝> origin/main` と `git push --force-with-lease` でそろえましたが、このコマンドのほうが、消える物がないかを先に確かめます。
- **同じ部品を2つの会話で同時に大きく変えない。** 分けられるときは、ファイルごとに持ち主を一人にします（[AIに仕事を分けて頼む手引き 4章](AI_DELEGATION_GUIDE.md#4-ファイルごとに持ち主を一人)）。
- **決まったことは docs に書く。** ほかの会話が読めるのは、リポジトリの中身だけです。
