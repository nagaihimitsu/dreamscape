# 計ってから速く・軽くする

読み込み・生成・テストを速くしたいとき、配信する絵や本番に入れる物を軽くしたいときの手引きです。**主に開発者と AI エージェント向け**です。

- 新しい旅行編を足したとき、旅行編を公開するとき、「遅い」「重い」と感じたときに読みます。
- 元にしたのは、テストと生成の速さ（2026-11-06）、読み込みを速くする工夫（2026-11-13 #126）、立ち絵の軽い版（#127）、準備中の旅行編の写真を本番から外したこと（2026-11-16 #139）です。数字は、その日の記録とリポジトリのままです。
- 読み込みの工夫は、もう入っています。中身は [技術設計の「読み込みを速くする工夫」](../docs/02_TECH_ARCHITECTURE.md#読み込みを速くする工夫)、頼まれてから作るまでの流れは [調べて → 方法を決めて → 作る 8.4](RESEARCH_TO_BUILD_GUIDE.md#84-読み込みを速くする工夫2026-11-13-126127) にあります。この手引きは、次に同じ条件で計り直すために書きます。

## 1. 四つの約束

1. 直す前に、同じ条件で計る。どこで何秒・何バイトかかるかを数字にする。
2. 画質は、数値と目の両方で決める。
3. 本番だけ外す物は、生成のときに「外す一覧」を書く。前と後のファイル一覧を比べる。
4. 計った条件・数字・道具を残す。

なぜか。

- 遅いのは、遊ぶ人のスマートフォンです。開発の機械では速く見えます。遅い回線で計ると、最初の場面のヒロインが出るまで約18秒かかっていました。その間、遊ぶ人はヒロインのいない場面を見ていました。
- 計ると、どこが遅いかがはっきりします。単体テスト一式の待ち時間610秒は、1つのファイル（609秒）が決めていました。作業時間の72%は、会話の全分岐の検査でした（4章）。見当で直すと、効かない所を直してしまいます。
- 前と後を同じ条件で計らないと、直した効果か、機械の混み具合かが分かりません。
- 道具と条件が残っていれば、旅行編を足した後に流し直せます。後で「なぜ品質85か」と聞かれても答えられます。

## 2. 同じ条件で計る

### 2.1 そろえる条件

- 同じ機械、同じコア数で計る。ほかの重い仕事は止める（[AIに仕事を分けて頼む手引き 6章](AI_DELEGATION_GUIDE.md#6-ディスクポート重いコマンド)）。混み具合で数字は変わります。E2E の開発サーバーの段は、ほかの作業がほとんどない4コアで44件が約3分20秒、負荷の高い4コアでは38件でも3分〜3分50秒でした（[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md) の E2E の表）。
- 「前」は、直す前のコミットのきれいな作業木で計る。2026-11-06 は 560bbdc で計りました。
- 同じものを3回ずつ計り、幅で書く（例：`content:build` 15.3〜15.6秒）。
- キャッシュの有無を書く。会話の検査のキャッシュ、ブラウザのキャッシュ、サービスワーカーで、数字は大きく変わります。

### 2.2 読み込みの計り方

2026-11-13 の条件です（[技術設計の「計り方」](../docs/02_TECH_ARCHITECTURE.md#読み込みを速くする工夫)）。

| 項目 | 条件 |
| --- | --- |
| 計る物 | `npm run build` の後の `dist/` |
| 配信 | GitHub Pages と同じく、サブパスで、gzip・`ETag`・`Cache-Control: max-age=600` を付ける |
| ブラウザ | Playwright の Chromium、390×844 |
| 回線 | CDP の通信制限で、約1.6Mbps・往復150ms |
| 計る点 | 新しいブラウザで、タイトル（「旅をはじめる」が出るまで）と最初の場面。同じブラウザで、2回目以降の訪問（セーブから場面が出るまで） |

- `vite preview` は文字のファイルを圧縮しません。そのまま計ると、公開版より重く出ます（`tests/e2e/boot.spec.ts` の注記）。
- 回線の制限は、たとえば次のように付けます（1.6Mbps は 1秒に200,000バイト）。上りの値は記録にないので、決めて書き残します。

```ts
const cdp = await page.context().newCDPSession(page);
await cdp.send("Network.enable");
await cdp.send("Network.emulateNetworkConditions", { offline: false, latency: 150, downloadThroughput: 200_000, uploadThroughput: 200_000 });
```

- 数字だけでなく、遅い回線の画面を目で見ます。「何が、いつ、消える・遅れるか」を書きます。以前は、表情が変わるたびに、新しい絵が届くまで立ち絵が消えていました（53f7bfa で、前の絵を残すように直した）。

### 2.3 生成とテストの計り方

- どこが遅いかは、CPU の記録で見ます。方法の一つ：`npx tsx --cpu-prof --cpu-prof-dir=<リポジトリの外のフォルダ> scripts/build-content.ts`。できた `.cpuprofile` を Chrome の開発ツールで開きます。
- 単体テストのファイルごとの時間：`npx vitest run --reporter=dot --reporter=json --outputFile.json=<出力先>.json`（先に `content:build`）。JSON の各ファイルの `startTime`・`endTime` を比べます（[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md#単体テストの組と所要時間)）。
- 見本の編を読むテストも入れて計るときは、先に見本を含めて生成し、終わったら見本なしで生成し直します。`npm run test:with-sample -- <vitest の引数>` なら、それ1つで済みます（2026-11-16 から）。
- `npm run content:build` は「`Ink validation cache: 212 reused, 0 run`」のように、検査を使い回した数と流した数を出します。計る前に、この行でキャッシュの状態を確かめます。

### 2.4 記録の形

一つの表に、前と後を並べます。後から読む人が、同じ条件で流し直せるようにします。

```
| 日付 | コミット（前→後） | 機械・負荷 | 条件 | 前 | 後 | 道具 |
```

## 3. 実例：読み込み（#126・#127）

頼み（2026-11-13）：「ロードを速くする工夫を入れたい、画像を読み込まれた時に読み込むのではなく、バックグラウンドでこっそり読み込ませるなどテクニックは色々あると思う 調べて使えそうで有用なものは実装して」

先に計りました（2.2 の条件）。

- 新しい旅の始めの約40秒、回線を可逆の立ち絵と音楽が埋めていました。立ち絵は1枚約300〜900KB、ヒロインの12表情で5.2MB、全79枚で38.8MB でした。
- 最初の場面のヒロインが出るまで、約18秒かかっていました。

2人に分けて直しました。

- 場面の先読み（bbabf77）：次の行の絵・声・音を、急ぎの順に裏で読む。省データや2G並みの回線では「次」だけ読む（`src/media/preload-queue.ts`）。
- 最初の読み込み：旅行編ごとのデータ（6ce8614）、地図や窓を後から読む（3b51f2e）、フォントへの先の接続（19b300c）、最初の旅行編を `index.html` から先に読む（658695b）、サービスワーカー。

直した後（2026-11-13 の報告）：

| 計る点 | 前 | 後 |
| --- | --- | --- |
| 初めて開いたときのタイトル（ミラノ） | 約5.9秒 | 約4.4秒 |
| 初めて開いたときのタイトル（インド） | 約5.9秒 | 約5.1秒 |
| 2回目以降の訪問（キャッシュの期限切れ） | 約0.9秒 | 約0.5秒 |

- 2回目以降は、キャッシュの期限が切れたとき（`max-age=0`）の値です。期限内のミラノでは、約0.6秒 → 約0.4〜0.5秒でした（元の記録の表）。
- 立ち絵は、それまで可逆のまま配る決まりでした。数字を添えて聞き直し、ユーザーが「軽い版を配る」を選びました（問いの窓、2026-11-13）。前の決めごとを数字が覆すときは、黙って変えず、聞き直します（[決め方の手引き 4.2](DECISION_GUIDE.md#42-必ず聞くこと)）。
- 直した後の「最初の場面のヒロインまで」の秒数は、記録に残っていません。次は、前と後を同じ表に並べます（2.4）。

## 4. 実例：テストと生成（2026-11-06）

先に CPU の記録で計りました（4コア、ほかの仕事なし）。

- 生成1回は約15秒。そのうち約12秒が、デートの会話の全分岐の検査（`validateStory`、生成1回で212回）でした。Ink のコンパイルは約1秒です。
- 単体テスト一式では、`validateStory` が18,441回呼ばれ、全ワーカーの作業時間1,471秒のうち1,066秒（72%）でした。
- 全体の待ち時間610秒を決めていたのは、1つのファイル（`scripts/city-bundle.test.ts`、609秒）でした。1つのファイルの中のテストは順に流れるからです。

直したこと。

- 長いファイルを4つに分けた（32da75a）。ワーカーをコアの数だけ使う（69fd147）。
- 検査の結果を覚えておくキャッシュを足した（a399028）。
- 各旅行編のフォルダを外して試すテスト（`scripts/journey-folders.test.ts`）は、消さずに速くするだけにしました（ユーザーの判断）。遅くても意味のあるテストは、消さずに速くします。

結果は [開発時の確認の所要時間の表](../docs/10_DEVELOPMENT_CHECKS.md#単体テストの組と所要時間) にあります。

- 全単体テスト：分ける前に約610秒、分けた後に約400秒、キャッシュが保存済みで約150秒。
- 生成：約15.7秒 → 保存済みで約3.4秒。`npm run verify`：約416秒 → 約165秒。

速くしても、結果は変えません。

- `npm run content:build -- --no-cache` と、ふつうの `content:build` が同じ結果になることを、`scripts/story-validation-cache-content.test.ts` が確かめます。
- `npm run verify` の最初の生成はキャッシュを使いません。PR の CI はキャッシュを持ち越さず、空から始めます（[会話の全分岐検査のキャッシュ](../docs/10_DEVELOPMENT_CHECKS.md#会話の全分岐検査のキャッシュ)）。

## 5. 画質は、数値と目の両方で決める

立ち絵の軽い版（#127、cbd2e1f）の決め方です。比べた表は、ほかに残っていないので、ここに写します。

### 5.1 比べ方

- 可逆の元の絵（全79枚：ヒロインの12表情、インド編の人物の絵67枚）から、設定を変えて全部作る。sharp 0.35.5（libwebp 1.6.0）、`effort: 6`。
- 人物の所だけを切り抜く（透明でない所に16pxの余白）。明るい灰（90%）と暗い灰（10%）の上に重ね、悪い方を取る。
- SSIMULACRA2（Python で書き直した ssimulacra2 0.3.0）で、等倍と、スマートフォンの大きさで比べる。スマートフォンの大きさは、両方を0.55倍に縮めた絵です。高さ1536pxの絵を高さ 844css px（DPR 3）で出す、いちばん大きい場合に合わせました。
- 物差しの目安（SSIMULACRA2 の説明）：90 は等倍で点滅させても違いが分からない、85 は等倍で切り替えても分からない、80 は等倍で並べても分からない、70 は高画質。
- 縁：透明の縁の帯で、明るさの差（ΔL*）の99.9パーセンタイルと最大を見る。にじみや輪郭のゆらぎは、ここに出ます。
- 透明度：差の最大を見る。0なら、元の絵と同じです。
- 目：スマートフォンの大きさの画面（明るい背景と暗い背景）と、顔と髪を2倍にした切り抜きを作る。いちばん点の低い絵（gt_duggal）、gt_kamla、ヒロインの3表情を選びました。見比べの画像は、ユーザーにも送りました。

### 5.2 結果

どれも `alphaQuality: 100`（透明度の差は0）。可逆の WebP は全79枚で 38.8MB でした。

| 設定 | 全79枚 | 小さく | 等倍の最低 | スマホの大きさの最低（中央） | 縁 ΔL*（99.9% / 最大） |
| --- | --- | --- | --- | --- | --- |
| 品質75 | 4.90MB | 87.4% | 67.9 | 81.2（84.6） | 12.7 / 21.2 |
| 品質80 | 5.71MB | 85.3% | 74.4 | 84.8（87.2） | 10.5 / 17.8 |
| 品質80＋smartSubsample | 5.83MB | 85.0% | 74.8 | 85.2（87.6） | 10.4 / 19.5 |
| 品質85 | 6.69MB | 82.7% | 79.3 | 87.7（89.4） | 9.1 / 14.4 |
| **品質85＋smartSubsample（選んだ）** | 6.85MB | 82.3% | 79.7 | 88.0（90.1） | 6.6 / 10.0 |
| 品質90 | 8.27MB | 78.7% | 84.8 | 90.4（91.7） | 4.4 / 6.6 |

### 5.3 決めた理由

- 決まり：スマートフォンの大きさで違いが見えない、いちばん小さい段にする。
- 品質80は、スマホの大きさで85を割る（84.8）。目で見ても、2倍の切り抜きで顔の細い線（しわ・まつげ）が少しぼける。数値と目が同じことを言ったので、使いません。
- 品質85は、いちばん悪い絵でも88で、余裕があります。
- `smartSubsample` は2.4%大きくなりますが、縁の差が約3分の1減ります。髪や服の色の輪郭が、後ろの場面ににじみにくくなります。
- `alphaQuality: 90` は0.1%しか減らず、透明度が変わるので使いません。品質90は、スマートフォンの大きさでは見えない差のために、大きくなります。
- 決めた設定は `scripts/image-optimization.ts` の `PORTRAIT_WEBP` にあります。`npm run images:optimize -- --write` で作ります（[制作ガイド](CONTENT_GUIDE.md#基本の衣装表情の画像を足す)）。

## 6. 本番だけ外す物

準備中の旅行編の写真・絵・音を、本番に入れないようにしたとき（2026-11-16、80ceb4d、#139）の進め方です。残っていたおすすめの案（この件を含む）に、ユーザーは「A,B,Dはおすすめで」と答えました。決まりの全文は [技術設計](../docs/02_TECH_ARCHITECTURE.md#共通データと旅行編フォルダ) の「準備中の旅行編のファイルは本番ビルドに入れない」にあります。

### 6.1 外す一覧は、生成のときに書く

- 決まりは1つの関数です（`src/content/journey-catalog.ts` の `journeyFilesShip`）。旅行編の名前はコードに書きません。
- `content:build` が、外すファイルを旅行編ごとに `src/content/generated/withheld-files.json` に書きます（`scripts/content-outputs.ts` の `withheldFiles`）。
- 本番のビルドだけが、その一覧を使います（`scripts/withheld-files.ts` の `withheldFilesPlugin`）。

なぜ、生成のフォルダから消さないのか。

- 開発サーバーと本番は、同じ生成のフォルダを使います。そこから消すと、開発サーバーで準備中の写真が見られなくなります。
- どのファイルがどの旅行編から来たかを知っているのは、`content:build` だけです。

### 6.2 前と後のファイル一覧を比べる

| | ファイル数 | バイト |
| --- | --- | --- |
| 前（dd635a5） | 997 | 154,147,616 |
| 後（80ceb4d） | 897 | 137,873,775 |
| 外した物 | 100 | 16,274,034（ウズベキスタン：写真40と縮小版40、ルアンパパーン：10と10） |

- 前と後で違ったのは、外した100ファイルと、名前（ハッシュ）が変わったスクリプトだけでした。
- タイトル画面までの読み込み量は、前も後も 587.3KiB（12ファイル）でした。写真はタイトルで読まないからです。「軽くなった」のは配信の総量で、最初の速さではありません。分けて書きます。
- 本番に残る物も書きます。準備中の旅行編のデータ（`journey-parts/uzbekistan` のスクリプト 1.44MB、gzip で約57KB）は、Debug の地図の確認が使うので残しました。その旅行編を選んだときだけ読み込まれます。
- 副作用も書きます。サービスワーカーの絵と音の版はファイルの中身で決まるので、この公開で一度だけ変わりました。

一覧は、次のように作れます（リポジトリの外に書きます）。

```sh
# 直す前のコミットで npm run build の後
(cd dist && find . -type f | sed -E 's/-[A-Za-z0-9_-]{8}\.(js|css)$/-#.\1/' | sort) > /tmp/dist-before.txt
find dist -type f | wc -l; du -sk dist
# 直した後で同じように /tmp/dist-after.txt を作り、比べる
diff /tmp/dist-before.txt /tmp/dist-after.txt
```

`sed` は、Vite が名前に付ける8文字のハッシュを `#` に替えます。名前が変わっただけのスクリプトを、違いとして出さないためです。

### 6.3 見張りが働くことを確かめる

- `npm run dist:check` は、外すファイルが `dist/` にあると止まります。最後の1行に「公開中でない旅行編（uzbekistan・luang_prabang）の配信ファイル 100 件は入っていません」のように出ます。
- 手で `dist/` に準備中の写真を1枚置き、止まる（exit 1）のを見ました。消すと通りました。
- 画面からも確かめます。本番の「出典・権利の一覧」は、外した写真を載せません（`src/content/credits.ts` の `photoCredits`）。本番の Debug で準備中の都市を開いても、外したファイルを読みません（`tests/e2e/debug-mode.spec.ts`）。

## 7. 計る道具を残す

### 7.1 今ある道具

| 計る物 | 道具 |
| --- | --- |
| タイトル画面までの読み込み量 | `tests/e2e/boot.spec.ts` の報告（`npm run test:e2e:prod`）。種類ごとの表と `title-transfer.json`・`title-transfer.md` を出す。CI では実行のまとめに書く |
| 最初の3分 | Debug の「導入の計測」（`src/app/intro-timing.ts`）。最初の選択・最初のクイズの答え・最初の街歩き・最初のデートまでの時間と行数 |
| 生成の検査 | `content:build` の「Ink validation cache」の行と `--no-cache` |
| テストのファイルごとの時間 | vitest の JSON の報告（2.3） |
| 本番に入る物 | `npm run dist:check` の最後の1行と `withheld-files.json` |
| 立ち絵の設定 | `PORTRAIT_WEBP` と `npm run images:optimize` |

- 読み込み量は報告にして、合否にしません（ユーザーの判断。`boot.spec.ts` の注記）。ビルドを止めるのは、本番に入れてはいけない物が入ったときのように、壊れているときだけです（[AGENTS.md](../AGENTS.md#目的と第一原則) の第一原則）。

### 7.2 残っていない道具（2026-11-16）

- 遅い回線でタイトルと最初の場面の秒数を計るスクリプト。残っているのは、2.2 の計り方の文だけです。
- SSIMULACRA2 で比べるスクリプト。比べ方と表は、この手引きの5章に写しました。
- 前と後の `dist/` の一覧。6.2 のコマンドで作り直せます。

次に計った人は、道具をリポジトリに残します。置き場所の例は `scripts/dev/` です（画面一覧の道具 `npm run screens` がある所。これも合否にしない道具です）。結果は、日付と条件を付けて docs に書きます。読み込みなら [技術設計の「計り方」](../docs/02_TECH_ARCHITECTURE.md#読み込みを速くする工夫)、時間なら [開発時の確認の表](../docs/10_DEVELOPMENT_CHECKS.md#単体テストの組と所要時間) です。道具が残らないと、次の人は一から作ります（[旅の数字の決め方](NUMBERS_GUIDE.md) にも、ミラノの路面電車の道具が今はない、とあります）。

## 8. 新しい旅行編を足したら

旅行編が増えると、時間も量も増えます。足した後に、同じ条件で計り直します。

1. 生成とテスト
   - `content:build` を、キャッシュが空のときと保存済みのときで計る。会話の検査は、デートが増えるほど長くなります。
   - `scripts/journey-folders.test.ts` は約1分で、旅行編が増えるほど長くなります。`npm run test:walk` は約22秒で、開始地点が1つ増えるごとに約4秒長くなります（[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md)）。
   - 1つのファイルだけが飛び抜けて長くなったら、分けます（4章）。
2. 本番に入る物
   - 準備中のうちは、写真・絵・音は自動で外れます。`dist:check` の最後の1行で、件数を見ます。
   - 公開する（`journey:release`）と、そのファイルが本番に入ります。前と後のファイル一覧を比べ（6.2）、増えた物がその旅行編の物だけかを見ます。サービスワーカーの絵と音の版も、そこで変わります。
3. 読み込み
   - `boot.spec.ts` の報告で、タイトル画面までの量を見る（2026-11-16 は 587.3KiB・12ファイル）。ほかの旅行編のデータをタイトルで読まないことは、`dist:check` が確かめます。
   - その旅行編でも、2.2 の条件で、タイトル・最初の場面・2回目以降の訪問を計る。前の数字と並べます。
   - タイトルが開く旅行編は、最後に開いた旅行編の記録（`dreamscape.last-journey.v1`）で変わります。ミラノとインドでも秒数が違いました（3章）。どの旅行編で計ったかも書きます。
   - 画像は、旅行編ごとに分けて読み込んでいません（配信物の合計は約41MB、2026-11-08）。分けるかどうかは、必要になったときに計り直して決める、と [技術設計](../docs/02_TECH_ARCHITECTURE.md) にあります。
4. 立ち絵
   - 新しい人物の絵は、`images:optimize` で同じ設定の軽い版にします。
   - 品質85は、2026-11-13 の79枚で計って決めた値です。描き方の違う絵（細い線が多いなど）が増えたら、その絵で5章の比べ方を流し直します。

## 9. チェックリスト

計る前

- [ ] 何を速く・軽くしたいかを、遊ぶ人の困りごとで書いた（例：最初の場面のヒロインまで約18秒）
- [ ] 機械・コア数・負荷・キャッシュの有無を書いた
- [ ] 「前」を、直す前のコミットで、3回ずつ計った
- [ ] CPU の記録か通信の記録で、どこが遅い・重いかを数字にした

直すとき

- [ ] 遅くても意味のあるテストは、消さずに速くした
- [ ] キャッシュを足したら、なしで流した結果と同じになることを確かめた
- [ ] 前の決めごとを覆すときは、数字を添えて聞き直した
- [ ] 画質は、数値（SSIMULACRA2、等倍とスマホの大きさ）と目（明るい背景・暗い背景、2倍の切り抜き）の両方で決めた
- [ ] 本番だけ外す物は、生成のときに一覧を書き、本番のビルドだけが使う形にした

直した後

- [ ] 前と同じ条件で計り、前と後を同じ表に並べた
- [ ] 前と後のファイル一覧を比べ、違いが狙った物だけだと確かめた
- [ ] 見張りが止まることを、わざと入れて確かめた
- [ ] 「総量」と「最初の速さ」を分けて書いた。副作用（サービスワーカーの版など）も書いた
- [ ] 計る道具をリポジトリに残し、結果を日付と条件つきで docs に書いた
