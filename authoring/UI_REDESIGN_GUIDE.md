# 画面を作り直す進め方

画面の形や操作の仕方を大きく変えるときの進め方です。主に、開発する人と AI のエージェントに向けて書きました。ユーザー（作者）が読んでも分かるようにしてあります。

読むのは、見本の絵を渡されて「この形にしたい」と言われたときや、上の帯・会話の窓・街歩きの画面のように、いくつもの場面で使う部品を変えるときです。ボタン1つの言葉や位置を直すだけなら、[画面の点検表](../UI_REVIEW_CHECKLIST.md) と [決め方の手引き 11章](DECISION_GUIDE.md#11-遊ぶ人に見える言葉を変えるとき) で足ります。

- 元にしたのは、2026-11-07〜11 の画面の作り直しです。
  - 段階0〜2の作り直し：上の帯と⚙設定、会話の窓、街歩きの画面ほか（#16、#19、#21、#23、#25、#26、#29、#30、#32）。
  - 写真札で旅先を選ぶ「B案」と、iPhone で触った後の手直し（#44、#47〜#49、#51）。
  - どこを押しても話が進む仕組み（#16）と、古い保存データの整理の画面（#15）。
- そのときの設計書と部品の一覧は、会話ごとの作業用フォルダにありました。会話が終わると読めないので、要る中身はこの手引きに写しました。
- UI の決まりは [UI_RULES.md](../UI_RULES.md)、変えた後の点検は [画面の点検表の「Dreamscapeで何度も起きたこと」](../UI_REVIEW_CHECKLIST.md#dreamscapeで何度も起きたこと)、画面一覧とペルソナの確認は [開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md#人が画面を確かめる) にあります。ここには写しません。

## 1. なぜ進め方が要るのか

画面の作り直しは、多くの場面と部品に一度に触ります。新しい形は目に入りますが、なくなった物は目に入りません。

- 2026-11-07、ユーザーが渡した見本の絵は2枚でした（観光の場面と、ミラノの地図の画面）。今の画面と比べると、どちらの絵にもない情報と操作が35項目ありました。セーブ、ロード、英語ノート、待機、休む、二人の名前、曜日、所持品、交際中、旅の記録、画像の出典、「観光」「デート」の字、AP、「おすすめ」、行けない理由、エピローグ、次の都市への出発などです。
- 押し間違い一つが、ゲームの中の事故になります。どこを押しても進む仕組みを作ったときは、場面の終わりの二度押しで次のデートが始まり、AP を使うことが分かりました。
- 大きく作ってから見せると、違ったときに戻す手間が大きくなります。

だから、書き出す・測る・決めてもらう・小さく入れる・見せてから大きく入れる・戻せる形で残す・まとめて実機で見る、の順に進めます。

## 2. 流れ

1. 今ある画面と部品の一覧を作る（3章）。
2. 問題が出る大きさで、全部の場面を測る（4章）。
3. 設計を書き、番号つきの問いとおすすめで決めてもらう（5章）。
4. 小さく確かな直しを先に入れる（6章）。
5. 大きな段は1段ずつ、前後の画像を見せてから入れる（7章）。
6. 前の画面は、1行で戻せる形で残す（8章）。
7. ユーザーが iPhone で触った後の直しは、小さく分けて入れる（9章）。
8. 二度押しと押せる所を試し（10章）、最後に実機でまとめて見る（11章）。

「調べて → 方法を決めて → 作る」の一般の流れは [調べてから作る手引き](RESEARCH_TO_BUILD_GUIDE.md#2-流れ) にあります。この手引きは、その画面版です。

## 3. 今ある画面と部品の一覧を作る

作る前に、読むだけの調べを1回します。コードも画面も変えません。2026-11-07 の一覧は、上の帯・会話の窓・街歩きと地図・場面の見出しの4つを調べました。

**なぜ**：見本の絵や頼みの言葉は、新しい形を言います。今ある物の一覧は言いません。

### 3.1 場面ごとの表

どの場面に、どの帯や窓が出ているかを1つの表にします。部品を変えたときに、どの場面に響くかが分かります。2026-11-07 の表の一部です（今の画面とは違います）。

| 場面 | 上の帯 | 待機・休む | 見出し | 会話の窓 |
| --- | --- | --- | --- | --- |
| 街歩き | 上に残る | ある | 読み上げ用の「{都市}の行き先」 | なし |
| 観光案内 | ある | なし | 名所の名前と「手がかり帳」 | ある |
| クイズの問題 | ある | なし | 場所の札・相手の名前・問いの進みの帯 | なし |
| デート | ある | なし | 窓の中の行き先の札 | ある |
| 到着 | ある | なし | 窓の中の「{都市}に到着」 | ある |

表の下には、画面の大きさで変わる所も書きます。例：高さ500px未満の画面では、遊ぶ所の高さを決めず、ページ全体をスクロールする。

### 3.2 部品に番号を付け、なくしてはいけない物を並べる

- 部品ごとに番号を付けます。2026-11-07 は、上の帯が H1〜H23、会話の窓が D1〜D20、街歩きと地図が F1〜F24、場面の見出しが S1〜S10 でした。各行に、何を見せるか、コードのどこか、どのテストが頼っているかを書きます。
- 見本の絵があるときは、部品ごとに「同じ」「形が変わる」「ない」「絵にだけある」を付けます。「ない」の行を集めると、なくしてはいけない物の一覧になります（1章の35項目）。
- 「絵にだけある」物は、作るかどうかを問いにします。例：見本の絵の「戻る」は作らないと決まりました（U4）。街歩きはいちばん上の画面で、戻る先がありません。押しても何も起きないボタンになるからです。
- 見本の絵の中身も確かめます。2026-11-07 の絵では、写真が別の場所でした（ガッレリアの札にドゥオモの正面、など）。作るときは、登録済みの写真を使います。
- 調べると、思い込みが見つかります。場所の名前は2種類ありました（上の帯の「現在地」は地図の地点、場面の題は名所の名前）。「閉じる」は2つの意味を持っていました（観光案内では案内を閉じて観察へ、ほかの会話では窓を隠すだけ）。見本の絵では、どちらも1つにまとまっていました。
- 使われていないコードも書き出します。作り直しで写さず、最初の段で消せます（段階1.1、#19）。
- 設計を書き終えたら、一覧の番号が全部、設計のどこかに行き先を持つかを確かめます（「一覧 → 設計の節」の対応表）。
- 設計の頭には「変えないもの・なくさないもの」を並べます。2026-11-08 の設計でなくしたのは、小さい地図の折りたたみ1つだけでした。理由も書きました（たたんだままだと、1回目に押したときの地図の動きが見えない。U27）。

### 3.3 同じ部品を使う画面を全部並べる

2026-11-07 のユーザーの頼みです（原文のまま）。

> ストーリー時の画面のクリック/タップで、現在はセリフの部分をタップしたときだけ、話が進むようになっているが、画面のどこを押しても(ボタン以外なら基本的に)ストーリーが進むようにしたい

- 作る前に、会話の窓を使う画面を全部調べました（観光案内・デート・道中交流・到着とエピローグ・クイズの会話）。
- 「押しても進まない物」（ボタン・リンク・入力欄・`data-no-advance` の付いた範囲など）を1つの純粋な関数にまとめ（`src/components/scene-tap.ts`）、場面の根に聞き手を1つだけ付けました。
- 確かめの回で、観光の画面の抜けと、二度目のタップが次の画面へ漏れる所が見つかりました。確かめるときは、ユーザーの言葉「ボタン以外なら」をもう一度読み、抜けた画面がないかを見ます。
- 前と同じにするか迷う所（最後の行を押すと場面が終わる）は、ユーザーへの問いに残しました。
- 作り直しで変わる動きは、1つずつ書いて見せます。例：段階1.3では、クイズの場所の札とデートの行き先の札を押しても、台詞が進まなくなりました（場面の札の行に移ったため）。設計の要約にそう書き、[技術設計の「UX/スマホ」](../docs/02_TECH_ARCHITECTURE.md#uxスマホ) にも残しました。

## 4. 測ってから聞く

### 4.1 例：24本のクイズを 320×568 で測った

- 段階0の直し F（低い画面で、クイズの上の部分を詰める）を入れた後で、遊べるクイズ24本の最初の問いを、全部 320×568 で測りました（2026-11-07）。3つ目の答え（C）まで最初から見えるのは、24本中3本でした（ドゥオモ・スフォルツェスコ城・ミラノのフィナーレ）。直す前は0本でした。
- 残りは、少し足りないもの（1px と 7px）が2本、ほかは53〜154px 足りませんでした。問いが3〜4行、答えが3行になるインド編と「最後の晩餐」のクイズです。どれも、短く1回スクロールすれば答えが見えます。
- 次の段（上の帯を約96pxにする段階1.2）で空くのは約8pxです。それでも全部は見えるようにならない、と見積もりました。
- この数を添えて、問い U29 を出しました。案は、①今の形で受け入れ、段階1.2の後に測り直す（おすすめ）、②さらに詰める（約50〜70px 空くが、説明が読めなくなり、押す所が詰まる）、③段階1.2を待ってから決める、の3つです。ユーザーはおすすめを選びました（2026-11-08）。

**なぜ**：数がないと、「C が見えないことがある」としか言えません。数があると、どれだけ直れば足りるか、残りをどうするかを、ユーザーが選べます。

### 4.2 どの大きさで、どう測るか

- 大きさは、点検表の行と同じです（幅 320・360・390px、低い画面 320×568・320×480、横向き、文字200%。[画面の点検表](../UI_REVIEW_CHECKLIST.md#dreamscapeで何度も起きたこと)）。
- iPhone の Safari では、ブラウザの帯の分だけ見える高さが低くなります。2026-11-08 の設計では、320×460 と 375×553 も見ると決めました。
- 計算で出した値は、そう書きます。U22 の設計にはこう書きました：320px の iPhone では、一覧の見える高さは約156px（2行）。実機では未確認なので、段階1で測る。
- 字の幅は、ゲームの字体で測ります。例：上の帯の「英語ノート」は55px。320・360・390px に入ることを測ってから決めました。
- 色の見分けも数で言います。例（U21）：選んだ地図の印は、黄色だけだと地図の地との明るさの差が1.4:1 で見えにくい。そこで紺の丸で囲み、黄色と紺の差を9.5:1 にしました。
- 画面の一覧は `npm run screens`（320 と 390px）で撮ります。24本のクイズのような「全部の場面 × 1つの大きさ」は、部品の箱の位置を Playwright で読む使い捨ての道具で測りました。結果は JSON に残し、前後で比べました。高さを測るときは、通常の遊びと同じ画面で測ります。Debug の画面では、ゲームの高さが抑えられるからです（[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md) の `short-screen.spec.ts` の行）。
- 撮るたびに変わる画面（演出の途中、地図のタイル）は、比べる前に止めます。止めないと、毎回「変わった」と出ます。`npm run screens` は、外への通信を止め、演出を短くして撮ります。

### 4.3 測るのは、決める前に一度

- 全部の場面を測るのは、問題の大きさを知り、問いに数を添えるためです。直すたびに、全部の大きさの組み合わせで測り直すためではありません。
- ユーザーの決まり（2026-11-10）：「組み合わせで何通りもやるのもやめてもらいたい」。作る段の確かめは、代表の1つの大きさでします。狭い画面の直しなら 320px です（[AIに仕事を分けて頼む手引き 1章](AI_DELEGATION_GUIDE.md#1-分ける理由と変えない決まり)）。
- 「後で測り直す」と決めたもの（U29）は、続けて持つ一覧に入れます（[決め方の手引き 8章](DECISION_GUIDE.md#8-話の糸を落とさない)）。

## 5. 番号つきの問いで決めてもらう

問いの型（番号・おすすめ・理由・手間）は [決め方の手引き 3章](DECISION_GUIDE.md#3-聞き方番号おすすめ理由) のとおりです。ここでは、画面の作り直しで加えることだけを書きます。

- **設計の頭に、ユーザー向けの要約を置く。** 2026-11-08 の設計（第5版）の頭は、「画面の変わり方」「変えないもの・なくさないもの」「決まったことと、決めてほしいこと」「進め方」の4つでした。部品の対応やテストの話は、その後ろ（エージェント向け）に置きました。
- **問いに、測った数を入れる。** 4章の U29、U21 の色の差、U22 の見える高さです。
- **見た目の問いは、画像で聞く。** 街歩きの背景の写真（U8）は、作る前に 320・390px の見え方を画像で見てもらうと決め、段階1.5で画像を見せました（7章）。
- **答えが、新しい問いを生むことがある。** U24 で、歯車のボタンの字は「設定」になりました（おすすめは「メニュー」でした）。すると、中の項目の「設定」と名前がぶつかります。それを U28 として聞き、中の項目は「ゲームの設定」に決まりました。その後 2026-11-14 のユーザー判断で、このボタンは「≡メニュー」になりました（この手引きの「⚙設定」は、そのときの名前です）。
- **答えは、日付と番号で設計に書き戻す。** 問いは U1〜U29 でした。2026-11-07 と 11-08 の答えで全部が決まり、設計は第5版になりました。前の版は、別のファイルに残しました。
- **遊ぶ人に見える言葉を変えたら**（U24・U28）、画面・テスト・資料の言葉を全部探します（[決め方の手引き 11章](DECISION_GUIDE.md#11-遊ぶ人に見える言葉を変えるとき)）。
- **UI_RULES と違う形に決まったら**、[UI_RULES.md](../UI_RULES.md) の頭の「Dreamscapeでの読み方と例外」に1行書きます。例：写真札の出発は、上へはじく操作だけ（A-2・A-5 の例外。2026-11-11 のユーザー判断。67e5914）。

## 6. 小さく確かな直しを先に入れる

段階0（#16、2026-11-08）では、もう承認されていた小さな直し5つを、大きな段より先に入れました。1つに1コミットです。

| 記号 | 直したこと |
| --- | --- |
| C | クイズの結果の見出しを、読み上げでも日本語で読む |
| J | 誤答の後の「正しい答え」に、日本語の訳を添える |
| F | 低い画面（320×568）で、クイズの上の部分を詰める |
| I | タイトルの名前の欄は、初期の名前を薄い見本の字にする。空のままなら初期の名前 |
| L | 最後に開いた旅行編を、端末ごとに覚える |

- それぞれ、320×568・360×640・390×844 で前後を撮りました。
- 先に入れる理由
  - 大きな決めごとに左右されず、すぐ遊ぶ人に届く。
  - 大きな段が、測り直した土台から始まる。F の後で測った「24本中3本」が、U29 の材料になった（4章）。
  - 小さいので、違っていてもすぐ戻せる。
- 大きな段が、小さな直しを崩していないかを毎段で見ます。設計では、段ごとの確かめに「F が 320×568 でまだ効いている」を入れ、段階2の計画にも「段階0の直しを崩していないことを確かめる」と書きました。
- 同じファイルを書き換える別の仕事があれば、その合流を待ちます。段階1は、交通の仕組みと「どこを押しても進む」が本線に入ってから始めました。どちらも、段階1で大きく変えるファイルを書き換えていたからです（[ファイルごとに持ち主を一人](AI_DELEGATION_GUIDE.md#4-ファイルごとに持ち主を一人)）。

続く段階2で、ほかの画面を同じ見た目にそろえました（見た目だけ。#32）。

- 段階1.5では、本線に入れる前に、ユーザーに画面の画像を5枚見せました。設計では、背景の写真と、選んだ印・上に残る地図の見え方を、作る前に見てもらうと決めていました。
- 前後の比べ方：前の `artifacts/screens/` を別の場所へ写しておき、`npm run screens -- --previous <そのフォルダ>` とします。場面と幅ごとに「新規」「変更あり」「ごく小さな差」「変更なし」が付きます。合否ではなく、見る場面を絞る目印です（[人が画面を確かめる](../docs/10_DEVELOPMENT_CHECKS.md#人が画面を確かめる)）。
- 変わらないはずの所は、同じであることを示します。段階0の C は、3つの幅で画素が前と同じでした。F は、360・390px と横向きで差が0でした。示し方は [大きな作り替えで「前と同じ」を確かめる](SAME_AS_BEFORE_GUIDE.md) にあります。
- Debug で開いた場面を撮るときは、Debug の帯を隠す「撮影の形」を使います（今作っている道具）。それまでは、撮るたびに CSS で帯を隠していました。
- 操作が大きく変わる段では、押す回数が増えるかも数えて書きます。段階1.6の設計では、ミラノで最初の観光地へ行くまでの押す回数が、1回から2回になると書きました（行き先を1回押すと地図に出て、もう1回で出発するため）。
- ゲームの規則・保存・進行は変えません。2026-11-08 の設計は頭にそう書き、出発や休むは今と同じ関数を通しました。
- 段ごとに [画面の点検表](../UI_REVIEW_CHECKLIST.md) で自分で点検し、確かめた範囲を報告に書きます。

## 8. 前の画面は、すぐ戻せる形で残す

例は、街歩きの画面の「B案」です。

- 2026-11-10、ユーザーは街歩きの画面を、写真札で旅先を選ぶ B案にすると決めました。頼みは、作るのはまだで、先に仕様を考えることでした（記録からの言い換え）。
- 仕様の問いへの答え（原文のまま）：「縦持ちならとりあえず3かな」「押すのではなく、写真札はフリックでスクロール選択にする」「写真で」。前の画面は「コメントアウト等で残す」。
- 残し方：コメントにはせず、前の画面の部品 `MapListFreeTime` を、変えないまま `src/features/journey/FreeTimeHub.tsx` に置きました。毎回のビルドで型検査されます。
- 戻し方：`FreeTimeHub` が返す1行を `<MapListFreeTime {...props} />` に替え、前の画面を確かめる `tests/e2e/travel-select.spec.ts` の先頭の `test.skip` を外します。この手順は [技術設計の「UX/スマホ」](../docs/02_TECH_ARCHITECTURE.md#uxスマホ) の「前の画面に戻すには」に1行で書きました。
- コメントにしない理由：コメントの中のコードは型検査されません。周りが変わると、戻したときに動かなくなります。
- 設定に切り替えのボタンは作りませんでした。戻すのは1行で足り、先回りして仕組みを作らない（[AGENTS.md](../AGENTS.md) の YAGNI）からです。
- B案は同じ日に入りました（#44、28703cd）。前の画面は、2026-11-16 の今も残っています。

**なぜ**：前の画面が残っていると、新しい案を安心して試せます。違えば、1行で戻せます。

## 9. iPhone で触ってもらった直しは、小さく分けて入れる

B案が入った後、ユーザーが iPhone で触り、画面の写しと直してほしい点を送りました。2026-11-10〜11 の2日で、約8回ありました。それを4つの小さな PR に分けて入れました。

| PR | 直したこと |
| --- | --- |
| #47（2d9cb6b） | 字を消した（観光の進みの「0/4」、「デリーの行き先」の見出し、札の下の行、「AP不要」、注記など）。英語ノートと写真の出典は⚙設定の中へ。下の帯をなくし、「ホテルに戻る」を札の列に入れた |
| #48（9bf3da0） | 会話の画面の上の帯は、場所・日時と設定だけ。所持品・お金・AP・手がかり帳は、選択肢の間だけ |
| #49（e25e0c9） | 札を大きく。場所の名前を「…」で切らない。札の紹介文は、出来事の予告ではなく、その場所の説明にする |
| #51（271ed33） | 札は3枚見せる。選んだ札を上へはじいて出発。左端に「待機」、右端にホテルの札 |

- **なぜ小さく分けるか**：ユーザーが次に iPhone で見るとき、変わった所が1つにしぼれます。読み違えた所も、すぐ戻せます。
- 実際に、2026-11-11 には2回、直し方の訂正がありました（記録からの言い換え）。AI が会話の画面で場所と時刻の札も隠すと決めたら、ユーザーから、場所と時刻の札は残し、場面の名前の札を消す、と訂正が来ました。札を約2倍にする頼みも、同じ日に、2倍は大きすぎる、3枚見せる、に変わりました。どちらの訂正も、次の小さな PR にそのまま入りました（#48、#51）。
- 頼まれていない所を自分で決めたときは、報告に「自分で決めた所」として並べます。訂正は、そこに来ます。
- 直しの多くは、消すことでした（説明の文・注記・同じことを言う札）。点検表の「同じことを言う字や印を、二重に出していない」の行に当たります。
- iPhone でしか分からないこともあります。例（2026-11-15）：iPhone の Safari では、窓の外の暗い所をたたいてもクリックが来ず、地図とアルバムが閉じませんでした。指を離したときに閉じるようにしました（4d8f23d、#133）。
- 送られた画像が、どの版のどの画面かを確かめてから直します。不具合として調べるときは [不具合を調べる手順](BUG_HUNT_GUIDE.md) を使います。

## 10. 作り直した画面で、まず試すこと

作り直しの後に何度も起きたのは、二度押しと、押せない部品でした。くわしい行は [画面の点検表](../UI_REVIEW_CHECKLIST.md#dreamscapeで何度も起きたこと) にあります。ここでは例だけを書きます。

- **古い保存データの整理の画面（#15）**：確かめの回で、二度押しの2回目が「消去する」に当たる所が見つかりました。確認の窓の大きさを固定して、2回目の指が「消去せず戻る」に落ちるようにしました。消す画面では、最初に押した所に、次の窓で何が来るかを見ます。
- **どこを押しても進む仕組み（#16）**：場面の始まり・ロード・旅行編の切り替えの0.35秒は、タップを受けないようにしました（[演出の待ち時間](../docs/10_DEVELOPMENT_CHECKS.md#演出の待ち時間)）。
- **押せるかは、部品の真ん中で見る。** 例：390px で「画像の出典」が「手がかり帳」に重なったことがあります。見えるかだけを調べる試験が通っても、上に別の物が重なって押せないことがあります。

## 11. 最後に、まとめて実機で見る

- 2026-11-07〜09 の作業の報告には、「確かめていないこと：実機・WebKit・読み上げ」が24行ありました。作業ごとに書いても、確かめる人は来ません。
- そこで、実機は最後にまとめて1回見ます。公開の前か、作り直しの段が全部入った後です。
  - 本物のスマートフォン2台（iPhone と Android）で、主な流れを通す。
  - WebKit の段（[WebKit](../docs/10_DEVELOPMENT_CHECKS.md#webkit)）。Linux の WebKit は実機の Safari と同じではないので、実機は省かない。
  - 読み上げ（VoiceOver・TalkBack など）。
  - 想定する遊び手になりきって、目標まで遊ぶ（[想定する遊び手での確認](../docs/10_DEVELOPMENT_CHECKS.md#想定する遊び手での確認)）。始める前に `npm run screens` の一覧で、通る画面を見ておく。
- 作る間の確かめは小さく、全体の確かめは最後に一度にします。2026-11-09 のユーザーの言葉「確認しすぎ」の後、この形にしました（[AIに仕事を分けて頼む手引き 1章](AI_DELEGATION_GUIDE.md#1-分ける理由と変えない決まり)）。
- 実機を持っているのはユーザーです。見てほしい点を短く並べて頼みます。確かめられなかったものは、そう報告します。
