# AIに仕事を分けて頼む手引き

会話を進める AI（以下「メインの会話」）が、Dreamscape の仕事をいくつものエージェントに分けて頼むときの手引きです。速く進めながら、作業がぶつからず、確かめていない結果がそのまま入らないようにします。読むのはふつう AI ですが、ユーザーが読んでも分かるように書きました。

- 元にしたのは、2026-11-14〜16 の会話の進め方です。中心は、インド編の2回の改稿（2026-11-14 の #132、2026-11-15 の #136）と、その後の小さな仕事（#139〜#141）です。
- そのときの指示書と報告（`COMMON.md`・`BRIEF.md`・`DIAG_TASK.md` など）は、会話ごとの作業用フォルダにありました。リポジトリの外なので、会話が終わると読めません。この手引きは、その中身を写して残すためのものでもあります。
- 決まりの元は [AGENTS.md](../AGENTS.md) です。確認のコマンドの詳しい説明は [開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md) にあります。シナリオの改稿をどの段で進めるかは [シナリオ改稿のポイント](SCENARIO_EDITING_GUIDE.md#5-進め方とチェックリスト) の5章にあるので、ここには写しません。

## 1. 分ける理由と、変えない決まり

ユーザーは「たくさんのエージェントで速く」進める形を好みます。分けると速くなるのは、**同時に進められて、触るファイルが重ならない仕事**があるときです。同じファイルを何人もが直すと、合流に時間を取られ、速くなりません。

分けるもう一つの理由は、目を新しくすることです。書いた人は自分の意図を知っているので、書いていないことも伝わっていると感じます（[知識の呪い](SCENARIO_EDITING_GUIDE.md#21-知識の呪い画面に出たことだけで読む)）。直す人・点検する人を別のエージェントにすると、意図を知らない目で読めます。

### ユーザーの変わらない決まり

- **Workflow の道具は使わない。** エージェントを一人ずつ立てて頼む。
- **エージェントのモデルを軽くしない。** モデルは指定せず、メインの会話と同じにする。ユーザーの言葉（2026-11-10）：「作業者に、軽いモデル（Sonnet）を使う。…これは絶対にやめてください」
- **報告は日本語で。** ユーザーの言葉（2026-11-10）：「報告連絡相談は日本語で」。指示書は英語で書いてもかまいません（11月の回は英語で書いた）。エージェントの報告は日本語にします。ユーザーもそのまま読めるからです。
- **確認の組み合わせを増やさない。** ユーザーの言葉（2026-11-10）：「組み合わせで何通りもやるのもやめてもらいたい」。エージェントを増やすのは、仕事を速く進めるためです。同じ確認を何人にもさせるためではありません。
- 小さな仕事は、メインの会話が自分でします。指示書を書く手間の方が大きいからです。

### 確かめと直しの回数の目安

2026-11-06〜09 の作業の記録には、見出しだけで、確かめの回が51、直しの回が27ありました。直しが4回まで続いた仕事もあります（どこを押しても話が進む、統一の段4、Debug）。その後、ユーザーはこう言いました（2026-11-09）。

> ハッキリ言って確認しすぎです。作業が全然進んでません ガンガン作って最低限のチェック入れて ラストにしっかりテストすればいいのでは

それからの目安です。

- **点検は、1つの仕事に1人。** 同じ所を、見方を変えて何人にも見させない。
- **直した後は、直した所だけを確かめる。** 全体の確かめは、公開の前か大きな変更のときに一度します（[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md)）。
- **指示書に「何回目で止めるか」を書く。** 例：「点検1回、直し1回。残った指摘は直さずに報告に書く」。止めどころが書いていないと、見つけるたびに次の回が始まります。
- **3回を超えたら、まず仕様の問いが残っていないかを見る。** 決まっていないことは、直す人が回ごとに違う形で埋めるので、指摘が終わりません。どこを押しても話が進む仕事では、直しが4回になる間ずっと、「最後の行を押すと場面が終わるか」の問いが「待ち」のままでした（2026-11-07〜08）。そういう問いは直さず、ユーザーに聞きます（[AIと決めごとを進める型](DECISION_GUIDE.md)）。

## 2. 共通の指示書

その回のエージェント全員が最初に読む1枚を作ります（2026-11-15 の回は `COMMON.md`）。どのエージェントにも同じことを書くと、書き漏らしや食い違いが出ます。1枚にまとめて、一人ずつの指示書からは「まずこれを読む」と指します。

`COMMON.md` に書いたこと：

- **作業の場所。** 自分の作業木で作業する。元のブランチとコミット（「`tmp` = origin/main 67039a7」のように）。push しない。本体の `/home/user/dreamscape` に触らない。合流はメインの会話がする。
- **`node_modules` のリンク。** 作業木に `node_modules` がなければ `ln -s /home/user/dreamscape/node_modules node_modules` でリンクする。`node_modules` は 9.4GB あり（2026-11-16 に測った）、作業木ごとに入れるとディスクが埋まるからです。直しの指示書には、終わる前にリンクを消すことも書きました。`.gitignore` の `node_modules/` はフォルダにしか効かないので、リンクは `git status` に未登録のファイルとして出て、コミットに紛れ込むことがあるからです。
- **確かめ方。** `content:build` の基準（そのときは「通って、注意17件」。注意を増やしたら理由を書く）、`npx tsc -b`、自分の変更に関わる単体テストだけを流すこと。重いコマンドは一度に一つ（6章）。見本の編が要るテスト（6章）。
- **ポート。** 指示書で渡した番号だけを使う。4173・4175・4331・4332 は使わない（6章）。
- **コミット。** 英語で書き、末尾に、その会話で決められた2行をそのまま付ける。
- **よく破られる決まり。** AGENTS.md から、その仕事で効くものだけ（出典を作らない、「クイズ」「相手」と呼ぶ、名前は `{player_name}` などのまま、アルバムの `# photo:` に触らない、録音済みのヒロインの台詞は指示書が許した人だけが変える、一行60字ほどまで）。
- **報告の形。** 書く場所（`answers/<名前>.md`）、書くこと（変えた所をファイルと行で、理由、出典は URL とページの言葉と読んだ日、できなかったこと、流した確認とその結果、ブランチとコミット）、返信の長さ（報告の場所と5行の要約）。

確かめ方の量は、ユーザーの決まりで変わってきました。2026-11-13 の回の共通の指示書では、手元では何も流さずに CI に任せる決まりでした。2026-11-15 の `COMMON.md` では、変えた所に関わるテストだけを手元で流す決まりでした。どちらにしても、その回の決まりを共通の指示書に書きます。エージェントは前の回の決まりを知りません。

指示書と報告は、回ごとに作業用フォルダの中の1つのフォルダに集めました（1回目は `clarity/`、2回目は `polish2/`、2026-11-15 からは `answers/`）。次の段の人に「このフォルダの、この報告を読む」と指せます。

いくつものエージェントが互いを指すときは、名前を先に決めて共通の指示書に書きます。2026-11-16 の5つの手引きでは、ファイル名を先に決めて、まだ書かれていない手引きにもリンクを張れるようにしました。

### 日本語・コミット・生成物の決まり

次の3つも、共通の指示書に毎回書きます。会話の終わりの見張り（Stop hook）に止められないためです。2026-11 の会話のまとめ11本のうち7本に、英語で止められた記録がありました。Git に入れていないファイルで止められたのは5回です。止められると、書き直しやコミットのために、もう一度やりとりが要ります。

- **最初から日本語で書く。** 返答と報告は、下書きから日本語にします。このリポジトリの見張り（[japanese-guard.py](../.claude/hooks/japanese-guard.py)）は、英語が主の返答を差し戻します。後で訳すと、同じ文を二度書くことになります。コミットの文は、英語のままでかまいません（上の `COMMON.md` の「コミット」）。
- **途中でもコミットする。** コミットしてよい人（作業木の人と、メインの会話）は、区切りごとにコミットします。会話の環境の見張りは、コミットしていない変更や Git に登録していないファイルを見つけると、コミットと push を求めて止めるからです。2026-11-16 には、エージェントが書いている途中の手引きを途中の版でコミットし、仕上がった版を後でコミットし直しました。本体で新しいファイルを1つ書くだけの人は、コミットしません（4章）。
- **生成物は `.gitignore` に入れる。** テストや道具が作るファイルで、Git に入れないものは、止められる前に除外します。例：`tsconfig.tsbuildinfo` が残って止められたときは、消して `*.tsbuildinfo` を `.gitignore` に足しました。手元だけの E2E の設定（`playwright.local-*.config.ts`）は、`.git/info/exclude` で除外しています（6章）。

## 3. 一人ずつの指示書

エージェントは、この会話を知りません。知っているのは、指示書に書いたことと、自分で読んだファイルだけです。メインの会話にとって当たり前のこと（ユーザーが何を嫌ったか、どこまで決まったか）ほど、書き漏らします。同じ力を持つ仲間に、初めて仕事を頼むつもりで書きます。

書くこと：

1. **目的。** 何のための仕事か。ユーザーの言葉を、日付と一緒にそのまま引く。1回目の `BRIEF.md` は、ユーザーが分からなかった行と、ユーザーの言葉（「説明不足で、なんでそういう話になってるの！？って。」）をそのまま載せ、そのうえで、話は変えずに細部を書き直す、と言い換えました。
2. **もう決まっていること。** 日付とユーザーの言葉で。途中で方針が変わったら、指示書の頭に日付つきの「UPDATE」を足し、どの決まりを置き換えるかを書く。1回目は、ミラノ編を外すこととヒロインの台詞を最後の手段として変えてよいことを、UPDATE で足しました。
3. **先に読むもの。** 順番をつけて。前の段の報告も、ここで指す。
4. **受け持ち。** 触ってよいファイル。触らないファイルと、その持ち主。「担当外で直すべきことは、報告の『他の担当へ』に書く」（4章）。
5. **確かめること。** コマンドと、合格の目安（「注意が増えていない」「`voice:changes` に出るのは、一覧にした台詞だけ」）。
6. **作業の場所。** 作業木か本体か。元のコミット。使うポート。
7. **報告。** 書く場所と形。返信は短く。

**仮説は「候補」として渡す。** 疑いを書いて渡すと、エージェントはそれを確かめる方へ読みがちです。2回目の診断の指示書は、機械で数えた候補の一覧を渡すときに、目安なので間違うことがある、一つずつ本文で確かめるように、と書きました。それでも、診断の一つは前提が誤っていて、点検の人が見つけました（「診断の『チャンドニー・チョークのまま』は前提が誤り」）。だから、「直す所なし」「候補は違った」も正しい結果だと指示書に書きます（2回目の診断の指示書は、「直す所なし」を正しく大事な結果だと書いた）。

**意見が分かれたときに、どちらに従うかを先に決める。** 2回目の直しの指示書は、点検の判断を優先する、ただし本文を読んで具体的な理由があればそれに従い、報告に書く、としました。

**並行して進む別の仕事を知らせる。** 2回目は、`# leave:` をすべての画面で効かせるコードの直しが、別の作業として同時に進んでいました。シナリオの直しの指示書には、その直しはまだ作業木にないかもしれないが、札は方法の資料のとおりに書く、と書きました。

## 4. ファイルごとに持ち主を一人

一つのファイルを直すのは、同じときに一人だけです。持ち主を決めてから立てます。

| エージェント | 作業の場所 | コミット |
| --- | --- | --- |
| ファイルを直す | 自分の作業木（`.claude/worktrees/agent-<ID>`、ブランチ `worktree-agent-<ID>`） | 作業木でする。push しない |
| 新しいファイルを1つだけ書く | 本体を共有してよい | しない。メインの会話がする |
| 読むだけ（診断・点検・見直し） | 本体 | しない。書くのは報告のファイルだけ |

- 2026-11-16 の手引きの5人のうち、すでにあるファイルも直す1人だけは作業木で作業し、そこでコミットします。ほかの4人は本体で自分のファイルを1つ書くだけです。
- 作業木の始まりのコミットが、`tmp` の今の先頭と違うことがあります。指示書に元のコミットを書き、エージェントに `git log -1` で確かめてもらいます（2026-11-16 の手引きの担当は、作業木を `tmp` に早送りしてから始めた）。
- **生成物も、持ち主のいるファイルです。** `src/content/generated/` は本体に1つしかありません。読むだけのエージェントは `content:build` を流しません（1回目の診断の指示書も、ほかのエージェントと生成物を共有しているから、と理由を書いた）。2回目の見直しの指示書には、生成物は合流したブランチから作ってあり皆で共有している、と書きました。
- 目次のように、皆が足したくなるファイル（`README.md`・`AGENTS.md` など）は、メインの会話が持ちます。2026-11-16 の手引きの5人は自分のファイルだけを書き、README などからのリンクはメインの会話が足す決まりにしました。
- 共通の大きなファイル（`src/app/GameApp.tsx`、docs）に何人もが少しずつ足すときは、「変更は小さく、その場所だけに」と指示書に書きます（2026-11-13 の回の共通の指示書）。
- 担当外のファイルに直すべき所を見つけたら、自分では直さず、報告の「他の担当へ」に書いてもらいます。持ち主が直すか、メインの会話が受け持ちを決めます。

## 5. 大きな内容の仕事は段に分ける

インド編の改稿は、段ごとに別のエージェントが受け持ちました。段の中身（何を見て、何を書くか）は [シナリオ改稿のポイントの5.1](SCENARIO_EDITING_GUIDE.md#51-流れ) にあります。ここでは人の分け方を書きます。

| | 1回目（2026-11-14、#132） | 2回目（2026-11-15、#136） |
| --- | --- | --- |
| 準備 | 共通の指示書 `BRIEF.md` と、方法の資料 `method.md` | 方法の資料 `method2.md`。調べもの、機械の数え上げ（候補の一覧） |
| 診断（読むだけ） | 6人 | 6人 |
| 診断の点検（読むだけ） | なし | 6人（診断1つに1人） |
| 直し（作業木） | 6人 | 6人。ほかに、画面のコードの直し（`# leave:`）が別に1つ |
| 合流した後の見直し（読むだけ） | 1人（全体） | 3人（都市ごと） |

- **分け方。** 都市ごとに、本筋の側（宿・本筋の観光地・ツアー・差し込みの場面）とデートの側（デートの場所と宿のデート）の2つに分け、3都市で6組にしました。どのファイルも、どれか一つの組だけが持ちます。地名の表記のように Ink の外のデータに広がるものも、持ち主の組を決めました。
- **段ごとに、別のエージェント。** 診断した人は、もう意図を知っています。2回目の点検では、診断の110件のうち、採用65件、直し方を変えて採用29件、不採用15件でした（ほかに、ユーザーに聞くので判断しないもの1件）。4割ほどが、別の目で変わったことになります。
- **前の段の報告の形を、指示書で決める。** 次の段の人が読みやすいように、見出しの形まで書きました（1回目の診断は、場面ごとに「初見の人に伝わること」「作者の意図」「伝わっていないこと」）。
- **ほかの組への指摘も拾う。** 直す人には、ほかの組の診断から、自分のファイルを指す指摘を探してもらいました。
- **見直しは、合流した後のブランチで。** 見直す人は、直した人の報告を、自分の判断を固めてから読みます。結論を借りないためです（2回目の見直しの指示書）。見直しで出た所は、合流したブランチの上で直してから PR にしました（1回目 `795609d`、2回目 `a13ba8d`・`cd577d3`）。

## 6. ディスク・ポート・重いコマンド

### ディスク

立てる前に `df -h` で空きを見ます。2026-11-16 の空きは約6GB でした。

- `node_modules` はリンクにする（2章）。`node_modules` のない作業木は 250MB ほどです。
- 終わる前に、作業木の生成物（`src/content/generated`・`artifacts`）を消してもらう。`npm run content:build` で作り直せます（2026-11-15 の報告にも「ディスクが少ないため」消したとある）。
- 合流した作業木は、メインの会話が `git worktree remove` で消す。`locked` と出る作業木は、まだ使われているかもしれません。そのエージェントが終わったのを確かめてから消します。
- 古い作業用のフォルダは、ユーザーの了解を得てから消す。2026-11-08 には、ディスクがほぼいっぱい（空き約230MB）になり、ユーザーの「消してよい」を得て、終わった確認用のリポジトリの写し（2時間より古いもの）と古いテスト用フォルダを消しました。記録・設計のメモ・動いている仕事は消しません。
- 空きがないと、テストは関係のない所で落ちます。以前の回では、空き約270MB で全部を並列に流すと、内容を写すテストが空きなし（ENOSPC）で止まりました。空きが数百MBの別の回では、Chromium が `ERR_INSUFFICIENT_RESOURCES` で落ちました。

### ポート

| 番号 | 使うもの |
| --- | --- |
| 4173 | E2E の開発サーバーの段と画面一覧（`playwright.config.ts`） |
| 4174 | 本番ビルドの段（`playwright.prod.config.ts`） |
| 4175 | 見本の編の段（`playwright.sample.config.ts`） |
| 4331・4332 | 本体にある手元用の E2E の設定（`playwright.local-night.config.ts`・`playwright.local-sample.config.ts`）。共通の指示書で、エージェントは使わないとした |

- 4173 がいちばん危ない。CI でないときは、その番号で動いているサーバーをそのまま使う設定なので、ほかのエージェントのサーバー（別の作業木のコード）を相手にテストが動きます。通っても落ちても、自分の変更を確かめたことになりません。
- エージェントには、ほかと重ならない番号を1つか2つ渡します。11月の回では 4341・4343・4345・4347・4349、4351と4352（本番の段と開発サーバー）、4391と4392（gate と debug）のように渡しました。
- E2E は、設定を写して番号だけ替えます。名前を `playwright.local-<名前>.config.ts` にすると、`.git/info/exclude` に入っているので Git に入りません（作業木でも同じ）。`artifacts/` に置いてもかまいません。サーバーには `--strictPort` を付けます（番号が使われているときに、別の番号へ黙って移らず、止まる）。11月の回は `--trace off --workers 2` で流しました。

### 重いコマンドは一度に一つ

機械は皆で使っています。`COMMON.md` の決まり：重いコマンドは一度に一つ、流す単体テストは変更に関わるファイルだけ（`npx vitest run <ファイル>`）、全部のテストは流さない。広く流すのは、合流した後のメインの会話です（7章）。

### 見本の編の生成

`npx vitest run` は、流す前に生成しません。見本の編（架空の「見本の街」）を読む単体テストは、先に `npm run content:build -- --with-sample` が要り、終わったら見本なしで生成し直します。生成物は1つなので、見本が残ると開発サーバーにも見本が出るからです。2026-11-15、2回目の合流の後に見本なしの生成のまま流すと、見本の街を読むテストが38件「Unknown city: mihon」で失敗しました。中身の誤りではなく、生成の仕方の誤りです。E2E の見本の編の段（`npm run test:e2e:sample`）も生成物を書き直すので、ほかの段と同時に流しません。

## 7. 合流の前に、メインの会話が確かめる

エージェントの報告は、その人が確かめた範囲の話です。合流する前と後に、メインの会話が自分で確かめます。

- **報告を読む。** できなかったこと、注意が増えた理由、「他の担当へ」、「決めていただきたいこと」を見落とさない。
- **差分を見る。** 担当外のファイルが変わっていないか（`git diff --stat`）。シナリオなら、触らない札が変わっていないか（[シナリオ改稿のポイントの5.3](SCENARIO_EDITING_GUIDE.md#53-検査)）。
- **スクリーンショットを見る。** 画面の仕事では、エージェントに撮ってもらい（作業用フォルダの `answers/*-shots/` など）、メインの会話が開いて見ます。報告の「見えた」を、そのまま信じません。
- **合流した後のブランチで、もう一度流す。** `npm run content:build`（注意の数と中身を前と比べる）、`npx tsc -b`、関わる単体テスト、E2E の段（自分のポートで）。一人ずつは通っていても、合わせると落ちることがあります。1回目の合流の後には、デリー到着が長くなったため、到着のテストの回数の上限を緩めました（`0082bbe`）。2回目の合流の後は、単体テスト148ファイル・1225件と、E2E の gate と debug の段（58件通過、13件は決まりどおり飛ばす）を流してから PR にしました。
- **衝突は、両方の意味を残して解く。** どちらかを捨てると、片方のエージェントの仕事が黙って消えます。2026-11-16、`# remembered` の作業木に `tmp` を合流したエージェントは、新しい都市の手引きに手順10b（編集者の改稿）と手順16（`# remembered`）の両方が残っていることを確かめて、報告に書きました（そのときは衝突なし）。
- **報告は、ユーザーの承認ではない。** エージェントの「問題なし」「これでよい」は、ユーザーの了解の代わりになりません。報告の「決めていただきたいこと」は、メインの会話がユーザーに聞きます（[AIと決めごとを進める型](DECISION_GUIDE.md)）。
- **報告も間違う。** 2回目の診断は、1回目の報告にあった「山羊の台詞が二度出る」が誤りだと指摘し、点検の人も本文で確かめました。数や行番号は、差分と照らします（2回目の見直しの報告は「数はすべて diff と一致した」と書いた）。

### 段の終わりの点検

段（作る・直す・点検する、の一区切り）の終わりに、次を見ます。指示書の「確かめること」に書いてエージェントにも頼み、合流の前にメインの会話が報告で確かめます。どれも、記録で何度も後から直したことです。

- **書き手の台本に触っていないことを、毎回示す。** 触らないフォルダ（たとえば `content/journeys/golden_triangle/stories/`）について、`git diff --stat <元のコミット> -- <フォルダ>` が空だと、コマンドと一緒に報告に書きます。2026-11-07〜09 の記録では、11回、そのつど手で示していました。決まった欄にすれば、読む人が探さずに済み、書き手の台詞が黙って変わることも防げます。
- **変えた決まりの古い言い方を、資料から探す。** 2026-11-08 に本筋の決まりを外した後も、docs/01 には「自由時間には任意の道中交流にも立ち寄れる」が残り、記録に4回出てきました（61a991f で直した）。変えた決まりの言葉で、`AGENTS.md`・`docs/`・`authoring/` を探します。
- **「必ず」は、テストで確かめたときだけ書く。** docs/02 の「src/dev が入ると必ず失敗」は、目印の文字で見つける検査だったので、言い過ぎでした。確かめていないことは、確かめた範囲で書きます。
- **合流の注意を、報告の欄に書く。** ほかの作業と同じ名前や同じ所を足したら書きます。2026-11-08、2つのブランチが `tests/e2e/helpers.ts` に別の意味の `ops.tap` を足しました。Git は黙って両方を合わせ、型の検査で落ちました（6eff659 で片方を `ops.tapAt` にした）。
- **受け持ちの外の気づきは、作らずに1行で残す。** 報告の「他の担当へ」か改善案の一覧に、どの仕事から出たかと規模を付けて書きます。その場で作ると、受け持ちと確かめの範囲が広がるからです。2026-11-05 からの作り替えでは、こうしてためた行を、後の改善計画が仕事に割り振りました（108件）。
- **同じ調べ道具を2回作ったら、`npm run screens` の選択肢にして残す。** 一度だけの道具は、終わったら消します。ただ、記録には使い捨ての調べ道具の行が30あり、同じ種類（押せる所、出典の表示の重なり、大きさごとの見え方）を4回以上作り直していました。2回目のときに `npm run screens -- --<名前>` にしておけば、3回目は作らずに済みます。今の選択肢は `--previous` と `--config` です（[開発の手引きのコマンド](../docs/12_DEVELOPMENT.md#コマンド)）。

## 8. 続きは、同じエージェントに頼む

終わったエージェントに、もう一つ頼みたいことが出たら、新しいエージェントを立てず、そのエージェントにメッセージを送って続けてもらいます（`SendMessage`）。そのエージェントは、読んだファイルと、決めた理由を覚えています。新しく立てると、同じものをもう一度読ませ、もう一度説明することになります。

例（2026-11-16）：回想の台詞の札 `# remembered` を作ったエージェントに、「同じ思い出の絵が続く間は、思い出の音を1回だけ鳴らす」直しを送りました。そのエージェントは同じブランチに直しを足し（`e32aaf6`）、報告の頭に「追記」として書き足しました。

ただし、新しい目が要る仕事は、新しいエージェントに頼みます。点検・二人目の読み・見直しは、直しに関わっていない人がします（5章）。

## 9. 公開の流れ

合流した作業ブランチ（手元の `tmp`）を main に入れる手順です。

1. `tmp` を、リモートの作業ブランチ（今は `claude/dreamscape-code-refactor-3dp0r3`）に push する。押し付ける push（`--force-with-lease`）は、ユーザーの了解があるときだけ。
2. PR を開く。本文に、変えたことと確かめたことを書き、末尾にその会話で決められた行を付ける。PR の知らせを受け取るようにし（subscribe）、様子を見に戻る予約（check-in）も置く。
3. 必須のチェック「Content, types and production build」を待つ。PR で動くのはこれだけです（[CI](../docs/10_DEVELOPMENT_CHECKS.md#cigithub-actions)）。
4. squash で合流する。そのとき、確かめた先頭のコミットの SHA を全部の桁で渡す。後から別のコミットが push されていたら、合流は断られます。確かめたものだけが main に入ります。
5. 作業ブランチをそろえる。main の squash のコミットから始めて、前の `tmp` の先頭を合流する（メッセージは「Merge branch head <短いSHA> into tmp after the squash merge of #<番号>」）。中身は main と同じで、前の歴史もつながったままです。だから、前の `tmp` から作った作業木のブランチも、そのまま合流できます。そろえた `tmp` を、また push する。
6. PR の知らせの受け取りをやめ（unsubscribe）、様子を見に戻る予約を消す。

## 10. チェックリストと指示書の型

### 立てる前に

- [ ] 同時に進められる仕事か。触るファイルが重ならないか。小さな仕事なら自分でする（1章）
- [ ] ファイルごとの持ち主を決めた。生成物と、目次のような共通のファイルの持ち主も（4章）
- [ ] 直す人は作業木、新しいファイル1つだけの人は本体（コミットしない）、読むだけの人は報告だけ（4章）
- [ ] 元のコミットを決めた。互いに指す名前（ファイル名・報告の名前）を先に決めた（2章）
- [ ] 共通の指示書が、その回の決まりになっている。確かめ方の量も（2章）
- [ ] 共通の指示書に、最初から日本語で書く・途中でもコミットする・生成物は `.gitignore` に、を書いた（2章）
- [ ] 指示書に、点検は1人、何回目で止めるかを書いた（1章）
- [ ] 決まっていることを、ユーザーの言葉と日付で書いた。決まっていないことは、先にユーザーに聞くか、報告で返してもらう（3章）
- [ ] ポートを、ほかと重ならないように渡した（6章）
- [ ] `df -h` で空きを見た（6章）
- [ ] Workflow の道具を使っていない。モデルを指定していない（1章）
- [ ] 前に同じ仕事をしたエージェントがいるなら、そのエージェントに続けてもらえないか考えた（8章）

### 指示書の型

```text
# <仕事の名前> — <担当> への指示書
まず共通の指示書 <パス> を読む。

## 目的
（何のための仕事か。ユーザーの言葉を、日付と一緒にそのまま）

## もう決まっていること
（日付・ユーザーの言葉・そこから決めたこと。途中で変わったら、頭に「UPDATE（日付）」）

## 先に読むもの（順に）
1. …
2. 前の段の報告：…

## 受け持ち
- 触ってよい：…
- 触らない（持ち主）：…
- 担当外で直すべき所は、報告の「他の担当へ」に書く

## 守ること
（この仕事で特に効く決まり。仮説は「候補」と書き、「直す所なし」も結果と書く。
 意見が分かれたらどちらに従うか。並行して進む別の仕事）

## 作業の場所
- 作業木／本体。元のコミット：…（`git log -1` で確かめる）
- ポート：…

## 確かめること
- コマンド：…
- 合格の目安：…
- 止めどころ：点検…回、直し…回。残った指摘は直さずに報告に書く
- 段の終わりの点検（7章）：古い言い方を探す、「必ず」を確かめる

## 報告
- 書く場所：…（日本語）
- 書くこと：変えた所（ファイルと行）、理由、出典、できなかったこと、確認と結果、ブランチとコミット
- 決まった欄：触らないフォルダの差分（コマンドと、空であること）、合流の注意、他の担当へ（1行ずつ）
- 返信：報告の場所と5行の要約
```

### 合流の前に

- [ ] 報告を読んだ。「できなかったこと」「他の担当へ」「決めていただきたいこと」を拾った（7章）
- [ ] 差分を見た。担当外のファイルと、触らない札が変わっていない（7章）
- [ ] 報告に、触らないフォルダの差分が空だと書いてある（7章）
- [ ] 段の終わりの点検をした。古い言い方を探し、「必ず」を確かめ、合流の注意と受け持ちの外の気づきを読んだ。2回作った調べ道具は `npm run screens` に残した（7章）
- [ ] 直しが3回を超えた仕事は、仕様の問いが残っていないかを見た（1章）
- [ ] 画面の仕事なら、スクリーンショットを自分で見た（7章）
- [ ] 合流した後のブランチで、`content:build`（注意の数と中身）、`npx tsc -b`、関わる単体テスト、E2E の段を流した。見本の編が要るものは見本を含めて生成し、後で見本なしで生成し直した（6章・7章）
- [ ] 衝突は、両方の意味を残して解いた（7章）
- [ ] ユーザーに聞くことを、エージェントの報告で済ませていない（7章）
- [ ] 大きな内容の仕事なら、合流した後に、直しに関わっていない人が見直した（5章）
- [ ] 合流した作業木を消した。生成物とリンクが残っていない（6章）
