# 大きな作り替えで「前と同じ」を確かめる

遊ぶ人から見て何も変わらないはずの作り替えを、どう確かめるかの手引きです。主に、開発する人と AI のエージェント向けです。ファイルの置き場所を変える、仕組みの中身を入れ替える、一律の決まりをデータに移す、新しい札を足す、といった変更が当たります。

- 作り替えを始める前に読みます。「前と同じ」と言うための記録は、変える前にしか取れないからです。
- 元にしたのは、2026-11-05〜16 の作り替えです。旅行編ごとのフォルダへの作り替え（#7）、条件の仕組み（#24）、仲直りの会話の条件（#138）、2人を立たせる札 `# together:`（#137）などです。
- 新しい仕組みを調べて作る流れの全体は [「調べて → 方法を決めて → 作る」の進め方](RESEARCH_TO_BUILD_GUIDE.md)、札の決め方は [表現の道具を足すときの考え方](EXPRESSION_TOOLS_GUIDE.md) にあります。ここでは「前と同じ」の確かめ方だけを書きます。

## 1. どんなときに使うか

「前と同じ」が約束になる変更に使います。約束を守れたかは、目で見ても分かりません。数千の状態や何十枚もの画面を、人が一つずつ見ることはできないからです。そこで、変える前の結果を機械で記録し、変えた後と機械で比べます。

| 作り替え | 約束 | 比べたもの | 結果 |
| --- | --- | --- | --- |
| 旅行編ごとのフォルダへ（2026-11-05〜06、#7） | 生成物とゲームの動きを変えない | 生成したデータ、配信ファイル、本番ビルド、制作ツールの出力、保存のキーなど | 段ごとに「違いなし」。最後は、決めて入れた違い4つだけ |
| 条件の仕組み（2026-11-09、#24。題は「遊びは変えない」） | どの場面がいつ出るかを変えない | ゲームの状態 6,505 | 段ごとに違い0 |
| 仲直りの会話を制作者の条件に（2026-11-15、#138） | ミラノで地図に出る時を変えない | 192通りの組み合わせ | 前の決まりと全部同じ |
| `# together:`（2026-11-15、#137） | 札のない場面の見た目を変えない | 14枚の画面と舞台の DOM | 1画素も違わない |

使わないとき：

- 振る舞いを変えるのが目的の変更。その場合は、新しい動きをテストで確かめます。
- 小さな直し。比べる道具を作る手間の方が大きくなります（10章）。

## 2. 流れ

```text
1. 変える前の結果を記録する（3章）
2. 比べる道具を先に作り、わざと壊した写しで試す（4章）
3. 計画の数と場所を、今のコードで確かめ直す（5章）
4. 段に分けて作り、段ごとに比べる。意図した違いは書き残す（6章）
5. 足したテストは、守る所を1つ壊して、落ちるのを見る（7章）
6. 最後にもう一度比べてから、一度だけの道具を消す（9章）
```

## 3. 変える前に記録する

### 何を記録するか

遊ぶ人か書く人が気づけるものを選びます。何が変わりうるかで決まります。

- **フォルダの作り替え（#7）** では、次を記録しました。
  - `content/` の JSON 72ファイル（書式の違いは無視し、項目の順までは比べる）
  - 生成した `stories.json`・`quizzes.json` のハッシュ
  - 配信する画像などの127ファイルのハッシュ
  - 本番ビルドの出力（コードの束は、名前のハッシュを外して、あるかないかだけ）
  - 制作ツールの出力（`journey:readiness` などを3つの旅行編で。`india:check`）
  - ゲームが読むデータの書き出し、クイズ24本・観光地・物語104本・交流12の指紋、4つの旅行編の保存のキー
- **条件の仕組み（#24）** では、ゲームの状態を記録しました。決まった5つの種で1,200手ずつ歩いた途中の状態（始めの状態を含めて6,005）と、組み立てた状態500です。組み立てたのは、各都市の始め、エピソードごと、ミラノの順の組、特別なクイズごと、クリアの後です。それぞれに、関係の値を変えた形と、観光地の観察を開いた形も足しました。状態ごとにハッシュを取りました。
- 道具の外のものも、同じときに記録しました（#24）：`content:build -- --verbose` の注意の一覧、`journey:readiness` の出力、`india:check`、`npm run test:walk` の要約、画面一覧（58枚）。

### 揺れをそろえる

変えていないのに毎回変わるものは、そろえるか外します。残すと、違いが出ても意味が分かりません。

- inkjs は、物語ごとに新しい乱数の種を選びます。状態の記録では、この種をそろえました（#24）。
- コードの束の名前のハッシュ、絶対パス、長い16進数、Node の警告、スタックの行は外しました（#7）。

### 記録の置き場所

- 記録は Git の外（`artifacts/` や作業用フォルダ）に置きます。
- 元にしたコミットを書いておきます。#7 は、記録のフォルダに元のコミットと作り直し方の README を置きました。記録が消えても、そのコミットから作り直せます。

## 4. 比べる道具を先に作り、わざと壊した写しで試す

道具が「違いなし」と言っても、道具に違いが見えていないだけかもしれません。そこで、使う前に2つ確かめます。

1. **変えずに2回流して、違いが0になる。** #7 の道具は、2回とも「EQUIVALENT: no differences.」でした。#24 も、記録と同じコードで比べて違い0でした。揺れが残っていれば、ここで出ます。
2. **わざと壊した写しで、違いが出る。**
   - #7：記録の写しの6か所を書き換えました（項目の順、書き出しのファイルを1つ消す、指紋の値、配信ファイルのハッシュ、制作ツールの1行、クイズを1つ増やす）。道具は6つとも挙げ、終了コード1で終わりました。
   - #24：初めに、前のコードでデートの理由の文を1つ変えると、20の違いが出ました。最後に、新しいコードの判定 `meets` を1つずらす（エピソードの数を1つ違える）と、また20の違いが出ました。

なぜ前と後の両側で壊すのか：記録する側も、比べる側も、見落としうるからです。

道具の形：

- 出力は「同じ」か、違いの一覧（ファイルや項目ごとに1行）にします。違えば終了コード1にします。
- 段ごとに流せる速さにします。#7 の道具は約45秒でした。
- 道具は作業のブランチにコミットします（#7 は 1ba98d1、#24 は 571c4b8）。読む人が何を比べたか分かり、消した後も履歴から取り出せます（9章）。

## 5. 作る前に、計画の数と場所を確かめ直す

計画を書いた時と作る時とで、コードは進んでいます。確かめ直す理由と例は [「調べて → 方法を決めて → 作る」の手順8](RESEARCH_TO_BUILD_GUIDE.md#手順8-作る前に計画の数と場所を今のコードで確かめ直す) にあります（2026-11-07〜09 だけで9回ほど）。

「前と同じ」にとっての良いことは、比べた結果に出るはずの違いを、作る前に言えることです。

- 例（#24、399d179 の上で数え直した）：同じ判定（`attempts > 0`）の写しが11か所、デートが36（ミラノ17、インド編18、見本1）、`until` が1つ、入場の決まりが8（ミラノだけ）。新しく出るはずの注意は、ミラノの「出ることがない」5件と書きました。
- 作った後の注意の一覧は、前の一覧に、ちょうどこの5行を足したものでした。

## 6. 段ごとに比べ、意図した違いを書き残す

- **段に分け、段ごとに比べます。** 違いが出たら、その段の変更の中にあります。#7 は P2 で道具を作り、その後の段（P3〜P10）で毎段比べました。#24 は段 C1〜C3 の後に、どれも違い0でした。
- **意図した違いは、記録を取り直して消しません。** 比べた結果の中で、一つずつ書き残します。#7 の P7 で決めた違いは4つでした。
  - ミラノの品物3つの `iconPath`
  - 入場の決まり1つの `quizAfterLandmarkBattle`
  - ミラノの会話の背景 `storyBackgroundAssetId`
  - ゲームが読む書き出しの名前の入れ替え

  P8〜P10 では、毎回「P7 の意図した違いだけ」と確かめました。
- **道具が見ないものも書きます。** P7 では、旅の始めの見出しと、Debug の仮の場面の品物の絵も変わりました。道具は画面を見ないので、別に書きました。
- **前からあるテストは、変えずに通します。** `# together:` の舞台のテスト3ファイルは1文字も変えずに、仲直りの会話の前からのテスト5つも何も変えずに通りました。変えるなら、それも意図した違いとして書きます。
- **了解の条件になることもあります。** インド編のクイズ15本を新しい1本の流れの形に移すとき（台詞・クイズ・行き先は変えない）、ユーザーの了解には、どのクイズでも台詞が同じだと確かめるテストが通る、という条件が付いていました。15本とも通りました（#40、2026-11-10）。

## 7. テストを足したら、守る所を1つ壊す

一度も落ちたことのないテストは、本当に守っているか分かりません。足したら、守りたい所をコードで1つ壊し、テストが落ちるのを見て、元に戻します。

- **画像を軽くする道具（2026-11-08、#16）**：色の情報を残す設定を外す、置き換えずに上書きする、など5か所を1つずつ壊すと、どれも `optimize-images.test.ts` が落ちました。注意の配線を外すと、`content.test.ts` が落ちました。壊すたびに戻しました。
- **準備中の旅の写真を本番に入れない（2026-11-16、#139）**：`dist/` に写真を1枚手で置くと、本番の検査が終了コード1で止まりました。消すと通りました。

壊しても落ちないこと（生き残り）もあります。見つけたら、理由をつけて報告します。

- **守りがなかった。** Debug をだれでも使えるようにした作業（2026-11-08、#20）の確かめでは、本番の検査が調べるファイルから Debug の束を外しても、`scripts/` のテスト373件がすべて通りました。検査の配線そのものにテストがありませんでした。検査を関数に分けて、テストを足しました。
- **生き残っても困らない。** 条件の仕組みの記録（#15）の確かめでは、28か所を壊し、23か所で落ち、5か所で通りました。3つは本当に守りがなく、テストを足しました。2つは、今のビルドの検査がその形をもう作らせないので、通っても困らないものでした。
- **中身を変えた写しでも試せます。** #7 の見直しで、インド編の ID をすべて変えた公開中の写しを足すと、テストが1つ落ちました。旅行編の ID を決め打ちしていました。データを読む形に直しました（81fbde5）。

## 8. 比べ方：画面・台詞・注意

### 8.1 画面は画素で比べる

目で見比べると、1画素のずれや、わずかな色の違いを見落とします。「見た目は同じ」と書いても、読む人は確かめられません。画素で比べれば、数で言えます。

**1つの場面が変わらないことを見るとき：**

- Debug起動URL（[開発時の確認](../docs/10_DEVELOPMENT_CHECKS.md#debug起動url)）で同じ場面を開き、同じ行まで進めて、同じ大きさで撮ります。
- 前の側は、元のコミットの作業木で動かします（例 `git worktree add --detach <フォルダ> <元のコミット>`）。`node_modules` のリンクとポートの分け方は [AIに仕事を分けて頼む手引きの2章と6章](AI_DELEGATION_GUIDE.md#6-ディスクポート重いコマンド) にあります。前と後は、同じ機械・同じブラウザで撮ります。
- 例（#137）：インド門のデート（ヒロイン1人と、ヒロインとモヌの2人）、クトゥブ・ミナールのクイズ、マリアム廟のデートを、390×844 と 320×568 で撮りました。14枚が1画素も違わず、舞台の層の DOM（`style` を除く）も同じでした。
- Debug の帯は、前も後も同じ形で隠して撮りました（CSS で隠した）。帯を隠す Debug の「撮影の形」を、今作っています。

**多くの画面をまとめて見るとき：**

- 変える前に `npm run screens` を流し、`artifacts/screens/` を別の場所へ写します。変えた後に `npm run screens -- --previous <そのフォルダ>` とします。場面ごとに「新規」「変更あり」「ごく小さな差」「変更なし」が付きます（[開発時の確認の「人が画面を確かめる」](../docs/10_DEVELOPMENT_CHECKS.md#人が画面を確かめる)）。合否ではなく、見る場面を絞る目印です。
- 先に、変わるはずの画面を書いておきます。変わった画面が、その一覧と合うかを見ます。
- 読み方の例：
  - UI 段階1.3（2026-11-09、#23）：前58枚・後64枚。20枚が同じ、6枚が新しい、37枚が変わった。37枚のうち36枚は、場面の札の行と会話の窓の、意図した変更でした（いくつか開いて見た）。1枚は前から知られたページ全体のずれ、ほかに1枚が描画のにじみ（アンチエイリアス）ほどの差でした。
  - 画像を軽くした（2026-11-08、#16）：ヒロインが写る26枚は、色の値が最大で1/255違いました（WebP と PNG の読み込みの丸め）。ほかの18枚はバイト列まで同じで、並びは変わりませんでした。

### 8.2 台詞は voice:changes で比べる

`npm run voice:changes -- --journey <旅行編ID>` は、ヒロインの台詞を、録音した文と渡した台本の文と比べます（[開発の手引きのコマンド](../docs/12_DEVELOPMENT.md#コマンド)）。

- **変える前にも流し、出力をファイルに残します。** 前からある行が出るからです。2026-11-15〜16 は、録り直しの1行（`gt_delhi_jama_masjid_guide_003`）がいつも出ていました。比べるのは「0件か」ではなく、「前の出力との違いが、頼んだ行だけか」です。
- 例：ヒロインの台詞の発注（2026-11-15、#137）は15行（新しい行14、直した行1）。`voice:changes` で、変わったのはこの15行だけでした。`# remembered` の作業（2026-11-16、#141）では、出力が前と完全に一致しました。
- 発注の台本に入れた行は「渡した」と数えられ、一覧から消えます。台本の作り方は [発注マニュアルの3.4](ORDERING_MANUAL.md#34-発注のファイル) にあります。
- 触らない札（`# voice:` など）が変わっていないかは、[シナリオ改稿のポイントの5.3](SCENARIO_EDITING_GUIDE.md#53-検査) の `git diff` の形で見ます。

### 8.3 注意は数と内訳で比べる

`npm run content:build` は、通ると、注意の数と種類ごとの内訳を1行で出します（`17 content warning(s): …` の形）。一つずつの文は `-- --verbose` で出ます。前後で比べることは、[シナリオ改稿のポイントの5.3](SCENARIO_EDITING_GUIDE.md#53-検査) と [AIに仕事を分けて頼む手引きの2章](AI_DELEGATION_GUIDE.md#2-共通の指示書)（基準は「通って、注意17件」）にもあります。ここでは比べ方を足します。

- **数だけでなく、内訳と中身を比べます。** 数が同じでも、1つ消えて1つ増えたかもしれないからです。`# together:` の作業では、注意が17件で、内訳も同じだと確かめました。
- **同じ形の生成どうしで比べます。** 見本の編を入れると数が変わります。#138 の報告では、見本なしで17件、見本つきで21件でした。
- **新しく出るはずの注意は、先に書きます**（5章の5件）。
- **道具：** 変える前に `npm run content:warnings -- --save` で注意を残し、変えた後に `npm run content:warnings -- --compare` で比べます。2026-11-16 に作りました。それまでの作業の報告のほとんどが、「注意17件」を手で確かめていたからです。保存先は `artifacts/content-warnings.json`（Git に入れない）で、比べると種類ごとの前 → 今と、増えた注意・消えた注意が出ます。
- 道具がない古い版を比べるときは、注意の一覧（`content:build -- --verbose` で標準エラーに出ます）をファイルに写して、前後を `diff` で比べます。

  ```sh
  npm run --silent content:build -- --verbose 2> artifacts/warnings-before.txt
  # 変えた後
  npm run --silent content:build -- --verbose 2> artifacts/warnings-after.txt
  diff artifacts/warnings-before.txt artifacts/warnings-after.txt
  ```

### 8.4 そのほかの比べ方

- **ファイルの一覧。** 準備中の旅の写真を本番から外したとき（#139）、本番ビルドは997ファイルから897ファイルになりました。前後の一覧を比べ、変わったのは外した100ファイルと、名前のハッシュが変わったスクリプトだけだと確かめました。
- **生成物のバイト列。** ミラノの交流のファイルの見出しのコメントだけを直したとき（2026-11-08、#17）、`content:build -- --no-cache` の前後で、生成物180ファイルがバイトまで同じでした。物語の指紋も保存も変わらない、と言えます。
- **組み合わせのテスト。** 前の決まりをテストの中に参照として残し、組み合わせで突き合わせます。仲直りの会話は192通りでした。手順は [表現の道具を足すときの考え方の10.2](EXPRESSION_TOOLS_GUIDE.md#102-手順) にあります。

## 9. 終わったら、一度だけの道具を消す

- #7：P10 で最後に比べ（P7 の意図した違いだけ）、比べる道具と、フォルダを分ける道具を消しました（563ca0b）。道具のためだけに外へ出していた関数 `encounterFingerprint` も元に戻し、ほかに使う所がないことを `grep` で確かめました。
- #24：最後に比べて違い0、新しいコードでわざと壊して20の違いを見てから、消しました（981b9c9）。コミットの文には「The test was meant for this change only.」とあります。

なぜ消すのか：比べる相手は、作り替える前の記録です。作り替えが終われば、比べる相手はもうありません。残すと、後の意図した変更のたびに違いが出て、読む人が「これは何を守るテストか」で迷います。

消しても、履歴には残ります。#7 では、見直しの直しの後に、道具を 6ba60bc から使い捨ての作業木へ戻して、もう一度比べました。

残すもの：

- **何度も作り直した道具は、コマンドにします。** 画面の前後の比べ（`npm run screens -- --previous`）がそうです。注意の前後の比べ（8.3）も、今コマンドにしています。
- **小さく書ける参照のテストは、残してかまいません。** 仲直りの会話の192通りは `src/domain/recovery.test.ts` にあります。ミラノの条件を書き換えると、このテストが知らせます。
- 確かめる道具は、毎回のビルドに入れず、要るときに流すコマンドにします（2026-11-16 のユーザーの判断「一度登録したものをビルドが毎回確かめる必要はありません」。#145 では、写真と音のクレジットの中身を、毎回のビルドで確かめない形にした）。

## 10. 確かめすぎない

ユーザーは、確かめの多さを何度も止めています（2026-11-09 の「確認しすぎ」、2026-11-10 の決まり）。言葉と決まりは [AIに仕事を分けて頼む手引きの1章](AI_DELEGATION_GUIDE.md#1-分ける理由と変えない決まり) と [AIと決めごとを進める型の9章](DECISION_GUIDE.md#9-了解はユーザー本人の言葉だけ) にあります。

- この手引きの道具は、大きな作り替えのためのものです。1つの作り替えに比べる道具は1つ、流すのは段ごとに1回です。
- わざと壊すのは、道具には前後の両側に1つずつ、足したテストには1つです。全部の行を壊して回りません。7章の #16 と #15 の例は、何か所も壊していますが、この決まりの前（2026-11-08）のものです。
- 組み合わせは、1つのテストの中で回します（192通りは、1つの単体テストの中です）。人やエージェントが同じ確かめを何度も流すのとは別です。
- 全部のテストは、最後に1回流します。

## 11. チェックリスト

始める前：

- [ ] 「前と同じ」の約束を一文で書いた（何を変えず、何を変えるか）（1章）
- [ ] 遊ぶ人と書く人が気づけるものを選び、変える前に記録した。元のコミットも書いた（3章）
- [ ] 毎回変わるもの（乱数の種、ハッシュの名前、絶対パス）をそろえた（3章）
- [ ] 道具を2回流して違い0、わざと壊した写しで違いが出ることを確かめた（4章）
- [ ] 計画の数と場所を今のコードで数え直し、出るはずの違いを書いた（5章）

作る間：

- [ ] 段ごとに比べた。意図した違いは、記録を取り直さずに一つずつ書いた。道具が見ないものも書いた（6章）
- [ ] 前からあるテストを変えずに通した。変えたなら理由を書いた（6章）
- [ ] 足したテストは、守る所を1つ壊して落ちるのを見て、戻した。生き残りは理由つきで報告した（7章）
- [ ] 画面は画素で、台詞は `voice:changes` の前後の出力で、注意は数と内訳で比べた（8章）

終わり：

- [ ] 最後に比べてから、一度だけの道具と、そのためだけに外へ出した関数を消した（9章）
- [ ] 報告に、比べたもの・結果・意図した違い・確かめていないことを書いた
